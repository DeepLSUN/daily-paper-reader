## 摘要
循环工程正在成为一种围绕编码智能体组织开发工作的实践。从业者不再手动编写每个提示，而是设计循环来监控进度、分配工作、运行检查，并决定智能体下一步应该做什么。即使拥有一个能力强大的编码智能体，循环也可能信任过时的进度说明、跳过必要的验证、将预算浪费在错误的方向上，或者在任务安全提交之前就停止。然而，一次端到端运行的最后结果无法判断成功或失败是反映了循环的指导还是编码智能体执行任务的能力。我们引入了LoopArena，一个基准测试，用于评估一个模型在长时间运行任务中如何引导另一个独立的编码智能体。被评估的模型是\textbf{控制器}：在每一轮编码之后，它接收运行的结构化摘要，并指示一个独立的、固定的编码智能体（即\textbf{工作者}）下一步该做什么或验证什么，或者决定是否停止。LoopArena在三种互补的设置中评估这种能力，这些设置在执行范围和成本上有所不同。类型I通过执行验证的问题来评分下一步循环契约的选择，而无需在评估时运行工作者。类型II在完整任务的选定片段上执行重复控制，而类型III从原始状态评估配对的完整任务。在完整任务上，观察到的最佳严格成功率为\textbf{24.69\%}，在长视野循环控制方面仍有很大的改进空间。在各种控制器中，估计推理成本的配对降低平均为\textbf{64.4\%}，并且类型II在主要核心标准下产生相似的排序（Spearman's \(ρ=\textbf{0.9747}\)）。我们在https://github.com/AMAP-ML/LoopArena 发布基准数据和评估代码。

## Abstract
Loop Engineering is emerging as a practice for organizing development work around coding agents. Instead of writing each prompt by hand, practitioners design loops that monitor progress, assign work, run checks, and decide what the agent should do next. Even with a capable coding agent, a loop may trust a stale progress note, skip needed verification, spend its budget in the wrong direction, or stop before the task is safe to submit. Yet the final outcome of one end-to-end run cannot tell whether success or failure reflects the loop's guidance or the coding agent's ability to carry out the task. We introduce LoopArena, a benchmark for evaluating how well one model can guide a separate coding agent through a long-running task. The model under evaluation is the \textbf{Controller}: after each coding round, it receives a structured summary of the run and instructs a separate, fixed coding agent, the \textbf{Worker}, on what to do or verify next, or decides whether to stop. LoopArena evaluates this ability in three complementary settings that differ in execution scope and cost. Type I scores next-step Loop Contract selection through execution-validated questions without running the Worker at evaluation time. Type II executes repeated control over a selected slice of a full task, while Type III evaluates the paired full task from its original state. On full tasks, the best observed Strict Success Rate is \textbf{24.69\%}, leaving substantial room for improvement in long-horizon loop control. Across Controllers, the paired reduction in estimated inference cost averages \textbf{64.4\%}, and Type II produces a similar ordering under the main Core criterion (Spearman's \(ρ=\textbf{0.9747}\)). We release the benchmark data and evaluation code at https://github.com/AMAP-ML/LoopArena .

# LoopArena 论文详细总结

## 1. 核心问题与研究动机

- **背景**：Loop Engineering（循环工程）正成为围绕编码智能体组织开发工作的新实践。开发者不再逐条手写提示词，而是设计“循环”来监控进度、分配任务、运行检查并决定智能体下一步做什么。
- **核心问题**：即使编码智能体本身能力很强，控制循环仍可能犯错——例如相信过时的进度记录、跳过必要的验证、预算使用方向错误、或过早停止。但一次端到端运行的成功或失败，无法区分这究竟归因于循环的引导质量，还是编码智能体本身的任务执行能力。
- **研究目标**：将“模型作为运行时控制器（Runtime Controller）”的能力单独评测出来，即评估一个模型在长时间任务中引导另一个固定编码智能体的水平。
- **关键概念**：
  - **Controller（控制器）**：被评估的模型，在每个编码轮次后接收结构化摘要，并指示固定 Worker 下一步做什么、验证什么，或决定是否停止。
  - **Worker（工作者）**：一个固定配置的编码智能体，负责实际执行代码任务。
  - **Inner loop（内循环）**：Worker 的任务执行；
  - **Outer loop（外循环）**：Controller 对整体流程的引导。

## 2. 方法论

### 2.1 核心思想

- 构建一个双智能体评测框架：评估对象是 Controller 模型，而 Worker、工具、任务环境、预算、评估器等全部固定不变，从而将“循环控制能力”从“编码系统整体能力”中分离出来。
- 通过三种互补的设置（Type I/II/III），分别覆盖**单步决策**、**任务切片控制**和**完整任务控制**，在评估成本与执行范围之间做出权衡。

### 2.2 控制循环流程

1. Worker 完成一个分配段后暂停，持久化对话保留。
2. Harness 创建一个临时 **Reporter** 智能体（与 Worker 同模型配置），复制 Worker 对话历史，用只读工具检查工作区，生成包含四部分的报告：
   - 任务上下文与约束；
   - 已完成工作与当前状态；
   - 可获得的验证证据；
   - 未解决问题与不确定性。
3. Harness 将报告和引用的 Worker 轮次格式化为结构化 **Evidence Packet**（只读摘要）。
4. Controller 读取 Packet（及此前历史），输出结构化 **Loop Contract**：
   - `advance`（继续推进）、`verify`（聚焦验证）或 `stop`（结束运行）；
   - 对于继续类决策，包含目标、上下文、必需结果、禁止行为、完成条件、受保护不变项等。
5. Harness 验证 Contract 后，将其渲染为 Worker 的下一条指令；若为停止，则提交当前工作区给评估器。

- Controller 没有代码工具，只能通过指令影响任务结果；Reporter 不能修改工作区。

### 2.3 三种评测设置

| 设置 | 范围 | 评估方式 |
|---|---|---|
| **Type I** | 单一控制决策 | 从冻结的控制点给出 Evidence Packet 和四个候选 Loop Contract，Controller 只需做四选一；正确选项在基准构建期间通过执行候选契约并由两次匹配回放确定。评估时无需运行 Worker。 |
| **Type II** | 任务切片 | 从准备好的中间工作区开始，评估 Controller–Worker 循环完成一个连贯阶段；启动时工作区至少未通过该阶段引入的一个检查，完成状态必须满足该阶段所有要求。 |
| **Type III** | 完整任务 | 从原始状态开始，Controller 管理完整运行，覆盖调查、实现、验证到停止的全过程。每个 Type II 切片与对应的 Type III 完整任务配对。 |

### 2.4 关键设计细节

- **Type I 正确选项确定**：在基准构建时，从冻结状态用两个预先声明的匹配回放调度执行四个候选契约（随机种子差 1,000,000 和 2,000,000），要求两个调度识别同一唯一赢家；若分歧或没有唯一赢家则拒题。赢家按“任务成功 → 下游控制循环数少 → 下游 Worker 轮次少”排序决定。
- **参考策略**：
  - **无控制（No control）**：Worker 接收任务后自主运行到完成，无循环引导。
  - **固定控制（Fixed control）**：在每个非终止交接点，确定性策略重复陈述原始目标，不根据执行证据调整；不调用模型 Controller。
- **成本核算**：估计推理成本 = 每个模型调用的输入/输出 token 数 × 冻结的公共标准价格，假设无提示缓存；报告每轮平均估计成本。
- **排序一致性**：用 Spearman 秩相关系数 ρ 评估 Type II 与 Type III 的 Controller 排序相关性（仅基于 Controller 模型，排除参考策略）。

## 3. 实验设计

### 3.1 数据集 / Benchmark 组成

- 源任务来自两个基准：
  - **SCBench（SlopCodeBench）**：长视野迭代编码任务；
  - **BeyondSWE**：超越单仓库 bug 修复的软件工程任务。
- 最终组成：
  - **Type I**：90 个控制决策问题（SCBench 40、BeyondSWE 50）。
  - **Type II**：27 个任务切片（SCBench 11、BeyondSWE 16）。
  - **Type III**：27 个完整任务（同上，与 Type II 一一配对）。
- 每个任务使用官方原始说明、起始状态、流程与评估器；SCBench 任务的多 checkpoint 顺序执行但按一个任务计数。

### 3.2 对比方法 / 模型

- **被评估的 Controller 模型**：
  - Qwen3.7-Plus
  - DeepSeek-V4-Flash-0731
  - GLM 5.2
  - GPT-5.5
  - Claude Opus 4.8
- **参考策略**：无控制、固定控制。
- **共享 Worker**：所有 Type II/III 运行使用 Qwen3.7-Plus 作为 Worker；Reporter 同配置。

### 3.3 执行细节

- 每任务每策略运行 **3 次**（K=3）。
- Worker 主回合上限 600 次 ReAct 回合，或 7200 秒墙钟时间；Controller 最多 128 个控制循环；Reporter 每次最多 50 回合。
- 无控制与固定控制参考运行每任务只收集一次，并在所有 Controller 比较中复用。
- 成功率定义：严格成功率（SSR）= 通过任务评估器的运行数 / 总运行数；SCBench 默认要求所有 Core 检查通过，BeyondSWE 要求官方 Harbor 评估器奖励为 1。

### 3.4 验证与质控

- 自动化检查：任务绑定、泄露防护、Type I 答案稳定性、Type II 切片有效性、评估器区分度。
- 冻结后 LLM 辅助与专家审计：检查问题清晰度、候选合理性、信息泄露，但不可改变回放确定的答案。

## 5. 实验数量与充分性

### 5.1 实验规模

- **Type II**：27 个切片 × （5 Controller + 2 参考）× 3 次运行 ≈ 405 次可控/参考运行中的模型控制运行（参考共享），实际每个 Controller 81 次运行。

### 5.2 充分性与公平性

- **优点**：控制变量到位——Worker、工具、任务环境、执行预算、评估器、提示模板和模型版本全部固定；参考运行复用，避免额外方差；重复 3 次运行评估稳定性；对排序一致性做了统计检验（Spearman ρ）。

## 6. 主要结论与发现

- **完整任务控制仍然困难**：Type III 严格成功率在 5 个 Controller 中为 16.05%–24.69%，最佳仅 **24.69%**。
- **固定目标重复并不足够**：固定控制将 Type II 成功率从 39.51% 提升到 46.91%，但 Type III 仍是 18.52%（与无控制相同），说明全任务需要适应运行状态的引导，而非仅持久重申目标。
- **Type II 能以更低成本保留 Type III 排序**：配对成本降低平均 **64.4%**；在核心标准下 Type II 与 Type III 的 Controller 排序相关性 **ρ=0.9747**，九个严格排序对无反转，一个平局。
- **Type I 能区分个体控制决策质量**：契约准确率 72.22%–87.78%，GPT-5.5 最高（87.78%）；所有响应均可解析（Invalid Rate 0%）。
- **快捷方式均远低于 Controller**：最强确定性快捷方式（多数位置）仅 31.11%，低于最弱 Controller 的 72.22%。

## 7. 优点

1. **清晰的评估对象分离**：固定 Worker 与执行环境，使循环控制能力成为独立评测目标，避免端到端结果混叠。
2. **三种层级互补**：Type I（低成本单决策）、Type II（切片控制的低成本闭环）、Type III（完整任务评估），兼顾诊断、效率与真实性。
3. **执行验证的答案生成**：Type I 的正确选项由实际执行 + 双回放一致性确定，而非依赖人工判断或模型偏好，保证客观性。
4. **严格的污染/泄露防护**：模型输入不暴露解决方案、私有评分或后续轨迹事件；候选与顺序在执行前冻结。
5. **丰富的诊断分析**：包括快捷方式基线、SCBench 评分敏感性、运行稳定性、输出上限影响等，提升了结果可信度。
6. **开源可复现**：释放基准数据、构造记录、运行配置、提示模板、评估代码等完整资料。

## 8. 不足与局限

1. **任务覆盖有限**：仅限仓库级编码任务，未覆盖其他软件工程领域或多 Worker 协作、不同循环组织等。
2. **Worker 模型单一**：所有实验使用 Qwen3.7-Plus 作为 Worker，结论可能受到 Worker 特性的影响；论文未评估 Controller 能力在不同 Worker 下的泛化性。
3. **参考策略的兼容性**：固定控制运行由较早 harness 产生，虽作归一化处理，但仍存在潜在实现差异。
4. **成本计算简化**：假设无缓存、仅按公开标准价格估算，未反映实际的缓存折扣、批量折扣或企业价格，因此是“标准化估计”而非真实花费。

6. **Type I 规模较小**：90 个问题不足以覆盖大量真实控制场景，且问题来自有限源任务，可能存在偏差。
7. **模型面板时效性**：评测的模型版本为 2026 年特定版本，快速迭代的模型生态可能使结果快速过时。
8. **无法完全排除语义歧义**：尽管有人工审计，但 Evidence Packet 和候选契约的措辞仍可能影响模型表现，导致非控制能力的评分偏差。
