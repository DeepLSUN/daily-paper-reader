## 摘要
长周期编码智能体在演化中的仓库状态上运行，同时日益依赖于异构能力、委派智能体和多智能体协调。这些趋势对智能体框架提出了两个互补的挑战。首先，开发者需要组合能力、重新配置执行逻辑，并扩展日益复杂的智能体系统，而无需反复重建编排。其次，复杂的编码任务会持续产生新证据——例如语义诊断、执行结果、任务进度以及不断变化的上下文相关性——这些证据应动态影响后续的运行时决策。我们将这些挑战概括为结构可组合性与运行时自适应性。我们提出了openJiuwen，一个旨在实现开发者可组合性和自适应任务执行的开源框架。openJiuwen提供了一个共享的执行基座，以及基于Rail的能力组合，支持单一智能体、委派子智能体和Swarm Flow，使开发者能够在共同的执行语义下构建复杂的智能体框架。它进一步在固定模型策略下自适应地调整框架控制的运行时决策，允许演化的证据动态影响上下文、反馈和任务控制，以成功完成任务。我们在SWE-bench Verified和Terminal-Bench 2.1上系统地评估了openJiuwen，分别达到82.6%和87.19%，超过所选官方排行榜最强点估计3.4和3.39个百分点。这些结果表明，openJiuwen在复杂编码任务上实现了强劲性能，同时提供了可组合且自适应的框架设计。

## Abstract
Long-horizon coding agents operate over evolving repository states while increasingly relying on heterogeneous capabilities, delegated agents, and multi-agent coordination. These trends pose two complementary challenges for the agent harness. First, developers need to compose capabilities, reconfigure execution logic, and scale increasingly complex agent systems without repeatedly rebuilding orchestration. Second, complex coding tasks continuously produce new evidence---such as semantic diagnostics, execution outcomes, task progress, and changing context relevance---that should dynamically influence subsequent runtime decisions. We characterize these challenges as Structural Composability and Runtime Adaptivity. We present openJiuwen, an open-source harness designed for both developer composability and adaptive task execution. openJiuwen provides a shared execution substrate and Rail-based capability composition across single agents, delegated sub-agents, and Swarm Flow, enabling developers to construct sophisticated agent harnesses under common execution semantics. It further adapts framework-controlled runtime decisions around a fixed model policy, allowing evolving evidence to dynamically affect context, feedback, and task control toward successful completion. We systematically evaluate openJiuwen on SWE-bench Verified and Terminal-Bench 2.1, where it achieves 82.6% and 87.19%, respectively, exceeding the strongest selected official-leaderboard point estimates by 3.4 and 3.39 percentage points. These results show that openJiuwen achieves strong performance on complex coding tasks while providing a composable and adaptive harness design.

## 2. 方法论：核心思想、关键技术细节

### 2.1 总体设计

openJiuwen 围绕两个正交维度组织：
- **结构可组合性**：定义系统如何被组装——从单智能体到委派子智能体再到多智能体流，共享同一执行核心。
- **运行时自适应性**：定义执行如何随新信息演化——调整上下文、反馈、任务控制和跨任务经验。

### 2.2 结构可组合性

**（1）Inner Loop / Outer Loop 分层执行引擎**
- **Inner Loop（内层循环）**：负责模型–工具交互。每步构造模型可见上下文 → 调用策略 π → 执行工具调用 → 记录观测结果，循环至模型返回答案、中断或达到步数上限。生命周期回调在模型/工具边界触发，Rail 可在此观察或修改执行，而无需在循环内嵌入特定逻辑。
- **Outer Loop（外层循环）**：负责任务级继续/终止决策。一次完整的 Inner Loop 调用构成一轮 Outer Loop，由可组合的评估器（语义完成信号、资源限制、用户自定义条件）决定是否进入下一轮。还负责异常处理和有限重试/恢复。

**（2）Rail：有序能力组合机制**
- 生命周期钩子空间定义为：H = H_invoke ∪ H_call ∪ H_task（分别对应调用级、模型/工具调用级、任务迭代级事件）。
- Rail 抽象表示为：ρ = (Hρ, fρ, pρ)，即**挂载的钩子集合、处理函数、优先级**。同优先级按确定性顺序执行；合并策略允许替换以实现受控覆盖。
- 组合顺序是**显式元数据**，而非执行循环内偶然分支的结果。增删能力只需修改 Rail 配置，核心执行循环不变。
- **可见性门控**：g(ρ, u) ∈ {0,1} 表示 Rail ρ 对执行主体 u 是否可见，从而支持有界递归委派、渐进能力披露和角色隔离。

**（3）Swarm Flow：可组合多智能体协调**
- 提供一系列协调算子：`budget()`（预算查询）、`parallel()`（并行分支）、`compact()`（过滤无效结果）、`pipeline()`（流式传递中间结果）、`agent_session()`（有状态会话）、`human()`（人工干预）、`return`（终止并返回结果）。
- 开发者可自由组合/重排/省略算子，构建任务特定的多智能体工作流。论文示例：领导者查询预算 → 确定 worker 数量 → 并行生成候选 → 过滤空结果 → 流式审查 → 有状态仲裁者聚合 → 必要时人工干预 → 返回最终结果。
- 关键是：**所有智能体实例（独立、子智能体、流内）复用同一 Inner/Outer Loop 执行核心**，缩放结构不引入新执行引擎。

### 2.3 运行时自适应性

**形式化框架**（概念性的约束在线优化视角）：
- 上下文构建：c_t = κ_t(M_t)，固定策略 π 给出动作 a_t ~ π(·|c_t)。
- 运行时配置：Θ_t = (κ_t, Φ_t, ι_t)，分别对应上下文构建、语义接受/停止、诊断反馈注入。
- 轨迹效用：J(Θ_0:T) = E[Σ(r_t − λ·cost_t)]，受三个可行性约束：上下文预算 C1（|c_t| ≤ B_ctx）、反馈过滤约束 C2、语义接受/停止约束 C3。
- 状态相关调整：Θ_{t+1} = A(Θ_t; M_t)。

**四个具体机制**：
1. **Context Management（上下文管理）**：实现 κ。采用渐进压缩（m⁰→m¹→…→mᴸ，越往后保真度越低）、结构感知约简（代码 diff、日志、表格先做确定性压缩再做模型摘要）、死循环折叠（折叠重复无用的推理/工具调用）、卸载与检索（全文→结构化/语义摘要→紧凑句柄→按需检索）。支持 KV-cache 复用与会话亲和。
2. **Goal Mode（目标模式）**：实现 Φ。维持显式任务目标，语义完成评估器返回 Φ_t(M_t) ∈ {continue, complete, blocked}，与配置的硬限制（最大尝试次数/时间/资源）分离，停止时间为两者先到者。支持自评估、独立评估、混合评估三种策略，共享同一接口。
3. **LSP-Driven Passive Feedback（LSP 驱动的被动反馈）**：实现 ι。语言服务器协议（LSP）在代码变更后机械地产出语义诊断，经过排名、去重、限量（K_file、K_sem）后注入后续执行。与主动语义查询（定义查找、引用查找等）的区别是**控制权**：被动诊断自动浮现，主动信息由智能体显式请求。
4. **Self-Reflection（自我反思）**：跨任务非参数化适应。已完成轨迹经 Ψ 提取经验 X_n，通过 U 验证/去重/合并/修订后持久化；新任务通过检索得到 R_{n+1}，进入信息池（仍受上下文管理约束）。**不更新模型参数**。

## 6. 主要结论与发现

- **Terminal-Bench 2.1**：openJiuwen + GPT-5.6 Sol 达 **87.19%**，超过官方榜最强（Claude Code + Fable 5，83.8%）**3.39 个百分点**；Fable 5 模型匹配下达 84.04%，超 Claude Code（83.8%）0.24 个百分点、超 Terminus 2（80.4%）3.64 个百分点。
- **SWE-bench Verified**：openJiuwen + Claude 4.5 Opus 达 **82.6%**，超过最强非 bash-only 结果（79.2%）**3.4 个百分点**。最强的此前系统同样使用 Claude 4.5 Opus，说明差异不能归因于更强模型。
- **类别分析**：文件操作（0.76 vs. 0.56/0.52）和系统管理（0.889 vs. 0.778/0.844）等工具密集型类别优势显著，归因于开箱即用的操作工具集与统一执行接口。
- **长周期鲁棒性**：在 <15 分钟桶达 91.75%、15 分钟–1 小时桶达 81.23%（均最优）；1–4 小时桶达 52.38%，远超同模型设置下 mini-swe-agent（35.71% 高推理 / 42.86% 中推理），接近最强的 live-SWE-agent（54.76%）。观察到的 mini-swe-agent 高推理设置下性能下降（上下文预算效应）在 openJiuwen 中未出现，与上下文管理机制的作用一致。
- **总体**：在两个差异化显著的 benchmark 上同时超过最强基线，支持可组合 + 自适应 harness 设计的有效性。
