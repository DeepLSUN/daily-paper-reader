## 摘要
最近的研究表明，从执行反馈中进行强化学习可以显著提高文本到SQL的性能，通常使较小的模型能够匹配甚至超过更大的系统。然而，现有的大多数方法将SQL生成视为单轮任务，限制了模型通过迭代修正从错误中恢复的能力。我们提出了ReToolSQL，一个用于文本到SQL的两阶段训练框架，它结合了（i）在拒绝采样推理轨迹上的监督式热启动，以及（ii）在多轮工具使用轨迹上的智能体强化微调（RFT）。关键洞察在于这两个阶段在互补的维度上发挥作用：在验证过的特权教师轨迹上的监督微调（SFT）扩展了可解决问题集（提高了最困难案例的pass@k覆盖率），而RFT通过教会模型何时验证、检索什么证据以及如何根据执行反馈修复有缺陷的SQL，将这种扩展的能力转化为更高的单次通过准确率。应用于Gemma 4指令调优模型（31B）时，仅RFT在BIRD-SQL开发基准上就达到了73.66%的执行准确率（EX）（使用自一致性时为74.12% EX）。从SFT检查点初始化RFT（SFT→RFT）得到了我们最强的模型，单次通过EX为74.32%，自一致性EX为74.77%。在撰写本文时，这在BIRD单模型开发集排行榜上排名第一。该方法使用基于执行正确性的复合奖励，除了基准本身外不需要任何人工标注，并且在单个密集的31B模型内运行，表明在工具使用轨迹上精心设计的SFT→RFT流水线是实现稳健的企业级文本到SQL的实用路径。

## Abstract
Recent work has shown that reinforcement learning from execution feedback can substantially improve text-to-SQL performance, often enabling smaller models to match or exceed much larger systems. However, most existing approaches treat SQL generation as a single-turn task, limiting the model's ability to recover from errors through iterative refinement. We present ReToolSQL, a two-stage training framework for text-to-SQL that combines (i) a supervised warm-start on rejection-sampled reasoning traces with (ii) agentic reinforcement fine-tuning (RFT) over multi-turn tool-use trajectories. The key insight is that the two stages act on complementary axes, the supervised fine-tuning (SFT) on verified privileged-teacher traces expands the set of solvable questions (raising pass@k coverage on the hardest cases), while RFT converts that expanded capability into higher single-pass accuracy by teaching the model when to verify, what evidence to retrieve, and how to repair faulty SQL from execution feedback. Applied to Gemma 4 instruction-tuned (31B), RFT alone achieves 73.66% execution accuracy (EX) on the BIRD-SQL development benchmark (74.12% EX with self-consistency). Initializing RFT from the SFT checkpoint (SFT$\to$RFT) yields our strongest model at 74.32% EX single-pass and 74.77% EX with self-consistency. At the time of writing, this ranked first on the BIRD single-model development-set leaderboard. The approach uses composite rewards anchored on execution correctness, requires no human annotation beyond the benchmark itself, and operates within a single dense 31B model, showing that a properly designed SFT$\to$RFT pipeline over tool-use trajectories is a practical path toward robust enterprise-grade text-to-SQL.

- **整体定位**：论文提出 ReToolSQL，将 Text-to-SQL 构建为一个**工具增强的序列决策问题**，用强化学习训练模型学会何时验证、检索什么证据、如何根据执行反馈修复 SQL，最终在 BIRD-SQL 开发集取得单模型排名第一的性能。

## 2. 方法论：核心思想与关键技术细节

### 2.1 整体框架：两阶段 SFT→RFT 管线

- **第一阶段——监督微调（SFT）热启动**：在拒绝采样（rejection-sampled）的特权教师推理轨迹上进行监督预热。
- **第二阶段——智能体强化微调（RFT）**：基于 GRPO 对多轮工具使用轨迹进行强化学习。
- **互补性设计**：SFT 阶段通过注入验证过的教师轨迹**扩大可解决问题的覆盖范围**（尤其在困难问题上提升 pass@k）；RFT 阶段则将这些扩展的能力**转化为更高的单次通过准确率**，教会模型验证、检索与修复。

### 2.2 问题建模：POMDP 框架

- 每个实例被建模为部分可观测马尔可夫决策过程 (Q, S, T)，其中：
  - Q = 自然语言问题（可选附带提示/hint）
  - S = 目标数据库 D 的模式
  - T = 固定的一组只读工具
- 策略 πθ 为自回归语言模型；每轮 t 观察到上下文 cₜ，生成工具调用或最终 SQL；环境返回观测 oₜ，上下文按 cₜ₊₁ = [cₜ; aₜ; oₜ] 自回归扩展。
- 轨迹在模型输出 `<final_answer>` 或耗尽每轮工具预算（T_max = 8 轮）时终止。

### 2.3 模式接地：M-Schema 编码的观察空间

- 采用 **M-Schema 序列化**，比原始 DDL 或扁平列列表更强，因为其暴露了类型、外键和数据证据。
- 每个表携带行/列数、列名与类型、自然语言含义、键/可空性标记、统计摘要（Nulls、Distinct、Min/Avg/Max）、高频分类值 Top 以及示例值；末尾附外键连接路径。
- 使用 BM25 检索少量示例（few-shot），排除与目标 db_id 共享的样本以防泄漏。
- 训练时提示词上限 15,500 tokens，完成长度上限 8,000 tokens，超长直接过滤而非截断。

### 2.4 动作空间：验证优先的工具套件

三个确定性只读工具：

| 工具 | 功能 | 解决的关键问题 |
|------|------|----------------|
| `sqlite_query` | 沙箱化 SQL 执行器（仅 SELECT/WITH），返回结果列/行或结构化错误 | 执行引导的自我修复 |
| `sqlite_peek` | 列剖析器：类型、空值/去重计数、min/max、代表性样本、字符类摘要 | 解决百分比vs分数、日期格式、连接键类型不匹配 |
| `bm25_search_sqlite` | 基于 BM25 + 正则/子串回退的混合词法搜索 | 映射释义实体到精确存储拼写，修复字面量不匹配 |

- 严格的轮次协议：每轮助手包含有界 `<scratch_pad>`（意图、预期输出列、候选 SQL）+ 一个工具调用或 `<final_answer>` 块。
- 最后定稿前必须输出 `<relevant_tables>` 和 `<relevant_columns>` 标注，供链接奖励使用。

### 2.5 策略优化：GRPO 与 DAPO 非对称裁剪（公式说明）

- 对每个问题采样 G=16 条完整轨迹，奖励通过组内相对归一化计算优势：

  Âᵢ = (Rᵢ − μ_G) / (σ_G + ε)

- 使用 DAPO 的非对称裁剪目标（ε_lo=0.20, ε_hi=0.28），允许策略对稀有高奖励轨迹的概率提升比失败轨迹的概率降低更激进，防止熵提前崩溃。
- 结合衰减 KL 惩罚调度（β: 0.005 → 0.001 → 0）保持策略熵和探索能力。

### 2.6 关键训练技术

- **DAPO 动态采样**：对每个候选提示组采样 G=16 个完成，只有奖励存在异质性（std ≥ 10⁻⁶）的组才保留；过采样因子 K=12，避免全对/全错的无梯度组浪费计算。
- **工具观测掩码（Tool-Observation Loss Masking）**：对日志中环境注入的观测 token 置掩码为 0，梯度只流过策略自身生成的 token（推理、工具调用、最终 SQL），防止模型学习记忆数据库内容，也防止训练/测试模式泄漏。
- **长度正则化**：DAPO 软超长惩罚，L_target=6000, L_max=8000, α=0.5。
- **复合奖励**：7 个组件加权求和 R = ΣwₖRₖ，执行结果项（R_exec，权重 2.0）主导，辅助项（格式、语法、表集合、列 Jaccard、非空、长度）防止组内优势平坦。最大可达到奖励为 3.8。奖励权重为启发式设置而非搜索。
- **推理时执行共识（Execution Consensus）**：采样 N=16 条候选轨迹（温度 1.2），执行后按结果集相等聚合，丢弃错误或空结果，返回最大簇的代表性 SQL。

### 2.7 SFT 预热：特权推理轨迹

- 用 pass@16 解码挖掘"全错带"（所有轨迹都失败的困难问题）。
- 对这些问题，向模型提供**金标准参考 SQL 作为特权上下文**，生成分步推理链；只有最终 SQL 通过执行匹配的轨迹才保留。
- 对较容易的问题，收集模型自身的正确轨迹（不附带特权信息），避免分布偏移。

## 6. 主要结论与发现

1. **SFT→RFT 复合管线最优**：单次通过 EX 达 74.32%，带执行共识的 SC 达 74.77%，在 BIRD 开发集单模型排行榜中排名第一。
2. **RFT 单独优于 SFT 单独**（单次 73.66% vs. 72.69%），但 RFT 不显著提升 pass@16（77.2% vs. 76.9%），说明 RL 主要锐化单次准确率而非扩展覆盖率。
3. **SFT 显著提升 pass@k 覆盖率**：从 76.9% 提升至 81.29%，对困难问题的覆盖率扩展是 RL 能发挥作用的先决条件。
4. **工具与 RL 存在显著交互效应**：工具单独 +2.02%，RL 单独 +0.45%，两者结合 +3.97%，超出加性效应 1.50%，证明 RL 具体教会了模型使用工具而非仅仅提供工具。
5. **熵保存是 RL 持续学习的必要条件**：衰减 β 调度比 β=0 提高 2.09%（贪心）和 1.96%（SC），且将熵维持时间延长约 2 倍。
6. **较小模型从 RL 中获得更大的相对增益**：E4B 获得 +3.33% 而 31B 为 +1.95%，原因可能是 31B 基策略已较强。

## 7. 优点：方法与实验设计的亮点

- **任务重构创新**：将 Text-to-SQL 从单轮生成重构为**工具增强的多轮决策问题**，模型在训练中内化验证与修复能力，而非外部流水线编排。

## 8. 不足与局限

### 8.1 实验覆盖局限

- **单基准验证**：仅在 BIRD-SQL 开发集上评估，未覆盖 Spider、WikiSQL、KaggleDBQA 等通用 NLP 基准，泛化性证据不足。
- **无测试集结果**：虽然声称排行榜第一，但该排行榜基于开发集；BIRD 官方排行榜通常要求测试集提交，两者的分布差异可能影响结论的可靠性。
- **单一模型族**：实验全部基于 Gemma 4 系列（31B 和 E4B），未在 Qwen、Llama 等其他模型家族上验证，方法与模型的具体组合可能存在内在依赖。

### 8.2 潜在偏差风险

- **基准过拟合**：在 BIRD 训练分区的 6,601 个问题上训练，目标正是 BIRD 的评价指标；虽然开发集数据库不相交，但训练数据的分布与评价基准高度一致，跨基准迁移能力未验证。
- **奖励权重缺乏敏感性分析**：作者声称"性能对精确辅助值不敏感"，但未提供数据支撑。
- **知识泄漏防范**：虽然排除了训练集中共享 db_id 的 few-shot 示例，但未讨论 BM25 示例检索中是否存在列名语义重叠等问题。

### 8.3 应用限制

- **假设数据库工具可用**：方法依赖沙箱化 SQL 执行器、列剖析器和 BM25 搜索在训练和推理时均可用，对于没有良好工具接口的数据库环境难以部署。
- **只读工具限制**：当前仅支持 SELECT/WITH，不支持 INSERT/UPDATE/DELETE 或 DML 场景，适用范围有限。
- **候选多样性不足**：31B 模型每个问题平均仅生成 3.37 条唯一 SQL（16 个样本中），自一致性提升有限（+0.46%），且 pass@16 上限（77.2%）与 SC（74.12%）之间存在 3.08% 的未实现潜能——模型差异度不足限制了投票机制的有效性。
- **算力需求未全面披露**：训练时长未报告，难以估计整体成本。
- **企业部署的现实障碍**：虽然架构简单，但仍需 vLLM 服务器 + 权重同步的分布式训练基础设施；推理时的执行共识需要数据库访问，对延迟敏感场景不友好。
