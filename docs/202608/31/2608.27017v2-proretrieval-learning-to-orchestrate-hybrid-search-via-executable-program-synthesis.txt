Abstract
Real-world retrieval often composes structured
constraints with semantic intents over text
and images through arbitrary Boolean logic.
Existing hybrid pipelines such as reciprocal
rank fusion or self-querying retrievers admit
only a fixed form of composition, while recent
reinforcement-learning retrievers train the
language model as a query generator for a
single backend, leaving the orchestration
of heterogeneous retrieval paths outside its
action space. We propose ProRetrieval, which
recasts the language model as a retrieval
orchestrator: given a natural-language query,
it synthesizes an executable program in a
hybrid
DSL
interleaving
SQL
operators
over structured fields with vector-retrieval
primitives over text and images, with SQL
itself providing the logical algebra that fuses
heterogeneous candidate sets. We train Qwen3-
4B with GRPO and DAPO under a hierarchical
four-term reward, and evaluate on two new
benchmarks built from Amazon products
and Enron email. Our 4B model surpasses
GPT-5.5 (Hit@1 0.81 vs. 0.69 on e-commerce;
0.91 vs. 0.86 on email) and Claude Opus
4.7 and a comprehensive suite of retrieval,
LLM-augmented, structured-query, and graph-
based baselines. Code: https://anonymous.
4open.science/r/ProRetrieval/;
data:
https://huggingface.co/datasets/
anonymous-7219/ProRetrieval.

Introduction
Real-world retrieval rarely reduces to either sym-
bolic filtering or pure semantic matching. A user
may ask for “last week’s emails from the market-
ing team about the Q3 budget, but not the archived
ones”, or for “a wireless headphone under $200
from Sony or Bose, with strong noise-cancelling
reviews, in matte black”. Such queries share two
properties: information is split across heteroge-
neous backends (relational fields, text and image
*Corresponding authors.
indices), and constraints are composed by arbitrary
Boolean connectives (disjunction, negation, and
nested groups). Solving them requires not only un-
derstanding what the user wants, but deciding how
to find it: which conditions to push down as exact
filters, which intents to pose as semantic queries,
and how to logically combine the resulting candi-
date sets.
Existing methods fall short along two axes. On
expressive power, pure retrievers (Robertson and
Zaragoza, 2009; Karpukhin et al., 2020) cover a
single modality; fusion pipelines (Cormack et al.,
2009) express only weighted disjunction; and self-
querying retrievers (Chase, 2023) admit simple key–
value conjunctions but not disjunction, negation,
or nested predicates. On orchestration capability,
recent RL approaches such as Search-R1 (Jin et al.,
2025) and DeepRetrieval (Jiang et al., 2025a) train
models to issue better queries to a single backend
but cannot compose across heterogeneous stores.
Hybrid retrieval therefore requires enlarging the
model’s role from query generator to retrieval or-
chestrator, with an action space that is itself an
executable program over a logically complete oper-
ator set.
We propose ProRetrieval, a framework that
trains a small language model to orchestrate hy-
brid retrieval by synthesizing executable retrieval
programs. Our key observation is that SQL’s log-
ical algebra (selection, conjunction, disjunction,
negation, and nested subqueries) can serve as the
orchestration skeleton, while vector retrieval is in-
corporated as a first-class primitive whose results
plug into SQL through candidate-set placeholders
(e.g., id IN <text_0>). This reduces orchestra-
tion to learnable program generation in a hybrid
DSL while inheriting SQL’s logical completeness
for free. We train Qwen3-4B with GRPO (Shao
et al., 2024) and DAPO (Yu et al., 2025) under a
hierarchical four-term reward (format, execution,
result, length) that mirrors the layered correctness

Related Work
Hybrid retrieval.
Sparse and dense retriev-
ers (Robertson and Zaragoza, 2009; Karpukhin
et al., 2020; Khattab and Zaharia, 2020) and mod-
ern multimodal embedders (Chen et al., 2024;
Faysse et al., 2024), optionally followed by cross-
encoder rerankers (Nogueira and Cho, 2019; Xiao
et al., 2023), each operate within a single rep-
resentational space. Industry pipelines combine
them at the rank level via reciprocal rank fu-
sion (Cormack et al., 2009), which captures only
a weighted disjunction, or through self-querying
retrievers (Chase, 2023), whose filter language
admits only conjunctions of simple key–value
predicates. Knowledge-graph retrievers such as
2


GraphRAG (Edge et al., 2024) introduce an orthog-
onal structured signal and are complementary to
our field-centric design. Across this line the orches-
tration logic is fixed by the pipeline designer and
cannot adapt per query.
RL for retrieval.
Recent work uses RL to
train language models that interact with retrieval:
Search-R1 (Jin et al., 2025) interleaves reasoning
with calls to a search engine; DeepRetrieval (Jiang
et al., 2025a) optimizes structured Boolean / SQL-
like query reformulation against a single backend;
s3 (Jiang et al., 2025b), R1-Searcher (Song et al.,
2025), and follow-ups (Chen et al., 2025; Li et al.,
2025) explore further variants, and SQL-R1 (Ma
et al., 2025) applies RL to text-to-SQL. These meth-
ods improve the queries a model issues, but the ac-
tion space is restricted to the type of query a single
fixed backend accepts and none orchestrates mul-
tiple heterogeneous backends with arbitrary log-
ical composition. In particular, SQL-R1 cannot
express semantic similarity queries (e.g., “shoes
that look like classic sneakers”) because SQL lacks
vector retrieval operators; our action space abla-
tion (§4.3) quantifies this gap: SQL-only achieves
0.650 Hit@1 vs. 0.809 for the full hybrid DSL. We
compare directly with Search-R1, DeepRetrieval,
and SQL-R1.
DSLs for retrieval.
DSLs have long bridged lan-
guage models and symbolic computation in pro-
gram synthesis (Balog et al., 2017; Chen et al.,
2021) and tool use (Yao et al., 2023; Schick et al.,
2023). Closest to our work, SUQL (Liu et al.,
2024) extends SQL with a SUMMARY operator for
conversational QA, and Text2VectorSQL (Wang
et al., 2025) proposes a unified SQL interface
with vector search predicates. Text2VectorSQL
embeds vector operations as SQL UDFs, cou-
pling retrieval and fusion in a database-native en-
gine; our placeholder injection decouples them,
enabling independent optimization and extension
to image modality. The two systems target differ-
ent tasks—Text2VectorSQL evaluates SQL execu-
tion accuracy on Spider/BIRD-style benchmarks,
whereas we evaluate document retrieval quality
(Hit@1, MRR)—and our SFT baseline already
represents the same supervised-learning paradigm,
upon which RL provides a further +12.9 pp gain
(§4.2). Other approaches include TableQuery (Pal
et al., 2024) and CRUSH (Zhou et al., 2024), fo-
cusing on structured-only retrieval without vector
primitives. All of the above rely on prompting or
SFT. ProRetrieval differs by treating the DSL as a
learnable policy space optimized end-to-end by RL
with a hierarchical reward tailored to executable
hybrid programs.
3
Method
ProRetrieval trains a small language model to act
as a retrieval orchestrator that synthesizes exe-
cutable hybrid retrieval programs.
The frame-
work, illustrated in Figure 1, comprises three
components: (i) a hybrid retrieval DSL that in-
terleaves SQL operators with text and image
vector-retrieval primitives (§3.1); (ii) a query
construction pipeline that automatically produces
(NL query, gold DSL, ground-truth documents)
triples covering single-leaf to nested Boolean ex-
pressions (§3.2); and (iii) a two-stage training pro-
cedure that warm-starts the model with supervised
fine-tuning on gold DSL and then optimizes it with
reinforcement learning under a hierarchical com-
posite reward (§3.3).
3.1
Hybrid Retrieval DSL
Syntax.
A program in our DSL is a JSON object
with two fields:
{
"sql": "SELECT DISTINCT id FROM <T>
WHERE <conditions>",
"retrieval_list": [
{"type": "text",
"field": "<f1>",
"query": "<semantic phrase>"},
{"type": "image", "field": "<f2>",
"query": "<visual phrase>"},
...
]
}
The sql field is a standard SQL query over the
structured fields of the underlying table; it may
invoke vector retrieval through placeholders of the
form <text_k> or <image_k>, where k indexes
the corresponding entry in retrieval_list. Each
entry specifies the modality, the field on which
similarity is computed, and the textual query to
be embedded. Because the placeholders appear
as candidate-set constraints inside arbitrary SQL
clauses, the program inherits SQL’s full logical
algebra: AND, OR, NOT, and nested subqueries can
freely combine structured predicates with semantic
ones.
Execution.
At execution time, each entry in
retrieval_list is dispatched to the correspond-
ing backend (a text or image encoder followed by
3


approximate nearest-neighbor search), which re-
turns the top-K candidate identifiers Ck (we use
K=20 throughout all experiments). The placehold-
ers are then substituted by the corresponding sets,
transforming semantic similarity into set member-
ship predicates (e.g., id IN (P001, P042, ...)).
The resulting SQL is executed against the relational
backend, which performs the final logical compo-
sition via its native query engine. This two-phase
design (vector retrieval followed by relational fu-
sion) decouples the embedding computation from
the logical orchestration, allowing each component
to be optimized independently.
The DSL strictly subsumes the action spaces of
prior methods: reciprocal rank fusion corresponds
to a disjunction of vector predicates without struc-
tured filtering; self-querying retrievers to a single
vector predicate conjoined with key–value filters;
pure text-to-SQL to the empty retrieval_list.
This hierarchy means any query expressible by
a simpler paradigm is expressible in our DSL,
while the converse does not hold—queries requir-
ing cross-modal logical composition (e.g., struc-
tured AND semantic AND visual) are unique to the
full DSL. Figure 2 shows a worked example.
3.2
Query Construction Pipeline
Since no existing benchmark covers hybrid
structured–semantic retrieval with executable
ground truth, we construct two datasets, e-
commerce (Amazon ESCI + Reviews) and email
(Enron), via an automated, complexity-driven
pipeline.
Given a corpus D and a per-domain
schema, each instance is produced in four steps.
(i) Structure. We sample the number of leaves
N ∈{1, . . . , 5} from a fixed distribution that
sets the query level (L1/L2/L3) and partition them
into K groups under two-level Boolean templates
(c1∧· · ·∧cm) ∨(cm+1∧· · ·∧cN) or (c1∨· · ·∨cm) ∧
(cm+1∨· · ·∨cN), which together with K=1 (flat con-
junction or disjunction) cover all single- and two-
level nested patterns. (ii) Grounding. A small gold
set G ⊂D anchors the query (one shared gold per
inter-group ∧, one distinct gold per group under ∨);
each leaf is assigned a field with weights favoring
structured over text/image and is marked positive
or negated with probability growing in N. Posi-
tive leaves take satisfying values extracted from the
gold (exact categorical, comparator+threshold nu-
meric, LLM-extracted text phrase, VLM-generated
visual description); negated leaves take violating
values. (iii) Compilation. Leaves are compiled
into SQL predicates and id IN <text/image_k>
clauses to form the gold DSL, which is executed
on D to obtain the ground-truth set T ⊇G; we
accelerate this with a structural-only super-query
that evaluates only the SQL predicates (ignoring
vector placeholders) to cheaply prune instances
whose structured conditions alone yield empty or
oversized candidate sets, and filter instances with
empty or oversized T . (iv) Verbalization. An
LLM (GPT-4o) rewrites the gold DSL as a fluent
NL query. Each instance is stored with full meta-
data (level, leaves, groups, operator pattern, modal-
ity usage). Figure 3 summarizes the resulting test
split.

equal weights; the layered dependency already pro-

insensitive to moderate weight variations (±0.5).
Implementation.
We train on the verl frame-
work (Sheng et al., 2025) from Qwen3-4B and
Qwen3-8B bases. SFT runs for 3 epochs with learn-
ing rate 5×10−5 and batch size 64; we select the
checkpoint with the lowest validation loss. Text
and image candidates for vector primitives are pre-
computed offline with Qwen3 text and vision em-
bedding backbones, indexed for nearest-neighbor
lookup, and shared across all baselines.

Experiments
4.1
Experimental Setup
Datasets.
We
evaluate
on
two
hybrid
re-
trieval scenarios with distinct modality compo-
sitions. E-commerce is constructed from Ama-
zon ESCI (Reddy et al., 2022) and Amazon
Review data, containing 3,000 products with
structured fields (brand, category, price, rating),
text fields (title, description, review), and prod-
uct images.
Email is derived from the Enron
email corpus (Klimt and Yang, 2004), containing
5,000 emails with structured fields (sender, date,
read/starred status) and text fields (subject, body).
For each scenario we construct 20,000 training and
3,000 test queries, stratified into three complex-
ity levels: L1 (single condition, ∼40%), L2 (2–3
conditions, ∼40%), and L3 (4–5 conditions with
OR/NOT/nesting, ∼20%).
Metrics.
We report Hit@1 (primary), Hit@3,
MRR, and NDCG@3. For DSL-based methods
5


we additionally report execution success rate.
Implementation.
We
train
Qwen3-4B
and
Qwen3-8B (Yang et al., 2025) with SFT using
verl (Sheng et al., 2025); the 4B model is fur-
ther optimized with RL (GRPO (Shao et al., 2024)
or DAPO (Yu et al., 2025)). RL uses batch size
32, learning rate 1×10−6, KL coefficient 0.001,
and 4 rollouts per prompt. Embeddings are com-
puted with frozen Qwen3-Embedding-8B (text)
and Qwen3-VL-Embedding-8B (image); these en-
coders are not updated during training and are
shared across all baselines. Training uses 2×RTX
PRO 6000 (96 GB); inference uses a single RTX
4090, with end-to-end latency ∼50 ms per query
dominated by vector retrieval (∼80%; details in
Appendix G).
Baselines.
We compare against four paradigms
of increasing action-space expressiveness:1
• B1 Pure Retrieval: BM25 (Robertson and
Zaragoza, 2009), BGE-Reranker (Xiao et al.,
2023).
• B2 LLM-Augmented: RankGPT (Sun et al.,
2023) with GPT-5.4 listwise reranking.
• B3 Constrained Structured Query: DeepRe-
trieval (Jiang et al., 2025a) (Boolean+BM25,
RL), Search-R1 (Jin et al., 2025) (multi-turn
BM25, RL).
• B4 KG Retrieval: LightRAG (Guo et al.,
2024).
We additionally compare against commercial
LLMs (GPT-5.5, Claude Opus 4.7) generating DSL
under few-shot prompting: each prompt includes
the full corpus schema and 6–7 exemplar DSL pro-
grams covering all modality types (Appendix H), to
isolate the effect of dedicated training from model
scale.

Action space complexity creates an optimiza-
tion challenge for SFT.
Reducing the action
space to SQL+text yields 0.752, surpassing the
full three-modality DSL (0.680) by +7.2 pp. This
is not because the image modality is useless, but
because the 4B model cannot jointly learn three
retrieval modalities via imitation alone. On image
queries, full-DSL SFT achieves only 0.323 (the
model attempts image retrieval but orchestrates
it incorrectly), while SQL+text falls back to text-
based matching and reaches 0.547 (Appendix Ta-
ble 3). This is a classic multi-task optimization
interference: the harder action space dilutes learn-
ing across all pathways.
RL overcomes this barrier.
RL on the full DSL
(0.809) surpasses every restricted variant’s SFT per-
formance, including SQL+text (0.752). The gain
is concentrated exactly where SFT fails: image
queries improve from 0.323 to 0.716 (+39.3 pp),
the largest single-modality gain. Structured and
text queries also improve (+10.0 pp and +5.8 pp
respectively), exceeding the SQL+text SFT upper
bounds (0.828 and 0.671) in both cases. The very
difficulty of the full action space is what makes
RL necessary: reward-driven exploration discovers
effective multi-modal orchestration strategies that
demonstration-based learning cannot acquire.

Conclusion
ProRetrieval recasts the language model as a re-
trieval orchestrator that synthesizes executable
hybrid programs interleaving SQL with text and
image vector primitives, trained via a hierar-
chical four-term reward.
A 4B model reaches
80.9%/90.9% Hit@1 (e-commerce/email), surpass-
ing the best commercial LLM by +11.6/+5.4 pp;
OOD evaluation confirms generalization within
3 pp. Action space ablations show that the full
DSL underperforms simpler variants under SFT
due to multi-task interference, but RL overcomes
this barrier (+39.3 pp on image retrieval); at 8B
scale, SFT alone captures the key patterns, sug-
gesting RL is most critical when model capacity
is the bottleneck. These results establish retrieval
program synthesis over a compositional DSL as
a promising direction for unified retrieval across
modalities and query complexities.

Limitations
While ProRetrieval demonstrates strong results on
hybrid retrieval, our study has several limitations.
(i) Schema dependence. The DSL assumes a prede-
fined schema; extending it to schema-free or evolv-
ing corpora (e.g., via automatic schema discovery)
is left to future work. (ii) Bounded logical depth.
Our query construction pipeline samples logical
expressions up to two levels of nesting; deeper
nesting is syntactically expressible but underrepre-
sented in training. (iii) Two-domain evaluation. We
validate on e-commerce and email; broader gener-
alization to scientific literature, legal documents,
and personal knowledge bases remains to be tested.
(iv) Moderate corpus scale. Our benchmarks con-
tain 3,000 products and 5,000 emails, respectively.
While sufficient for evaluating retrieval accuracy,
scaling to corpora with millions of documents may
introduce additional challenges in DSL execution
latency and candidate-set composition. (v) Single-
turn retrieval. The framework synthesizes a sin-
gle program per query; extending to multi-turn
interaction where the model refines its DSL based
on intermediate results is a promising direction.
(vi) Dependence on embedding backbones. Image
retrieval quality is bounded by the text-to-image
alignment of the underlying multimodal embed-
der. (vii) Statistical variance. We do not report
cross-seed variance due to RL training cost. Two
independent RL algorithms (GRPO, DAPO) con-
verge to similar performance, and key effect sizes
(+12.9 pp SFT→RL) are 4–5× typical cross-seed
variance; bootstrap 95% CIs (Appendix F) confirm
all pairwise differences are significant. (viii) Bench-
mark construction. Our pipeline uses GPT-4o for
query verbalization (§3.2), which may introduce
stylistic biases; however, such bias should favor
commercial LLMs more than our 4B model. OOD
evaluation with human-annotated queries (§4.4)
shows ≤3 pp IID-to-OOD gaps. (ix) Production
fallback. The system does not include automatic
fallback when DSL generation fails; a cascade to
vector retrieval on execution failure would improve
robustness in deployment.
Ethics Statement
ProRetrieval is a retrieval orchestrator that synthe-
sizes executable programs to locate existing docu-
ments; it does not generate user-facing content and
therefore poses minimal risk of producing harmful
or misleading text. All experiments use publicly
available research datasets: Amazon ESCI (product
metadata) and Enron (public email corpus released
for research). We do not attempt to re-identify indi-
viduals in the Enron dataset and use only metadata
and text fields for retrieval evaluation. We note that
structured filtering conditions (e.g., brand or price
constraints) could in some applications systemati-
cally exclude certain groups or information sources,
and that biases in the underlying embedding models
may propagate into retrieval rankings; practition-
ers should audit filter distributions and embedding
fairness when deploying program-based retrieval
in sensitive domains.

Figure 7 compares the training curves of GRPO and
DAPO on e-commerce (4B). Both algorithms con-
verge to similar peak performance (GRPO: 0.809

diversity in the rollout distribution. On email, both

The dominant error mode across all trained mod-

strategy, not syntax compliance.

G
Inference Latency
DSL execution involves three stages: vector re-
trieval, placeholder injection, and SQL execution.
On our benchmarks, vector retrieval dominates
(∼80% of total latency), placeholder injection is
negligible (<1 ms), and SQL execution on K=20
candidate sets completes in <1 ms.
Total per-
query inference latency is comparable to single-
backend retrieval methods and substantially faster
than multi-turn approaches such as Search-R1,
which require multiple retrieval–reasoning cycles.
