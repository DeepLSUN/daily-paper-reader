## 摘要
语言模型（LM）越来越多地通过用领域特定语言（DSL）编写的程序与外部服务交互。遗憾的是，由于DSL通常是低资源的且相对冷门，LM在这些语言中经常产生语法无效的程序。语法约束解码可以消除此类失败，但需要语法约束。这些约束通常以目标语言的上下文无关文法形式存在，而该文法对于第三方DSL而言很难获得。在本工作中，我们定义了一个名为Autogrammar的智能体，它能够从文档和执行数据中自动学习上下文无关文法。Autogrammar被形式化为一个Kripke结构，其非确定性选择由语言模型解析，从而能够通过线性时序逻辑约束对智能体行为进行声明式控制。我们在三个DSL（即Amazon CloudWatch Logs Insights、Dynatrace Query Language和Datadog Search Syntax）上评估了Autogrammar的四个版本，发现其生成的文法在未见数据上能达到接近完美的精确率；时间约束可将执行时间减少3.8倍，同时不产生统计上显著的精确率损失；执行数据至关重要，而文档并非必需；使用Autogrammar生成的文法进行语法约束解码，在十个真实任务中的八个上显著提升了端到端LM性能，达到或超过了专业维护文法的性能。相比之下，现有LM基线和最先进形式技术生成的上下文无关文法在同一评估中表现显著更差。

## Abstract
Language models (LMs) are increasingly used to interact with external services via programs written in domain-specific languages (DSLs). Unfortunately, since DSLs are often low-resource and esoteric, LMs frequently produce syntactically invalid programs in these languages. Grammar-constrained decoding can eliminate such failures, but requires syntactic constraints. These are usually in the form of a context-free grammar for the target language, an artifact that is hard to come by for third-party DSLs. In this work, we define an agent, called Autogrammar, that automatically learns context-free grammars from documentation and execution data. Autogrammar is formalized as a Kripke structure whose nondeterministic choices are resolved by a language model, enabling declarative control of agent behavior via linear temporal logic constraints. We evaluate four versions of Autogrammar on three DSLs (i.e., Amazon CloudWatch Logs Insights, Dynatrace Query Language, and Datadog Search Syntax) and find that it generates grammars that achieve near perfect precision on unseen data; that temporal restrictions reduce execution time by 3.8x without incurring statistically-significant loss in precision; that execution data is crucial while documentation is dispensable; and that grammar-constrained decoding using Autogrammar-generated grammars significantly improves end-to-end LM performance on eight out of ten real tasks, matching or exceeding the performance of a professionally-maintained grammar. In comparison, the context-free grammars generated by existing LM baselines and a state-of-the-art formal technique perform significantly worse over the same evaluation.

- **核心痛点**：对于第三方专有DSL（如AWS各服务的查询语言），现成的CFG往往不存在，手动编写昂贵且易出错（论文引用相关研究表明即使手写正则表达式也很困难）。
- **关键观察**：论文统计发现，在416个AWS Boto3 SDK服务中，23%的服务暴露了需要符合DSL的字符串参数，AWS至少使用了59种独特的DSL。这些DSL的资源量远低于Python等通用语言，导致LM性能不佳。
- **核心问题**：**能否自动学习高质量的CFG**，从而让GCD技术得以应用于缺乏现成文法的第三方DSL？

## 2. 方法论

### 2.1 核心思想
- 将LM智能体（Autogrammar）形式化为**Kripke结构**，其非确定性选择由底层LM做出，行为通过**LTL约束**进行声明式控制。
- 学习过程是**被动式**（passive）的：不依赖可任意查询的membership oracle（不同于主动学习），仅利用已有的执行日志（正/负例）和文档。

### 2.2 Autogrammar的Kripke结构定义
- **状态变量**：训练数据（正/负字符串示例）、文档、候选CFG集合、元数据（如最小拒绝次数、时间戳）。
- **动作集合（工具）**：
  - `add_g`：提出候选CFG
  - `eval`：用所有训练示例测试文法
  - `add_s` / `del_s`：增删训练样本
  - `gen_ts`：基于文档生成针对性测试字符串（针对文法缺陷）
  - `return`：返回最终文法
- **ghost变量 `head`**：记录每次工具调用及其参数，用于定义标签（labels）和LTL约束。

### 2.3 LTL约束的四个版本
| 版本 | 说明 |
|---|---|
| **Unlimited** | 最少LTL约束，仅保留安全约束（如 `∀x. G(eval(x) ⇒ x ∈ C)`，即只能评估候选集中的文法） |
| **Performance** | 增加效率约束（如公式1：禁止无数据变更时重复评估同一文法；公式3：设定时间上限b，超时强制返回文法） |
| **No Documentation** | 在Performance基础上禁用依赖文档的动作 |
| **No Execution Data** | 在Performance基础上禁用依赖执行数据的动作 |

### 2.4 关键技术细节
- **约束实施**：通过**拒绝采样**实现——若LM的决策违反LTL约束则拒绝并要求重试。
- **形式保证**：
  - **安全性**：底层LM无法接触测试数据（工具集受限）。
  - **进展性**：通过类似公式4的约束（如 `gen_ts` 对同一文法只执行一次）防止LM陷入低效循环。

## 6. 主要结论与发现

### 6.1 RQ1：文法精度
- Unlimited版本的Autogrammar在CWIL上精度0.999±.003、DQL上1.00±.000、DSS上0.910±.124——在数据量更充足的两个DSL上达到**接近完美的精确率**。

### 6.2 RQ2：与基线对比
- Autogrammar的精度**显著优于**Arvada（CWIL精度仅0.025）、LM-0（0.046-0.228）和LM-40（0.074-0.510），所有对比通过Holm-Bonferroni校正。
- Arvada失败原因：CloudWatch服务过于宽容（接受任意文本作为filter表达式），负例不足导致Arvada无法泛化，仅记忆训练示例。
- LM-40在DQL上达到的最高0.51精度仍远低于Autogrammar的1.00，说明**LM预训练知识本身不足以解释Autogrammar的成功**。

### 6.3 RQ3：性能约束
- Performance版本与Unlimited版本在精度上**无统计显著差异**，但执行时间从平均461分钟降至120分钟（约**3.8倍加速**）。
- 代价是CWIL的**召回率显著下降**（0.555→0.176），说明性能约束可能遗漏部分有效语法。

### 6.4 RQ4：消融研究
- **执行数据是关键的**：移除执行数据后，CWIL精度从0.989暴跌至0.113（灾难性下降），DQL也有明显下降（1.00→0.892）。
- **文档是可选的**：移除文档后，CWIL和DSS无显著精度损失；仅DQL有小幅但显著的精度下降（1.00→0.975，p=0.027）。
- 结论：对某些DSL，LM可能无法有效利用文档信息。

### 6.5 RQ5：端到端效果
- 在10个真实任务中，Autogrammar文法在**8/10任务上显著提升**了LM生成CloudWatch日志查询的成功率（相较于无反馈基线）。
- 与专业维护的现有文法相比：在**1/10任务上显著超越**，其余任务持平。
- 相对提升实例：任务1从23%提升至40%（Autogrammar）和45%（Existing）；任务7从57%提升至79%（Autogrammar）和89%（Existing）等。

## 7. 优点

- **新颖的形式化框架**：将LM智能体定义为Kripke结构+LTL约束，弥合了声明式编程与智能体设计之间的鸿沟，使得安全性和进展性可以形式化验证。
- **声明式控制**：通过简单修改LTL约束即可实现不同策略（如效率优化），无需修改代码逻辑，编程效率高。
- **无需oracle**：与Arvada等主动学习方法不同，Autogrammar作为被动学习方法，不依赖可查询的membership oracle，适用于受限API环境。
- **形式保证**：能够明确保证智能体不会接触测试数据（安全性）以及避免低效循环（进展性）。
- **实用性**：在真实AWS DSL上验证，端到端实验使用了6个不同LM，且与专业维护文法直接对比，结果可信。
- **工程意义**：解决了GCD落地的一个先决条件问题——文法获取。

## 8. 不足与局限

- **DSL类型覆盖有限**：仅评估了三个查询/搜索类DSL，均为相对简单的语法形式；未涵盖更复杂的DSL（如IAM policy、cron等）或通用编程语言。对复杂嵌套、递归结构显著的DSL效果未知。
- **LM单一性**：RQ1-4仅用Claude Opus 4.6，若换用其他LM（如GPT系列、开源模型），Autogrammar的表现可能不同。
- **数据规模不均衡**：DSS数据集过小（838条），负例仅17条，模型精度的置信区间极宽；CWIL虽有4万+数据，但负例仅占2.5%，属于极端不平衡数据。
- **召回率偏低**：Unlimited版本的召回率在CWIL和DQL上仅0.555和0.514，说明学习的文法偏向保守（精确但漏接受）。若用于GCD可能过度拒绝合法程序，影响任务完成率。
- **时间约束的副作用**：Performance版本虽保持精度，但CWIL召回率显著下降，说明120分钟时间上限可能不足以完全收敛。
- **文档利用率低**：消融实验表明文档对最终性能贡献有限，这暗示当前流程可能未充分利用文档信息，存在潜在改进空间。
- **泛化性威胁**：训练数据如果未覆盖DSL的全部语法特征，学习到的文法可能仅覆盖子集；论文虽通过端到端实验部分缓解了这一威胁，但无法完全排除数据偏差。
- **成本问题**：Unlimited版本平均461分钟的学习时间成本较高；尽管Performance版本降至120分钟，但相比纯LM基线仍较昂贵。
- **缺少与其他智能体编程框架的对比**：论文提到Strands等现有框架，但未实证对比LTL约束方法与手工提示工程/规则过滤方法的优劣势。
