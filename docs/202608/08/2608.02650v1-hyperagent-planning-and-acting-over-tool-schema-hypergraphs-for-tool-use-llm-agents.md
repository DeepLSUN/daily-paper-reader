## 摘要
大型语言模型（LLM）代理越来越依赖外部工具来完成复杂的现实世界任务。然而，由于隐式推理的局限性和现实执行环境的不断演变，可靠的工具使用规划仍然具有挑战性。现有的工具使用代理通常依赖LLM从文本描述中推断工具组合，这可能在复杂任务中导致低效的探索和不可靠的执行。为了应对这些挑战，我们在模式级别对工具关系进行建模，并构建了一个有向的工具-模式超图，其中工具被表示为从其所需输入模式节点到其输出模式节点的超边。此外，我们提出了HyperAgent，一种工具-模式超图引导的动态规划与执行框架。给定一个任务，HyperAgent首先提取任务相关的工具上下文图，并利用它来指导构建模式感知的任务DAG。在执行过程中，HyperAgent通过赤字导向扩展来动态实现每个子任务，该扩展根据当前代理状态识别未解决的依赖并检索支持性生产者工具。在AppWorld上的实验表明，与现有代理基线相比，HyperAgent在提高任务完成性能的同时，减少了冗余API调用、LLM交互和令牌消耗。

## Abstract
Large language model (LLM) agents increasingly rely on external tools to complete complex real-world tasks. However, reliable tool-use planning remains challenging due to the limitations of implicit reasoning and the evolving nature of real-world execution environments. Existing tool-use agents typically rely on LLMs to infer tool compositions from textual descriptions, which can lead to inefficient exploration and unreliable execution in complex tasks. To address these challenges, we model tool relations at the schema level and construct a directed Tool--Schema Hypergraph, in which tools are represented as hyperedges from their required input-schema nodes to their output-schema nodes. Furthermore, we propose HyperAgent, a Tool--Schema Hypergraph-guided framework for dynamic planning and execution. Given a task, HyperAgent first extracts a task-relevant tool context graph and uses it to guide the construction of a schema-aware Task DAG. During execution, HyperAgent dynamically realizes each subtask by constructing a state-conditioned tool support graph through deficit-oriented expansion, which identifies unresolved requirements and retrieves supporting producer tools according to the current agent state. Experiments on AppWorld demonstrate that HyperAgent improves task completion performance while reducing redundant API calls, LLM interactions, and token consumption compared with existing agent baselines.

## 1. 核心问题与整体含义

**研究动机**：大型语言模型（LLM）智能体在执行复杂任务时，越来越依赖外部工具（API、操作系统、软件服务）。然而，现有工具使用智能体大多依赖 LLM 从工具文本描述中“隐式”推断工具组合与调用链，存在两个关键问题：

- **不可靠**：面对大量工具文档时，模型不仅要找到语义相关的工具，还要识别其输入参数的前置生产者工具，依赖关系推理非常脆弱。
- **不适应动态状态**：工具是否可执行取决于当前代理状态（已获取的值、已实现的环境效果），静态预规划的工具路径容易变的冗余或不完整。
- 已有图式方法（如 ToolNet、GTool）虽然显式建模了工具依赖，但粒度较粗，未指定“哪个上游输出满足哪个下游输入”，且缺乏对执行状态的感知。

**整体含义**：本文提出在“模式（schema）层”对工具间关系进行精细化建模，构造有向工具–模式超图（Tool–Schema Hypergraph, TSH），从而将工具依赖的结构化知识显式注入智能体的规划与执行过程，使 LLM 智能体能够更可靠、更高效地完成多步工具调用任务。

## 2. 方法论

### 2.1 工具–模式超图（TSH）构建
- 将每个 API 工具建模为一条**有向超边**：从输入 schema 节点集合指向输出 schema 与效果（effect）节点集合。
- 在输出节点与另一工具输入节点之间建立 **port-level schema 依赖链接**，表示“某输出可作为某输入”，并赋予权重 \(w\)。
- 基于专家标注的 In-N-Out 参数级 API 图进行图转换，再通过 GPT-4o 提取工具文档中的“前置条件/效果状态”（如登录会话），人工双重验证后补充到超图中。
- 定义邻居工具（upstream/downstream neighbor）：若工具 \(e_i\) 的输出支持 \(e_j\) 的输入，则 \(e_i\) 为 \(e_j\) 的上游邻居。

### 2.2 任务级规划（离线/在线前段）
- **任务解释**：对用户请求 \(t\)，用 LLM 生成结构化解释 \(d_t = (d^{op}_t, d^{sch}_t)\)，分别捕获操作意图与涉及的 schema/实体/约束。
- **种子锚定**：
  - 超边锚定：计算工具描述与 \(d^{op}_t\) 的余弦相似度，选取 Top-K 超边作为种子。
  - 节点锚定：将 \(d^{sch}_t\) 分别与输入侧节点、输出侧节点计算相似度，得到种子节点集合。
- **上下文图提取**：从种子节点和超边出发，执行有界反向扩展（沿依赖链接向生产者工具回溯），依据评分 \(s_{back}(e, d^{op}_t)=w(v_o, v_i)\cdot \cos(z(e), z(d^{op}_t))\) 保留候选生产者；直到跳数预算耗尽，得到紧凑的任务相关工具上下文图（Tool Context Graph）。
- **任务 DAG 生成**：将上下文图序列化为结构化描述（工具、schema 节点、依赖边），提示 LLM 将任务分解为子任务节点，并在子任务间建立 schema 级数据/效果依赖边，形成有向无环图 Task DAG；每个子任务包含局部目标、期望输出 schemas 和候选终止工具集合。

### 2.3 执行阶段（工具级动态规划）
- **拓扑执行**：按 Task DAG 的依赖关系挑选就绪子任务执行，维护代理状态 \(S_\ell = (C_\ell, R_\ell, I_\ell)\)，其中记录执行历史、子任务状态和运行时 schema–值绑定/已实现效果。每步执行后用新增绑定 \(\Delta I_\ell\) 更新状态。
- **子任务验证**：不是仅仅检查 API 调用成功，而是将执行轨迹与支持图对齐，检查所需输出/效果是否有具体的 schema 级证据，成功后才标记子任务完成；否则保留观测并修正 DAG。
- **赤字导向扩展（DOE）**：为每个子任务的候选终止工具，根据当前代理状态识别“赤字集”（尚未被满足的输入 schema），迭代选择能最大化覆盖赤字集的工具超边（通过预计算的 Tool-Schema Support 矩阵 \(\rho(e,r)\) 与重叠度 \(\Omega(e, M)\)），增加生产者工具，更新赤字集，直到赤字为空。最后选出对当前状态“结构完整”的工具支持子图并执行。

## 3. 实验设计

### 3.1 数据集与 Benchmark
- 使用 **AppWorld** 基准：模拟邮箱、支付、音乐、购物、电话、文件管理等多应用环境，共 250 个场景 ×3 个变体 = 750 个任务。
- 官方划分为训练集（35 场景）、开发集（20 场景）、正常测试集 **TEST-N**（56 场景, 168 任务）和挑战测试集 **TEST-C**（139 场景, 417 任务）。TEST-C 需要更长交互序列，并可能涉及训练中未见应用。
- 评估指标：**TGC**（单个任务目标完成率）和 **SGC**（场景级完成率，即该场景下所有任务变体全部成功）。

### 3.2 对比方法
- **SFT**：SFT-GT、RFT、EI。
- **DPO**：DPO-MCTS、DMPO。
- **RL**：PPO、RLOO、GRPO、LOOP（bandit/turn/token 变体）。
- **非微调（NFT）**：ReAct、PlanExec、FullCodeRefl、Traj（SetBSR+Snippet）。
- 主实验以 GPT-4o 为骨干，另在 GPT-4-Turbo、Llama-3-70B-Instruct 上验证框架迁移性；SFT/DPO/RL 基线使用 Qwen2.5-32B 骨干。

## 6. 主要结论与发现
- HyperAgent 在 AppWorld 上一致优于 ReAct、PlanExec、FullCodeRefl 等非微调基线，并显著提升 TGC 与 SGC；在 TEST-N 上 TGC 最高达 67.1%，TEST-C 上 SGC 达 26.1%，与经过大规模 RL 训练的 LOOP（token）结果相当或接近。
- 对比 ReAct，HyperAgent 减少了约 50% 的 LLM 交互轮次、约 35–50% 的 API 调用量，以及约 60% 的 token 消耗。
- 消融证明“工具上下文图”和“状态相关的工具支持图”均对任务完成有贡献，并有效降低冗余工具探索。
- 隐藏依赖工具（semantically distant but operationally necessary）可通过超图反向扩展被有效恢复，这是纯语义检索做不到的。
- 显式建模 schema 级工具依赖可以很好地补充 LLM 的语义推理能力，实现更可靠、高效的工具使用规划。

## 7. 优点
- **细粒度建模**：通过超边和 port-level 依赖链接，精确刻画“谁为谁提供哪个参数”，避免了普通工具图的歧义。
- **状态感知规划**：DOE 只修复当前代理状态中真正缺失的输入，使每次工具组合都贴合现实执行上下文，减少无效调用。
- **两阶段“离线超大图 + 在线小子图”** 设计：离线构建 TSH 是确定性的，在线检索和扩展计算开销低，真正需要 LLM 的地方主要是语义解释和规划。
- **系统性地优化了成本**：不仅报准确率，还报告调用数、token、LLM turns，对真实部署有参考价值。
- 具备明确的模块化结构，能适配不同 LLM 骨干，说明方法并非绑定某个模型。

## 8. 不足与局限
- **未披露算力开销**：没有说明离线 TSH 构建、GPT-4o 调用量或训练资源，限制了复现和成本评估。
- **单一数据集**：只在 AppWorld 上评估，工具数量与应用类型有限；对更大规模真实 API 生态（如 ToolBench）的迁移能力未验证。
- **依赖专家标注与 LLM 构建**：TSH 构建依赖人工验证和 GPT-4o 抽取效果/条件节点，流程较昂贵，且新工具的增量更新策略未提及。
- **与图增强方法缺乏直接实验**：论文声称优于现有图方法，但主要对比的是普通 agent 框架，没有同一基准下复现 ToolNet、GTool 等。
- **LLM 规划仍可能出错**：任务 DAG 和子任务分解由 LLM 生成，若子任务划分本身错误，超图只能保证工具层完整性，无法纠正任务理解偏差。
- **对新场景的泛化有限**：虽然 TEST-C 包含未见应用，但 TSH 本身仍是静态的、预构建的；当全新工具出现时，需要重新构建图，部署维护成本较高。
