## 摘要
随着编码代理被部署用于持续的长期软件开发，编码代理基础设施正在从测试台工程转向循环工程。现有基准测试通常关注局部任务或最终状态结果，对持续执行的洞察有限。我们引入了LOOPSBENCH，一个用于编码代理评估中循环工程的长期基准。每个任务是一个依赖DAG（有向无环图），节点是可单独测试的开发单元，边是具有源代码证据的先决条件关系。LOOPSBENCH包含来自真实来源的112个任务，涵盖8种编程语言和9个领域。其流程感知运行时沿就绪边界发布测试，并将已完成节点保留为回归义务。我们评估了与广泛使用的循环实现配对的前沿编码代理。最强的配置，Opus-4.7与Claude Code和外部延续，解决了25.00%的任务。记录的计划仅恢复了源恢复的先决条件DAG的一部分，并且在评估的循环配置文件中回归事件仍然可见。我们在microsoft/Loopsbench开源了基准数据与代码，包括所有任务、超过5,300个开发单元以及可执行测试。

## Abstract
Coding agent infrastructure is shifting from harness engineering toward loop engineering as coding agents are deployed for sustained long-horizon software development. Existing benchmarks often center on localized tasks or end-state outcomes, offering limited insight into sustained execution. We introduce LOOPSBENCH, a long-horizon benchmark for loop engineering in coding agent evaluation. Each task is a dependency DAG over separately testable development units with source-evidenced prerequisite edges. LOOPSBENCH comprises 112 tasks from authentic sources spanning 8 programming languages and 9 domains. Its flow-aware runtime releases tests along the ready frontier and retains completed nodes as regression obligations. We evaluate frontier coding agents paired with widely used loop implementations. The strongest configuration, Opus-4.7 with Claude Code and outer continuation, resolves 25.00% of tasks. Recorded plans recover only part of the source-recovered prerequisite DAG, and regression events remain visible across the evaluated loop profiles. We open source the benchmark data and code, including all tasks, more than 5,300 development units, and executable tests, at microsoft/Loopsbench.

## 论文核心问题与整体含义（研究动机与背景）

随着编码智能体（Coding Agent）被部署到长期、持续的软件开发场景中，其基础设施的核心挑战正从“测试台工程”（Harness Engineering）转向“循环工程”（Loop Engineering）。所谓“循环”，是指智能体外层持续运行的控制机制——包括目标设定、进度判定、上下文管理、工作分配与残余任务路由等——它（而非单个模型调用或单次编辑能力）决定了智能体能否在长周期内持续推进复杂软件任务。

然而，现有基准测试存在根本性局限：

- **任务形态终端化**：无论是 SWE-bench 系列还是 FeatureBench、SWE-EVO 等，任务都被打包为“独立 issue 或扁平规格说明”，只按最终状态评分。
- **中间过程不可见**：智能体是否维持中间义务、避免回归、遵循可行依赖顺序完成子问题，都无法从现有基准中获得证据。
- **评估维度单一**：缺少对执行顺序、状态连续性、回归压力的系统性度量。

为此，论文提出 **LOOPSBENCH**——一个面向循环工程评估的长期基准，核心转变是：**将“最终产物评分”扩展为“对循环执行过程的可诊断追踪”**，使循环工程本身成为可测、可比的评估维度。

## 论文提出的方法论

### 核心思想

LOOPSBENCH 将每个长周期任务建模为一个**依赖有向无环图（DAG）**：

- **节点**：可单独测试的开发单元（Development Unit），每个单元包含需求、文件/符号范围、前置单元集合、参考补丁贡献和标准测试。
- **边**：带源代码证据的先决关系，仅通过四种明确模式判定（基于合并提交历史的顺序 PR 链、文件/符号的复用依赖、生产-消费者 API 边、组合分层）。
- **就绪前沿（Ready Frontier）**：只有全部前置单元已通过测试的节点才被释放（即加入“就绪前沿”）。
- **回归义务（Regression Obligations）**：已完成单元保留为后续持续执行的回归测试，任何后续编辑不得破坏其已满足行为。

### 关键技术流程

1. **任务收集（Task Collection）**：从三类真实来源收集任务材料——课程实验（Course Labs）、PR 序列（PR Sequences）、研究演化（Research Evolutions），合计 112 个任务，覆盖 29 个 PR 序列、57 个课程实验、26 个研究演化，涵盖 8 种编程语言和 9 个领域。

2. **任务预处理（Task Preprocessing）**：将异构来源归一化为统一候选任务：
   - 课程实验：统一语言（转为英语）、重组骨架代码为单一任务根；
   - PR 序列：克隆完整 git 历史，按角色（测试/源码/辅助）拆分为每个合并 PR 的 diff，并通过 Claude Code 提取聚合段落；
   - 研究演化：以高影响力种子论文为中心，基于“承重继承边”聚类引用网络。

3. **任务选择（Task Selection）**：两个来源无关的过滤阈值——时间跨度 ≥2.5 个月、解决方案规模 ≥1,200 行，最终保留 112 个任务。

4. **开发单元与依赖恢复（Intra-Task Relation Recovery）**：依据源代码证据（hunk 重叠、符号级依赖、热文件 denylist）恢复单元间依赖 DAG。该 DAG 作为评估契约，而非对真实开发顺序的最优性声明。

5. **任务插桩（Task Instrumentation）**：
   - **指令形式化**：基于 gold diff 恢复开发者验收意图，同时剥离仓库名、课程名、论文标题、作者等可识别源信息，降低污染风险；
   - **环境与测试套件合成**：通过 Claude Code 生成 Dockerfile 与依赖环境，按拓扑序遍历 DAG 编写每个单元测试，并经三重验证：gold 全解能翻转为通过（可解性）、空工作区全失败（非平凡性）、仅祖先补丁仍至少一个测试失败（判别性）。

6. **流式评估运行时流程**：
   - 测试沿就绪前沿逐层释放，多前置节点的门控节点须在所有前置单元通过后才释放；
   - 完成节点的测试与前置节点的测试保持为后续层的回归测试；
   - **双容器快照流水线**：容器 A 供智能体编辑，容器 B 通过定期快照独立评测——智能体可继续编辑，评测不等待；
   - 记录循环追踪（loop trace）：访问序列、计划 DAG、测试编写统计、回归事件等。

### 核心评估指标（正式化总结）

- **Resolve Rate (RR)**：任务最终所有已释放测试全部通过的比例；
- **Test Pass Rate (TPR)**：最终已释放测试的平均通过比例；
- **Depth**：首次外部延续前可达的归一化依赖深度；
- **Regression Rate (Reg)**：已通过义务测试在后续检查点失败的比例；
- **Tokens (Tok)**：每个任务的总计费 token 消耗；
- 计划忠实度指标：Edge F1、TC-F1、Layer ρ、Critical Path Ratio (CPR)、Width Ratio (WR)、Branch Switching Rate (BSR)。

## 实验设计

### 基准与数据

- **LOOPSBENCH 全量发布**：112 个任务，5,300+ 开发单元，中位依赖深度为 6，中位补丁规模 5,499 行，累计 37,296 个测试，74 个 Docker 环境，平均任务时长 6.6 分钟（测试运行）。
- 任务来源分布：PR 序列 29 个（前端 13、后端应用 13、基础设施/数据 3）、课程实验 57 个（实验系统 24、应用 23、游戏引擎 10）、研究演化 26 个（网络 9、编译器 5、验证 12）。
- 对比的已有基准：SWE-bench Verified、TerminalBench 2.0、SWE-bench Pro、MLE-Bench 等（非统一对比实验，而是作为相关工作的定位参照）。

### 实验设计：三个研究问题

**RQ1：编码智能体的循环能在多大程度上持续保持进展？** 三个维度：
- 模型族内扩展（对应厂商循环）：GPT 系列（GPT-4o/5/5.2/5.5 + Codex）、Claude 系列（Sonnet-4/4.5、Opus-4.5/4.7 + Claude Code）、Qwen 系列（Qwen2.5-72B/3-Max/3.5-Plus/3.6-Plus + Qwen Code）；
- 固定循环（Claude Code）下的模型横扫：Opus-4.7、GPT-5.5、GLM-5.1、DeepSeek-V4P、Gemini-3.1-Pro、Qwen3.6-Plus、Kimi-2.6、Grok-4.1-FR；
- 固定模型（gpt-5.4）下的循环实现横扫：Codex、Claude Code、GitHub Copilot、OpenHands、SWE-agent、mini-swe-agent。

**RQ2：编码智能体的循环如何维护计划、代码和测试状态？** 使用循环追踪记录，从规划、实现、测试三个维度对比记录计划 DAG 与源恢复的人类开发 DAG 的一致性。

**RQ3：哪些循环工程因素影响长期执行？** 比较四种代表性循环：Codex goal mode（内部持久目标）、Claude Code goal mode（会话条件维护）、Claude dynamic workflows（动态任务专用 worker）、Ralph 循环（外部重启残余工作），统计上下文预算轮数、每轮回归事件、解决率。

### 实验充分性与公平性

- 每对模型-循环配置默认单次试验，但对族内扩展补充 pass@3 验证单调性稳定；
- 所有实验使用完整的 112 个任务发布版本，非抽样；
- 提供可见性契约：评估方可见内容（任务指令、单元清单、测试绑定）与仅评估方可见内容（就绪前沿、检查点结果、gold 解、回归状态）被严格区分；
- LoopsBench 接受任何与 DAG 一致的拓扑执行顺序，而非要求复现历史总顺序。

## 论文的主要结论与发现

1. **长期循环进展仍极为有限**。最强的模型与循环组合（Opus-4.7 + Claude Code + 外部延续）仅解决 25.00% 的任务。限制因素不是单单元代码生成能力，而是全局计划维护、残余连续性、回归义务保留等循环级能力。

2. **评估的循环在计划、实现、测试三个维度均存在系统性缺陷**：
   - 计划恢复的依赖结构仅部分匹配源恢复的参考 DAG（Edge F1 ≤ 0.71）；
   - 补丁比参考更长（PatchLen 1.58–2.54 倍于 gold），token 级重叠仅中等（Jacc 0.62–0.76）；
   - 智能体自写测试远少于原生测试套件（每任务 11–28 个 vs 44 个），回归事件在每个循环配置中仍可见。

3. **上下文更新策略显著影响循环行为**：
   - 动态工作流（Claude dynamic workflows）上下文预算轮数最高（97.96 轮/run），解决率也最高（24.11%）；
   - Ralph 循环轮数最低（13.24），解决率也最低（7.84%）；
   - 但上下文更新并未消除回归压力——所有四种循环配置的每 run 回归事件在 0.13–0.36 之间。

4. **循环实现差异对结果有独立于模型的显著影响**：固定 gpt-5.4 时，Codex（18.75%）比 mini-swe-agent（7.14%）解决率高 2.6 倍以上。

## 优点（方法或实验设计上的亮点）

1. **问题定位准确、有前瞻性**：将“循环工程”从“测试台工程”中独立出来，并将其定义为可测的评估维度，切中当前编码智能体部署的核心瓶颈。

2. **依赖 DAG + 流式测试释放的评估契约设计精妙**：
   - 使中间开发单元可独立测试；
   - 就绪前沿机制让执行顺序可观察但不强制；
   - 回归义务将已完成工作纳入持续约束——这是现有基准的结构性缺失。

3. **多样化的真实来源**：课程实验（教育者）、PR 序列（开发者社区）、研究演化（研究者）三源互补，覆盖 8 种语言 9 个领域，远超多数仅针对 GitHub issue 的基准。

4. **循环追踪（loop trace）指标体系完整**：将规划（Edge F1、Layer ρ、CPR、WR）、实现（PatchLen、Jacc）、测试（#T、F2P、Reg）分离，支持对模型选择与循环配置进行联合归因。

5. **工程严谨性**：三重测试验证机制（可解性、非平凡性、判别性）、双容器快照流水线、明确的可视性契约、输入侧匿名化和污染分析——展示了对基准可信度的严肃态度。

6. **开放完整资产**：112 个任务、5,300+ 开发单元、可执行测试、构建代码、配置、轨迹和校验和全部开源，为后续研究提供公共平台。

## 不足与局限

### 实验覆盖方面

- **RQ3 实验规模偏小**：仅 4 种循环配置、102–112 个任务、单次运行，结论更多是现象描述而非受控因果推断；
- **单次试验方差未完全排除**：pass@3 仅覆盖族内扩展，固定模型循环横扫和 RQ3 均无重复试验；
- **PR 序列任务区分度不足**：绝大多数配置解决率为 0%，聚合结果主要由课程实验驱动。作为一个诊断性基准，这可能导致“表面进展、实际困难”的误读。

### 偏差风险

- **DAG 是下界而非完整因果图**：仅基于四种证据模式，可能遗漏配置、数据格式、构建系统或跨服务行为中的隐式依赖，导致“依赖结构被低估”的系统性偏差；
- **模型辅助构建存在偏差**：Claude Code 参与指令形式化和测试合成，可能导致措辞偏向特定模型的理解习惯；
- **污染风险未完全消除**：即使匿名化处理，来源材料（尤其是公开课程实验）可能在训练集中以权重记忆形式存在。论文通过 25% 上限作为反证，但无法根除；
- **回归度量的信息限制**：隐藏检查点状态可能导致回归事件反映反馈有限，而非完全是回归纪律问题。

### 应用限制

- **固定 DAG 的适用边界**：探索性重设计（替换早期需求的任务）不在抽象范围内，限定了适用任务类型；
- **可审计证据的窄化**：仅纳入有可审计先决证据的来源，排除了移动端、前端重型、硬件相关项目，限制任务类型的迁移性；
- **正确性测度与语义等价不完全对等**：所有度量（TPR、RR、Reg）都绑定在可执行测试套件上，测试覆盖率不完整时，高得分不代表语义正确；
- **评估成本高**：每任务数百万 token 的消耗（最强配置 6.91M tokens），加上 ≥2 小时的墙钟时间，扩展性和可复现性面临现实约束；
- **内部事件不可观测**：循环追踪仅记录循环实现主动暴露的事件，超出接口的内部状态无法测量。
