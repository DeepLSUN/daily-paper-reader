## 摘要
大型语言模型（LLM）智能体越来越依赖调用外部工具来完成现实世界任务。工具检索——在智能体行动前从包含数千个工具的工具库中选择一小部分与任务相关的子集——因此已成为LLM智能体流程中的关键组成部分。然而，现有的检索器要么孤立地评估每个工具，要么顺序地组装工具集，因此候选集的联合效用从未被整体评估。在本文中，我们提出HYSET，即基于超边的集级工具检索（HYperedge-based SEt-level Tool retrieval）。我们的贡献有三方面：（i）我们将工具检索形式化为工具共调用超图上的查询条件超边预测，其中工具集本身成为评分单元，大多数现有检索范式可归约为受限实例；（ii）我们通过基数特定交互捕获依赖于规模的工具兼容性；（iii）我们将HYSET设计为预选模块，无需对下游智能体进行任何修改。在ToolBench上的实验表明，HYSET在工具检索性能和端到端任务成功率上均持续优于最先进的基线方法。除域内设置外，HYSET还支持零样本/少样本迁移，能够以极少的监督泛化到未见过的工具/类别和未见过的领域。

## Abstract
Large language model (LLM) agents increasingly rely on invoking external tools to complete real-world tasks. Tool retrieval, which selects a small task-relevant subset from a library of thousands of tools before the agent acts, has therefore become a critical component of LLM agent pipelines. However, existing retrievers either score each tool in isolation or assemble the tool set sequentially, so the joint utility of a candidate set is never evaluated as a whole. In this paper, we propose HYSET, short for HYperedge-based SEt-level Tool retrieval. Our contributions are threefold: (i) we formulate tool retrieval as query-conditioned hyperedge prediction on a tool co-invocation hypergraph, under which the tool set itself becomes the unit of scoring and most existing retrieval paradigms reduce to restricted instances; (ii) we capture size-dependent tool compatibility through cardinality-specific interactions; and (iii) we design HYSET as a pre-selection module requiring no modification to the downstream agent. Experiments on ToolBench demonstrate that HYSET consistently outperforms state-of-the-art baselines in both tool retrieval performance and end-to-end task success. Beyond the in-domain setting, HYSET further supports zero-shot/few-shot transfer, generalizing to held-out tools/categories and unseen domains with minimal supervision.

## 论文详细总结

### 1. 核心问题与研究动机

- **背景**：LLM智能体日益依赖调用外部工具（API）完成现实任务。工具库规模已从几十个函数扩展到包含上万个API端点的大型生态系统（如ToolBench含16,464个API端点），使得将全部工具描述注入上下文变得不可行。尽管长上下文窗口在扩展，但经验证据表明超长上下文的有效信息利用率急剧下降（"Lost in the Middle"现象），且会产生高昂延迟与成本。
- **核心问题**：现实任务通常需要多个API联合调用，工具检索必须选择**联合有用的工具集（set）**而非仅排序单个工具。然而，现有三类检索范式均未把候选工具集作为整体评分：
  - **语义匹配检索**（BM25、Contriever、Sentence-BERT等）：每个工具独立评分，集合分数只是个体分数的聚合，无法捕获"单独低分但在特定组合中不可或缺"的工具，也无法防止"多个高分工具重复覆盖同一子任务"的冗余问题。
  - **图增强检索**（COLT等）：虽有协同信号，但训练时蒸馏到逐工具嵌入，推理仍退化为独立Top-K排序，集合级一致性只是近似而非显式评分。
  - **生成式检索**（ToolGen等）：顺序逐个生成工具标识符，完整候选集从未被显式比较，集合是否连贯完整只能事后判断。
- **关键洞察**：工具间的交互模式**依赖集合的基数（cardinality）**。例如，货币转换器和天气查询在四工具任务中频繁共现，但在两工具任务中极少共现，这种差异远超随机增加所能解释。工具不是孤岛，工具检索本质上是**集级问题**。

### 2. 方法论：HYSET

#### 核心思想
将工具检索形式化为**查询条件超边预测（query-conditioned hyperedge prediction）**：构建工具共调用超图（tool co-invocation hypergraph）H = (V, E)，节点是工具，超边是训练集中的真实标注工具集，每个候选工具集本身即一条超边，是评分的基本单元。

#### 评分函数分解
Fθ(x, E) = Fset(E) + Falign(x, E)

- **集合交互项 Fset(E)**：建模工具间内部交互，与查询无关。
  - Fset(E) = Σ_{1≤a<b≤m} z⊤_{j_a} M_m z_{j_b}，其中 z 为工具嵌入，M_m 为**基数特定（cardinality-specific）的对称交互矩阵**，不同大小的工具集使用不同矩阵。
  - 关键定理（Theorem 1）：Fset 是成对可分解的当且仅当所有基数下的 M_m 一致（M_2 = M_3 = ... = M_M）。当 M_m 随基数变化时，可通过成对加和表达**三阶及以上交互效应**，捕获超越普通图的联合兼容性——用 O(M·d²) 参数实现了 O(d^M) 高阶效应。
- **查询-集对齐项 Falign(x, E)**：通过冻结的预训练语言编码器 r(·) 计算查询嵌入，以跨注意力池化将工具嵌入聚合为集合表示，注意力权重依赖于集合内所有工具，因此对齐项本身也是集级评分，并非简单的个体分数加权。

#### 训练目标
- **集级检索损失 Lret**：基于负采样，构建候选池（50% 同尺寸均匀采样、30% 批内负样本、20% 基于最近邻的硬负样本），使用 InfoNCE 风格对比损失提升真实工具集得分。
- **执行反馈自训练损失 Lself**：利用冻结LLM智能体在限制工具集上执行的结果奖励（ExecScore），加权强化成功模型选择的工具集。
- 总损失：L = Lret + η·Lself + λ·Σ||M_m||²_F，并约束工具嵌入单位范数。

#### 推理流程（两阶段近似）
1. **短列表构建**：按单工具得分（Eq. 12）取 Top-K₁，再用工具与 Top-K₁ 集合的互补性得分（利用基数 M 的交互矩阵）扩展至 Kpool 个工具。
2. **集级重排**：在短列表生成的所有子集空间 E_M(S) 中穷举最大化 Fθ(x, E)，返回最优工具集 bÊ(x) 传给下游 agent。排序指标通过贪心边际增益生成固定长度排名。

### 3. 实验设计

#### 数据集与Benchmark
- **ToolBench（主benchmark）**：13,860个可调用API端点，200,311条带真实工具集标注的训练指令，6个保留测试集共600条查询。
- **UltraTool（跨域验证）**：2,032个工具、22个领域，与ToolBench工具库完全不相交，仅6.1%工具集为单元素（ToolBench为20.4%）。
- **迁移场景**：held-out tools（UT）、held-out categories（UC）、cross-domain transfer（CD），及UC的1/5/10-shot目标类别适应。

#### 对比基线（涵盖三类范式）
- BM25（稀疏语义匹配）
- Contriever（稠密语义匹配）
- ToolLLaMA-Retriever（微调稠密检索器，官方ToolBench检索器）
- ToolRerank（层次感知重排序）
- COLT（图增强检索，完备性导向）
- ToolGen（生成式检索）

#### 评估指标
- **检索质量**：Recall@K、NDCG@K
- **集合完备性**：COMP@K（完整真实工具集被Top-K覆盖的比例）
- **端到端**：GPT-4 Pass Rate、Human Pass Rate（按官方ToolEval协议）
- 每个方法传递给agent的工具数不少于HYSET，工具预算对基线有利。

### 4. 资源与算力

- **训练**：43.2 GPU小时 + 186美元 judge API调用费用（两张RTX 4090 GPU）；ToolGen为38.6 GPU小时。
- **推理**：12.4 ms/query、3.21 GB内存（|V|=13,860时）；对比ToolLLaMA-Retriever为6.5ms、1.71GB，ToolGen为378.4ms、6.83GB。
- **参数量**：HYSET可训练参数约1,359万（BERT配置，d_z=768），其中工具嵌入Z为1,064万，冻结编码器为1.095亿；仅训练θ=(Z, {M_m}, P)。
- **执行反馈**：最多20,000次rollout，奖励基于5,000条训练查询，每20,000步刷新一次，全部由缓存的StableToolBench API镜像提供（非实时端点）。

### 6. 主要结论与发现

- HYSET在所有检索指标和端到端指标上**一致超越所有基线**：COMP@5相对提升10.8%（BERT配置）和11.6%（Qwen配置），GPT-4 Pass Rate最高相对提升13.1%。
- 仅用标注数据（去掉执行反馈），HYSET仍比ToolGen在COMP@5上相对提升10.0%，证明**集级建模本身是主要增益来源**。
- 两个设计选择的作用分离：**集级评分Fset主要提升集合完备性（COMP@5）**，移除后COMP@5下降13.1%；**执行反馈主要提升下游任务成功率**，移除后Pass Rate下降6.5%但COMP@5仅下降0.7%。
- **基数特定交互矩阵是核心差异**：共享矩阵（基数无关）性能接近Set Transformer，而基数特定版本又提升了6.4%的COMP@5，验证了"兼容性随集合大小变化"的假设。
- **迁移能力强**：跨域零样本保留79.9%的域内COMP@5，5-shot UC恢复93.2%全监督性能；在完整工具集未见过的严格设置下，COMP@5相对提升13.1%。
- 推理时传递的可变大小集合 bÊ(x) 在相同工具预算下比固定Top-5有约7%的完备性提升，且接近翻倍精确匹配准确率。

### 7. 优点

- **问题建模视角新颖**：首次将工具检索形式化为查询条件超边预测，为这一任务提供了统一的数学框架，并证明了现有三种范式是该框架的受限特例——理论贡献清晰有深度。
- **方法论设计精巧**：用基数特定交互矩阵在成对加和的简洁形式下隐含了高阶交互效应（Theorem 1），以O(M·d²)的参数量实现了O(d^M)的表达力，同时保留了可解释性。
- **实用性强**：设计为纯预选模块，下游agent和查询编码器均冻结，接入成本低；推理阶段两阶段近似使计算成本与工具库规模解耦（仅取决于Kpool和M），支持大规模工具库。
- **执行反馈闭环**：通过奖励加权自训练将下游执行信号反馈到检索器，形成agent-检索协同优化，且该设计被证明对基线和HYSET同样有益，并非不公平优势。
- **实验严谨**：消融和设计对比有效隔离了各组件的贡献，跨域和少量样本实验验证了方法的现实可用性。

### 8. 不足与局限

- **依赖标注数据**：训练需要带真实工具集标注的指令数据（且需要完整工具集而非单工具标注），这在实际场景中获取成本可能很高。
- **最大工具集大小假设**：假设推理时所需工具集不超过训练中观测的最大值M（论文取5），若出现更大工具集则无法处理。
- **工具库固定假设**：方法假设工具库V在推理时不变。论文明确指出"扩展到动态增长的工具库仍是未来工作"，这是一个实际部署中的重要限制——工具库在现实世界中是持续演化的。
- **负采样偏差风险**：虽然论文在补充材料中报告了负采样引入的假阴性率，但负采样策略（特别是50%均匀采样）可能在训练中引入将真实工具集当作负样本的偏差，需依赖补充材料的额外分析来佐证稳健性。
- **主结果对比公平性瑕疵**：HYSET的两行主结果使用了执行反馈训练（A+R），而六个基线仅在标注上训练（A），尽管作者做了控制实验（给基线同样加入执行反馈），但主表呈现方式仍可能让读者高估优势幅度。
- **资源成本**：训练需要额外的自动评估成本（2万次rollout + judge调用，约186美元+GPU时间），且执行反馈机制本身涉及额外的实现复杂度；推理时对Kpool规模的二次枚举虽与|V|解耦，但仍需权衡Kpool与精度。
- **端到端验证范围**：Pass Rate评估主要基于ToolLLaMA-2-7B-v2这一个下游agent，未验证在不同agent（如GPT-4o、Claude等）上的通用性；UltraTool仅验证了检索指标，未做端到端pass rate验证。
