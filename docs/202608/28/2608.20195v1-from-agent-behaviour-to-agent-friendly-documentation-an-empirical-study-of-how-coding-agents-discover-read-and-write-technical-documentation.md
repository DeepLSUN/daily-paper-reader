## 摘要
技术文档是为人类开发者编写的，但现在越来越多的软件更改由自主编码智能体完成。它们会查阅哪些文档、何时查阅以及之后会发生什么，目前仍不得而知。我们对两个公共数据集中的智能体-文档交互进行了基于行为的研究：来自SWE-chat的557个智能体编码会话，产生了94,813个开发事件，包括3,033次文档交互；以及来自AIDev的33,097个智能体拉取请求，包含690,260条分类后的文件级变更记录。四项发现挑战了当前的文档实践。第一，智能体的文档工作以面向智能体的工件为主：指令文件和工作笔记占所有文档交互的60.5%，而经典技术文档仅占10.6%，API参考仅占1.3%。第二，查阅与代码编辑之间的联系尚不明确：相邻转移概率为0.002，未经调整的三事件提升度为1.05，而分段调整后的模型将其置于1以上（OR 1.33 [1.09, 1.62]）；文档创建的未调整提升度为1.67，但其调整后的置信区间包含1。第三，未观察到基于文档的显式验证序列，且查阅与即时测试减少相关（提升度0.23，聚类置信区间0.08-0.45；调整后OR 0.39 [0.25, 0.60]）。第四，查阅是自我发起的（70.2%）远多于失败驱动的（7.5%），且文档滞后于代码：在同时修改两者的多提交拉取请求中，代码先被触及的频率是文档的4.7倍。从这些痕迹中，我们推导出一个描述性模型，将智能体-文档交互描述为双叶循环而非线性旅程，并表明“智能体友好型”文档的两个广泛假设属性——可操作性和可验证性——缺乏一致的行为支持。我们公开发布了我们的流水线、编码方案和事件级数据。

## Abstract
Technical documentation is written for human developers, but an increasing share of software changes is now authored by autonomous coding agents. Which documents they consult, when, and what follows remain unknown. We conduct a behaviour-grounded study of agent-documentation interaction across two public datasets: 557 agentic coding sessions from SWE-chat, yielding 94,813 development events including 3,033 documentation interactions; and 33,097 agentic pull requests from AIDev, with 690,260 classified file-level change records. Four findings challenge current documentation practice. First, agents' documentation work is dominated by agent-facing artefacts: instruction files and working notes account for 60.5% of all documentation interactions, versus 10.6% for classical technical documentation and 1.3% for API references. Second, the link between consultation and code editing is unresolved: the adjacent transition probability is 0.002 and the unadjusted three-event lift 1.05, whereas a stage-adjusted model places it above unity (OR 1.33 [1.09, 1.62]); documentation creation is elevated unadjusted (lift 1.67) but its adjusted interval includes unity. Third, no explicit documentation-based validation sequence was observed, and consultation is associated with less immediate testing (lift 0.23, cluster CI 0.08-0.45; adjusted OR 0.39 [0.25, 0.60]). Fourth, consultation is self-initiated (70.2%) far more often than failure-driven (7.5%), and documentation trails code: among multi-commit pull requests changing both, code is touched first 4.7x more often. From these traces we derive a descriptive model of agent-documentation interaction as a two-lobed cycle rather than a linear journey, and show that two widely assumed properties of "agent-friendly" documentation - actionability and verifiability - lack consistent behavioural support. We release our pipeline, coding scheme, and event-level data.

- 现状：技术文档传统上以人类开发者为目标读者，但自主编码智能体日益成为代码变更的主要作者。它们会查阅什么文档、何时查阅、查阅后产生什么后果，此前缺乏实证测量。
- 问题：现有“智能体友好型文档”指导（如清晰标题、可运行示例、llms.txt）多基于“智能体应当如何行事”的直觉，而非对其实际行为的观察。

## 6. 主要结论与发现

- 核心发现一：智能体文档交互以“面向智能体的工件”为绝对主流。
  - 指令文件（AGENTS.md、CLAUDE.md 等）占 35.4%，智能体工作笔记（计划、thoughts/ 等）占 25.1%，合计 60.5%。
  - 经典技术文档仅 10.6%，API 参考仅 1.3%，故障排除文档仅 0.4%。
  - 智能体重加权后，面向智能体文档在咨询事件中约占一半（50.1%），仍显著压倒 API 参考与故障排除文档。
- 核心发现二：阅读文档后立即编辑代码的模式几乎不存在。
  - 相邻转移概率 `P(edit code | read doc) = 0.002`；
  - 阅读后更常跟随后续阅读（0.270）或推理（0.245）；
  - 三事件窗口未调整提升度 1.05，但分段调整后 OR 1.33 [1.09, 1.62]，故“阅读→编写”关联“未解决”。
- 核心发现三：未观察到文档作为验证基准的显式行为。
  - 零个 Validate 与 Escalate 阶段事件；
  - 咨询后测试（lift 0.23）与构建（lift 0.15）均显著下降，调整后仍成立（OR 0.39、0.25）。
- 核心发现四：文档相较代码整体滞后。
  - 41.5% 的智能体 PR 修改文档；代码与文档共变 PR 占 32.0%。
  - 可观察顺序的多提交 PR 中，代码先被修改的比例（47.3%）是文档先修改（10.0%）的 4.7 倍；不同提交且可排序时，代码先行为 82.5%。
- 交互触发：自我启动（70.2%）远高于失败驱动（7.5%），说明智能体不是“卡住才查文档”，而是在任务推进过程中常规查阅。
- 智能体既是文档消费者也是文档生产者：产出事件数为咨询的 0.87 倍；智能体还会修改自己的指令文件（AGENTS.md 出现在 692 个 PR 中）。
- 对“智能体友好文档”的挑战：可操作性（actionability）与可验证性（verifiability）两大常用属性在本语料中缺乏一致行为支持。
- 最终模型：文档交互为“双叶循环”（咨询叶 + 产出叶），而非线性旅程。

## 7. 优点

- 开创性实证视角：基于真实智能体会话与真实 PR 制品，而非合成任务或人工基准，填补了“智能体如何实际使用文档”的空白。
- 双层分类与透明编码：Tier 1 规则 + Tier 2 语言模型标注，明确标注哪些类别是人验证过的、哪些未验证；事件保留证据字符串，可审计性较好。
- 严格统计意识：集群自助区间、GEE 调整、三种加权、明确指出“unadjusted vs adjusted”不一致的含义，不以单一估计下结论。
- 对测量偏差的自我暴露：如 shell 路径解析前后某一智能体从“零事件”变为有事件，说明跨智能体比较受提取覆盖影响；未受人类验证的 Tier-2 标签也被明确标注为需后续编码研究。
- 负面结果同样贡献：明确列出数据不支持的常见建议（可操作性、可验证性、文档作为失败恢复首选、恢复策略排序），并解释为何不能下结论。
- 开源可复现：提供提取流水线、编码方案、事件级数据与图表生成代码，所有表格由代码直接生成，避免手工转写误差。

## 8. 不足与局限

- 构造效度限制：
  - 文档仅通过文件路径识别；docstring、内联注释、源码内文档完全不可见，造成系统性低估且低估不均。
  - 交互“意图”被刻意放弃：只报告触发、交互类型和结果，不妄断智能体为何读某文件，但这也限制了机制解释。
  - Tier-2 分类（尤其 `agent_working_note` 25.1% 这一核心发现）未经人类验证，精确份额应视为临时性，未来需 200–300 事件的双人编码与 Cohen's κ / Krippendorff's α。
- 内部效度限制：
  - 阶段分配启发式有“粘连”问题：一旦出现失败信号，会话一直滞留于调试阶段，可能夸大调试占比。
  - 结果检测依赖正则表达式，缺失输出不等于失败；可观测结果的失败片段仅 662/2034，存在选择偏差风险。
  - 转移概率是一阶的；更长程或经由不可观测推理的文档影响无法被测出。
  - 触发回看窗口固定为四事件，窗口外原因可能被误归为“智能体主动”，而这是最大类别。
- 外部效度限制：
  - SWE-chat 是自愿遥测数据，87% 会话来自单一智能体家族，用户可能偏向经验丰富、开源倾向开发者。
  - AIDev 只覆盖早期采用智能体且对智能体贡献开放态度的公共仓库，不能推广到私有代码库。
  - 两个数据集描述不同群体，只能互补验证模式，不能交叉验证同一测量。
  - 语料是快速变化实践的快照：60.5% 的份额是快照值，可持久的是“该类别存在且重要”，而非确切数字。
- 小型子单元不足：故障恢复仅 11 例可观测结果，所有恢复策略区间重叠；API 参考仅 40 次交互，难以做任何稳健的领域内分析。
- 缺少干预实验：所有结论均为观察性，设计启示（如“可执行文档”）是待验证的假设而非因果证据。
- 未报告算力、多假设检验校正（作者明确未校正，因此相邻层间小差异不作结论）、以及未做人类双编码检验 Tier-2 分类，是剩余的方法学缺口。
