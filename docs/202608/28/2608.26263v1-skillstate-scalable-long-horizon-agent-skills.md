## 摘要
大型语言模型（LLMs）越来越多地作为自主智能体执行复杂、长时程的程序性技能。现有的智能体运行时通过不断将观察、动作和中间推理轨迹追加到不断增长的对话历史中来维持执行，导致在长时间跨度内出现延迟退化和上下文污染失败。我们提出了SKILL.state，一种运行时架构，用显式、可变的执行状态取代仅追加的对话历史。在每个执行步骤中，模型仅接收不可变的技能规范、当前结构化执行状态和最新观察。中间推理在产生经过验证的状态更新后立即被丢弃，防止提示随执行历史而增长。在多种数据集、模型和执行环境中，SKILL.state提高了任务准确性，同时大幅减少了累计令牌消耗。我们的结果表明，显式执行状态是一种有效的、与架构无关的抽象，适用于可扩展的长时程智能体技能。

## Abstract
Large Language Models (LLMs) increasingly act as autonomous agents executing complex, long-running procedural skills. Existing agent runtimes maintain execution by continually appending observations, actions, and intermediate reasoning traces to an ever-growing conversation history, causing latency degradation and context-poisoning failures over long horizons. We present SKILL.state, a runtime architecture that replaces append-only conversational history with an explicit, mutable execution state. At each execution step, the model receives only the immutable skill specification, the current structured execution state, and the latest observation. Intermediate reasoning is discarded immediately after producing a validated state update, preventing prompt growth with execution history. Across diverse datasets, models, and execution environments, SKILL.state improves task accuracy while substantially reducing cumulative token consumption. Our results demonstrate that explicit execution state is an effective and architecture-agnostic abstraction for scalable long-horizon agent skills.

## 1. 核心问题与整体含义（研究动机）

**核心问题：**
- 大语言模型（LLM）作为自主智能体执行长时程、程序性技能时，现有运行时普遍采用"对话式执行模型"——每一步都将推理、动作、观察和工具输出不断追加到持续增长的对话历史中。
- 这种设计导致两个根本性缺陷：
  - **提示规模随执行长度增长**：token消耗和推理成本呈二次方增长（O(T²)）；
  - **上下文污染**：过时的观察和无效推理长期残留在上下文中，模型被迫不断区分"当前事实"与"历史工件"，导致长时程下执行正确率下降。

**整体含义：**
- 论文提出将"程序性技能执行"从"对话历史积累"重新定义为"显式状态转换"过程，即执行本身是一个系统问题，而非纯粹推理问题。SKILL.state通过显式、可变的执行状态代替追加式历史，实现**O(1)的提示足迹和O(T)的累计token复杂度**，做到与架构无关的规模化长时程执行。

## 2. 方法论（SKILL.state 运行时架构）

**核心思想：**
- 每个执行步骤 t，模型仅接收三元组输入：**不可变技能规格 P + 当前结构化执行状态 Σₜ + 最新环境观察 Oₜ**。
- 模型生成三元输出：**多步链式推理 Rₜ + 结构化状态更新 ΔΣₜ + 待执行动作 aₜ**。
- 推理轨迹仅在产出经过验证的状态更新后立即被丢弃，永不进入后续提示。

**关键技术细节：**

| 组件 | 说明 |
|---|---|
| 执行状态 Σₜ | 结构化schema（JSON字典），每个领域只需编写一次；例如 InterCode CTF 的100个任务全部复用单一静态5字段schema：`discovered_flags`、`tested_hypotheses`、`active_files`、`working_dir`、`cmd_summary` |
| 状态更新 ΔΣₜ | 格式为JSON字典的键值变更/删除操作 |
| 合并运算 ⊕ | 运行时确定性执行的字典合并算子，支持 null-删除语义：`Σₜ₊₁ = Σₜ ⊕ ΔΣₜ` |
| 验证机制 | 确定性验证是运行时而非模型的责任；非法patch触发回滚-重试循环，保证持久状态不被污染 |

**算法流程（Algorithm 1）：**
```
for t = 0 ... T:
    1. 接收最新观察 Oₜ
    2. 构造提示 (P, Σₜ, Oₜ)
    3. 调用LLM生成 (Rₜ, ΔΣₜ, aₜ)
    4. 验证 ΔΣₜ
    5. 应用状态更新 Σₜ₊₁ ← Σₜ ⊕ ΔΣₜ
    6. 执行动作 aₜ
```

**复杂度分析：**
- 对话式运行时：提示规模 |Cₜ| = O(t)，累计token复杂度 **O(T²)**
- SKILL.state：|Pₜ| = O(|P| + |Σ| + |O|)，与已执行轮次无关，累计token复杂度 **O(T)**

**与DST（对话状态跟踪）的区别：**
- DST在完整对话记录旁附带维护用户槽值；SKILL.state则将结构化状态视为**充分统计量**，直接丢弃对话历史，适用于动态环境的自主技能执行。

## 3. 实验设计

**基准测试（Benchmarks）：**

| 基准 | 领域 | 规模/特点 |
|---|---|---|
| SkillExecBench（自建） | 环境1：仓库管理（500个独立货架）；环境2：软件仓库（Git分支、PR、CI状态） | 确定性ground-truth转换，隔离执行机制与开放搜索 |
| InterCode CTF | Linux终端漏洞利用（逆向、取证、密码学、二进制利用） | 100个bash夺旗挑战，二进制验证 |
| Sierra τ-Bench | 企业客服（零售 + 航空两大领域） | 多轮工具-智能体-用户交互，SQLite数据库API，事务性操作 |

**对比基线（两类）：**
- **主运行时范式：** Prompt（ReAct风格，不断追加历史）、Memory（摘要式，滚动3步窗口+周期性自然语言摘要）、Stateful（LangGraph风格，结构化状态+完整对话记录）
- **预算匹配与压缩控制：** Truncated（滑窗截断）、Summary-capped（硬性摘要token上限）、ReAct + LLMLingua（基于小型模型困惑度的预算感知压缩）

**评估维度：**
1. 任务准确率/成功率（SkillExecBench为连续动作正确率；InterCode CTF为二进制pass@1；τ-Bench为官方程序化评估器）
2. 平均提示大小（每次LLM调用的token足迹）
3. 累计token消耗（整个执行周期的总token量）

**模型：** Gemini-3-Flash（闭源）、Gemma-4-31B-it、Qwen-3-8B-it（开源权重），temperature=0.0、top-p=1.0，保证确定性复现。

## 6. 主要结论与发现

1. **准确性全面领先：** 在Warehouse管理T=200时，SKILL.state达到0.94准确率，而Prompt基线降至0.74、Memory降至0.84、Stateful降至0.88；在InterCode CTF上pass@1达54.2%，比最强基线高7.8个百分点。
2. **token消耗大幅降低：** T=100 Warehouse中，SKILL.state消耗65k tokens，Stateful消耗1.06M tokens，实现**16.2×的token缩减**；T=200时，Memory基线膨胀至6.1M tokens，而SKILL.state仅消耗122k。
3. **噪声鲁棒性显著：** 50事件/轮高噪声下，Prompt基线从0.68降至0.53，而SKILL.state保持0.98；干扰在状态patch生成时被过滤，永不进入后续提示。
4. **零步状态恢复：** 面对外部环境漂移，SKILL.state立即响应修正（0恢复步骤），而历史基线需要5-14步才能克服陈旧上下文的干扰。
5. **结构优于压缩：** 预算匹配实验中，滑窗截断降至0.18、LLMLingua降至0.22，而SKILL.state保持0.94——统计压缩器破坏精确关系依赖，结构化状态维护保留关键信息。
6. **小模型的主要瓶颈是结构化输出遵循而非推理能力：** 68%的错误为状态覆盖/删除、20%为schema理解错误、12%为JSON语法错误——为约束解码等改进方向提供了明确指引。

## 7. 优点（亮点）

**方法设计方面：**
- **概念简洁而深刻：** 用"显式状态转换"替代"历史积累"这一范式转移，将执行从文本重构的隐性负担中解放出来，理论复杂度清晰（O(1)提示足迹/ O(T)累计token）。
- **架构无关性：** 在闭源（Gemini）和开源（Gemma、Qwen）多模型家族上一致有效，证明抽象本身的普适性。
- **确定性验证保障安全：** schema所有权和验证逻辑由确定性运行时掌控，模型无法用格式错误的输出污染持久状态。
- **有限推理保留：** 步骤内部的多步思维链完整保留以支持复杂演绎规划，但仅在生成期间存在，投影为状态后即丢弃——兼顾推理能力与上下文纯净。

**实验方面：**
- 自建诊断基准（SkillExecBench）与公开真实基准（InterCode CTF、τ-Bench）互补，兼顾受控变量隔离与生态效度。
- 预算匹配控制实验有效排除了"只是因为提示更短"的替代解释，强化了结构化状态价值的因果论证。
- 状态恢复和噪声注入实验模拟了真实世界的静默漂移与密集遥测，提升了结论的实践相关性。

## 8. 不足与局限

**根本假设的适用边界（论文已承认）：**
- **状态必须可被表示为充分统计量**——即所有影响未来决策的历史信息必须在出现时即可投影到结构化状态中。以下三种情况该假设失效：
  1. **动态schema发现：** 任务过程中状态结构本身需要动态探索和演进，无法预先固定；
  2. **延迟相关性的识别：** 早期观察在当时的价值未被识别，未提交至状态，后续才被确认为关键——历史被丢弃后无法追溯；
  3. **历史本身就是目标输出：** 审计、调试溯源、解释过去行为等任务中，轨迹历史是交付物而非运行时开销。

**实验覆盖的局限：**
- **多智能体场景未验证：** 文章指出显式状态可以自然扩展到多智能体协调（替代二次方对话交换），但并发写入所需的确定性冲突消解语义在单智能体实现中未被评估。
- **小模型性能差距明显：** Gemma-4-31B在T=100时仅0.42、Qwen-3-8B仅0.34，大幅低于Gemini-3-Flash的0.94；虽然错误分类有助于归因，但结构化输出遵循在小型模型上仍是明显瓶颈。
- **部分结果报告不够透明：** 噪声实验无标准差；恢复实验无重复次数说明；budget匹配对比仅给出了单一horizon下的结果。

**应用限制：**
- 要求为每个领域预先设计schema，这本身是一种人工成本，跨领域的schema泛化和自动生成问题尚未解决。
- 状态被压缩为结构化摘要的同时会丢失历史语义的"软信息"（如微妙的环境暗示、审美判断等），在需要隐性语境感知的任务上可能不如完整历史。
- 论文评估的任务集（仓库管理、软件仓库、CTF、客服）虽具代表性，但未覆盖多模态、具身控制、长时间开放世界探索等更复杂场景。
