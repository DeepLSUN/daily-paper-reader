## 摘要
编码代理越来越多地在组织内部运行，其安全控制（作用域凭据、受限出口、只读文件系统、非root执行）像约束任何其他软件一样约束着它们。然而，现有基准几乎完全在宽松的沙箱中评估代理，因此当强制执行策略时性能如何变化尚属未知。在本工作中，我们基于常见的真实企业限制派生的嵌套安全策略级别，在Terminal-Bench 2.1上评估了12个编码代理。硬化从来不是免费的，但远非均匀：在最严格的策略下，成功率损失高达18.3个百分点，成本膨胀达167.3%，且这两个指标并不一致；最能保持成功率的模型也是效率损失最大的模型，因此模型选择取决于策略。除了总体分数外，我们还刻画了当策略阻止代理行为时它们如何行动，并分解了硬化所导致的失败：运行会陷入超时或错误解决方案，而不是提前停止，且不同模型的混合情况不同。为了给比较提供依据，我们验证了最严格策略下任务的可解性，将模型失败与策略排除的任务区分开来。我们发布了Boundary-Bench，一个开源硬化插件，能够在Terminal-Bench及兼容基准上对编码代理进行策略约束评估。

## Abstract
Coding agents increasingly run inside organizations whose security controls (scoped credentials, restricted egress, read-only filesystems, non-root execution) constrain them like any other software. Existing benchmarks, however, evaluate agents almost exclusively in permissive sandboxes, so it is unknown how performance changes when policy is enforced. In this work, we evaluate 12 coding agents on Terminal-Bench 2.1 across nested security policy levels derived from common real-world enterprise restrictions. Hardening is never free but far from uniform: under the strictest policy, success losses reach 18.3 points and cost inflation 167.3\%, and the two axes disagree; the model that best preserves success is also the one that loses the most efficiency, so model choice is policy-dependent. Beyond aggregate scores, we characterize how agents behave when policy blocks their actions and decompose the failures hardening induces: runs grind into timeouts or wrong solutions rather than stopping early, in a mix that differs by model. To ground comparisons, we verify task solvability under the strictest policy, separating model failures from tasks the policy forecloses. We release Boundary-Bench, an open-source hardening plugin enabling policy-constrained evaluation of coding agents on Terminal-Bench and compatible benchmarks.

**研究动机：**
- 编码代理（coding agents）在企业中的实际部署环境并非宽松的沙箱，而是受安全策略约束的生产环境：作用域凭据、受限网络出口、只读文件系统、非 root 执行等
- 然而，现有基准测试（如 Terminal-Bench、SWE-bench、OSWorld 等）几乎**全部在宽松（permissive）沙箱**中评估代理，不考虑安全策略的存在
- 安全策略的实施本质上是**一种结构化的运行时扰动**——它改变了代理可以观测和可以执行的操作集合，这不同于输入扰动或注入式故障
- 因此，现有评估无法回答一个关键问题：**当安全策略逐步收紧时，编码代理的性能和成本如何变化？** 无约束的排行榜可能严重高估代理在企业场景中的真实表现

**核心含义：**
- 论文系统性地证明了"硬化（hardening）"（即实施安全策略）对编码代理的性能有显著但**高度不均匀**的影响
- 在最严格策略下，成功率损失最高达 18.3 个百分点，成本膨胀最高达 167.3%
- 关键词：策略硬化是"免费"的假设不成立，且不同模型在成功率和成本两个维度上的响应模式差异巨大，这直接导致模型选择必须依赖于部署环境的策略等级

## 2. 论文提出的方法论：核心思想、关键技术细节

**核心思想：**
将安全策略的严重程度作为**独立的评估变量（independent variable）**，在共享的、嵌套的、基于 NIST 映射的策略梯度上，跨模型-框架捆绑（model-harness bundles）测量任务成功率和 token/美元花费的变化。

**关键技术细节：**

**（1）策略轴设计（三个维度，每种轴三个姿势）**

| 策略轴 | 机制 | 映射的 NIST 控制 |
|---|---|---|
| 网络出口（N） | 强制所有出口流量经 loopback 代理；代理默认拒绝不在固定 205 域允许列表内的所有域名；云元数据端点永远拒绝 | SC-7, SC-7(5), SC-7(8) |
| 文件系统范围（F） | 除工作区、/tmp、/dev/shm 及代理运行时缓存外，将操作系统树（/usr, /bin, /etc 等）bind-remount 为只读；写入返回 EROFS | AC-3, SC-39, AC-4, SC-4, AC-4(4), SC-7(21), CM-5(1) |
| 权限（P） | 以专用普通用户运行；无 sudoers 条目；锁定 root 密码；设置 no_new_privs；清空 capability bounding set；移除 setuid 位 | AC-6, AC-6(2), AC-6(3), AC-6(5), AC-6(10), CM-5(1) |

**（2）三层嵌套策略等级（累积严重性阶梯）**
- **Control（基准）**：root 权限 + 无限制出口 + 可写文件系统
- **Non-root**：仅移除 root 权限（隔离单个轴的影响）
- **NIST-derived high**：三轴同时完全锁定

**（3）强制执行方式**：所有限制由**原生 Linux 机制**执行（nftables 防火墙、只读挂载、setpriv、seccomp 等），而非向代理"请求"合作；代理遇到的是真实的运行时错误（HTTP 403、EROFS、EPERM）；子进程自动继承所有限制，无法通过启动子进程绕过

**（4）基准审计（Benchmark Audit）**——方法论的关键创新：
- **可解性验证（Solvability Witness）**：在最严格策略下重放任务自带的官方参考解；如失败，自编策略合规的参考解，确认哪些任务仍可解
- **Verifier 过度规范修复（Verifier Over-specification Repair）**：审计所有"代理已达成目标但 verifier 报错"的试验，对过度规范的断言进行**加法式放宽**（仅添加可接受的路径，不触及任何实质性检查），修复后对全部策略等级使用同一 verifier
- **失败分类**：按运行结束位置分类为 timeout（达 95% 预算）、early stop（底部十分位）、wrong solution（其余）

**（5）核心指标与公式：**
- 成功率 SR_m(ℓ)：捆绑 m 在策略 ℓ 下通过的试验百分比
- 平均每任务成本 C_m(ℓ)：美元
- 成功变化量：ΔSR_m(ℓ) = SR_m(ℓ) − SR_m(control)（绝对百分比点）
- 成本变化量：ΔC_m(ℓ) = 100 · [C_m(ℓ) − C_m(control)] / C_m(control)（归一化为百分比）

**基准（Benchmark）：**

**评估对象（12 个模型-框架捆绑）：**

| 模型 | 框架 |
|---|---|
| GPT-5.6 Sol / Terra / Luna | Codex |

- 通过成功率-成本 Pareto 前沿来体现不同 "policy→agent" 组合的权衡

## 6. 论文的主要结论与发现

1. **硬化非均匀且影响显著**：所有 12 个捆绑在最严格策略下都同时损失成功率和增加成本。成功率损失最大为 Claude Sonnet 5 的 −18.3 个百分点；成本膨胀最大为 Grok 4.5 的 +167.3%。

2. **权衡是普遍的，但"货币"因模型而异**：Grok 4.5 牺牲最小成功率（−7.1pp）但成本膨胀最大；GPT-5.6 Luna 成本膨胀最小（+16.0%）但成功率几乎下降最多（−18.0pp）；Claude Sonnet 5 则两者兼有。**最能保持成功率和最能保持成本的模型不是同一个**，模型选择必须依赖策略环境。

3. **失败模式是"磨耗"而非"投降"**：硬化增加的失败主要是超时（timeouts）和错误解（wrong solutions），而非提前停止（early stops 几乎不变，2.4%→2.7%）。匹配的通过运行也变慢：多 13% 墙钟时间、14% 工具调用、26% tokens。

4. **参考解兼容性可预测策略代价**：32 个受影响的（reference solution 不兼容）任务承载了 83.5% 的额外失败，成本膨胀集中于此（2.59× vs 1.14×）。这一指标可在任何代理运行之前计算，即可预判策略的代价——可推广到任何附带参考解的基准。

5. **Benchmark 自身存在伪影（artifact）**：5 个任务的 verifier 过度规范导致有效解未被识别（如 sqlite-with-gcov 从 0% 恢复至 80.6% 成功率）；7 个任务被策略设计性阻隔（如任务本身要求写入 /usr/local/bin）；count-dataset-tokens 被标记为基准完整性伪影——模型在未实际获取数据的情况下提交了精确的答案常量 79586，可能提示污染或记忆。

6. **安全策略对成本的影响独立于其对成功率的影响**：即使成功率保持不变的任务，中位单次运行成本仍膨胀约 3 倍，机制为 97% 的绕路构建（重新从源码构建工具链）。

## 7. 优点：方法或实验设计上的亮点

- **策略即变量（Policy as an independent variable）**：这是首个将安全策略严重程度作为系统性评估维度的 benchmark 研究，而非单点测量
- **原生 Linux 强制执行**：策略由 nftables、只读挂载、setpriv 等内核/系统原生机制实现，代理遇到的是真实错误，不可绕过，也不依赖代理"自觉遵守"
- **严谨的基准审计流程**：先验证任务可解性（solvability witness）再解释结果；区分"模型失败"与"策略排除任务"；对 verifier 过度规范进行只加不减的修复并统一用于所有策略等级
- **多维分析框架**：除总体分数外，还分解失败模式（timeout/early stop/wrong solution）、阻止动作暴露（blocked actions）、成本分布与来源（workaround 构建）、参考解兼容性分组，以及 provider 侧安全干预的透明披露
- **明确披露实验伪影**：包括 provider 介入、count-dataset-tokens 的完整性疑点、harness 版本不一致（Claude Opus 5 用了更新版本）等，均未隐藏
- **开源与可复现性**：发布 Boundary-Bench 插件（含完整代码、版本清单、策略构造细节与原始轨迹），允许在 Terminal-Bench 及兼容基准上复现和扩展

## 8. 不足与局限

- **单一基准**：所有证据来自 Terminal-Bench 的 89 个任务，结论的外推性有限。论文明确承认，扩展到新基准需重复全部审计与推理开销
- **少量重复与无置信区间**：每格仅 3 次有效试验，缺乏统计推断支持；Pareto 前沿的排序和敏感性结论是描述性的，不应过度解读模型间微小差异
- **捆绑级归因模糊**：评估单元是模型-框架捆绑体，效果不能单独归因于模型或框架。消融仅覆盖两个端点，框架变更同时改变提示词、工具与接口，无法彻底分离
- **策略现实性有限**：三层策略是通用企业限制的简化阶梯，NIST 映射是"动机记录"而非合规声明；未测量这些策略的实际安全有效性，只测性能代价
- **允许列表可能有偏好偏差**：205 域 egress 允许列表源自 Claude Code 的默认列表，且明确不含任何任务特定域——这保证了公平性，但也可能对熟悉特定包源的模型有利，而对依赖被阻断源的模型不利
- **成本深度采样覆盖面窄**：仅 2 个任务的 100 次/条件采样，机制归因（97% workaround）可能不具代表性
- **provider 侧干预不可控**：OpenAI 的网络安全风险筛查与 Anthropic 的拒绝/回退存在随机性，影响部分结果（虽已透明披露但不可复现），且 Claude Fable 5 的结果实质上是"门控路由"而非模型本身
