## 摘要
尽管由LLM驱动的修复代理能够处理复杂的、仓库级别的问题，但它们独立地处理每个问题，并丢弃了从先前修复中积累的程序性知识。我们提出了STAIR，一个将历史修复轨迹转换为分层的、可重用计划的框架，这些计划可以被调整以指导未来的修复。每个过去的轨迹被转换为一棵多级树，范围从细粒度的诊断操作到高层的修复策略，以多种粒度编码经验。当新问题出现时，STAIR从多个抽象级别选择相关的计划节点，将它们裁剪为可执行的、针对特定问题的计划，并通过提示提供给代理。在SWE-bench Verified上，集成Lingxi的STAIR在使用MiniMax M2.5时达到81.2%的Pass@1，使用GPT-5时达到79.2%。生成的计划还能跨代理泛化：无需任何代码更改，它们将结构不同的代理mini-SWE-agent v2的Pass@1从75.8%提升到81.0%。消融实验进一步表明，混合多个抽象级别优于任何单一级别，而原始的、未抽象化的轨迹转移效果明显更差。

## Abstract
Although LLM-driven repair agents can tackle complex, repository-level issues, they treat every issue independently and discard the procedural knowledge accumulated from previous repairs. We introduce STAIR, a framework that converts historical repair trajectories into hierarchical, reusable plans that can be adapted to steer future repairs. Each past trajectory is transformed into a multi-level tree that ranges from fine-grained diagnostic actions to high-level repair strategies, encoding experience at several granularities. When a new issue arrives, STAIR selects relevant plan nodes from multiple abstraction levels, tailors them into executable, issue-specific plans, and supplies them to the agent through its prompt. On SWE-bench Verified, STAIR integrated with Lingxi reaches 81.2% Pass@1 using MiniMax M2.5 and 79.2% using GPT-5. The generated plans also generalize across agents: without any code change, they lift the Pass@1 of a structurally different agent, mini-SWE-agent v2, from 75.8% to 81.0%. Ablation experiments further show that mixing multiple abstraction levels surpasses any single level and that raw, unabstracted trajectories transfer substantially worse.

## 2. 论文提出的方法论

### 2.1 总体架构（离线构建 + 在线指导）

STAIR 包含两大阶段：**离线知识构建**（将历史轨迹转化为层次化抽象知识库）与**在线计划生成与执行**（检索相关节点、适配为新问题的分阶段计划、引导代理解决）。

### 2.2 程序性知识构建

- 使用修复代理（Lingxi 去掉知识复用机制后的版本）在历史已解决 issue 上运行，生成修复轨迹 τ(u)（包含推理、工具交互、编辑决策、验证反馈）。
- 每条完整轨迹被划分为三个**修复阶段（stage）**的子轨迹：τ_localization（故障定位）、τ_planning（修复计划）、τ_execution-and-verification（执行与验证），保持各阶段信息类型（观察、思考、动作）统一。
- 历史 issue 选取遵循协议：与目标 issue 来自同一仓库、创建时间早于目标 issue（避免时间泄漏）、按嵌入相似度排序并经 LLM 相关性验证过滤。

### 2.3 层次化轨迹抽象（核心机制）

每个阶段的子轨迹被构造成一棵多级抽象树：

- **叶节点层 L0**：由原始轨迹中的单个步骤构成，每步包含 agent 的 thought、action、observation。
- **分组操作 Gℓ(·)**：LLM 将当前层节点划分为连续且共享连贯程序性意图的组（涉及低/中/高三个抽象粒度的分组指导，见图 2）。
- **抽象操作 Aℓ(·)**：LLM 将每组抽象为一个父节点（结构化节点，含 level、node_type、summary、intent、rationale、when_to_apply、key_actions、pitfalls 等字段，见图 3）。抽象程度越高，内容越通用。
- 形式化表示：Gℓ(Lℓ) = {Cℓ,1, Cℓ,2, …, Cℓ,mℓ}；Lℓ+1 = {Aℓ(Cℓ,j) | 1 ≤ j ≤ mℓ}；迭代直到 |Lℓ+1| ≤ K（根节点数 K=2）。
- 抽象过程中，LLM 决策提示从三个视角选择当前合适的抽象层次：low（基于项目具体制品的子目标）、medium（跨项目的调查策略）、high（跨项目的一般问题解决原则）。
- **对每个修复阶段独立应用上述抽象过程**，保留阶段分离性，以支持后续针对性检索。

### 2.4 指导检索与计划生成

- **检索**：对每个修复阶段独立检索，候选节点可来自任意抽象层次。先按 issue 报告与节点内容的文本相似度评分，再用 LLM 验证器过滤"词面相似但不可用"的节点；保留节点按其在源轨迹中的**原始执行顺序**排列，形成该阶段的 **Guidance Gs(u)**——一个有序的、保留历史修复程序结构的抽象过程序列。
- **计划生成**：将 issue 报告 u 与该阶段 Guidance 一起交给 LLM，生成**结构化的、针对当前 issue 的可执行计划 Ps(u)**（Plan）。LLM 选择性实例化适用过程、丢弃不相关部分，将抽象程序知识落地到当前仓库的具体上下文。
- **计划引导执行**：三阶段的计划分别引导故障定位（缩小搜索空间到候选位置集）、修复策略（给定修改范围与约束）、执行与验证（基于测试反馈迭代修正补丁）。计划不强制固定脚本，实际修复仍受新证据和验证反馈影响。

## 6. 主要结论与发现

### 6.1 主性能（RQ1）
- STAIR + MiniMax M2.5 达到 **81.2% Pass@1**，超过所有对比代理；STAIR + GPT-5 达到 **79.2%**。
- 在同骨干对比中：STAIR 在 GPT-5 上超过 OpenHands（71.8%）**7.4%**、Prometheus（74.4%）**4.8%**；在 MiniMax M2.5 上超过 mini-SWE-agent v2（75.8%）**5.4%**。
- 即便使用相对较弱的骨干模型，STAIR 仍超越基于 Claude 4.5 Opus 的最强基线（Sonar、live-SWE-agent 均为 79.2%），表明增益来自框架本身而非模型能力。
- 对比经验复用代理：STAIR 在 MiniMax 上超过同骨干 Lingxi **6.6%**（81.2% vs. 74.6%），在 GPT-5 上超过 **3.6%**（79.2% vs. 75.6%）。

### 6.2 跨代理迁移（RQ2）
- 将 STAIR 计划注入 mini-SWE-agent v2，Pass@1 从 **75.8% → 81.0%**（绝对提升 **5.2%**），同时平均 token 从 1,245k 降至 **1,180k**（减少约 5.2%），平均步数从 60.45 降至 58.18 —— 计划既提升效果又提升效率，说明学到的是**代理无关的通用修复策略**。

### 6.3 行为分析（RQ3）
- **增益来源**分为三类：修正错误定位（Wrong Location，mini-SWE-agent 占比最高 52%）、覆盖不完全修复的遗漏位置（Partial Fix，STAIR 占比最高 49%）、减少过度修改（Over-modification）。
- **回退原因**两类：计划本身覆盖不完整（8/17，如 django-11138 时间戳转换 bug 只修复部分后端）、计划合理但执行失误（9/17，如用错 API、偏离计划等）。

### 6.4 消融（RQ4）
- 原始轨迹（不抽象）效果最差：80.0% → **57.6%（∆= −22.4%）**，说明 issue 特定动作难以跨问题泛化。
- 单一抽象层均显著低于完整层次：Low-only 64.0%（−16.0%）、Medium-only 60.8%（−19.2%）、High-only 58.4%（−21.6%）。
- **结论：有效修复需要多粒度程序性知识同时可用，任何单一层次都会导致不完整指导。**

## 7. 优点

- **层级抽象设计直观且有效**：将轨迹从具体动作到通用策略组织为多级树，忠实模拟了开发者同时调用"具体 API 记忆"和"高层策略"的实践方式；消融充分证明了层次混合的必要性。
- **阶段感知的检索与指导**：将轨迹按修复阶段（定位、计划、执行验证）切分并分别检索，使知识传递

阶段感知的检索与指导：将轨迹按修复阶段（定位、计划、执行验证）切分并分别检索，使知识传递更精准、阶段匹配更灵活，避免了将整条轨迹作为一个整体导致的知识混杂与失效问题。
- **良好的实验结果与可迁移性验证**：在 SWE-bench Verified 上以 81.2% Pass@1 刷新 SOTA，并通过对 mini-SWE-agent v2 的注入证明所生成计划与代理无关，增强了结论的可信度。
- **成本透明度高**：明确给出单实例运行与离线预处理的成本估算，便于复现与公平对比。
- **方法论表述规范**：对抽象树构建、分组/抽象操作、检索排序等均有形式化定义（Gℓ、Aℓ、Lℓ 等），可复现性强。

## 8. 缺点与局限性

- **依赖 LLM 作为抽象与验证器**：轨迹分组、节点抽象、相关性过滤全部依赖 LLM 判断，若 LLM 对步骤意图理解错误或产生幻觉，错误会沿抽象树向上传播，且缺乏自动校验机制；论文未分析抽象过程自身的失败率。
- **消融规模偏小**：消融实验仅在 125 个实例（25%）上进行，且对难度分层抽样比例（约 3:1）做了说明，但统计功效有限，难以排除个别层差异的随机波动。
- **迁移验证范围窄**：跨代理迁移只测试了 mini-SWE-agent v2，且骨干同为 MiniMax M2.5，未验证在不同骨干（如 GPT-5、Claude）或不同工具设计（如基于编辑器的代理）下的迁移稳定性。
- **阶段性划分的合理性假设**：将修复轨迹硬性划分为定位→计划→执行验证三个阶段，可能不适用于非线性的真实调试流程（如边定位边验证、反复迭代），对这类轨迹的适用度存疑。
- **知识库构建耗时且不可扩展**：每新增一条历史轨迹需人工配置包含 target issue、构建脚本等完整记录；虽单次成本约 $0.44，但随仓库规模线性增长，且依赖人工修复标记，大规模应用瓶颈明显。
- **缺乏对失败案例的深入量化**：虽然对 17 个回退实例做了定性归因，但未给出各原因的比例统计，也未说明 STAIR 在哪些类型 issue 上系统性失败（如安全修复、性能优化、依赖版本问题）。
- **抽象层数固定为三级**：K=2 的根节点数及 low/medium/high 三层粒度是经验默认值，未探究最优层数或层次数量对效果的影响。
- **泛化性存疑**：实验仅覆盖 Python 语言和 12 个仓库，未证明在多语言、多包管理、异构构建环境下的有效性，也无法回答"历史轨迹缺失时系统表现如何"这一冷启动问题。

## 9. 总体评价与思考

STAIR 是"程序性知识复用"方向上的一项扎实工作，其核心贡献在于将隐性的修复轨迹显式地编码为多粒度、可检索、可适配的抽象计划，并在一流基准上取得显著收益。它实际上回答了一个关键问题：**成功的修复经验不仅包括"修了什么"，更包括"怎么定位、怎么计划、怎么验证"**。从方法论上看，层次化抽象树的构建类似于程序归纳中的"子目标发现"，而阶段感知检索则类似于"按需记忆"——两者共同模拟了人类工程师的类比推理机制。

值得关注的是，STAIR 的提升并非来自更强的单步推理能力，而是来自**对历史经验的结构化利用**，这为"如何让 LLM 代理持续学习"提供了一条不同于微调或 RAG 的新路径。其设计中的"抽象-检索-适配"三步流程也具有较强的框架独立性，理论上可嫁接到其他工具型代理之上。

不过，该工作也暴露出当前智能体学习范式的一个共同短板：**知识获取依赖历史修复轨迹的人工标注与整理**，缺乏从错误轨迹、失败尝试中自动提炼经验的能力；另一方面，抽象树的构建并未利用测试结果作为反馈信号，属于单向的知识压缩，而非闭环的自我改进。未来工作若能引入失败轨迹学习、抽象失败自校正或多仓库跨语言验证，将进一步增强其理论和实用价值。

总体而言，STAIR 在方法新颖性、实验严谨性和结果显著性上均达到较高水平，是自动化软件修复领域值得关注的重要参考；其局限性也极具启发性，为后续研究指明了方向。
