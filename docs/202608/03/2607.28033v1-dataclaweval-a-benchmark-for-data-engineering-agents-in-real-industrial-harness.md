## 摘要
大语言模型（LLMs）和基于LLM的智能体正越来越多地被部署来自动化复杂工作流，有望彻底改变数据管理和处理。然而，现有基准主要侧重于简化的Text-to-SQL转换或数据分析，而端到端数据工程这一关键且复杂的领域在很大程度上仍未得到探索。为了弥补这一差距，我们引入了DataClawEval，这是第一个专门用于评估真实世界数据工程场景中自主智能体端到端任务完成能力的综合基准。它基于专业企业数据工程师编写的生产级代码，包含100个严格的端到端任务，跨越五个执行引擎：PySpark、MySQL、HiveSQL、PrestoSQL/Trino和FlinkSQL。与不确定的LLM作为评判者的评分不同，每个任务都在针对具体案例的隔离沙箱中执行，并通过确定性的基于规则的脚本进行评分。评估16个前沿智能体揭示了关键局限性：最强的模型仅获得74.9的总体得分，且没有单一模型占主导地位，因为每个模型在不同的引擎上表现出色，显示出严格的领域专业化而非全能精通。因此，自主数据工程仍然是一个艰巨且尚未解决的挑战。我们在https://github.com/Dicemy/DataClawEval/tree/master发布了我们的数据集、容器化环境和确定性评估脚本。

## Abstract
Large language models (LLMs) and LLM-based agents are increasingly being deployed to automate complex workflows, promising to revolutionize data management and processing. However, existing benchmarks predominantly focus on simplified Text-to-SQL translation or data analysis, leaving the critical and complex domain of end-to-end data engineering largely unexplored. To bridge this gap, we introduce DataClawEval, the first comprehensive benchmark designed specifically to evaluate the end-to-end task completion capabilities of autonomous agents in real-world data engineering scenarios. Built upon production-grade code authored by professional enterprise data engineers, it comprises 100 rigorous, end-to-end tasks spanning five execution engines: PySpark, MySQL, HiveSQL, PrestoSQL/Trino, and FlinkSQL. Rather than non-deterministic LLM-as-a-judge scoring, each task is executed within a case-specific, isolated sandbox and graded by deterministic, rule-based scripts. Evaluating 16 frontier agents exposes critical limitations: The strongest model attains only 74.9 overall, and no single model dominates, as each excels on a different engine, revealing strict domain specialization rather than omnipotent proficiency. Thus, autonomous data engineering remains a formidable, unresolved challenge. We release our dataset, containerized environments, and deterministic evaluation scripts at https://github.com/Dicemy/DataClawEval/tree/master

### 2. 论文提出的方法论

**核心思路：**
- 从**真实生产代码**出发，通过**人机协同（human-in-the-loop）流水线**重构出具有"答案可辨识性"（answer-identifiable）的基准任务，配合**确定性的基于规则的评分脚本**在**隔离沙箱**中执行评估，保证评估的客观性、可复现性和区分度。

**数据集构建流水线（5个阶段）：**
1. **Stage 1：策展高质量生产代码**——从企业生产仓库收集真实数据工程代码，经过去敏、去重、分层抽样，保留跨编程范式、SQL 方言和业务场景的多样性，作为 ground-truth 代码。
2. **Stage 2：重构可执行的任务规范**——利用 LLM 从 ground-truth 代码逆向推断用户意图，并合成代表性输入表，生成初始任务规范（自然语言请求 + 输入表 + 标准实现）。
3. **Stage 3：迭代验证（差分测试思想）**——人工专家扰动 ground-truth 实现（保持可执行性），要求合成输入表必须能**区分正确实现与错误实现**；若无法区分，则将反馈返回给 LLM 修订，直到满足执行有效性和判别充分性两个互补要求。
4. **Stage 4：开发并验证任务专属评分脚本**——针对每个任务定制评分程序，覆盖模式正确性、数值正确性、业务逻辑等维度；ground-truth 实现必须得满分，扰动实现必须无法得满分。
5. **Stage 5：最终专家核验**——领域专家综合审查任务意图、输入表、标准实现、评分脚本和预期输出的一致性。

**评估框架：**
- **隔离任务执行**：每个任务在全新 Docker 容器中运行，预初始化所有服务（数据仓库、查询引擎等），防止信息泄漏，保证可重现性。
- **产物导向评估**：对比"产出的数据工件"而非源代码本身，评估五个维度：可执行性、模式正确性、行级对齐、数值准确性、类别正确性。
- **过程导向评估**：评估执行轨迹质量，涵盖探索充分性、执行效率、自我验证三个方面。
- **综合得分公式**：

```
Score = α·S_artifact + (1−α)·S_process
```

其中默认 α = 0.7，强调最终产物正确性，同时奖励高效可靠的工程行为。

### 3. 实验设计

**基准构成（DataClawEval）：**
- **100 个端到端任务**，全部源于专业企业数据工程师撰写的生产级代码。
- **5 种执行引擎分布**：HiveSQL（28 个）、PySpark（20 个）、MySQL（20 个）、FlinkSQL（20 个）、PrestoSQL/Trino（12 个）。
- **5 大业务领域分布**：运维与资源治理（30 个）、数据分析与用户增长（30 个）、安全与风控（16 个）、内容社区与研发效能（14 个）、广告与营销（10 个）。
- **双语任务**：50 个英文 + 50 个中文，反映原始生产日志语言。

**对照设置：**
- 16 个前沿 LLM 智能体，跨 8 个模型家族：GPT 5.5 / GPT 5.3 Codex、Claude Opus 4.8 / Claude Sonnet 5、Gemini 3.1 Pro / Gemini 3.5 Flash、DeepSeek V4 Flash / V4 Pro、GLM 5.1 / 5.2 / 5V Turbo、Kimi K2.6 / K2.7、MiniMax M3 / M2.7、Hy3。
- 全部使用**统一的 Tencent CodeBuddy 智能体框架**，仅替换底层 LLM，确保性能差异主要反映模型能力而非智能体实现差异。

**实验规模：**
- 主实验：16 模型 × 100 任务 = 1,600 次隔离运行。
- 稳定性实验：4 个代表模型（Gemini 3.1 Pro、DeepSeek V4 Flash、DeepSeek V4 Pro、Hy3）× 3 次独立重复运行。
- LLM-as-judge 对比实验：GLM 5.2 和 DeepSeek V4 Pro 分别对 Claude Opus 4.8 的全部 100 个输出独立评分 3 次。
- 附录还包括：低分运行错误分类分析（1,600 次运行全量）、超时运行特征分析、双语性能分解（按引擎、按模型）等。

### 6. 论文的主要结论与发现

1. **自主数据工程仍未解决，天花板显著**：最强模型 GPT 5.5 仅获得 74.9 分（满分 100），远未饱和，留有充分区分空间；模型分数跨度 60.3–74.9，区分度良好。
2. **各引擎难度极度不均**：MySQL 最易（所有模型超 74 分，最高 88.8），HiveSQL 最难（无人超过 69.8，部分模型低于 50），PySpark 和 FlinkSQL 区分度最大（跨模型差距超过 35 分）。
3. **没有万能模型，呈现严格领域专化**：GPT 5.5 在总体/HiveSQL/MySQL 领先；Claude Opus 4.8 在 PySpark 最佳（83.8）；DeepSeek V4 Pro 在 PrestoSQL/Trino 最佳（77.7）；DeepSeek V4 Flash 在 FlinkSQL 最佳（85.0）。引擎覆盖率比平均分更能反映真实能力。
4. **Token 成本与质量无正相关**：GPT 5.3 Codex 最省 token（271.4k）但排名靠后；Gemini 3.5 Flash 消耗最多（973.8k）仅中游；GPT 5.5 和 Gemini 3.1 Pro 在性价比上最优。
5. **LLM-as-judge 不可靠，规则化评估不可替代**：LLM 裁判系统性高估所有指标（过程分从 22.2 虚高至 75.0–76.0），不稳定（σ 最高 6.35，单案例偏差超 55 分），违背评分上限，且对流式计算语义（FlinkSQL）判断严重失灵。
6. **模型稳定性差异显著**：Gemini 3.1 Pro 最稳定（max-min 差 12.6 分，pass@3−pass³ 差 8.2%）；Hy3 最不稳定（max-min 差 26.8 分，pass@3−pass³ 差 26.5%）。
7. **工具调用效率比调用数量更关键**：顶尖模型集中在"少调用、高得分"的高效区域；频繁试错的模型得分反而更低。

### 8. 不足与局限

1. **任务规模有限**：100 个任务相对于数据工程的广阔领域仍显不足，某些引擎（PrestoSQL/Trino 仅 12 个任务）样本偏小，可能影响统计可靠性。
2. **单次运行的主评估**：除 4 个代表模型外，其余模型仅单次运行，而稳定性分析已证明模型表现波动显著（最高 26.8 分的差距），因此主结果中的部分排位可能对采样噪声敏感。
3. **超时处理可能扭曲排名**：GLM 5.2 因 22% 超时率被拉低 13.3 分（从最高分 82.1 的健康运行均值跌至第 11 名），说明超时机制对结果的潜在影响大，而主表未区分"超时得零"与"完成但错误"的差异。
4. **双语分析存在混淆**：英文和中文任务不是平行翻译，难度差异与语言因素混淆，无法得出"模型更擅长某种语言"的纯结论。
5. **资源信息不透明**：未披露 GPU 型号、数量及其他算力配置，影响实验的完全可复现性和成本对比。
6. **评分脚本设计的人工依赖**：虽然保证了每个任务的评分质量，但 100 个任务逐一人工编写和验证评分脚本的代价高，限制了基准快速扩展的能力。
7. **LLM 评测对象为未来模型名称**（如 GPT 5.5、Claude Opus 4.8 等），部分模型细节需要读者追溯原始技术报告，且这些模型可能尚未在公开 API 中开放，影响即时复现。
