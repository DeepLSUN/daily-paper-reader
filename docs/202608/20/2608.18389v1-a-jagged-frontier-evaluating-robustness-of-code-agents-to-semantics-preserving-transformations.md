## 摘要
人工智能代码代理正越来越多地被部署用于解决真实的软件问题，但它们在表面代码变化下的可靠性仍然知之甚少。我们评估了修复仓库级问题的编码代理在周围代码库被重写为语义等价形式时是否仍然可靠。我们引入了一个随机变体采样器，应用常见的语义保持变换（SPT）——涵盖控制流重写、死代码注入和标识符重命名——来生成扰动变体。我们评估了两种代理脚手架（mini-SWE代理和OpenCode），每种脚手架分别由四个前沿模型之一（Claude Opus 4.5、Kimi K2.5、MiniMax M2.5和Qwen 3.6-27B）提供支持，实例来自SWE-bench Verified和SWE-bench Pro。对于每个实例，代理在未扰动和扰动变体上多次运行，产生配对的分辨率估计，从而将扰动效应与内在随机性分离。我们发现大多数配置中出现了小幅退化：受影响最严重的配置中平均分辨率下降高达6.7个百分点，在模型、脚手架和数据集的16种配置中有6种存在统计显著的退化。关键的是，没有一个模型在鲁棒性上的排名在所有脚手架中保持一致——Qwen在mini-SWE代理下在SWE-bench Verified上属于最鲁棒之列，但在OpenCode下却最为脆弱——揭示了一个锯齿状的鲁棒性边界。较简单的脚手架（mini-SWE代理）对扰动更为鲁棒。我们的结果表明，即使是最前沿的模型也容易受到语义保持扰动的影响，尽管这种影响并非均匀分布，这引发了对AI代码代理在多样化真实世界代码库中部署可靠性的担忧。

## Abstract
AI code agents are increasingly deployed to resolve real software issues, yet their reliability under superficial code variations remains poorly understood. We evaluate whether coding agents that repair repository-level issues remain reliable when the surrounding codebase is rewritten into a semantically equivalent form. We introduce a random variant sampler that applies common semantics-preserving transformations (SPTs) - spanning control-flow rewrites, dead-code injection, and identifier renaming - to produce perturbed variants. We evaluate two agentic scaffolds (mini-SWE agent and OpenCode) each backed by one of four frontier models (Claude Opus 4.5, Kimi K2.5, MiniMax M2.5, and Qwen 3.6-27B) across instances drawn from SWE-bench Verified and SWE-bench Pro. For each instance, the agent is run multiple times on the unperturbed and perturbed variants, yielding paired resolve-rate estimates that isolate the perturbation effect from intrinsic stochasticity. We find small degradation in most configurations: up to 6.7 percentage points mean resolve-rate drop in the most affected configurations with statistically significant degradations in 6 of 16 configurations of model, scaffold, and dataset. Crucially, no single model ranking by robustness holds across scaffolds - Qwen is among the most robust under mini-SWE agent on SWE-bench Verified yet the most brittle under OpenCode - revealing a jagged robustness frontier. The simpler scaffold (mini-SWE agent) is more robust to perturbation. Our results demonstrate that even top frontier models are susceptible to semantics-preserving perturbations although the effect is not uniform, raising concerns about the deployment reliability of AI code agents in diverse real-world codebases.

## 1. 论文核心问题与整体含义

- **研究动机**：AI 编程工具（代码代理）已被广泛部署于真实软件开发中，但其在代码表面形式发生细微变化时的可靠性尚不清楚。已有研究表明，神经模型普遍存在“捷径学习”倾向，易受微小输入扰动影响。若代理行为随周边代码的表层改动而波动，则基准测试分数可能高估其部署可靠性，也说明模型依赖浅层句法模式而非对程序语义的深层理解。
- **核心问题**：本文首次系统评估仓库级代码代理在语义保持变换（Semantics-Preserving Transformations, SPTs）下的鲁棒性，即在代码库被改写为语义等价形式后，代理修复问题（issue）的成功率是否稳定。
- **整体发现**：变换会导致多数配置下的解析率轻微下降（最高平均下降 6.7 个百分点）；更重要的是，模型鲁棒性排序会随脚手架和基准的改变而反转，形成所谓的 **“锯齿状鲁棒性边界”（jagged robustness frontier）**——鲁棒性是模型、脚手架与工作负载三者的联合属性，而非模型独立属性，对部署选型构成警示。

## 2. 方法论

### 2.1 核心思想
设计一个**随机变体采样器（Random Variant Sampler）**，对种子仓库施加一组局部、语义保持的变换，生成扰动变体；通过**配对运行**（同一实例的未扰动版本和多个变体各运行多次）将扰动效应与代理内在随机性分离开来。与非对抗性设计一致，采样过程不依据模型输出反馈，因此测得的结果是 SPTs 影响的**下界**。

### 2.2 语义保持变换（SPT）目录
共实现 14 种变换，分为两类：

- **重写类**：`If Else Switcher`（交换 if/else 分支并取反条件）、`For Loop Rewriting`（用显式迭代器改写 for 循环）、`And Condition Splitter`（将 A and B 分解为嵌套 if）、`Comparison Swapper`（交换比较操作数并反转运算符）、`While Loop Unrolling`（展开 while 循环一次迭代）、`Double Negation Injector`（在条件上套 not not）、`Commutative Operand Permuter`（交换可交换操作数）、`Local Variable Renamer`（将局部变量改名为同义词）、`String Literal Splitter`（将字符串字面量拆分为拼接形式）。
- **惰性插入类**：`If True Wrapper`（用永真守卫包裹代码块）、`Try Except Injector`（包裹 try/except 并原样重抛）、`Dead Code Injector`（插入 if False 不可达块）、`Dead String Assignment`（插入含目标关键字的未读赋值）、`Dead Method Injection`（在类中追加含关键字的不可达方法）。后两者设计为**诱饵（decoy）**，干扰代理基于关键字的代码定位。

所有 SPT 的实现原则是**保守性**：当无法从代码静态确认安全性（如类型不确定、名称遮蔽、类命名空间可被观察等）时跳过该位置，避免破坏语义。

### 2.3 变体采样算法（Algorithm 1）
对每个种子实例，采样器做四层随机决策：

1. **选择变换**：从 14 种变换中随机抽取 $N_t = 3$ 种。
2. **选择文件**：对每种选中变换独立抽取文件包含概率 $p_{file} \sim U(0,1)$，按该概率包含源码文件（排除测试文件）；gold patch 涉及的文件**强制包含**，确保变体始终指向解决方案相关区域。
3. **选择站点**：在包含的文件中，随机选取 $\phi = 70\%$ 的候选站点进行重写。
4. **选择关键字**：对于关键字绑定变换（死字符串赋值、死方法注入），从 issue 描述中通过 LLM 提取候选关键字（方法名或字符串），每种变换最多绑定 $N_k = 5$ 个关键字。

超参数：$N=20$ 个变体/实例，$N_t=3$，$N_k=5$，$N_f=10$（限制关键字绑定变换涉及的最大文件数，防止代理直接检测到扰动并 git reset 还原仓库），$\phi=0.7$。

### 2.4 语义保持性的验证
通过**差分测试（differential testing）**在三个项目（SymPy 12,994 测试、sqlfluff 10,060 测试、xarray 19,917 测试）上逐一验证每种变换：对每个可应用站点施加变换后运行完整测试套件，比较逐测试结果与基线完全相同。验证覆盖以测试套件为界，不构成形式等价证明。

## 3. 实验设计

### 3.1 基准数据集
- **SWE-bench Verified**：28 个实例（人类验证的 500 实例子集）。
- **SWE-bench Pro**：26 个实例（731 实例的长期任务基准）。
- 实例选择：Verified 基于官方排行榜中 Claude Opus 4.5 可解决的实例做分层抽样；Pro 先均匀抽样运行后再挑可解实例。每个实例包含仓库基线提交、issue 描述、FAIL_TO_PASS 和 PASS_TO_PASS 测试集，以及 gold patch。

### 3.2 模型与脚手架（共 16 种配置）
- **模型**：Claude Opus 4.5（Amazon Bedrock）、Kimi K2.5（Bedrock）、MiniMax M2.5（Bedrock）、Qwen 3.6-27B（本地 vLLM 伺服）。
- **脚手架**：mini-SWE agent（简单单代理架构）与 OpenCode（子代理分工架构）。
- 所有模型温度设为 1.0。

### 3.3 实验协议
对每个实例：先执行 N=20 次未扰动基线运行；再用采样器生成 20 个变体；每个变体在**全新隔离环境**中运行一次代理；对生成的 patch 以同一测试 oracle 评估。每次运行（扰动或未扰动）均在独立 Docker 容器中执行，无状态跨运行传递。

### 3.4 统计方法
- 主要指标：逐实例退化 $\Delta(i) = r_0(i) - r_p(i)$，配置级汇总为平均退化 $\bar{\Delta}$。
- 效率指标：步数相对变化 $\delta_{step}$ 和令牌成本相对变化 $\delta_{cost}$。
- 置信区间：配置级均值用 20,000 次自助法（bootstrap）百分位区间；逐实例退化用 Newcombe 区间。
- **设计合理性**（附录 E 推导）：由于 $E[p_V]$ 的估计在任意 $K$（每变体运行次数）下无偏，且方差 $\mathrm{Var}(\hat{\mu}) = (K\sigma^2 + \nu)/R$ 随 $K$ 严格递增（$\sigma^2 > 0$ 时），因此固定预算 $R$ 下 **$K=1$（每变体仅运行一次）是方差最优分配**。

## 4. 资源与算力

- **硬件**：单台实验服务器，配备双 AMD EPYC 9554 64 核处理器（128 核/256 线程）、768 GB RAM、6 块 Nvidia RTX PRO 6000 Blackwell GPU（每块 96 GB VRAM）、7 TB NVMe 存储，Ubuntu 24.04.4 LTS。
- **模型服务**：Qwen 3.6-27B 以 vLLM v0.20.1 在 2 块 GPU 上本地伺服；Claude Opus 4.5、Kimi K2.5、MiniMax M2.5 通过 Amazon Bedrock API 访问。
- **总运行量**：54 个实例 × 40 次运行/实例 = **2,160 次代理运行**。成本以令牌数计：Bedrock 模型按厂商单价、Qwen 按 OpenRouter 同模型价格折算，以保证配置内一致性。
- 论文**未说明总训练/实验时长**，仅给出单次配置（16 种之一）成本约 2,160 次运行，也因算力约束未对采样器超参数做网格搜索。

## 5. 实验数量与充分性

- **实验规模**：16 种配置（2 脚手架 × 4 模型 × 2 基准）独立评估，每配置 54 个实例，每实例 20 次基线 + 20 次扰动运行。属于受算力预算约束下的中等规模但统计上谨慎设计的实验。
- **充分性评价**：
  - **客观性**：配对设计正确隔离扰动效应与代理随机性；引入的方差分解与 $K=1$ 最优性证明使统计分析严谨；每实例采样 20 个变体、每变体单次运行避免了重复运行导致的估计偏差。
  - **公平性**：相同配置、相同提示、相同 oracle 用于基线与变体；测试文件不被扰动，gold patch 文件强制包含，保证“靶心”一致。
  - **不足之处**：每实例仅 20 次/条件，导致逐实例 Newcombe 区间很宽（约 ±25 个百分点才能排除零），大多数逐实例效应无法单独确认；实例数量仅 54，对基准多样性的覆盖有限。论文也明确指出这是**非对抗性**下界估计，真实鲁棒性可能更差。

## 6. 主要结论与发现

1. **轻微但广泛的性能退化**：16 种配置中 13 种的平均退化 $\bar{\Delta}$ 为正，6 种统计显著；受影响最严重的配置（mini-SWE agent + Opus on SWE-bench Pro）平均下降 6.7 个百分点。
2. **鲁棒性排名不跨脚手架/基准迁移**：典型的“锯齿状”表现——Qwen 在 mini-SWE agent + Verified 下最鲁棒（0.2 点退化），在 OpenCode 下却最脆弱（5.5 点退化）；MiniMax 则相反。每个模型至少在一个单元中最鲁棒、在另一个单元中最脆弱。**按用户基准排名选择模型不可靠**。
3. **较简单的脚手架更鲁棒**：均值上 mini-SWE agent 在两种基准上的退化均小于 OpenCode（Verified 1.34 vs 1.88，Pro 1.88 vs 3.65），且该鲁棒性优势在绝对能力反转时依然存在。
4. **扰动提高代理开销**：即使解析率几乎不变，步数增加最多 9.9%、令牌成本增加最多 22.9%（Verified 上所有 8 种配置成本均显著上升）。步数与成本不同步增长，表明代理在每步中消费更多上下文，而非仅增加步数。
5. **退化具有集中性**：三实例（openlibrary 等）合计贡献约三分之二的 6.7 点最大平均退化；逐实例显著的单元格仅 14/432，说明脆弱性是“实例-配置”配对特有的属性。
6. **失败模式多样**：代理可能检测并回滚 SPT（如 git reset）；被诱饵关键字干扰而定位失败；顺手改写/“修复”扰动代码导致补丁体积扩大而失败；或将无关测试失败错误归因于扰动代码而放弃修复。

## 7. 优点

- **问题新颖且重要**：首次系统性地研究多轮、仓库级代码代理对语义等价扰动的鲁棒性，弥补了以往仅局限于单轮非代理任务的空白。
- **方法设计严谨**：
  - 随机采样器为非对抗性，结果可视为鲁棒性下界；组合变换可同时覆盖局部编辑与全局渗透。
  - 配对运行 + 方差分解（变体随机性 vs 代理随机性）的统计框架干净且可复现，$K=1$ 的分配有严格推导支撑。
  - 固定总体推断而非实例抽样推断，区间含义明确。
- **SPT 库的工程实现**：在大型真实仓库中保持语义等价需处理大量边界情况（名称遮蔽、类型不确定、框架约束等），论文的保守跳过策略保证变换安全性；差分验证覆盖了 4 万余测试用例。
- **洞察深刻**：发现鲁棒性是模型-脚手架-工作负载的联合属性，而非模型单一属性，对模型选型和部署策略有直接指导意义。
- **透明度**：代码、提示、实例 ID 列表、交互式结果浏览均公开，便于复现和后续扩展。

## 8. 不足与局限

- **实例选择偏向**：仅选取已知可被 Claude Opus 4.5 解决的实例，可能高估了代理在一般任务上的鲁棒性，并引入选择偏差；Pro 的实例选取过程中也依赖先验运行。
- **样本量与统计功效**：每实例仅 20 次运行/条件，逐实例难以检测小于 25 点的效果；54 个实例的总样本限制了结论向更广代码库的泛化。论文也指出少数单元格出现大幅反向摆动（如 seaborn +55 点），不应过度解读。
- **语义等价并非形式等价**：以测试套件等价作为操作性定义，受测试覆盖完整性限制；某些变换在未覆盖路径上可能改变行为，且组合变换依赖传递性而非重复验证。
- **超参数无搜索**：$N_t, N_k, N_f$ 等超参数仅根据观察经验设定，未做系统扫描，可能影响变体难度的代表性；$N_f=10$ 上限是为防止代理检测并回滚而设，这本身意味着变体与真实重构还存在差异。
- **非对抗性设计局限**：虽然有意为之以估计下界，但真实部署中攻击者或极端重构会带来更大破坏；同时，随机采样不能系统覆盖最坏情况。
- **仅评估代码修复任务**：未覆盖代码生成、代码审查、测试生成等其他代理任务；仅使用 Python 仓库，未考虑其他语言。
- **成本与可扩展性**：16 种配置 × 54 实例 × 40 次运行已经是重算力实验，限制了规模化复现；成本按令牌计算并在配置内一致，但跨模型的绝对成本可比性有限。
- **定性分析的样本较小**：仅对 20 条轨迹做了人工分析，且其中有 AI 辅助筛选环节，观察到的失败模式可能不是穷尽性的。
