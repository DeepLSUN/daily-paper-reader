## 摘要
长时程智能体可以持续执行，但人类注意力仍然是间歇性和稀缺的。这造成了双向协调问题：用户可能需要在后台工作继续的同时立即访问某个智能体，而智能体可能遇到需要用户判断的重要决策，此时用户已停止监控执行。我们提出一个始终在线的注意力协调层——Jarvis（以《钢铁侠》中的虚构AI助手命名）——来调解这一接口，并在一个或多个工作中的智能体之间分配人类注意力。我们引入JarvisBench来评估这种协调的两个方向：中介能否准确、及时地回答用户主动提出的关于正在进行的任务的问题，以及它是否能识别智能体何时需要用户判断，在恰当的时刻征求该判断，并将其传回以改善任务结果。JarvisBench包含45个智能体任务实例：20个单智能体任务和25个工作流，组织成10个多智能体项目。这些任务跨越19个领域，从2000多个公开候选项中筛选和改编而来。关键的是，对用户注意力的需求是在执行过程中自然产生的，而不是来自初始提示中的明显遗漏。JarvisBench旨在与任意智能体运行时集成，无需修改其底层执行循环。我们的参考实现还提供了全双工语音接口，使用户能够自然地与Jarvis交互，同时及时的注意力协调支持后台工作的智能体。通过将智能体执行与注意力协调分离，JarvisBench在智能体能力持续提升时提供了一个稳定的评估目标。

## Abstract
Long-horizon agents can execute continuously, but human attention remains intermittent and scarce. This creates a bidirectional coordination problem: users may need immediate access to an agent while work continues in the background, whereas agents may encounter consequential decisions that require user judgment after the user has stopped monitoring execution. We posit an always-on attention-coordination layer---\textit{Jarvis}\footnote{Named after the fictional AI assistant in \textit{Iron Man}.}---that mediates this interface and allocates human attention across one or more working agents. We introduce \textit{JarvisBench} to evaluate both directions of this coordination: whether an intermediary can accurately and promptly answer user-initiated questions about ongoing work, and whether it can recognize when an agent requires user judgment, solicit that judgment at the right moment, and route it back to improve task outcomes. JarvisBench contains 45 agentic task instances: 20 single-agent tasks and 25 workstreams organized into 10 multi-agent projects. The tasks span 19 domains and were selected and adapted from more than 2,000 public candidates. Crucially, the need for user attention arises naturally during execution rather than from an obvious omission in the initial prompt. JarvisBench is designed to integrate with arbitrary agent runtimes without modifying their underlying execution loops. Our reference implementation further provides a full-duplex speech interface, allowing users to reach Jarvis naturally while timely attention coordination supports agents working in the background. By separating agent execution from attention coordination, JarvisBench provides a stable evaluation target as agent capabilities continue to improve.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心矛盾**：长时程智能体（long-horizon agents）可以持续执行任务，但人类的注意力是间歇性（intermittent）且稀缺的（scarce）。随着智能体自主性和并行性的增强，日益需要及时的用户注意力，否则智能体会在错误方向上逐渐偏离用户真实需求。
- **双向协调问题**：
  - **用户到智能体方向**：用户希望在后台工作继续的同时，随时询问进展或提供指导，但现有系统往往被迫打断智能体执行，降低效率并污染工作上下文。
  - **智能体到用户方向**：当智能体遇到需要人类判断的关键决策时，无法确保用户正在监控，往往只能猜测后继续执行，糟糕的决策可能已经塑造了后续的全部工作。
- **现有研究的不足**：虽然让智能体主动暂停并征求用户意见看似自然，但近期研究（UserBench、π-Bench、VitaBench等）表明：*主动性（proactivity）是一种独立能力*，当前智能体对其校准很差；且这些研究只覆盖智能体到用户方向，没有提供用户连续可用的查询/指导接口。
- **整体含义**：论文提出一个**始终在线的注意力协调层（Jarvis）**——类似钢铁侠中的AI助手——来调解用户与一个或多个工作智能体之间的双向交互，分配稀缺的人类注意力，并构建相应基准 JarvisBench 来评估这一协调能力的两个方向。

## 2. 论文提出的方法论

### 2.1 Jarvis 协调层的核心设计
- **三层角色分离**：
  - **用户**：拥有意图、偏好、权威、私有上下文和接受判断；在受控评估中由带冻结任务特定用户画像的 LLM 模拟。
  - **Jarvis**：始终可用的中间协调层，观察有界任务事件（bounded task events），将用户指引传递给相关智能体；**不解决任务、不使用工作智能体的工具、不替代其计划**。
  - **工作智能体**（一个或多个）：执行任务，其底层执行循环（OpenClaw harness、提示词、工具、环境）完全保持冻结不变。
- **事件驱动的协作协议**：Jarvis 作为外部旁路（sidecar）通过任务事件和注意力请求与智能体运行时通信，无需修改执行循环，因此可推广到任意智能体运行时。

### 2.2 干预机制
- 当需要用户判断时，Jarvis 在**动作边界（action boundary）**暂停工作智能体，取消待处理动作，向用户提出一个**聚焦问题**。
- 将用户简短回答以**受限软指导（scoped soft guidance）**形式注入，然后继续执行，不丢弃已完成的工作。
- 采用轻量级干预策略：允许有用干预，但抑制不必要请求（避免过度打扰）。

### 2.3 JarvisBench 基准组成
- **45 个任务实例**：
  - **20 个单智能体任务**：横跨 15 个领域，覆盖 7 种注意力需求形式（潜在上下文揭示、授权边界、异常升级、工件审查、专家引导、风险决策、轨迹修复）。
  - **10 个多智能体项目（25 个工作流）**：5 个 2 工作流、5 个 3 工作流；各工作流耦合共享同一最终成果，协作中涌现项目级决策。
- **任务筛选流程**：审计 69 个现有智能体基准、对其中 12 个做逐任务评审，产生 2,038 个候选任务，最终按四条准则筛选（初始请求信息充分、决策在检查状态后才具体化、缺失信息属于用户拥有、单次干预可实质性改善结果）。
- **关键特性**：注意力需求在执行过程中**自然涌现**，而非初始提示中人为遗漏约束或字段。

### 2.4 评估指标与公式
- **任务结果得分（Task Outcome Score）**：每个任务定义冻结的加权检查点集合：
  \[
  S_i = 100 \sum_j w_{ij} c_{ij}
  \]
  其中 \( c_{ij} \in [0,1] \) 为第 j 个检查点得分，\( \sum_j w_{ij} = 1 \)。覆盖客观执行、用户决策对齐、交付物质量、安全性四个类别。
- **智能体协作轨道（Agent-Collaboration Track）**：报告 worker-only 均值 \(\bar{S}_{base}\)、带 Jarvis 均值 \(\bar{S}_{Jarvis}\)、平均注意力请求数 \(\bar{N}_{req}\)。**注意力效率（Attention Efficiency）**定义：
  \[
  Eff. = \frac{\bar{S}_{Jarvis} - \bar{S}_{base}}{100 \cdot \bar{N}_{req}}
  \]
  （每次请求产生的平均分数增益占满分比例）。
- **用户交互轨道（User-Interaction Track）**：通过**因果回放（causal replay）**协议，在 25% 和 75% 执行点各提出一个固定的 General 问题，由另一个 LLM 模型根据可见对话生成一个自然口语 Follow-up 问题；所有回答由独立评估器按 0/1/2 三级打分，0 分含重要事实错误、未来/私人信息泄漏等。

## 6. 论文的主要结论与发现

- **Jarvis 有效且跨模型泛化**：在不修改任何 worker harness 的情况下，Jarvis 改善了每个可完成的 worker 配置：单智能体任务增益 4.9–24.7 分，多智能体任务增益 12.5–28.2 分。
- **增益幅度高度依赖具体 worker 和 Jarvis LLM**：说明 Jarvis 不是被动消息路由器，它必须理解进行中的工作、识别人类判断何时重要，并转化为有效干预。
- **GPT-5.6-Sol 是最强默认 Jarvis**：在任务结果增益和最终得分上均为最优（单智能体 +24.1、多智能体 +28.2），且用户交互总分为最高（96.3）。
- **注意效率存在不同权衡**：DeepSeek V4-Pro 在固定 worker 为 Claude Opus 4.8 的多智能体任务上以 0.30 次请求/任务实现了 0.41 的效率，说明小增益可能更"注意高效"。
- **干预强度是开放问题**：没有唯一最优干预策略；任务质量、响应时间与人类注意力之间的价值取舍是可配置的。
- **分离执行与协调是可行且有价值的架构范式**：为长期改进中稳定的评测目标。

## 7. 优点

- **问题新颖且重要**：首次系统性地提出了双向注意力协调问题并构建评测基准，填补该方向空白；在商业产品（OpenAI Codex、Qoder）已出现类似功能但无对应评测的前提下尤其有价值。
- **架构优雅**：Jarvis 以外部 sidecar 形式接入 worker，不侵入执行循环，天然可集成任意 agent 运行时，评测协议与 worker 能力解耦，具有长期稳定性。
- **任务设计精心**：注意力需求在任务执行中自然涌现，避免"初始提示故意遗漏"的人造感；每种任务均验证了单次干预可以实质性改善结果。
- **双向评测体系完备**：Agent-Collaboration Track 关注结果质量与注意力效率，User-Interaction Track 关注用户体感；因果回放协议令用户交互评测不需要重跑 worker，成本可及且公平可复现。
- **诚实呈现权衡**：引入注意力效率指标并明确暴露任务质量-注意力成本-延迟之间的三重权衡，而非简单给出总分。
- **提供真实可运行参考实现**：含全双工语音交互、打断机制、模块化转向控制等工程细节，利于社区复现与扩展。

## 8. 不足与局限

- **实验覆盖有限**：
  - 未报告重复运行和方差，结论基于单次执行分数，统计显著性存疑。
  - GPT-5.6-Sol 作为 worker 的多智能体结果缺失，表 1 关键配置不完整。
  - 缺少消融实验（如取消事件观测、随机干预位置、不同注入策略）来归因增益来源。
- **评估者偏差风险**：用户角色由同一家族模型（GPT-5.6-Sol/Luna）模拟和打分，评估器与 Jarvis 可能共享同源偏见；对"来自未来或私人信息泄漏"的判定存在主观性。
- **模型本体虚构/时效性问题**：论文涉及的模型如 GPT-5.6-Sol、Claude Opus 5.0、Qwen235B 等属于未来发布型号，目前无法独立复现实验，可验证性存疑。
- **基线条件极端化**：worker-only 对照中用户完全不可用，忽略了真实世界中用户偶尔查看或不完整响应的中间情况，可能高估 Jarvis 增益。
- **干预策略固定且粗糙**：忽略用户响应质量差异（把任何响应当作有效指导）；没有基于任务置信度动态调节是否请求。
- **应用限制**：目前只针对"单次简洁干预能显著改善结果"的任务；对需要密集交互、长对话式协作或私有状态频繁变化的场景缺乏覆盖。
- **未报告完整算力与运行成本**：注意力协调层带来的延迟和 API 成本对真实部署可行性的影响未加讨论。
