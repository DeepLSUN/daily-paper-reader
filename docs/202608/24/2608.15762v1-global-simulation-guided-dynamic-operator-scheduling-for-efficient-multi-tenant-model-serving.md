## 摘要
容器粒度的调度会留下容器内大量短暂空闲的碎片化资源未被利用。在SLA约束下，重新分配容器过于笨重，难以利用这种细粒度的机会，而算子级调度则需要实时推理依赖关系、内存安全以及集群范围的执行动态。本文提出了SliceScheduler，一个面向多租户模型服务的动态算子级调度系统。其关键思想是暴露集群范围的算子执行状态，并支持对调度决策进行假设推理。SliceScheduler由四个关键组件组成。首先，我们引入了全局映射图（GMG），这是一种统一抽象，捕获算子依赖、张量形状、资源映射和执行状态，提供具有明确资源语义的实时集群范围视图。其次，我们在GMG之上构建了一个全局模拟器，用于预测候选放置方案下的算子级执行和内存演化。第三，我们设计了一个基于模拟的增量调度模块，选择放置方案以利用碎片化的空闲资源，同时避免内存违规并保持SLA。最后，我们开发了一个算子执行器，在GPU上实现调度决策，并协调计算与跨加速器传输。我们将SliceScheduler实现为PyTorch后端，并使用生产轨迹回放进行评估。实验结果表明，与现有方法相比，SliceScheduler将令牌吞吐量提高了1.10--2.29倍，同时将SLA违规率保持在9%以内。SliceScheduler证明了算子级调度是提高多租户LLM服务GPU利用率的实用且有效的方法。

## Abstract
Container-granularity scheduling leaves abundant short-lived idle slices within containers unexploited. Reallocating containers is too heavyweight to utilize such fine-grained opportunities under SLA constraints, and operator-level scheduling requires reasoning about dependencies, memory safety, and cluster-wide execution dynamics in real time.   In this paper, we present SliceScheduler, a dynamic operator-level scheduling system for multi-tenant model serving. The key idea is to expose cluster-wide operator execution state and enable what-if reasoning over scheduling decisions. SliceScheduler consists of four key components. First, we introduce the Global Mapping Graph (GMG), a unified abstraction that captures operator dependencies, tensor shapes, resource mappings, and execution states, providing a real-time, cluster-wide view with explicit resource semantics. Second, we build a global simulator on top of GMG to predict operator-level execution and memory evolution under candidate placements. Third, we design an incremental, simulation-based scheduling module that selects placements to exploit fragmented idle slices while avoiding memory violations and preserving SLA. Finally, we develop an operator executor that materializes scheduling decisions on GPUs and coordinates computation and cross-accelerator transfers. We implement SliceScheduler as a PyTorch backend and evaluate it using production trace replay. Experimental results show that SliceScheduler improves token throughput by 1.10--2.29$\times$ compared to existing approaches, while maintaining SLA violations within 9\%. SliceScheduler demonstrates that operator-level scheduling is a practical and effective approach to improving GPU utilization for multi-tenant LLM serving.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：现代多租户 LLM 推理服务集群中，GPU 资源利用率普遍偏低。生产轨迹分析显示，容器内部存在大量**毫秒至秒级的短命空闲切片（idle slices）**（p50≈2.55s，p90≈10.89s，p99≈17.79s），这些细粒度资源碎片在聚合规模上相当可观（平均 GPU 利用率仅约 64%）。
- **现有方案的根本矛盾**：
  - **容器级调度**（如 Kubernetes）虽能管理 GPU 分配，但只控制部署层面，无法直接操控 GPU 执行过程。重新调度涉及 checkpoint、冷启动、状态恢复等分钟级开销，完全无法匹配秒级空闲切片的利用需求。
  - **GPU 共享方案**（MPS、MIG 等）多局限于单卡或固定 GPU 子集，能实现静态空间划分，但无法捕获跨 GPU、跨容器、时间上不同步的碎片化空闲切片。
- **算子级调度的挑战**：将调度粒度下沉到算子（如 kernel、ATen op、LLM layer）后，需要解决三个核心难题——① 算子资源需求（显存占用）建模不足会导致 OOM；② 缺乏时间维度的执行演化预测能力，静态算子-资源映射效果有限；③ 缺少集群范围统一状态抽象以支撑实时调度推理。
- **整体含义**：论文主张突破容器边界，以**算子**为最小调度单元，通过全局仿真驱动的调度决策，实现低优先级算子对高优先级服务空闲片段的动态填充，从而在不违反 SLA 的前提下系统性提升多租户 LLM 服务的 GPU 利用效率。

## 2. 论文提出的方法论

### 2.1 核心思想

SliceScheduler 的关键理念是：**暴露集群范围的算子级执行状态，并支撑对调度决策的"假设推理"（what-if reasoning）**。通过全局模拟器在真实执行前评估候选放置方案的效果，以此实现安全、高效、SLA 感知的算子调度。

### 2.2 四大核心组件

- **全局映射图（GMG, Global Mapping Graph）**
  - 统一抽象：融合 Shape DAG（算子依赖 + 张量形状 + 执行器状态）与 Accelerator Set（资源映射）。
  - 生命周期管理：图模板"一次注册、多次实例化"；算子状态流经 unscheduled → issued → done。
  - 调度元数据：算子执行时间估计器、全局时间戳（下发时间/完成时间）、输出张量形状、检查点元数据（中间结果持久化位置），为增量式调度提供支撑。
  - 明确资源语义：每个算子携带形状信息，可推断出执行时间和 HBM 占用，从根源上保障内存安全。

- **全局模拟器（Global Simulator）**
  - **估计器设计**：采用轻量级线性回归模型——
    - 传输时延：$t = \alpha \cdot size + c$（$\alpha$ 为有效带宽倒数，$c$ 为固定开销）。
    - 算子执行时间：以 BMM 算子为例，$t = \beta_1(bmnk) + \beta_2(bmk) + \beta_3(bkn) + \beta_4(bmn) + \beta_5$，覆盖计算量（$bmnk$）、输入规模（$bmk, bkn$）、输出规模（$bmn$）及常数开销。
  - 模拟器构建：GMG 快照可等价还原各加速器的队列内容、执行状态与 HBM 占用。
  - 事件驱动推进：按最早完成事件逐级推进，级联触发后续算子启动与内存演化，输出集群级执行时间线和 HBM 使用变化曲线。

- **增量仿真调度模块（Scheduling Module）**
  - 维护两个边界集合：**scheduled frontier**（已有调度且含未调度后继的算子）与**unscheduled frontier**（所有前驱已完成调度的待调度算子）。
  - 调度流程（Algorithm 1）：批收集（沿高优先级算子收集连通算子子图，受 issued 算子预算限制）→ 并行 what-if 模拟（克隆 GMG → 应用到候选放置 → 构建模拟器 → 丢弃 OOM 方案）→ 选择模拟平均算子完成时间最小的 placement。
  - 内置的调度偏好：跨加速器传输会被显式计入模拟时间线，因此天然倾向数据本地性；高优先级算子优先被收集，保护 SLA；负载不均的放置会在模拟中暴露，实现自动负载均衡。

- **算子执行器（Operator Executor）**
  - 每加速器维护一个依赖驱动的本地算子队列：算子按数据依赖（而非下发顺序）就绪执行，每队列同时只执行一个算子。
  - 跨加速器张量传输仲裁：每个传输分解为 Intent → Recv → Send 三步；主节点维护通信图，在事件驱动（新 Intent 或传输完成）时选择一个无冲突传输集合，**强制 Recv-before-Send 顺序**以避免死锁和接收缓冲分配失败问题。

## 6. 论文的主要结论与发现

- **吞吐量显著提升**：相比所有基线，请求吞吐提升 9%–129%，Token 吞吐提升 10%–129%，GPU 利用率提升 17%–38%；相比 Full-Share，请求吞吐提升 49%。

- **系统开销可忽略**：SliceScheduler 与 Direct Execution 执行时间几乎一致（相对开销 0.0%），且比 Eager Execution 快 8%。

- **可行性边界**：在算子粒度 $g=10.575$ ms、预测视界 $l=3$、及时性 $t=0.1$ 的设定下，SliceScheduler 可扩展至约 64 个 GPU 的中小型集群。

## 7. 优点

- **问题定位精准**：以真实生产轨迹量化容器内空闲切片的规模与分布特征，动机扎实充分。
- **系统设计完整闭环**：从全局状态抽象（GMG）→ 行为预测（模拟器）→ 决策（增量调度）→ 执行（算子执行器及传输仲裁）→ 反馈（估计器在线更新），形成闭环，工程完成度高。
- **创新性的"仿真即调度"范式**：将 what-if 模拟引入在线调度路径，在真实部署前评估候选方案，同时规避 OOM 与 SLA 风险，设计理念新颖。
- **记忆安全与依赖关系统一建模**：GMG 对形状信息的显式建模从根源上解决算子级调度的内存安全问题，优于传统仅考虑依赖关系的图调度方案。
- **实用主义设计**：通过粗粒度算子（合并层）、小批增量调度、轻量线性估计器和并行模拟等机制控制调度开销，证明了算子级调度在实际系统中切实可行。
- **快速仿真器**：刻意减少流量细粒度调度模拟以换取约 10⁴ 倍的仿真吞吐提升，在调度场景中作出了合理的复杂度取舍。

## 8. 不足与局限

- **实验规模有限**：仅在 8-GPU 单机验证，缺少跨服务器、数百 GPU 大规模集群下的调度性能与通信瓶颈实测。可扩展性结论源于理论推导，而非实证。
- **工作负载类型较窄**：主要针对 Llama3-8B 这一单一模型架构，未覆盖 MoE、长上下文、多模型混合等现代 LLM 服务场景；离线负载采用固定请求速率和形状，多样性有限。
- **离线负载假设偏理想**：离线推理请求 1 req/s、固定输入 2048 / 输出 15 tokens，与真实异步离线批处理负载的多样性存在差异，可能高估碎片利用效果。
- **模拟器复杂度取舍**：全局模拟器忽略细粒度流量调度，虽然换来了吞吐优势，但在拓扑复杂或通信密集型场景下的精度值得存疑。
- **基线自实现风险**：对比的 GPU 共享等方法均为作者自行实现，可能与原始系统行为有偏差；缺少与生产级容器调度系统（如 Kubernetes + KServe）的直接实测对照。
- **算子合并策略未消融**：合并 8 层为一个调度算子的设定缺少敏感性分析，不同粒度对调度性能和 SLA 的影响未被充分讨论。
- **单主节点瓶颈**：集中式 master（GMG 维护、模拟调度、传输仲裁）在 64 GPU 以上规模可能成为性能瓶颈，论文对此仅给出建议性结论而无替代方案。
