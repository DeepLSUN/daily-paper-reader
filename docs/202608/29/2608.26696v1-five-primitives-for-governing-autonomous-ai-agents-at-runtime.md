## 摘要
企业级自主AI代理的部署继承了一种为人类用户和长期服务构建的控制模型，但这种适配在三个方面具体失败：代理主体是短暂的，出现和消失的速度快于配置；它们的行动是由模型而非编程选择的，因此它们可能尝试的行为集合无法预先知晓；并且代理群体是发现而非配置的，因为任何能调用API的人都可以创建一个。我们认为，治理这类代理是一个运行时问题——不是模型对齐问题，也不是构建时问题——我们从行动生效前和生效后必须回答的问题中推导出五个原语：发现、身份、治理、证明和供应链。对于每一个原语，我们说明如果缺失会导致什么失败，以及为什么其他原语无法在结构上替代它。我们描述了一个实现，其中代理的行动在生效前根据策略进行调解，根据每个租户的操作词汇表进行授权，并记录在一个哈希链接的签名账本中，第三方可以在供应商不参与的情况下验证。我们报告了该架构的代价：强制点位于请求的关键路径上，身份机制需要每个工作负载一个边车（sidecar），以及故障关闭（fail-closed）的调解将可用性事件转化为拒绝服务。我们明确说明实现状态：四个原语已构建并在私人试点中运行，第五个原语作为单独的工具构建，尚未集成到请求路径中。我们刻意将其保留在集合中：一个恰好与其作者所构建的内容相匹配的五部分分解，不是分类法，而是代码库的描述。

## Abstract
Enterprise deployments of autonomous AI agents inherit a control model built for human users and long-lived services, and the fit fails in three specific ways: agent principals are ephemeral, appearing and vanishing faster than provisioning; their actions are selected by a model rather than programmed, so the set of things they may attempt is not known in advance; and the population is discovered rather than provisioned, because anyone who can call an API can create one. We argue that governing such agents is a runtime problem -- not a model-alignment problem and not a build-time problem -- and we derive five primitives from the questions that must be answered before an action takes effect and after it has: discovery, identity, governance, attestation, and supply chain. For each we state what fails if it is absent and why the others cannot structurally supply it. We describe an implementation in which an agent's action is mediated against policy before it takes effect, authorised against a per-tenant action vocabulary, and recorded in a hash-linked signed ledger a third party can verify with the vendor out of the loop. We report what the architecture costs: the enforcement point sits on the request's critical path, identity requires a sidecar per workload, and fail-closed mediation converts availability incidents into denial. We are explicit about implementation status: four primitives are built and running in private pilots, and the fifth is built as separate tooling and not yet integrated into the request path. We keep it in the set deliberately: a five-part decomposition that exactly matches what its authors happened to build is not a taxonomy but a description of a codebase.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究背景**：企业部署自主 AI 代理（autonomous AI agents）时，沿用了为人类用户和长期运行服务设计的控制模型（身份提供者、RBAC、API 网关、审计日志等）。但代理与人类/服务主体有本质差异，导致现有控制机制在三个关键维度上失效：
  - **主体短暂性（ephemeral）**：代理实例可能只为一个任务而存在，出现和消失快于传统的人为配置流程。
  - **行为不可预知性（model-selected actions）**：代理的行动由模型在运行时从工具集中选择并组合参数，策略编写时无法预先枚举其可能尝试的操作。
  - **群体可发现性（discovered, not provisioned）**：任何能调用 API 的人都能创建代理，企业内部的代理群体无法通过人工维护清单来管理。
- **核心主张**：治理自主 AI 代理本质上是一个**运行时问题**，既不是模型对齐问题，也不是构建时静态分析问题。论文据此提出五项运行时治理原语，并给出一个具体实现架构。
- **整体含义**：该工作将智能体治理从“让模型更安全”或“在代码中预埋约束”重新定义为“在行动生效前后对运行时行为进行强制、授权和可验证记录”的工程问题，为企业级代理治理提供了新的分解方式和可落地参考。

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

### 2.1 核心思想：五项原语的推导
论文从单个代理行动（如支付、发邮件、写记录）生效前和生效后必须回答的问题出发，推导出五个不可约减的原语：

1. **Discovery（发现）**：这个代理是否存在，我们是否知道它？——解决“未自我上报的代理不可被治理”的问题。
2. **Identity（身份）**：它是什么，可证明吗？——为策略决策提供可靠主体，而非仅凭头部断言。
3. **Governance（治理）**：它被允许这样做吗，且在行动前决定？——授权决定必须先于行动效果，否则只是报告。
4. **Attestation（证明）**：发生了什么，且以他人可验证的形式记录？——提供独立于治理层自身的可验证证据。
5. **Supply chain（供应链）**：它由什么构成，是否发生了变化？——在请求路径之外，条件化其他所有原语的可信度。

论文论证了每项原语的必要性：缺少任何一个，剩余四个都无法从结构上弥补。例如，身份能验证主动上前的代理，但无法发现从不现身的代理；治理能决策，但无法自证其决策可靠；供应链关切的是代理的“构成”，而非其“行为”，与其他原语正交。

### 2.2 关键技术细节
- **架构形态**：
  - 代理通过边车（sidecar）获取基于 attestation 的工作负载身份（如 SPIFFE），通过 mTLS 调用统一的授权端点：`POST /v1/actions/authorize`。
  - 管理服务器包含：**调解器（mediator）**（策略评估与动作目录）、**证明工厂（attestation factory）**与后台验证器；后端使用关系数据库存储哈希链，密钥管理服务保管租户签名密钥（永不可导出）。
- **每个原语的实现要点**：
  - **Discovery**：采用“聚合而非追加”的存储（每组织每动作类型一行，upsert），只存参数名不存值，且记录失败不得影响授权结果——发现是观测而非治理。
  - **Identity**：使用 attestation-based workload identity，凭据分钟级过期；身份在传输层绑定，而非在 payload 中由代理自行声明；支持一个主体在存储、审计信封、策略实体间使用不同的词汇表，通过规范映射保证可追溯。
  - **Governance**：动作词汇表（action vocabulary）为**每租户、客户自定义**，而非供应商固定枚举，以适配代理不可预知的行动集；默认拒绝（deny-by-default）确保未注册动作被视为不可治理但可记录；提供逐请求查询的**kill switch**，实现对运行中代理的快速停止。
  - **Attestation**：每个授权决策写入追加式账本，行与前任哈希链接、规范化后由租户私钥签名；验证器必须运行在**供应商系统之外**，客户可独立导出证据包验证；导出时需明确记录窗口与完整性，完整性未知时默认为 false。
  - **Supply chain**：论文承认该原语尚未集成到控制面，但坚持保留——因为代理的构成包含模型、提示模板、工具描述等传统供应链工具不覆盖的元素，且其变化可在部署后随时发生，而其他四个原语无法回答“被治理的代理是否仍是操作者所相信的那个代理”这一问题。

### 2.3 算法/流程描述（文字说明）
- **单动作端到端流程（见附录 A）**：
  1. 代理 Pod 启动，边车从身份平面获取短时工作负载凭证；
  2. 模型选择 `send_email` 并组合参数（收件人、主题、正文）；
  3. 代理经 mTLS 调用授权端点，调解器基于连接层证明的身份和租户策略（Cedar）评估动作及属性，同时检查 kill switch 状态；
  4a. 若动作类型未知：默认拒绝；同时记录一条聚合的、仅含参数名的发现记录，供操作者定义新动作；
  4b. 若动作类型已知：返回允许/拒绝决定，代理据此执行或不执行；
  5. 每个决定被写入哈希链签名账本，后台验证器定期重验；
  6. 客户导出证据包，用独立验证器离线验证，供应商不参与。

## 6. 论文的主要结论与发现

1. **代理治理应被视为运行时问题**：基于对齐或静态构建的分析无法约束模型在运行时选择的行动和参数，必须在行动生效前与生效后进行干预。
2. **五个原语是必要且不可相互替代的**：发现、身份、治理、证明、供应链各自处理不同信任模型、失败模式和时间尺度；合并它们会继承各自最坏的失败模式。
3. **动作词汇表必须由租户定义并支持运行时扩展**：供应商无法枚举代理的所有行动，未知动作的“拒绝即发现”机制使策略能追赶现实。
4. **验证必须脱离供应商系统**：证明原语的价值取决于外部验证者能否独立运行；否认这一点会使审计沦为自证。
5. **自我治理是可行的且重要的**：控制平面自身的内部代理也经过同一套身份、调解、kill switch 和证明路径，且内部动作通过传输层身份检查而非仅靠命名空间隔离。
6. **架构有明确代价**：请求关键路径延迟、每工作负载 sidecar、fail-closed 将可用性事故转为拒绝服务、集成成本前高后低；但当动作集开放、群体不可枚举、或有第三方需要被说服时，这种代价是值得的。
7. **诚实的状态边界**：论文只声称分解有效、四项已实现，而不断言测量结果或五原语的充分性。
