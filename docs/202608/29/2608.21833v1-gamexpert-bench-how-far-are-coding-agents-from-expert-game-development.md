## 摘要
近期的大型语言模型（LLMs）能够作为编码智能体，根据自然语言请求构建完整的游戏。游戏开发尤为苛刻，因为程序逻辑、视觉和音频内容、界面、交互和可玩性必须在一个可执行的产物中协同工作。因此，衡量这一能力需要同时评估游戏产品和开发过程。现有基准通常通过评估最终产物或孤立的开发阶段来评估LLM的游戏开发能力。我们对完整的人机协同开发轨迹的分析识别出三个阶段，它们共同涵盖了使用编码智能体的游戏开发生命周期：初始游戏生成、缺陷诊断与修复，以及多轮优化。因此，我们引入了GameXpert-Bench，将这三个生命周期阶段具体化为三个互补的基准轨道。GameGen评估在空白工作区中根据单个请求创建完整游戏的能力。GameFix评估在报告缺陷或留给智能体自行发现缺陷时的诊断与修复能力。GameOpt通过由用户与智能体之间的真实开发轨迹衍生的请求链来评估累积优化能力。我们使用实时游戏交互、确定性行为测试或带回归检查的最终产品标准来评估每个轨道。该套件包含11种类型的97个生成任务；由人工验证的50个游戏关卡中的100个修复任务，每个关卡注入19-27个缺陷；以及17个优化链，包含6轮和102个请求。在三个轨道中，当前的智能体在生成可玩的基础版本和实现明确需求方面更为可靠，而在发现缺陷、验证运行时行为以及跨变更保持功能方面则较弱。

## Abstract
Recent large language models (LLMs) can operate as coding agents that build complete games from natural language requests. Game development is especially demanding because program logic, visual and audio content, interfaces, interaction and playability must function together in one executable artifact. Measuring this capability therefore requires evaluation of both game product and the development process. Existing benchmarks often assess the game development capabilities of LLMs by evaluating the final artifact or an isolated development stage. Our analysis of complete human-agent development trajectories identifies three stages that together span the lifecycle of game development with a coding agent: initial game generation, bug diagnosis and repair, and optimization over multiple turns. Therefore, we introduce GameXpert-Bench, which operationalizes the three lifecycle stages as three complementary benchmark tracks. GameGen evaluates complete game creation from a single request in an empty workspace. GameFix evaluates diagnosis and repair when defects are reported or left for the agent to discover. GameOpt evaluates cumulative optimization through request chains seeded by real development trajectories between users and agents. We evaluate each track using live game interaction, deterministic behavioral tests, or final product criteria with regression checks. The suite contains 97 generation tasks across 11 genres; 100 repair tasks from 50 game levels verified by humans, each with 19-27 injected bugs; and 17 optimization chains with six turns and 102 requests. Across the three tracks, current agents are more reliable at producing playable foundations and implementing explicit requirements than at discovering defects, verifying runtime behavior, and preserving functionality across changes.

## 2. 方法论：GameXpert-Bench

### 2.1 生命周期定义

通过对完整历史开发轨迹的迭代编码分析（排除环境设置等操作性交互），论文识别出三个重复出现的开发阶段，共同构成"完整用户侧编码智能体游戏开发生命周期"：

```
生成（Generation）→ 修复（Fix）→ 优化（Optimization）
```

- **生成**：从用户请求创建初始可玩游戏
- **修复**：诊断并修复生成或已有游戏中暴露的缺陷
- **优化**：通过连续请求改进游戏，同时保持既有功能

### 2.2 三个基准轨道

该基准将上述三个阶段实例化为三个互补的评测轨道：

### 2.3 关键技术细节

- **GameGen 混合自动化评分**：评估智能体先对全部模型生成的代码进行静态分析定位实现，再通过实时交互注入运行时状态、触发事件并验证行为。一项检查仅在**运行时行为与意图匹配**时计分，防止"代码看似存在但功能不生效"的误判。四个维度（完整性、丰富性、视觉质量、玩家体验）等权平均，总分公式为：`S_overall = (S_comp + S_rich + S_exp + S_vis) / 4`。

## 6. 主要结论与发现

1. **核心不对称**：当前智能体在**生成可玩基础**和**实现显式需求**方面表现可靠，但在**自主发现缺陷、验证运行时行为、跨改动保持功能一致性**方面明显不足。初始生成质量不足以表征智能体的完整游戏开发能力。
2. **GameGen 发现**：

3. **GameFix 发现**：
   - 基准远未饱和：最强模型 STRICT 仅39.0/100，中位数约14
   - 模型在**自我发现**模式下区分显著（跨度约38分），显式问题模式几乎饱和（跨度约13分）
   - **Cliff 随模型增强而缩小**：Opus 5 的 Cliff 为7.6，Hy3 高达32.8
   - 两大机制解释 Cliff：**发现不足**（弱模型找不到未提示的缺陷）与**修复授权**（模型把清单当作边界，拒绝修复未列项）
   - 识别出六种智能体能力轴：自我发现、行为验证、数值恢复、多缺陷覆盖与规划、回归控制、停止准则
4. **GameOpt 发现**：
   - Claude-Opus-5 第一（93.96），但维度分布极不均匀（平衡80.8 vs 美术100.0）
   - **数值平衡**（平均66.11）与**关卡设计**（66.36）是最弱维度，音频最强（81.97）
   - 模型性能随轮次呈**非单调变化**（各模型最弱点在2/3/4轮），不能简单解读为长上下文衰减
   - 案例研究（kimi-K3 vs MiniMax-M3）说明：局部合理的编辑若缺少端到端集成，可导致整页空白、所有请求维度全部失效

## 7. 优点与亮点

- **全生命周期覆盖**：首次将生成、修复、优化统一于一个评测框架，超越了以往孤立评估各阶段的做法，且生命周期来源于真实人机协作轨迹的实证归纳而非臆造
- **执行落地（Execution-Grounded）评分**：所有轨道均以可执行游戏的行为证据为准，而非静态代码检查；例如 GameFix 的确定性探针无 LLM 偏见、完全可复现
- **抗污染设计**：使用内部专有游戏（无公开来源）降低预训练记忆效应；可逆突变与黄金补丁提供精确真值
- **回归意识**：F2P/P2P 分离与 GameOpt 的回归检查使得"修复A不破坏B"成为评分核心，避免只奖励局部修不奖励全局稳定
- **防交叉缺陷污染门控**：GameFix 在编写测试时逐缺陷验证"黄金全绿/基座全红/单缺陷独立变红/P2P在合并基座下保持绿色"，排除了邻居缺陷造成误判的可能
- **丰富的数据与分析层次**：事件级、模型级、游戏级、维度级、轨迹级多层次报告，并包含2D/3D分解与人工–自动评分关联性验证
- **难度倾斜加权**（GameOpt 使用 `p(1−p)²`）防止高分饱和，提升模型区分度
- **框架效应控制**：同一模型在 Claude Code 与 Codex 两种框架下对比，分离框架影响与模型固有行为

## 8. 不足与局限

- **封闭集无法公开复现**：GameFix 的50个黄金游戏为专有内部游戏，出于保密与抗污染考量不对外发布，外部研究者无法直接复现核心修复任务
- **轮次与内容混淆**：GameOpt 中音频恒为第6轮、平衡集中在第3轮、美术集中在第4轮，位置与维度效应无法完全分离，作者自身也承认需要更长且平衡的轨迹来隔离影响因素
- **人工评估的主观性与成本**：视觉质量、玩家体验以及部分 GameOpt 的"代理指标"（如视觉一致性、游戏手感）依赖人工判断，虽与自动评分高度相关（r=0.898），但随模型版本迭代大规模重复标注的成本很高
- **多缺陷任务与真实场景有一定距离**：同时注入19–27个缺陷并非现实典型（作者解释是测试长程智能体行为的刻意设计，但确实影响了生态效度）
- **智能体框架与研究时点风险**：评估在特定代理框架（Claude Code/Codex）与特定模型 API 版本下进行，模型迭代或框架更新可能使分数快速过时；文中引用的模型版本（如 GPT-5.6、Claude Opus 5）具有很强的时点性
- **"已实现但失败"的比例仍有相当数量**：即便最强模型也有约0.9%的事件属于代码存在但运行失败，说明即使最先进模型在端到端集成上仍不完美，评估协议本身也可能存在判别边界问题
- **未披露算力成本**：缺少对评测总计算开销的估算，限制了社区对其资源可及性的判断
