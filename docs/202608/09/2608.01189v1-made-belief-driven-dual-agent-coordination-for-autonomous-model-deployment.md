## 摘要
基于大语言模型的智能体现已具备强大的通用能力。然而，它们在处理特定领域任务时仍显不足，这推动了集成外部工具以扩展其能力的需求。开源社区提供了大量AI模型，通常以异构研究产物的形式发布，而将其转化为可直接调用的API成本高昂且劳动密集。因此，自动化模型部署对于弥合模型资源与工具可用性之间的鸿沟至关重要，但它仍是一项尚未得到充分探索的长期、多阶段任务。为应对这一挑战，我们提出了模型自动部署引擎（MADE），一种双智能体协同系统。具体而言，给定一个模型资源，MADE迭代地构建并验证部署产物，基于执行反馈更新其部署信念，并重新检查无效的上游产物，直到模型成功作为可直接调用的API提供服务，供其他智能体使用。我们进一步引入了M2ABench，一个用于将模型转化为可直接调用API任务的基准。M2ABench包含122个真实世界模型，并配有标准化测试用例用于评估。实验结果表明，MADE实现了68.85%的部署成功率，分别比SWE-agent和OpenHands高出13.93和44.26个百分点。我们的代码和数据集公开于https://github.com/HITDiSC/MADE。

## Abstract
LLM-based agents now have strong general capabilities. However, they still struggle with domain-specific tasks, motivating the integration of external tools to broaden their capabilities. The open-source community offers a vast array of AI models typically released as heterogeneous research artifacts, whereas transforming them into ready-to-call APIs is costly and labor-intensive. Automated model deployment is therefore essential for bridging the gap between model resources and tool usability, yet it remains a long-horizon, multi-stage task that has not been sufficiently explored. To tackle this challenge, we introduce Model Automated Deployment Engine (MADE), a dual-agent coordination system. Specifically, given a model resource, MADE iteratively constructs and validates the deployment artifacts, updates its deployment belief based on execution feedback, and revisits invalid upstream artifacts until the model is successfully served as a ready-to-call API that can then be used by other agents. We further introduce M2ABench, a benchmark for the task of transforming Models to ready-to-call APIs. M2ABench comprises 122 real-world models with standardized test cases for evaluation. Experimental results demonstrate that MADE achieves a deployment success rate of 68.85%, outperforming SWE-agent and OpenHands by 13.93 and 44.26 percentage points, respectively. Our code and dataset are publicly available at https://github.com/HITDiSC/MADE.

## 2. 方法论：核心思想、关键技术与算法流程

### 核心思想
- **信念驱动的双智能体协同**：通过维护一个**轻量、确定性、可修正的部署信念**（belief），将协调机制从“反复LLM检查”转变为“基于状态变化驱动”，从而实现长轨迹下高效、低成本的自动化部署。

### 系统组成
- **MADE（Model Automated Deployment Engine）**：双智能体系统，包含：
  - **阶段执行者（Execution Master, EM）**：负责与代码和运行环境交互，收集第一手执行证据，执行具体动作。
  - **阶段管理者（Phase Manager, PM）**：负责全局部署状态监控，决定下一个执行阶段，并基于信念发出纠正指令。
- 两者通过共享的**制品状态信念**（artifact-state belief）和**制品存储**协调。

### 部署流水线（五阶段）
| 阶段 | 输入 | 功能 | 输出 |
|---|---|---|---|
| RepoIngest | 模型资源 | 解析仓库，识别任务 | 结构化资源（仓库布局、任务类型） |
| DockerSetup | 结构化资源、GPU配置 | 构建执行环境 | 运行中的容器E |
| WeightResolve | 结构化资源 | 定位并获取模型检查点 | 本地可用的权重WR |
| APIAdaptation | 资源、容器、权重 | 重建推理流程并暴露为服务，定义I/O契约 | 服务代码fD与契约(σin, σout) |
| APIValidation | 服务代码、契约、容器 | 启动服务、验证、修复失败 | 可调用的API A |

- 其中DockerSetup与WeightResolve在RepoIngest后并行执行。
- 所有代码运行在隔离的Docker容器中，保证依赖隔离、可复现性与宿主安全。

### 关键机制

1. **执行引导的环境修正**：通过构建Docker环境的迭代循环，根据失败反馈修正依赖配置（如适配PyTorch安装策略以解决CUDA兼容问题）。

2. **推理-契约协同生成**：APIAdaptation从模型自身推理代码重建fD，并同步生成输入/输出契约σin/σout，验证σin与预处理代码的字段访问一致性。

3. **标准引导的验证与有界修复**：APIValidation启动服务、调用评估器测试实时端点。对于局部问题直接修复；对于根因在上游的问题，上报给协调层进行跨阶段处理。

4. **非单调信念更新**：当后期失败揭示上游制品错误时，将候选根因制品加入失效集合，重新计算信念，将制品状态从`present`改为`invalidated`，并重定向执行到相应阶段重建它。

5. **一致性门控监督**：当EM提出的动作与信念冲突或进度停滞时触发干预；干预逻辑是确定性的，只有触发后才调用LLM生成纠正指令。

6. **证据支撑的仲裁**：EM可以接受、协商或拒绝PM的指令，尤其在直接执行证据与过时信念冲突时，允许第一手证据覆盖全局判断。

### 推理闭包导航
- MADE通过**递归解析静态可识别的本地导入**构建推理闭包C†，即推理入口点及其传递引用的所有本地文件。
- 整个语义决策仅花费一次LLM调用，其余步骤为确定性过程，从而减少无关代码并保留必要的本地依赖。

## 3. 实验设计

- **基准数据集**：M2ABench，首个“模型转API”基准，包含**122个真实世界开源模型**，涵盖文本（49）、图像（27）、科学结构（25）、音频（13）、多模态（8）。
- **测试用例**：每个模型配有5个人工编写的测试用例，输入/输出示例来自模型文档和训练数据。输出统一为文本形式以方便比较。
- **成功标准**：**结构一致性**（Deployment Success Rate, DSR）——端点对所有5个测试用例返回与期望输出结构（类型、嵌套、格式）一致的响应，不评估预测准确性。
- **对比方法**：
  - SWE-agent：面向仓库级问题解决的编码智能体。

## 6. 主要结论与发现

- **MADE显著优于通用编码智能体**：DSR达**68.85%**（84/122），超过SWE-agent（54.92%）13.93个百分点，超过OpenHands（24.59%）44.26个百分点。
- **效率平衡**：MADE每成功部署平均消耗**1058.297k tokens**，比SWE-agent低68.68%，同时DSR更高；OpenHands token消耗略低但仍远不如MADE。
- **成本分布**：token消耗集中于APIValidation和APIAdaptation阶段，说明高成本主要由重复执行-诊断-修复循环驱动；大部分部署低于1.5M tokens，呈长尾分布，少数困难仓库消耗极高。
- **消融验证**：去掉双智能体协调后DSR降至27.87%；去掉推理闭包导航后DSR降至16.39%，说明两个组件均至关重要。
- **失败根源**：**权重缺失/不可解析**占所有失败案例的50%，是最主要的瓶颈；其次是容器构建、导入解析、CUDA运行时等环境兼容问题；服务启动和契约不匹配占较少比例。

## 8. 不足与局限

- **实验覆盖有限**：仅与两个通用编码agent对比，未与更专门的部署工具或更新框架比较；消融实验只做两层，缺少对每个阶段机制的独立分析。
