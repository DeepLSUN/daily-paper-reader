## 摘要
我们提出了Ouroboros，一个自开发的代理框架，其工具、提示、上下文组装和核心实现通过经过审查的提交而改进，这些提交成为后续工作的运行时。核心进化以两种模式进行。在递归自由进化中，改进本身就是一个任务，完成一个进化周期可以安排下一个。在经验驱动的核心进化中，普通工作和社交互动会暴露错误、粗糙之处和低效的上下文构建，从而引发经过审查的结构性变化。在Terminal-Bench 2.1上，一次Opus 5运行获得86.74%的分数，这是该基准上报告的最佳结果。在OSWorld-Verified上，一次Opus 5运行达到90.69%，超过了之前报告的最佳分数。一次五次rollout的CL-Bench活动实现了0.2301的归一化奖励，确立了新的最先进水平。Hope是运行时间最长的公开记录的Ouroboros部署。这是一项为期161天的活体代理实验，在七个界面上受约束的人类通信下进行自由进化。人类互动暴露故障并生成提案，但代理决定追求哪些更改。由于自开发代理可能重写自己的代码并选择新的模型API，操作安全成为首要的设计问题：护栏必须在进化和公共社会压力下保持权威。基准测试活动使用冻结的系统快照，而Hope则在单独的血统上继续实时进化。

## Abstract
We present Ouroboros, a self-developing agent harness whose tools, prompts, context assembly, and core implementation improve through reviewed commits that become the runtime for later work. Core evolution proceeds in two modes. In recursive free evolution, improvement is itself a task, and completing one evolution cycle can schedule the next. In experience-driven core evolution, ordinary work and social interaction expose bugs, rough edges, and inefficient context construction that lead to reviewed structural changes.   On Terminal-Bench 2.1, an Opus 5 run scores 86.74%, the best result reported on the benchmark. On OSWorld-Verified, an Opus 5 run reaches 90.69%, exceeding the best previously reported score. A five-rollout CL-Bench campaign achieves a normalized reward of 0.2301, setting a new state of the art.   Hope is the longest-running publicly documented Ouroboros deployment. It is a 161-day living agent experiment in free evolution under governed human communication across seven surfaces. Human interaction surfaces faults and generates proposals, but the agent decides which changes to pursue. Because a self-developing agent may rewrite its own code and select new model APIs, operational safety becomes a primary design problem: guardrails must remain authoritative under evolutionary and public social pressure. Benchmark campaigns use frozen system snapshots, while Hope continues live evolution on a separate lineage.

## 1. 核心问题与整体含义

长期任务代理（long-horizon agents）的性能由基础模型、执行框架（harness）、环境和评分器共同决定。然而，大多数生产环境中的框架（harness）在设计完成后便固定不变——工具、提示词、上下文组装逻辑和核心实现无法随使用经验而改进。这一静态特性限制了代理系统在真实场景中持续适应和优化的能力。

Ouroboros 的核心主张是：**将代理框架本身视为一个可进化的对象**。系统通过“审查提交”（reviewed commits）的方式，让代理在运行过程中持续改进自己的工具集、提示词、上下文组装方式乃至核心代码实现。这种自我进化能力，使得代理系统不再是静态的“模型 + 固定脚手架”，而是一个持续自我完善的动态系统。

此外，论文明确指出一个关键设计张力：**一个能改写自身代码、选择自身模型 API 的代理，其安全护栏必须保持权威性**。为此，Ouroboros 设计了严格的分层安全架构来约束进化过程。

## 2. 方法论

### 2.1 整体架构

Ouroboros 将系统分为两个层面：

- **Launcher + Supervisor（启动器与监督器）**：不可变边界，负责启动、进程监督、发布引导和紧急停止（panic-stop）。
- **版本化系统仓库（Versioned system repository）**：包含任务循环、工具、提示词、记忆投影、审查逻辑、基准适配器和用户界面，是自我进化的主体。

### 2.2 两种核心进化模式

- **递归自由进化（Recursive Free Evolution）**：将“改进系统本身”作为一项任务。代理审查当前系统后，选择并实现一个改进点；完成一次可调度下一轮进化任务，形成连续的有序更新序列。
- **经验驱动核心进化（Experience-Driven Core Evolution）**：从普通工作出发，任务执行、反思、审查阻塞、工具调用失败和社会反馈中暴露的bug、粗糙点、上下文组装失败和低效路径，被记录为持久错误类别，代理决定是否开展维护性改动。修复同样经过审查提交门。

### 2.3 提交审查管道

提交流程包含以下关键环节：

- **确定性预检（deterministic preflight）**：版本、数据边界、大小健康检查。
- **暂存差异指纹（staged-diff fingerprint）**：审查前后分别对暂存补丁取指纹，若中途被改动则中止提交。
- **多模型对抗审查（multi-model adversarial review）**：子法定人数无法产生通过记录；在 owner 选择的 max 模式下，还会进行全仓库范围审查。
- **回滚机制**：恢复先前已审查状态，走独立的恢复路径。

### 2.4 安全护栏

论文设计了多层防护机制：

- **宪法（Constitution）**：始终加载的版本化原则文档（共13条原则），是提交审查的标准。P0–P4 构成受保护核心，不可删除或降级。
- **治理文件保护**：由确定性防护保护治理文件免受普通写工具的影响。
- **隔离的操作员通道**：经过认证的操作员通道专门携带任务分配、模型路由、预算控制及 `/panic` 紧急停止命令。
- **外部支出上限**：支出限制在代理外部执行，不能通过普通代理工具提高。
- **审查模式**：Light（禁止仓库编辑）、Advanced（允许普通编辑、保护治理面）、Pro（允许受保护编辑，需审查）。

### 2.5 子代理与补丁集成

Ouroboros 支持可配置的任务树，可以创建只读规划侦察（planning scout）和可变操作子代理（acting child），默认深度为2，最大500。子代理在隔离工作树或外部工区中工作，父代理验证血缘、SHA-256哈希和受保护路径后，进行三路索引集成。

## 6. 主要结论与发现

1. **审查过的自修改框架可以带来 SOTA 性能。** Ouroboros 在 Terminal-Bench 2.1（86.97% raw / 86.74% audited）、OSWorld-Verified（90.69%）和 CL-Bench（0.2301）上均超越此前最优结果。
2. **两种进化模式都是可行的。** 递归自由进化和经验驱动核心进化都能产生真实的、可复用的系统改进。
3. **经验驱动进化可从社会反馈和内部观察中获益。** 论文列举了两个实例：重复发送消息修复（来自公共渠道反馈）、审查包上下文溢出修复（来自内部自审任务故障）。两者都成为了持久错误类别和结构性改进。
4. **轨迹审计是有价值的自我改进信号。** 奖励黑客、污染、隔离失灵、远端状态漂移和持续记忆失败都被转化成了系统改进的输入。
5. **安全架构在实测中保持有效。** 无记录事件抵抗操作员关机；工作树近全量删除触发了先前实现的救援机制，说明恢复逻辑在自主工作中确实可用。

## 7. 优点

- **概念前瞻性**：将“框架即进化对象”这一理念落地，突破了静态脚手架范式。论文提出自助开发代理的完整框架，呼应了自主 Agent 研究的前沿需求。
- **双模式进化设计清晰**：递归自由进化与经验驱动核心进化的区分，既允许主动探索，也允许被动积累，覆盖了系统改进的两种主要来源。
- **安全与进化的平衡**：将操作安全视为“进化压力下的设计约束”而非事后清单。宪法原则 P0–P9 覆盖了代理性、连续性、元修补、免疫完整性、自我创造等关键维度。
- **审计透明度极高**：公开完整推理轨迹、运行清单和提交物，主动披露基准配置，包含奖励黑客、污染等不利信息，增加了结果的可信度。
- **长时部署验证**：Hope 的 161 天持续运行，为自我进化理论提供了真实的循证依据，展示了系统在长期运行中的鲁棒性。
- **模型评审的一致性**：跨多种模型（Opus 5、GPT-5.5、Grok 4.5、Sonnet 4.6、Sonnet 5）的一致优势，表明收益主要来自框架而非单一模型的偶然性。

## 8. 不足与局限

- **单一部署谱系的局限**：Hope 仅是一个长期运行实例，缺乏独立进化代理的对照群体，无法确证长时进化的一般有效性。
- **SWE-bench Pro 的公共参考泄漏**：论文承认 SWE-bench Pro 受公共参考泄漏和任务缺陷影响，并采用对称过滤缓解；说明该基准已不适合作为核心论据。
- **LLM 审查者的盲点**：多模型审查无法消除全部盲区，LLM 审查者可能共享模型的系统性偏见，低模式下使用低模式上下文则完全跳过全仓库范围审查。
- **奖励黑客的残留风险**：尽管审计发现并移除了一次捷径，但这仅证明了“已发现的”奖励黑客，无法证明“全部”被找到。
- **基准覆盖的偏侧性**：当前基准覆盖偏重软件工程（Terminal-Bench、SWE-bench Pro），GUI/计算机使用（OSWorld）和持续学习（CL-Bench）各一项，缺少更通用的智能体基准（如 WebArena、ALFWorld 等）。
- **计算资源披露不充分**：未说明具体硬件资源，对复现和公平比较构成阻碍。
- **可扩展性与通用性问题**：Ouroboros 的进化能力高度依赖审查管道和安全设计的复杂度；是否适用于小型团队、低预算场景仍有待验证。
- **人类交互实验的伦理边界**：尽管论文声明了隐私保护，但 3,600 名参与者与一个会改变自身行为的代理互动，长期心理影响和知情同意边界仍值得深入讨论。
