## 摘要
AI编码代理通常作为模型进行评估，但作为系统进行部署。其可靠性不仅取决于模型能力，还取决于工具框架、执行状态、检索、记忆与状态管理、权限、审查界面以及资源分配。本专著考察了这些边界，并开发了一个用于可靠评估和操作编码代理的框架。它通过结构化的多声部评审、针对性的更新审计、软件工程覆盖分析和分布式系统证据综合，综合了164篇学术著作、100条实践者记录、29条基准记录和17条作者系统案例记录。在这些证据中，许多明显的模型失败源于系统的其他部分，而某一层的改进往往无法传播到端到端的结果中。评估和操作被视为一个依赖链，其中任务构建、执行环境、检索、状态管理、验证或可观测性中的弱点可能使下游结论失效。本专著贡献了一个包含206条可靠性记录的版本化目录：193条受控实践（其中56条深入开发）加上13条研究线索；一份证据台账；一个跨代理生命周期的依赖和修复不对称框架；来自已操作代理系统的测量和失败案例；可运行的评估和可靠性协议；以及五个带有证据图谱的可复用代理技能。总之，这些提供了一种系统级方法论，用于区分模型能力与基础设施效应、设计可辩护的评估，以及构建在组件故障时能安全恢复的系统。本综述是结构化的而非详尽的，证据强度因主题而异，结果取决于工作负载和配置。方法记录了哪些搜索通道已执行、哪些仍未执行，以及证据分级声明的局限性。

## Abstract
AI coding agents are commonly evaluated as models but deployed as systems. Their reliability depends not only on model capability, but on the harness, execution state, retrieval, memory and state management, permissions, review interfaces, and resource allocation. This monograph examines those boundaries and develops a framework for evaluating and operating coding agents reliably. It synthesizes 164 scholarly works, 100 practitioner records, 29 benchmark records, and 17 author-system case records through a structured multivocal review, targeted update audits, software-engineering coverage analysis, and distributed-systems evidence synthesis. Across this evidence, many apparent model failures originate elsewhere in the system, while improvements at one layer often fail to propagate to end-to-end outcomes. Evaluation and operation are treated as a dependency chain in which weaknesses in task construction, execution environments, retrieval, state management, verification, or observability can invalidate downstream conclusions. The monograph contributes a versioned catalog of 206 reliability records: 193 gated practices, including 56 developed in depth, plus 13 research leads; an evidence ledger; a framework for dependency and repair asymmetry across the agent lifecycle; measurements and failure cases from operated agent systems; runnable evaluation and reliability protocols; and five reusable agent skills with evidence maps. Together, these provide a system-level methodology for distinguishing model capability from infrastructure effects, designing defensible evaluations, and building systems that recover safely when components fail. The review is structured rather than exhaustive, evidence strength varies by topic, and results depend on workload and configuration. The methods record which search lanes were executed, which remain unexecuted, and limits on evidence-grading claims.

- **核心矛盾**: AI编码代理被当作模型来评估（追求benchmark分数），却被当作生产系统来部署（依赖工具框架、执行环境、权限边界、状态管理等多个系统组件）。二者的割裂导致可靠性判断频频失真。

- **组织化框架**: 论文提出"可靠性依赖链"（reliability dependency chain）——测量→评分→约束与恢复→检索与上下文→审查与问责→分配与成本，每一层决定下一层可以信任什么。由此推导出"修复不对称"（repair asymmetry）：上游丢失的证据无法由下游机制修复。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想：依赖链框架
- 将评估和操作视为一条**证据义务链**：各层之间传递的是"信任边界"而非孤立子系统。每一层中的弱点会使下游结论失效。
- 提出**修复不对称**：下游添加更多机制（如更多样本、更多judge、更多agent）无法修复上游工具的缺陷。

### 2.2 多声部文献综述方法
- 综合**164篇学术著作 + 100条实践者记录 + 29条基准记录 + 17条作者系统案例**。
- 核心检索工具：SciX（NASA支持的天文文献服务）+ SciX Agent + Code Intelligence Digest。
- 设置了**四层证据分级**：
  - **强证据**（Strong）：受控对比、验证过的基准结果
  - **方向性证据**（Directional）：支持机制/威胁模型，但未建立完整推荐
  - **佐证证据**（Corroborating）：案例报告/实践者描述，确立合理性而非普遍性
  - **无效或冲突证据**（Null/Conflicting）：否定预期效应的结果
- 关键：**来源纳入**和**实践接纳**是两个独立决策；每条证据仅针对具体受范围限定的声明（scoped claim）成立。

### 2.3 核心方法论框架
- **软件工厂模型**（Software Factory as a Distributed System）：将编码代理系统视为分布式基础设施——持久化工作台账、调度器、一次性worker、被门控的发布路径。提出11项工厂契约（I1-I11），包括：重试保持逻辑身份（I4）、效果在重投递下安全（I5）、证据绑定版本（I7）、验证器故障≠软件故障（I8）、恢复路径具有生产权威（I10）等。
- **故障注入与恢复测试**：提出5个生命周期杀点（dispatch前、外部承诺前、承诺后确认前、确认后持久化前、持久化后），用于测试恢复机制的真实边界。
- **实践目录**：共206条可靠性记录（193条受控实践 + 13条研究线索），其中56条在正文中深度开发，每条具有稳定ID（ERCA-NNN）。

### 2.4 关键统计方法
- **配对比较**：两个系统在相同任务对上逐项比较（di = xi − yi），利用协方差减少任务难度影响。
- **功效分析**（Power Analysis）：在实验前计算最小可检测效应，基于pilot估计方差、设定显著性水平与检测概率、解得所需样本量。
- **Cohen's kappa / Fleiss's kappa**：评估标注者间信度，区分观察一致率与随机一致率。
- **最小通过方案**（Minimum Reliability Pass）：6步快速通道，产出6类可质疑的工件——配对分布、成本-质量记录、权威边界、独立验证的状态转换、种子失败语料库和预设决策规则。

## 6. 论文的主要结论与发现

1. **模型能力 ≠ 系统可靠性**: 系统各部分（工具框架、执行环境、检索、持久状态、权限、审查、验证）共同决定最终结果，仅看模型无法评估系统。
2. **修复不对称**: 下游添加更多机制无法修复上游丢失的证据。改进可以沿着链条向前传播，但不能向后修复缺陷。
3. **公共基准的可靠性受限**: 基准分数受污染、测试薄弱和任务代表性不足制约，公共分数≠系统性能。建议使用匹配对照组、时间隔离和本地工作负载的评估。
4. **持续评估与操作必须结合**: 评估不仅是测量，更是操作（门控、发布、资源分配）。单元测试不通过，任何后续的质量声明都失效。
5. **执行决定"工作是否有效"**: 模型的自评只能使状态就绪，真正的接受必须由独立观察的证据决定。
6. **恢复是实测属性**: 恢复不能从架构图推断，必须通过故障注入测量，且应在每个版本和配置变化后重新验证。
7. **检索是评估的一部分**: 检索质量必须单独评估，因为它与生成质量不同，而且改进不一定会传导到最终结果。
8. **人类审查必须可执行**: 只记录同意的门禁不是"门禁"，必须能改变执行路径。
9. **调度策略必须通过廉价基线**: 仅在已回放和影子运行中优于简单策略，才值得替换。

## 7. 优点：方法或实验设计上的亮点

1. **清晰的依赖链框架**: 提供统一视角，使不同领域的改进（检索、调度、审查、恢复）能在一个统一的评估坐标系内比较——这是本领域少有的系统级方法论尝试。
2. **透明的证据分级**: 对每条推荐标注证据等级（强/方向性/佐证/无效），并主动披露"章节有0个强证据"（如第8章）——极大提高了可辩护性。
3. **主动披露研究局限**: 明确列出未执行的检索通道、未覆盖的语料，以及"作者系统案例不是独立证据"。研究者不试图将轶事包装为统计结论。
4. **实用的"最小通过"协议**: 提供6步快速操作协议、每章的runable检查清单，便于实际部署落地。
5. **恢复测试的具体方法**: 5个生命周期杀点 + 分布式歧义故障矩阵，提供了可复现的恢复测试协议——这是实践中最缺乏的。
6. **可复现工件**: 提供机器可读的206条记录目录、证据账本、计算哈希——支持外部审查与版本追溯。

## 8. 不足与局限：包括实验覆盖、偏差风险、应用限制

1. **证据强度不均**: 某些章节（第8章：代理隔离与注入防御）完全没有强证据项，仅靠两条实践者轶事支撑。虽然作者主动披露，但这意味着"推荐始终基于薄弱的证据面"。
2. **作者身份与利益冲突**: 论文作者是CodeScaleBench（用于测量其产品的一方）的作者，这构成利益冲突。作者将其明确定位为"作者系统案例"而非"独立外部证据"，并未夸大，但读者在将结论迁移到自身工作负载前需考虑这一限制。
3. **对基准的覆盖与时效局限**: 部分核心基准（SWE-bench Verified）审计发现测试存在缺陷，作者也没有对所有基准进行独立复核。随着模型和基准共同演化，结论可能快速过时。
4. **缺乏端到端受控比较**: 论文本身未做"系统A vs 系统B、同样任务下、谁更可靠"的受控实验，而是**综合了外部文献 + 作者案例**。这对方法论有效，但无法解决"这套系统在真实部署中的平均收益有多大"的问题。

7. **未提供端到端可用性证明**: 虽然论文提供了大量协议和推荐，但未给出一个完整独立的、经过严格peer-reviewed验证的"这套方法在大型项目中真的提升了质量/降低了成本"的最终结果。
8. **计算成本与可访问性未透明化**: 未披露训练/推理的总算力消耗和环境。对于算力受限的团队，难以估算采用这套方法的实际开销。
