## 摘要
关于编码智能体的现有研究大多将应用开发组织为需求解释、实现、工具执行、评估和修复的迭代循环。随着这些循环运行时间的增长，需求可能会漂移；用户可能会对当前状态和变更理由失去认识；生成的应用可能仍然没有充分基于目标用户的背景和需求。因此，应用工程需要一种机制，将所有者意图、目标用户体验、开发变更和发布责任联系起来。我们提出了AppLooper，一个用于负责任发布的人类-编码智能体-虚拟用户应用工程循环。应用所有者确认冻结的需求，提供反馈，检查候选版本，并保留最终发布权。开发智能体生成并修订带版本号的候选版本。虚拟用户智能体群体执行基于目标用户和使用场景的界面场景。此外，一个所有者意图模拟智能体仅重新测试所有者明确确认的需求、约束和反馈，当证据不足时弃权。测试智能体通过复现报告的问题、运行现有的回归测试以及操作当前候选版本的浏览器界面来执行只读的开发性检查。编排层将产生的结果进行分组，并将它们路由到开发修订、定向重新测试和所有者检查。AppLooper将需求、反馈来源、界面目标、开发变更、重新测试结果、所有者交互和发布决策绑定到特定版本。从而将持续的编码智能体迭代扩展为一个可追踪、可审查的生命周期，其中人类保留发布的最终责任。源代码可在 https://github.com/ZihongHe/applooper 获取。

## Abstract
Much existing research on coding agents organizes application development as an iterative loop of requirement interpretation, implementation, tool execution, evaluation, and repair. As these loops run longer, requirements may drift; users may lose awareness of the current state and rationale for changes; and generated applications may remain insufficiently grounded in target users' contexts and needs. Application engineering therefore requires a mechanism connecting owner intent, target-user experience, development changes, and responsibility for release. We present AppLooper, a human--coding-agent--virtual-user application engineering loop for accountable release. An application owner confirms frozen requirements, supplies feedback, inspects candidates, and retains final release authority. A development agent produces and revises versioned candidates. A virtual-user agent cohort executes interface scenarios grounded in target users and contexts of use. Besides, an owner-intent simulation agent retests only requirements, constraints, and feedback explicitly confirmed by the owner, abstaining when evidence is insufficient. A testing agent performs read-only developmental checks by reproducing reported failures, running existing regression tests, and exercising the current candidate through its browser interface. The orchestration layer groups the resulting findings and routes them into development revision, targeted retesting, and owner inspection. AppLooper binds requirements, feedback sources, interface targets, development changes, retesting outcomes, owner interactions, and release decisions to specific versions. It thereby extends sustained coding-agent iteration into a traceable and reviewable lifecycle in which humans retain final responsibility for release. Source code is available at https://github.com/ZihongHe/applooper.

## 1. 核心问题与整体含义

**研究动机与背景：**
- 现有编码智能体（coding agent）研究将应用开发组织为「需求解释 → 实现 → 工具执行 → 评估 → 修复」的迭代循环，使智能体能够基于执行环境反馈持续改进代码。
- 随着循环运行时间延长，暴露出三个相互关联的问题：
  1. **需求漂移**：局部反馈驱动的修改可能偏离应用所有者的整体意图；
  2. **用户失去感知**：用户离开长时间运行的开发过程后，难以恢复对当前版本、变更理由和剩余风险的了解；
  3. **目标用户脱节**：通过测试或评估器判定并不足以证明应用真正支持目标用户的实际任务。
- 已有研究（如 Tang et al. 对 20,574 个真实会话的分析）表明，91.49% 的已解决可见偏差仍需用户明确纠正，说明长周期智能体开发需要建立用户目标、反馈与当前版本之间的持续连接。

**论文的核心回应：** 应用工程需要一种机制，将**所有者意图、目标用户体验、开发变更和发布责任**持续关联到具体版本，AppLooper 正是为此设计的系统。

## 2. 方法论

**核心思想：** 构建一个人类–编码智能体–虚拟用户协同的应用工程循环，以「版本化候选应用」为组织中心，使需求、反馈、变更、测试结果、所有者交互和发布决策全部绑定到具体版本，形成可追踪、可审查的生命周期。人类保留最终发布权。

**五大角色及其职责边界：**
- **应用所有者（Application Owner）**：确认冻结需求、在开发检查点提供反馈、通过实际界面体验完成中间验收与最终发布决策，拥有最终发布权。
- **开发智能体（Development Agent）**：以 Claude Code 为编码运行时，在隔离工作区中持续实现和修订应用。每次仅注入当前任务、冻结需求、依赖关系、已确认反馈与前一轮状态，而非完整聊天历史。
- **虚拟用户智能体群体（Virtual-User Agent Cohort）**：多个带有人设来源和适用边界的模拟目标用户，通过真实浏览器交互执行端到端任务，产生与具体页面、控件和交互轨迹相关联的形成性发现。明确禁止修改源码，只能通过界面操作完成任务。
- **所有者意图模拟智能体（Owner-Intent Simulation Agent）**：仅使用所有者明确确认的需求、约束和反馈，对相关候选版本进行最多两轮只读重测；证据不足时弃权并保留为未解决风险。
- **测试智能体（Testing Agent）**：执行只读灰盒开发性测试——复现开发者上报的失败、运行现有回归测试、结合源码诊断根因、通过浏览器操作当前候选版本。只报告观察到的缺陷，不修改产品源码。

**编排层（Orchestration Layer）**：维护反馈路由、任务依赖、候选版本、测试状态和循环状态，在安全开发检查点调度各角色，将多源发现分组并路由到修订、重测和所有者检查。

**关键技术流程：**

- **两阶段可行性判断**：
  - 第一阶段为确定性范围策略：使用固定关键字词典按固定顺序匹配，拒绝恶意请求（凭证窃取、恶意软件、绕过安全控制）和严重领域（医疗诊断、自动驾驶、武器核设施、高风险金融法律决策），对依赖真实敏感账户但可安全改写为模拟原型的请求返回重写需求。
  - 第二阶段为在线模型细化：使用 Agnes 2.5-flash（采样温度固定为 0）返回 JSON 结构化决策（PASS/REPHARSE/BLOCK），模型不可用时回退到第一阶段结果。
- **需求分解**：编排智能体将冻结需求分解为三个稳定结构——已确认约束（含可验证验收条件与来自开发意图的连续逐字摘录）、需求任务依赖图、虚拟用户画像（含标识符、覆盖用户群、人口统计描述、地点、角色、技术熟练度、设备、动机、约束、使用场景、习惯和任务脚本）。
- **反馈生命周期**：反馈 → 反馈簇 → 开发修订 → 候选版本 → 重测 → 所有者检查 → 候选绑定证据。每个反馈与来源、界面目标、修订结果、重测证据、所有者检查和候选版本持续关联。
- **场景管理**：每个反馈簇生成带版本号的定向检查场景，场景状态流转为 open → interact → judge → cleanup（清理临时状态）。仅打开页面未交互或未清理的场景不计为完成；候选版本变更后旧结论自动失效。
- **四层测试体系**：单元测试（纯逻辑）、集成测试（跨组件）、夹具重放测试（可重复状态）、真实浏览器交互测试；定向场景同步重新执行。
- **候选绑定验收与发布**：系统侧候选评估（独立评估智能体基于冻结约束、分层测试结果、关键用户旅程证据和严重缺陷状态做结构化判断）→ 达到阈值后冻结为不可变验收版本 → 所有者实际界面体验后做出通过/退回/延后决策。候选变更后先前批准自动失效。
- **证据分离**：虚拟用户和所有者意图模拟结果明确标注为模拟证据，与真实所有者操作数据分开存储。
