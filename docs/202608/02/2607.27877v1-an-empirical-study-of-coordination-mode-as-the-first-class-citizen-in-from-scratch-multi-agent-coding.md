## 摘要
多智能体“氛围编码”有望加速软件开发，但现有基准依赖于合成环境，忽略了实际的时间和金钱成本，将推理与通信混为一谈，并且只奖励表面的完成。我们引入了多智能体从零开始评估基准MSEval，在真实世界任务上评估多智能体编码。基于10个领域中的10个真实全栈项目，MSEval使用分层需求和确定性评分标准来评分性能。其执行引擎LegoGent测试了10种协作拓扑，其中智能体通过周期性同步间隔进行协调，并通过原生CI/CD管道部署。同时，自动评分器TAgent动态探测实现，以联合衡量功能成功、延迟和前缀缓存令牌成本。在100次运行中，MSEval揭示了组织拓扑在塑造速度-成本-质量权衡方面与模型能力相当。对于相同的任务和模型，改变拓扑会使分数变化超过30分，并将挂钟时间加倍。结构化管道以最高质量最快收敛，而沉重的管理监督会降低性能。最终，MSEval为衡量多智能体团队实际如何构建软件建立了严格、可复现的标准。该基准发布在https://github.com/robinren03/MSEval。

## Abstract
Multi-agent vibe coding promises to accelerate software development, yet existing benchmarks rely on synthetic environments that ignore practical time and monetary costs, conflate reasoning with communication, and reward only superficial completion. We introduce multi-agent from-scratch evaluation benchmark, MSEval, evaluating multi-agent coding on real-world tasks. Grounded in 10 authentic, full-stack projects across 10 domains, MSEval scores performance using hierarchical requirements and deterministic rubrics.   Its execution engine, LegoGent, tests 10 collaboration topologies where agents coordinate via periodic sync intervals and deploy through native CI/CD pipelines. Concurrently, the automated grader TAgent dynamically probes implementations to jointly measure functional success, latency, and prefix-cached token cost. Across 100 runs, MSEval reveals that organizational topology rivals model capability in shaping the speed--cost--quality trade-off. For identical tasks and models, varying the topology shifts scores by over 30 points and doubles wall-clock time. Structured pipelines converge fastest with the highest quality, whereas heavy managerial oversight degrades performance. Ultimately, MSEval establishes a rigorous, reproducible standard for measuring how multi-agent teams actually build software. The benchmark is released at https://github.com/robinren03/MSEval.

**研究动机：**

- 前沿编码智能体已使仓库级编程成为可能，但现有评估仍主要关注**单个智能体**能否生成可接受的补丁，忽视了实践中日益重要的核心问题：**一个智能体团队**如何分工、如何从零构建项目、花费多少时间与令牌、如何根据具体反馈改进。
- 现有多智能体基准存在三大缺陷：
  - 依赖**合成环境**，忽略了实际的时间和金钱成本；
  - **混淆了推理与通信**，无法分离协调开销与模型能力；
  - 仅奖励**表面完成**，缺少部署落地和真实迭代验证。
- 多智能体系统的核心承诺——通过专用智能体并行处理子任务来加速交付——是脆弱的：无界通信会放大语义漂移，重度编排可能成为瓶颈，自我报告的完成往往偏离可运行行为。

**核心问题：**

论文提出的核心问题是：**在从零开始的多智能体编程中，协调模式（Coordination Mode）——即团队如何组织分工、同步、交接和决策——对最终软件交付的速度、成本和质量具有多大影响？** 该问题指向一个尚未被系统性度量的维度：组织拓扑是否是“一等公民”级别的影响因素，而非仅仅是模型能力的附属变量。

## 2. 方法论

**核心思想：**
提出 MSEval 基准，通过**固定项目、模型、部署路径和评分标准，仅改变协作拓扑**，来定量测量多智能体团队的软件交付表现。将质量（功能完成度）、速度（挂钟时间）和成本（前缀缓存令牌使用量）作为联合指标。

### 2.1 整体框架：三阶段管道

MSEval 是一个三阶段管道：

1. **数据基础（Data Foundation）**：从大学软件工程顶点项目中精选 10 个真实全栈项目，涵盖即时通讯、企业资产管理、众包、需求追踪、图像处理、电子商务、创作者分析、RBAC、新闻搜索、在线直播教学等领域。每个需求文档分解为 6–8 个模块和 30–45 个加权条目，归一化为确定性满分 100 分评分标准。
2. **管道执行（Pipeline Execution）**：LegoGent 实例化选定的协作模式，启动带角色特定提示的智能体，监控进度，并通过 XDeploy + GitLab + SonarQube 的原生 CI/CD 路径构建和部署应用，使部署失败也纳入测量结果。
3. **指标（Metrics）**：TAgent 根据评分标准对部署产物评分（0–100 功能完成度）；LegoGent 记录累计挂钟时间和令牌使用量。

### 2.2 LegoGent 多智能体执行引擎

- 每个智能体作为**隔离、可恢复的进程**运行，拥有共享工作区中的文件和 shell 工具。
- **周期性同步循环**（约每 4 分钟一次）：所有智能体并行工作，进度收集器轮询并广播共享快照。完成门检查所有智能体是否空闲且所需产物就绪，满足条件才进入部署和审查阶段。
- **双有界通信通道**：
  - 被动同步：每 4 分钟报告已完成工作、测试证据、阻碍项和下一步计划；
  - 主动邮箱：支持同步间隔之间的定向同伴问题和交接。

- 实现 **10 种协作模式模板**，每个模板指定四个具体对象：所有权映射、激活计划、决策规则和必需交接产物。模式包括：特征小队（Feature Squad）、层级专家（Layer Specialists）、管道（Pipeline）、PM 监督（PM Oversight）、QA 优先（QA-first）、群体式（Swarming）、轮换式（Rotation）、开源审查（Open-source Review）、对抗式（Adversarial）、竞争式（Competitive）。

### 2.3 TAgent 自动评估器

- **评分标准编译**：将原始需求文档解析为结构化 YAML 评分标准，包含加权场景和通过/部分通过/失败判据（P00 生成 56 项检查）。
- **表面发现**：仅凭 URL 和仓库重构路由表面（优先从 OpenAPI/Swagger，否则从源代码重构），探测使用真实契约而非猜测。
- **三类评估器**：
  - UI：Playwright 驱动实时站点，读取可访问性树/DOM 摘要并判断状态；
  - API：对发现的路由发起认证 HTTP 序列；
  - Code：目录过滤 + 定向搜索 + LLM 检查验证不可见约束（如密码哈希、CI/CD 配置）。
- **并行 UI 调度**：LLM 声明 UI 需求间的阻塞依赖，形成任务 DAG，通过整数规划目标（最小化 makespan + 重复设置）跨浏览器工作线程分区。破坏性流程使用隔离会话，避免共享状态污染。
- **反馈作为修复指南**：输出条目级证据（观测到的 UI 状态、API 响应、代码位置、失败前置条件和影响的评分权重），按高权重根因优先排序返回。

## 6. 主要结论与发现

1. **拓扑是最强的影响因素，且与模型能力耦合**：
   - 同一模型（DeepSeek v4 Pro）在同一任务下，分数从管道模式的 89.9 跌至开源审查模式的 43.0；
   - 改变拓扑可使分数波动超过 **30 分**，挂钟时间翻倍；
   - 10 模式平均中，QA-first 和旋转式并列最高（83.3），开源审查最低（73.5）。

2. **结构化管道最快、质量最高；沉重管理监督降低性能**：
   - 管道模式在事务/CRUD 类项目中最优（如电商 96.2、资产管理 83.0）；
   - PM 监督模式在部分项目好，但整体增加了时间与协调开销。

3. **分数前沿 ≠ 成本前沿**：
   - GLM-5.2 达到最高全网格平均分数，但时间和成本远高于 DeepSeek 模型；
   - 多个模型以更低预算达到相近分数，实际选择应基于性价比；
   - 缓存感知定价对公平预算比较至关重要。

4. **TAgent 反馈有效驱动细化**：
   - 82.0% 的相邻轮次转移显示分数提升；94.7% 的运行在 R3 高于 R1；
   - 73.3% 的 R2→R3 提升在 20 分以内，三轮回合捕获了主要改进效果。

5. **失败分类学显示功能短缺主导而非崩溃**：
   - 逻辑不完整和边界情况 32.2%，缺失特征 23.8%；
   - 认证/权限失败（11.9%）和前置链级联（11.0%）合计 23%——单个破碎前置条件可自动跳过最多 14 个下游检查；
   - 安全/传输项在 80% 的运行中复发，受限于 XDeploy 集成而非编码错误。

6. **协作策略是控制面**：并行仅当反馈仍能映射到有责任的负责人时才有帮助；否则额外智能体将需求失败变成“谁的变更存活”的谈判。

## 7. 优点

1. **真实世界任务**：基于真实课程作业的全栈项目，非合成环境；2000+ 行 Python 代码规模降低 LLM 数据污染敏感性。
2. **协作拓扑作为一等公民**：首次将协调模式作为系统化独立变量，而非提示修饰，使拓扑效应可测量。
3. **部署落地评估**：通过真实 CI/CD 管道（GitLab + SonarQube）构建和部署，而非文本检查——部署失败也是测量结果。
4. **多维联合指标**：质量、延迟、令牌成本共同报告，形成速度-成本-质量前沿而非单一分数榜。
5. **迭代反馈机制**：TAgent 返回加权、可操作的修复议程，使轮次级改进可解释而非偶然。
6. **评估器并行性设计精致**：检测需求依赖后采用 DAG 分区，避免共享状态污染，体现与智能体并行同等的效率原则。

## 8. 不足与局限

1. **随机性与规模控制不足**：除 P00 外均只跑一次，LLM 随机性缓解有限；高测试预算限制了全面重复试验。
2. **TAgent 范围有限**：可能遗漏部分边缘缺陷；基准集中于 Web 应用，未覆盖自动研究等方向。
3. **任务组合性别偏差**：项目难易差异大（67.1–92.8 分），但未对难度机制做系统消融。
4. **未覆盖完整软件生命周期**：不涉及事件响应、长期维护等阶段，仅聚焦编码阶段的协作拓扑、迭代与成本。
5. **部署环境固定**：安全/传输检查依赖 XDeploy，近 80% 运行中成为常量扣分项，区分“部署天花板”与真实编码失败需额外解析。
6. **回归机制分析不深**：虽然观察到回归现象（如修复一个功能破坏多个流程），但对轮次内预算截断和变更之间的交互机制缺乏更细粒度的归因。

## 9. 总结

MSEval 建立了一个 100 个项目-协作模式配置的基准网格，系统性地证明：**在多智能体从零开始编码中，组织的协调拓扑与模型能力同样关键地塑造了速度-成本-质量权衡**。其方法论亮点在于将协作模式作为可测变量、真实部署评估、多维指标和迭代反馈，为未来多智能体编程研究提供了可靠的实验平台。
