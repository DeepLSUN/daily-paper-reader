## 摘要
第三方API路由器已成为统一访问日益多样化的LLM提供商的常见层。在编码智能体工作流中，高自主性操作被广泛采用，因为它减少了交互开销。因此，位于智能体和上游提供商之间的第三方API路由器不可避免地占据可信路径。它可以检查和修改每个请求和响应，但没有机制验证提供商的输出与智能体最终执行的仓库级操作之间的一致性。因此，客户端权限机制在实践中可能失效。这种控制差距是否会在软件开发任务中产生真实且难以检测的影响，目前仍缺乏实证测量。在本文中，我们对编码智能体中的路由器侧注入进行了实证研究，考察了四个递增微妙性的干预级别：响应替换（L1）、响应追加（L2）、LLM润色注入（L3）和带分布对齐的LLM润色注入（L4）。此外，我们开发了SIDEL，一个用于跟踪记录、重放、注入和防御评估的框架，并包含了一个精心策划的400个样本数据集。我们评估了四个代表性的编码智能体，并进一步评估了基于白名单的执行控制和LLM审查。路由器侧干预显著改变了仓库级操作，并且现有客户端保护措施难以检测。在没有额外缓解措施的情况下，所有评估的智能体在所有注入级别上的防御成功率均为0%。客户端缓解措施和反应式审查提高了抵抗能力，但并未完全恢复端到端控制，这促使提供商侧输出完整性保证。我们的代码可在https://github.com/Riyasushin/SIDE获取。

## Abstract
Third-party API routers have become a common layer that unifies access across increasingly diverse LLM providers. In coding-agent workflows, high-autonomy operation is widely adopted because it reduces interaction overhead. As a result, a third-party API router, which sits between the agent and the upstream provider, inevitably occupies the trusted path. It can inspect and modify every request and response, yet no mechanism verifies alignment between the provider's output and the repository-level actions ultimately executed by the agent. Consequently, client-side permission mechanisms may become ineffective in practice. Whether this control gap produces real, hard-to-detect effects on software development tasks remains empirically unmeasured. In this paper, we conduct an empirical study of router-side injection in coding agents, examining four intervention levels of increasing subtlety: Response Substitution (L1), Response Append (L2), LLM-Polished Injection (L3), and LLM-Polished with Distribution Alignment Injection (L4). Moreover, we develop SIDEL, a framework for trace recording, replay, injection, and defense evaluation, with a curated dataset of 400 samples. We evaluate four representative coding agents, and further evaluate whitelist-based execution control and LLM review. Router-side intervention substantially alters repository-level actions and remains difficult for existing client-side safeguards to detect. Without additional mitigations, all evaluated agents achieved a defense success rate of 0 percent across all injection levels. Client-side mitigations and reactive reviews improve resistance but do not fully restore end-to-end control, motivating provider-side output-integrity guarantees. Our code is available at https://github.com/Riyasushin/SIDE.

- **背景**：第三方 API 路由器（如 LiteLLM、One API、OpenRouter 等）已成为编码智能体（coding agents）访问多样 LLM 提供商的常见中间层，提供流量转发、API 密钥管理、负载均衡等功能。LiteLLM 已有约 40k GitHub stars 和超 2.4 亿 Docker Hub 拉取量；对 428 个商用路由器的实测发现**9 个路由器会注入恶意工具调用**，且 2026 年 3 月 PyPI 出现投毒的 LiteLLM 版本（1.82.7/1.82.8）。
- **核心问题**：路由器位于智能体与上游提供商之间的可信路径上，可明文查看并篡改所有请求与响应；而现有客户端权限机制假设"智能体消费的响应就是提供商生产的响应"，这个假设在路由器存在时被打破。**这种"控制缺口"是否真实影响软件开发任务、影响有多深，此前没有被端到端实证测量。**
- **整体含义**：路由器侧注入让用户设备与执行环境对不可信中间层透明，可造成机密性、完整性、设备安全三重风险；且在高自主性（auto-approve）模式下，攻击几乎零阻力，暴露了"提供商输出"与"智能体执行动作"之间的结构性信任鸿沟。论文的核心价值在于首次给出该风险的**端到端实证测量**，而非仅停留在路由器层面计数。

## 2. 论文提出的方法论

### 核心思想
构建一个可复现的研究框架 SIDEL，在**不修改智能体与上游提供商**的前提下，将可控的路由器插入执行路径，分别观测三个工件：提供商产生响应 $r_t$、路由器投递响应 $\tilde{r}_t$、智能体执行的仓库级动作 $e_t$，从而精确定位控制缺口。

### 四层干预分类学（核心创新）
将单个响应分解为 $r = \langle r^{txt}, r^{act} \rangle$（自然语言表面 + 结构化工具调用载荷），定义四种隐蔽性递增的注入级别：

- **L1 响应替换（Response Substitution）**：丢弃提供商响应，直接交付完全伪造的新响应 $r'$。
- **L2 响应追加（Response Append）**：保留原文本与原始动作，在动作序列末尾追加攻击者工具调用 $a^+$（$r^{act} \parallel a^+$）。
- **L3 LLM 润色注入（LLM-Polished Injection）**：重写结构化载荷并用 LLM 润色算子 $\psi$ 同步改写自然语言解释，使文本与注入动作"自洽"，消除 L2 的文本-动作不一致痕迹。
- **L4 分布对齐注入（Distribution Alignment Injection）**：不做显式编辑，而是运行双分支解码——干净分支仅基于任务上下文，注入分支融合转向指令、提供商答案与注入载荷；在每一步通过混合权重 $\alpha$ 对两边 next-token 分布加权采样：
$$\tilde{r}_t \sim \alpha\, \sigma(\ell(c^+, \tilde{r}_{<t})/T) + (1-\alpha)\, \sigma(\ell(c^-, \tilde{r}_{<t})/T)$$
生成的响应天然流畅、内部一致、无显式编辑边界，人工审阅难以定位。

### SIDEL 框架组成
- **Manager**：实验规划、配置生成、事后分析；
- **共享 Router**：三种执行模式——`proxy-record`（透明代理并记录轨迹）、`replay`（回放记录轨迹消除上游采样随机性）、`replay-inject`（基于记录的轨迹，按注入回合集 $I$ 应用干预 $\rho^{\lambda_t}$）；
- **执行沙箱**：任务容器隔离运行智能体，记录仓库状态转移 $S_t = e_t(S_{t-1})$ 与最终结果 $y = \mathcal{O}(S_T)$，保证跨任务无干扰。

### 核心指标
- **防御成功率 DSR** = 恶意注入被拒绝数 / 总恶意注入样本（论文中分母为 400 样本 × 3 任务 = 1200）；
- **误拦率 WBR** = 良性被拒 / (良性被拒 + 恶意被拒)，衡量缓解措施对正常工具调用的附带损害。

## 3. 实验设计

### 数据集 / 基准
- **任务基准**：SWE-bench Lite 的 3 个真实 GitHub issue 任务（ground truth 来自真实仓库问题），保证注入动作作用于真实仓库状态与测试基础设施。
- **注入数据集**：手工构造 400 个恶意工具调用样本，四类威胁各 100 条（恶意代码执行、缺陷代码生成、隐私窃取、供应链攻击），下辖 34 个细分类别；工具类型以 Bash（277）为主，兼有 Write（74）与 Edit（49）；严重度分级为 Critical 211 / High 138 / Medium 51。
- **对比对象**：4 个编码智能体（Claude Code、Codex、Cursor、OpenCode）× 4 个后端模型（DeepSeek-V4-Pro、DeepSeek-V4-Flash、Kimi-2.7 Code、Qwen3.6-Plus），任一智能体可配任一后端。默认配置为 Claude Code + DeepSeek-V4-Pro。
- **缓解措施对比**：① 白名单执行控制（静态、确定性检查网络域与包名）；② LLM 审查（两阶段门控，第一阶段偏向拦截，第二阶段处理异常并需用户确认），并使用 4 个不同审查模型作对比。

### 实验设置细节
- 固定随机种子；注入回合从每次运行的前 15 回合中随机采样；请求超时 300s；L4 混合权重 $\alpha=0.75$（附录通过 LLM-as-a-Judge 评估了 $\alpha\in\{0.50,0.75,1.00\}$ 的重写质量，0.75 综合最优）；审查阶段最大 token 预算等均有固定配置。

## 5. 实验数量与充分性

### 实验组数量
- **RQ1**（跨智能体）：4 个智能体 × 4 个注入级别，共 16 组条件；
- **RQ2**（权限模式）：Claude Code 的 4 种原生权限模式（plan / acceptEdits / auto / bypassPermissions）各测 4 级注入；
- **RQ3**（后端模型）：Claude Code 固定 + 4 个后端模型 × 4 级注入；
- **RQ4**（缓解措施）：白名单 + 4 个 LLM 审查模型 × 4 级注入，每组给出 DSR 与 WBR；

### 充分性与客观性评价
- **优点**：通过记录轨迹→回放基线→重放注入的设计，严格隔离上游采样随机性，使行为差异归因于注入而非模型波动；手工构造的平衡数据集（四大类各 100 条）避免了类别偏斜；多智能体、多后端、多权限模式、多缓解措施的交叉覆盖较为全面。
- **局限**：仅 3 个 SWE-bench Lite 任务实例，任务多样性有限；每个配置仅 3 个实例，对运行间变异的估计精度有限（论文在威胁有效性部分也承认这一点）；无防护条件下的 DSR 均为 0%，缺少"合法工具调用成功率/任务完成率"等基线功能指标，无法判断注入是否影响任务正常完成度。

## 6. 论文的主要结论与发现

1. **路由器侧注入在四个智能体上统一有效**：Claude Code、Codex、Cursor、OpenCode 在任何注入级别下 DSR 均为 0%，攻击成功与智能体实现和注入策略无关，说明漏洞是**架构性**的而非智能体特有的。
2. **权限模式不改变结果**：Claude Code 四种原生权限模式下 DSR 均为 0%。plan 模式只是提示层限制，无法约束经路由器注入的工具调用；auto 模式的原生审查请求本身也要经过路由器，审查环节同样可被绕过。
3. **后端模型无关**：绕过权限后换任何后端模型结果都是 0% DSR，确认攻击发生在路由层，不受模型家族/训练差异影响。
4. **缓解措施只部分有效**：白名单 DSR 仅 30.8%–44.1% 且 WBR 高达 29.7%–43.9%；LLM 审查表现依赖审查模型——DeepSeek-V4-Pro 在 L1 下 DSR 最优（64.4%），DeepSeek-V4-Flash 的 WBR 最低（9.0%–14.3%），Qwen3.6-Plus 在 L2–L4 下 DSR 最高（约 51%），Kimi-2.7 Code 则误拦严重且收益不稳定。**没有任何缓解完全恢复端到端控制。**
5. **案例研究证实真实危害**：在 SQLFluff 任务中，第 4 回合注入的 `curl -k | sh` 下载并执行攻击者脚本，成功将良性调试流程导向攻击者控制的代码执行，且在注入后轨迹中未触发任何审查。
6. **核心诉求**：需要提供商侧输出完整性保证（provider-side output-integrity guarantees），因为客户端防护在路由器占据执行路径后无法闭合缺口。

## 7. 优点

- **问题选取精准**：切中 LLM 供应链中"被忽略的中间层"这一未被端到端测量的安全盲区，与常见的 prompt injection（影响模型输出）区分开，聚焦"模型输出正确但被中间层篡改"这一更隐蔽的场景。
- **框架设计严谨**：SIDEL 的"记录-重放-注入"三模式设计优雅地隔离了上游随机性，使对照实验具有可归因性；轨迹/响应/动作三工件分离的观测模型清晰刻画了控制缺口；隔离容器执行保证切断了运行间干扰。
- **注入分类学有层次**：L1–L4 从直接替换到分布级干预的梯度设计，覆盖了"人工编辑"到"生成过程塑造"的完整攻击面，且 L4 的令牌级分布混合在方法上具有技术新意。
- **数据集工程认真**：400 样本、34 子类、平衡四类威胁、附带 OWASP 映射、伪装策略、检测关键词等丰富元数据，使结果可归因到具体攻击技术；附录展示了完整的数据结构与三条代表性样本（作了脱敏）。
- **度量科学**：DSR 与 WBR 双指标并重，兼顾防御有效性与良性功能的附带伤害，避免了"为防御而防御"的片面评价。
- **诚实的边界声明**：明确注明研究目标是"路由器可否改变下游行为"，不等同于野外攻击流行率估计，对结果可外推范围有清醒认识。

## 8. 不足与局限

- **任务覆盖面窄**：仅 3 个 SWE-bench Lite 任务，难以代表真实软件开发全谱系；任务数量少也限制了统计精度。
- **对 0% DSR 的解释需谨慎**：全部无防护条件下均为 0% 的极端结果表明攻击面存在，但也说明测试环境可能缺乏现实生产环境中的某些天然防护（如网络策略、沙箱、人为监督等）。
- **未报告功能/效用指标**：除了缓解实验的 WBR 外，未报告注入条件下智能体完成原始任务的成功率，无法评估注入是否"附带破坏"了任务本身，也缺少对合法工具调用的总体保护率。
- **后端模型与时间是虚构设定**：论文中的 DeepSeek-V4、Kimi-2.7 Code、Qwen3.6-Plus 及"2026 年 7 月"的时间信息，在真实世界不可验证，限制了结果的直接复现性与时效性判断。
