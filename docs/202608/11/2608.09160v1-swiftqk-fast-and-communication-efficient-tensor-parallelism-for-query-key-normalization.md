## 摘要
查询-键归一化（QK-Norm）提高了现代大语言模型（LLM）的训练稳定性和质量。然而，在张量并行（TP）下，逐层 QK-Norm 会因为归一化因子依赖于完整隐藏向量而引入额外的跨 GPU 通信。我们提出了 SwiftQK，一个多 GPU RMSNorm 内核，它仅交换标量归一化统计量，并在无死锁的持久内核中将剩余的逐点（Peer-to-Peer）规约与独立的逐元素计算重叠。在最近的 LLM 上的评估表明，与使用全向量 All-Gather 的标准 TP QK-Norm 相比，SwiftQK 将 QK-Norm 延迟降低了 81.4%--93.9%。在端到端服务中，与基于 All-Gather 的基线相比，SwiftQK 平均将 TPOT 降低了 29.5%，与优化的标量聚合实现相比降低了 14.3%。

## Abstract
Query-Key Normalization (QK-Norm) improves the training stability and quality of modern Large Language Models (LLMs). However, under Tensor Parallelism (TP), layerwise QK-Norm introduces additional cross-GPU communication because the normalization factor depends on the full hidden vector. We present SwiftQK, a multi-GPU RMSNorm kernel that exchanges only scalar normalization statistics and overlaps the remaining Peer-to-Peer reduction with independent element-wise computation in a deadlock-safe persistent kernel. Evaluations on recent LLMs show that SwiftQK reduces QK-Norm latency by 81.4--93.9% relative to the standard TP QK-Norm using full-vector All-Gather. In end-to-end serving, SwiftQK reduces TPOT on average by 29.5% over the All-Gather-based baseline and by 14.3% over an optimized scalar-aggregation implementation.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：大型语言模型（LLM）的规模迅速增长，使得分布式推理成为解决单 GPU 显存容量不足和高延迟瓶颈的必需手段。张量并行（Tensor Parallelism, TP）通过将每一层的计算切分到多张 GPU 上并行执行，成为现代推理引擎（如 vLLM）最广泛采用的策略之一。
- **QK-Norm 的兴起**：为了提升训练稳定性和注意力质量，现代 LLM（如 OLMo2、OLMo3、OLMoE）在注意力计算前，对投影后的 Q（Query）与 K（Key）张量施加 RMSNorm（即层级的 QK-Norm）。这一机制显著改善了大模型的训练稳定性。
- **核心矛盾（问题提出）**：在 TP 模式下，Q/K 的隐藏维度被切分到多张 GPU 上，而层级 QK-Norm 的归一化因子依赖完整的隐藏向量。这导致每个 GPU 必须跨卡同步完整的 Q/K 向量（通常使用 All-Gather），在原本高效的 TP 执行流中插入了高昂的跨 GPU 通信开销。
- **问题量化（动机数据）**：论文实测显示，在 4 GPU 配置下，TP 相比 Pipeline Parallelism（PP）在 OLMo（无 QK-Norm）上可降低 36.2% 延迟，但在 OLMo2 和 OLMo3（有 QK-Norm）上仅分别下降 7.5% 和 12.0%。QK-Norm 的通信开销（尤其 Q/K 同步）在 TP 下占比高达 30% 左右，且随 TP 并行度增加而恶化，严重削弱了 TP 的延迟优势。
- **整体含义**：这是一个典型的“算子级通信瓶颈”问题。该论文不仅解决一个具体算子（QK-Norm）的 TP 低效问题，更启示了在分布式推理中，通信量的根本性削减比单纯的通信-计算重叠更为关键。

### 2. 论文提出的方法论（SwiftQK 设计）

**核心思想**：SwiftQK 是一款通信高效的多 GPU RMSNorm 内核，力图解决 TP 下的 QK-Norm 瓶颈。其核心策略是 **“通信量最小化”与“通信-计算重叠”相结合**：

- **Phase A: 局部聚合（通信削减）**——用标量聚合替代全向量交换。
  - RMSNorm 的计算公式为：RMSNorm(x) = x / sqrt( (1/H) * Σ(x_j²) + ε ) * γ。
  - 归一化因子只依赖隐藏向量的 **平方和（Σx²）**，而非全部元素本身。
  - SwiftQK 在各 GPU 上先计算**局部的平方和**（FP32 累加），然后只跨 GPU 交换这些 **O(1) 量的标量部分和**，取代了原先 All-Gather 中 **O(H) 量级的全向量交换**，在大幅降低通信数据量的同时，保持了相同的归一化语义。

- **Phase B: 通信-计算重叠（延迟隐藏）**——用专用 Warp 做通信，其余 Warp 做计算。
  - 尽管通信量降为标量，但跨 GPU 的 Peer-to-Peer (P2P) 规约同步仍需等待时间。
  - SwiftQK 将 Warp 0 专用于通信路径（执行 P2P 规约，获取全局平方和），而**其余 Warps** 同时执行与归约结果无关的**逐元素权重相乘（× γ）**。该计算与全局平方和无关，因此可以在 P2P 通信期间安全进行，从而隐藏大部分同步延迟。

- **Phase C: 最终归一化（输出）**。
  - 待全局 RMS 因子及权重乘加结果均就绪后，计算最终归一化因子：RMS⁻¹ = 1 / sqrt( (S_global / H_total) + ε )，应用到每个元素上，并只将归一化后的本地分片写回 HBM。

- **无死锁的持久化执行（关键工程实现）**：
  - 由于执行的是内核内的 P2P 同步，必须保证同步的所有参与 block 都常驻在 SM 上，否则会造成循环等待（死锁）。
  - SwiftQK 采用 **持久化（persistent）内核**，只启动与 SM 上最大常驻块数（B_res × N_SM）等量的 block，而非每个 token 一个 block。
  - 超过常驻块数的 token 由已有 block 以 **块级令牌流水线（block-level token pipeline）** 的方式循环处理，保证死锁安全，并避免频繁 launch 通信与计算内核的开销。

### 7. 优点（方法或设计上的亮点）

- **切入角度精准**：不仅将问题视为通信延迟隐藏，而是从**算子依赖关系**出发，识别出 RMSNorm 的数学特性（只依赖平方和），将通信量从 O(H) 减至 O(1)，从底层逻辑上消除了瓶颈。
