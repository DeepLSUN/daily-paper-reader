## 摘要
基于LLM的编码代理能够从高层次描述生成完整的软件系统，然而关于架构规范的格式如何影响生成代码的质量，或者这种影响是否依赖于模型能力，目前知之甚少。我们进行了一项受控实验，比较了五种信息等价的规范格式（非正式散文、带约束和ADR的Mermaid图、OpenAPI、C4/Structurizr DSL，以及带ArchUnit风格规则的TypeScript接口契约），使用了来自三个供应商家族（Anthropic Claude、OpenAI GPT、Google Gemini）的六种模型。在90次多轮代理试验中，规范格式显示出强烈的格式与模型交互作用。在最强模型（Sonnet 4.6、GPT-5）上，格式几乎无关紧要（质量差异为0.17-0.92）。在较弱模型上，格式产生0.83-2.42分的差异，其中接近代码的格式（OpenAPI、TypeScript契约）弥补了大部分能力差距。中档模型在进入编译调试循环时，可能比前沿模型消耗更多令牌却产生更差的输出，而更强模型则能避免这种循环。自验证率从100%（Sonnet）降到0%（Gemini Flash），跨越了能力谱系。TypeScript契约使最弱模型的API路由覆盖率增加了两倍（从33%提升至100%）。结构化架构规范作为能力均衡器，其价值与模型强度成反比，对于成本优化的部署回报最大。

## Abstract
LLM-based coding agents generate complete software systems from high-level descriptions, yet little is known about how the format of architecture specifications affects the quality of generated code or whether this effect depends on model capability. We present a controlled experiment comparing five informationally equivalent specification formats (informal prose, Mermaid diagrams with constraints and ADRs, OpenAPI, C4/Structurizr DSL, and TypeScript interface contracts with ArchUnit-style rules) across six models from three vendor families (Anthropic Claude, OpenAI GPT, Google Gemini). Across 90 multi-turn agent trials, specification format shows a strong format x model interaction. On the strongest models (Sonnet 4.6, GPT-5), format barely matters (quality spread 0.17-0.92). On weaker models, format produces spreads of 0.83-2.42 points, with code-proximate formats (OpenAPI, TypeScript contracts) recovering most of the capability gap. Mid-tier models can consume more tokens than frontier models for worse output when they enter compilation debugging loops that stronger models avoid. Self-validation rates collapse from 100% (Sonnet) to 0% (Gemini Flash) across the capability spectrum. TypeScript contracts triple API route coverage for the weakest model (33% to 100%). Structured architecture specifications serve as a capability equalizer, with value inversely proportional to model strength and the largest returns for cost-optimized deployments.

## 1. 核心问题与整体含义

- **研究动机**：LLM 编码代理（如 Claude Code、Copilot Workspace、Cursor）能够通过多轮交互从高层描述生成完整软件系统，但开发者如何向代理传达架构意图（例如通过 `ARCHITECTURE.md`、系统提示或现有代码）仍属经验性实践，缺乏系统研究。
- **核心问题**：架构规范的**格式**是否影响代理生成代码的质量？该影响是否**依赖于模型能力**？——即同一套架构信息，用散文、图表、API 契约或类型接口表达，对前沿模型和弱模型的效果是否不同。
- **总体含义**：结构化架构规范并非单纯“锦上添花”，而是一种**能力均衡器**（capability equalizer）：对前沿模型格式差异几乎无关紧要，但对弱模型和成本优化部署，格式选择直接决定输出质量，价值与模型强度成反比。
- **验证前提**：作者额外做了无架构指南的基线实验，确认“提供架构指导有益”这一前提成立（无架构 vs 散文总分差距达 3.34 分）。

## 2. 方法论

- **核心思想**：通过**受控实验**，在“信息等价”的前提下仅改变架构规范的表现形式，隔离格式对编码代理行为和质量的影响。
- **被测系统**：设计了一个“任务管理 API”（Task Management API），包含 7 个组件：API Router、User/Project/Task/Comment/Notification 五个服务、内存事件总线（Event Bus）。
- **架构定义**：架构被明确为 7 个元素——组件、通信模式（服务之间只允许通过事件总线发布/订阅，禁止直接调用）、数据所有权（服务独占自身存储）、6 条行为约束（如仅 Router 处理 HTTP、状态只能正向流转）、25 条 API 路由、设计决策记录（ADR）、文件结构。
- **五种信息等价的规范格式**：
  1. **Prose（控制组）**：自然语言散文描述。
  2. **Mermaid + 约束 + ADR**：Mermaid 图 + 结构化组件块 + 编号约束列表 + 架构决策记录 + 路由表。
  3. **OpenAPI + Mermaid + 约束**：在上一格式基础上增加完整 OpenAPI 3.0 YAML 契约。
  4. **C4 / Structurizr DSL**：C4 模型的分层分解（System Context → Container → Component），辅以 Mermaid 图和约束/ADR。
  5. **TypeScript 契约 + 架构规则**：直接给出数据模型和服务接口的 TypeScript interface，以及 ArchUnit 风格的伪代码规则（如禁止跨服务导入）。
- **实验流程**：每个试验都是一个多轮会话，代理获得规范后，使用 `write_file`／`read_file`／`list_files`／`run_command`／`done` 工具迭代生成 TypeScript 代码。
- **评估方法（三通道）**：
  - **LLM-as-judge**：由 Claude Sonnet 4.6 对每个代码库盲评 4 个维度（架构遵循度、完整性、代码质量、约束遵循度），1–10 分。
  - **自动化静态验证**：API 路由覆盖率（25 条路由）+ 加权架构合规分数（组件、通信、约束、路由、数据、结构各占不同权重），可覆盖约 80% 的架构。
  - **过程度量**：令牌消耗、编译尝试次数、演示脚本运行率、文件重写率、回合数等。

## 3. 实验设计

## 6. 主要结论与发现

- **格式 × 模型交互显著**：前沿模型（Sonnet 4.6、GPT-5）的格式差异仅为 0.17 和 0.92 分；非前沿模型的格式差异为 0.83–2.42 分（最大为 Gemini Pro 2.42）。
- **代码近似的格式最能弥补能力差距**：OpenAPI 和 TypeScript 契约在弱模型上恢复大部分能力差距；TypeScript 契约是唯一在所有六个模型上达到 100% 路由覆盖率的格式。
- **TypeScript 契约提升最弱模型 3 倍路由覆盖**：Gemini Flash 在散文格式下只实现 33% 的 API 路由，在 TypeScript 契约下达到 100%。
- **倒置的成本效率**：中档模型 Haiku 4.5 平均消耗 735K 令牌，比 Sonnet 多 15%，却低 1.9 分——陷入“编译死亡螺旋”。而 GPT-5-mini 和 Gemini Flash 消耗更少令牌、但以“过早终止”为代价，分数略低。
- **自验证能力随模型能力单调下降**：演示运行率从 Sonnet 的 100% 降至 Gemini Flash 的 0%。作者建议将“代理是否运行自己的测试”作为部署就绪信号。
- **三类失败模式**：
  1. 编译死亡螺旋（中档模型，反复修复引入新错误）；
  2. 过早终止（小模型，不编译不测试就停止）；
  3. 完美主义迭代（强模型 + 结构化格式，过度追求规范符合性而消耗大量令牌）。
- **无架构基线证实架构指导的必要性**：无架构时 Sonnet 总分仅 5.08，有架构（散文）为 8.42，且完全没有产生事件总线。
- **不存在普遍最优格式**：不同模型偏好不同格式（Sonnet 偏好 Mermaid、Haiku/Gemini Pro 偏好 OpenAPI、GPT-5 偏好 TS 契约、Gemini Flash 偏好 C4），需要针对模型测试。
- **Judge 有效性**：GPT-5 重新评审与 Sonnet 评分排名一致性中等（r=0.47–0.60），且未发现同族偏差，而是统一的宽松偏差（GPT-5 平均高 0.42 分）。

## 7. 优点

- **受控信息等价设计**：五种格式内容完全一致，仅改变表现形式，这比简单比较“有无规范”更精确，能隔离格式效应。
- **混合评估体系**：将 LLM 主观评分、自动化静态检查和过程指标结合，弥补单一评估的盲区（例如 Judge 发现自动化检查看不到的语义违规）。
- **引入过程指标作为一等公民**：令牌消耗、编译尝试次数、演示运行率、重写率揭示了“相同分数、不同过程”的深层差异，这在现有基准中很少见。
- **跨供应商、跨能力梯度的因子设计**：能直接观测格式与模型能力的交互，而非只在单一模型上做对比。
- **严谨的 Judge 验证**：通过交叉 reviewer、同族偏差检验、Judge–自动化相关性分析增强结论可信度。
- **实际可操作性**：给出了按模型层级的规范选择建议（前沿用散文、中档用 OpenAPI/TS、弱模型必须用 TS 契约），并开源全部数据与工具，可复现。

## 8. 不足与局限

- **样本量过小**：每格仅 3 次重复，无法做显著性检验，作者自己也承认统计功效不足。
- **单一系统与语言**：只测试了一个中等复杂度的 TypeScript 任务管理后端；其他领域（数据管道、UI 等）和更大规模系统（10+ 服务）的效果未知。
- **模型覆盖有限**：全部为闭源模型，无开源模型（Llama、Mistral）对比；且模型版本随时间可能变化，结果可能不可复现。
- **Judge 潜在偏差**：所有主评分由 Sonnet 4.6 给出，虽经交叉检验无同族偏差，但绝对分数校准和语义判断仍可能异于人类专家。
- **格式覆盖有限**：未测试 UML、SysML v2、AADL、Terraform 等系统/基础设施描述语言，结论不能推广到这些格式。
- **规范质量偏差**：所有规范由同一作者编写，散文可能异常清晰、结构化格式可能异常规整，现实中规范质量参差不齐。
- **时序效应**：六轮模型实验顺序运行而非交错，API 负载、模型更新等时间因素可能引入混淆。
