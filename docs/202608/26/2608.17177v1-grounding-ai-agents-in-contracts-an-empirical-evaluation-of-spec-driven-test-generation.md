## 摘要
基于LLM的代理越来越多地用于编码任务，在这些任务中，它们已经超越了众多经典方法，并扩展到了仓库级别的任务，如测试生成。然而，当直接提示生成测试时，这些代理可能无法对代码及其底层合同进行推理，从而错过影响测试质量的边缘情况和行为边界。为解决这一局限，我们提出了规范驱动的测试生成，即指示代理首先对代码前置条件、后置条件和未定义行为进行推理并明确记录。这种中间半形式化规范充当认知脚手架，以指导后续的测试生成。我们对Google生产环境中缺陷的评估表明，与传统的测试生成代理基线相比，规范驱动的代理在缺陷检测率上可提升9.8个百分点（$p=0.0352$），在分支覆盖率上可提升2.5个百分点（$p=0.0034$）。通过使用LLM作为评判，我们进一步表明，规范驱动代理生成的测试套件在77.8%和56.7%的情况下分别优于基线和人类编写的测试，并在遵循最佳实践、可读性和边缘案例覆盖方面表现出改进。

## Abstract
LLM-based agents are increasingly used for coding tasks, where they have outperformed many classical approaches and scaled to repository-level tasks, such as test generation. However, when directly prompted to generate tests, these agents can fail to reason about the code and its underlying contracts, thereby missing edge cases and behavioral boundaries that affect test quality. To address this limitation, we propose Spec-Driven Test Generation, where we instruct an agent to first reason about -- and explicitly document -- code pre-conditions, post-conditions, and undefined behaviors. This intermediate semi-formal specification acts as a cognitive scaffold to guide subsequent test generation. Our evaluation on production bugs from Google shows that the spec-driven agent can deliver a 9.8 percentage points ($p = 0.0352$) improvement in bug detection rate and a 2.5 percentage point ($p = 0.0034$) improvement in branch coverage, compared to a traditional test generation agent baseline. Using LLM-as-a-Judge, we further show that test suites generated by the spec-driven agent are superior to the baseline and human-authored tests in 77.8% and 56.7% of the cases, respectively, and demonstrated improvements on following best practices, readability, and edge-case coverage.

## 1. 论文的核心问题与整体含义

- **研究动机**：LLM 代理在编码任务上表现出色，但在直接生成测试时往往无法充分推理代码及其底层行为契约（pre-conditions、post-conditions、undefined behaviors），导致测试对边界情况覆盖不足、对潜在缺陷不敏感，测试质量难以达到生产级标准。
- **整体含义**：论文借鉴“Design by Contract (DbC)”思想，提出应让代理在生成测试前先提取并记录代码的半形式化规范（semi-formal specification），以此作为一种“认知脚手架”，将显式契约作为测试生成的逻辑锚点，从而提升 AI 代理在真实工业代码上的测试生成质量。

## 2. 论文提出的方法论

- **核心思想**：在测试生成之前增加一个规范提取阶段，让代理先系统性地理解并文档化代码组件的契约，再进行测试代码合成。
- **关键技术**：**Spec-Driven Test Generation**，采用两阶段代理框架：
  - **Phase I: Specification Extraction（规范提取）**：
    - Context Aggregation：读取目标源代码、docstrings、注释、协议文档等；
    - Contract Inference：推导每个代码单元的**前置条件（Preconditions）**与**后置条件（Postconditions）**；
    - Coverage Assessment：比对现有测试（如有），标记契约条件是否已被测试（Tested/Untested）；
    - Artifact Generation：为未测试条件生成测试建议，输出统一的 `.spec.md` 规范文档。
  - **Phase II: Oracle-Driven Test Generation（规范驱动的测试生成）**：
    - 代理基于生成的规范文档，系统性地将测试建议实现为具体测试用例，并执行编译、运行、验证；
    - 规范文档作为“oracle”，引导测试生成覆盖边界路径和错误行为。
- **规范的形式化定义**：每个代码单元的规范表示为四元组 $S_c = \langle D_c, Pre_c, Post_c, Sug_c \rangle$，分别对应自然语言描述、前置条件集合、后置条件集合、测试建议集合。
- **可选流程**：框架支持在规范提取后的人类介入（Human-in-the-Loop）修正环节，但实验部分为减少人为干扰，跳过了此环节。

## 3. 实验设计

- **数据集**：
  - 90 个来自 Google 内部问题追踪系统的历史生产 bug（包含 buggy 与 fixed 版本代码对）；
  - 覆盖多种语言：C++、Java、Python、Go；
  - 筛选条件：仅包含由人类填写、有已验证修复的可复现运行时故障的 bug；排除语法修复、多媒体处理、PII 相关 bug。
- **Benchmark/场景**：
  - 采用 **Greenfield Test Generation** 设置：移除已有测试套件，代理仅基于修复后的源码生成全新测试套件；
  - 代理全程对 bug 信息、修复 diff 和 commit message 不可见，避免评估循环偏差。
- **对比方法**：
  - **Baseline Agent**：直接提示生成测试套件的标准 prompt-to-code 代理；
  - **Spec-Driven Agent**：本文提出的两阶段代理（规范提取 + 测试生成）；
  - 两者使用相同的底层模型（Gemini 3 Flash）和相同的代理工具集（view_file、list_dir、write_to_file、run_command、grep_search、find_by_name、run_test）。
- **评估指标**：
  - pass@k（测试套件有效性）；detect@k（bug 检出率）；行/分支覆盖率；
  - LLM-as-a-Judge（Gemini 3.1 Pro）评估可读性、最佳实践、边界覆盖、整体质量；
  - 新增 **ContractCoverage@k** 指标，衡量生成的规范是否捕获了历史 bug 违反的行为契约。

## 6. 论文的主要结论与发现

- **RQ1 - 定量有效性**：
  - pass@k 两者基本持平（k=5 时均为 98.9%），说明规范提取不损害代码生成能力；
  - detect@k：Spec-Driven Agent 在 k=1 时为 41.1%（+4.2%），k=5 时达到 63.2%，较基线（53.4%）提升 **9.8 个百分点**（p=0.0352，统计显著）；
  - 分支覆盖率：提升 2.5 个百分点（48.9% vs 46.4%，p=0.0034，统计显著）；
  - 行覆盖率：两者接近（74.4% vs 74.8%，不显著）。
- **RQ2 - 定性质量**：
  - 与基线对比：Spec-Driven 生成测试在最佳实践（65.6%）、可读性（68.9%）、边界覆盖（83.3%）和整体质量（77.8%）上全面占优；
  - 与人类开发者测试对比：Spec-Driven 在 56.7% 的情况下整体上优于人类测试，达到与专家持平的水平。
- **RQ3 - 规范准确性**：
  - ContractCoverage@1 为 61.1%，ContractCoverage@5 提升至 78.9%；
  - 当规范成功覆盖违规契约时，bug 检出率显著更高（54.9% vs 19.4%），证明规范质量与测试有效性强相关；
  - 失败模式分类：规范生成失败主要源于方法遗漏（35/141）、缺失错误处理（32/141）、数据转换遗漏（27/141）等；测试生成失败主要源于输入数据不足（37/110）、场景遗漏（36/110）、断言薄弱（20/110）。
- **RQ4 - 成本效益**：
  - 总 token 消耗增加 38.0%（336.7M vs 243.9M）；
  - 每检测到一个唯一 bug 的 token 成本增加 16.2%（5.9M vs 5.1M），但额外检测到 9 个唯一 bug（+18.8%），性价比可接受。

## 7. 优点

- **方法新颖且创新**：首次系统性地将“先提取契约，再生成测试”的两阶段范式引入代理测试生成，将经典的 DbC 原则与 LLM agent 结合。
- **评估真实且严格**：使用 Google 生产环境的真实历史 bug，而非合成缺陷；绿色字段设置避免了测试修复/复制等捷径；对源码篡改进行了运行时检查（post-execution sanity checks），防止假阳性。
- **统计方法稳健**：bootstrap 置信区间、McNemar 检验、Wilcoxon 符号秩检验、Fisher 精确检验并用，显著增强了结论可信度。
- **评价维度全面**：同时覆盖结构覆盖率、真实缺陷检测率、LLM 定性评估、规范语义完整性和成本分析五方面。
- **提出新度量（Contract Coverage）**：为评估 AI 生成规范提供了可操作的缺陷驱动代理指标，而非不切实际的形式化完备性判断。
- **对 LLM-as-a-Judge 的偏差控制良好**：采用更强模型评审弱模型输出，5 次独立运行多数投票，随机化顺序和匿名化处理，减少了自偏好和顺序偏差。

## 8. 不足与局限

- **数据来源单一**：实验数据全部来自 Google monorepo，代码风格、工程规范、bug 类型均可能带有单一组织特征，结论向开源或其他企业代码库推广需谨慎；数据集规模（90 bugs）相对有限，检测率置信区间较宽。
- **历史 bug 评价范式限制**：评估基于“固定历史漏洞是否能被测试捕获”，只能验证回归测试价值，无法证明代理能发现**新 bug**，对实际生产力提升的推断是间接的；以 bug 检测作为“黄金变异体”，未比较广泛变异测试集下的表现。
- **模型单一性**：所有实验基于 Gemini 系列模型（Flash 生成 + Pro 评测），未验证方法在其他 LLM（如 GPT、Claude、Llama）上的泛化性。
- **LLM-as-a-Judge 固有风险**：尽管做了多重缓解，LLM 评判仍可能存在系统性偏好和噪声，且定性评估依赖的“最佳实践”准则由 LLM 从 Google 内部文档提炼，缺乏独立验证其完整性。
- **成本开销未充分讨论**：38% 的 token 开销仅用总资源估算，未报告时间、算力（GPU）和实际部署成本。
- **HITL 环节未评估**：框架声称支持人工修正规范，但实验中完全跳过了该环节，人类介入是否进一步提升效果尚属未知。
- **单文件修复限制**：数据仅包含修复涉及单一生产代码文件的 bug，无法评估方法在多文件、跨模块复杂变更场景下的表现。
