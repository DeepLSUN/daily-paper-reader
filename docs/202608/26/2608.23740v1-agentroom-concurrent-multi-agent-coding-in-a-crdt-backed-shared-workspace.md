## 摘要
并发多智能体编码有望在多文件项目的自然粒度上实现跨模块分工、通过冗余提高鲁棒性以及并行探索。实时协作编辑协议通过无冲突复制数据类型（CRDTs）为人类团队解决了这种协调问题，但底层的大语言模型一次生成一个token，现有的多智能体编码系统继承了这种串行限制：它们要么通过阶段交接来排序智能体，要么池化独立样本而不进行协调，单个智能体可能会用一个文件的桩代码和退出方式放弃多达一半的困难任务。AgentRoom是一种面向并发编码智能体的实时协作编辑协议。其运行时层在CRDT合并的共享文件系统上，以MCP工具的形式暴露文件级别的声明、状态和广播。五个前沿编码CLI模型运行了四个后端编码任务，并在Python DevBench和Rust+axum上进行了跨语言检查。对于CLI稳定的模型，使用2个智能体的AgentRoom比单独使用更少放弃任务，并且运行间变化更小。在匹配计算量下，一个正的LLM判断平均对比使AgentRoom优于并行合并。另一个对比（即捆绑探针）使完整的AgentRoom优于每个部分情况：这是一个排序而非百分比分割。承担负担的是协调，而不是并行性或CRDT合并。

## Abstract
Concurrent multi-agent coding promises division of labor across modules, robustness through redundancy, and parallel exploration at the natural granularity of multi-file projects. Realtime collaborative editing protocols solve this coordination problem for human teams via Conflict-free Replicated Data Types (CRDTs), but the LLMs underneath generate one token at a time and existing multi-agent coding systems inherit this serial limit: they either sequence agents through phase handoffs or pool independent samples without coordination, and a single agent abandons up to half of hard tasks with a one-file stub-and-exit. AgentRoom is a realtime collaborative editing protocol for concurrent coding agents. Its runtime layer exposes file-level claim, status, and broadcast as MCP tools on a CRDT-merged shared filesystem. Five frontier coding-CLI models ran four backend coding tasks, with cross-language checks in Python DevBench and Rust+axum. For CLI-stable models, AgentRoom with 2 agents abandons fewer tasks than Solo and has less run-to-run variation. At matched-compute, one positive mean LLM-judge contrast puts AgentRoom over parallel-merge. The other contrast, a bundle probe, puts full AgentRoom above each partial case: an ordering rather than a percentage split. Coordination, not parallelism or CRDT-merge, bears the load.

## 1. 论文的核心问题与整体含义

- **背景**：并发多智能体编码（multi-agent coding）在理论上可以带来跨模块分工、冗余带来的鲁棒性，以及并行探索，特别适合多文件项目的天然粒度。但底层 LLM 逐 token 生成，现有系统大多继承了串行限制：要么让智能体按阶段交接（如设计→实现→评审），要么将独立样本池化而不做协调。
- **痛点**：单智能体在困难任务上高达约一半比例的失败模式是“1-file stub-and-exit”——只生成一个文件骨架便提前退出，认为任务太难。
- **已有探索**：隐式并发协调（如 CodeCRDT）结果不稳定（21% 加速 / 39% 减速），且存在 5–10% 语义冲突。
- **核心问题**：在匹配计算量（matched compute）下，在一个 CRDT 合并的共享工作区上，显式协调能否同时胜过串行交接范式和隐式 CRDT 并发范式？
- **AgentRoom 的定位**：一套面向并发编码智能体的实时协作编辑协议，构建在 CRDT 合并的共享文件系统之上，通过 MCP 工具向智能体暴露文件级声明（claim）、状态（status）和广播（broadcast），从而实现显式、有结构的协调。
- **核心主张**：性能提升的主要来源是“协调”（coordination），而非“并行性”本身或 CRDT 合并机制。

## 2. 论文提出的方法论

### 2.1 总体架构

- AgentRoom 是一个单一集成原语，包含三部分（三者协同设计）：
  1. **CRDT 共享工作区 W**：所有 N 个智能体在同一文件系统上工作，任何智能体的写入立即可见；pycrdt（Yrs 移植）在约 2 秒窗口内做字符级合并，并附加括号/花括号配平检查。
  2. **协调接口（MCP 工具）**：
     - `room_claim(path)`：原子分配文件所有权，冲突时拒绝。
     - `room_broadcast` / `room_read`：追加型 JSONL 消息日志。
     - `room_state`：展示各个智能体状态（活动声明 + 最近日志窗口）。
     - `room_read`：读取文件。
  3. **协作协议（advisory，建议式）**：
     - 六步流程：写前读room状态 → 声明拟创建文件 → 冲突时改选文件 → 写已声明文件 → 子任务间轮询更新 → broadcast完成。
     - 两条常设规则：房间拒绝已被他人持有的文件声明；提示智能体写前先读已有文件并 import 队友代码。
     - 协议属于“prompt 层建议”而非内核强制，类似 Chubby 式 advisory lock。

### 2.2 形式化基础

- **SEC**：基于 op-based 序列 CRDT（Lamport 时间戳），满足强最终一致性，保证字节级并发编辑不丢失数据。
- **关键不足**：SEC 只保证字节级合并，不保证语义兼容——两个智能体在同一字符偏移插入不兼容的函数签名，可能都存活并导致编译失败。
- **碰撞率**：若 N 个智能体从 Kt 个候选文件中独立选择目标文件（实际因共享任务/工作区而有偏，所以是下界），碰撞概率为
  \[
  p_{collision}(N,K_t)=1-\prod_{k=0}^{N-1}\left(1-\frac{k}{K_t}\right)
  \]
  在 N=2、Kt≈5 时约 0.20。碰撞代价高，claim 原语以 O(1) 每编辑成本将碰撞率降到零。
- **信息密度动机**：把 patch 看作覆盖 rubric 维度的随机变量，在有 claim 协调的并行采样中，每步跨智能体的联合信息接近线性扩展；无协调时因碰撞导致联合熵坍缩，并行算力浪费在冗余编辑上。

## 6. 主要结论与发现

### 6.1 Tier I：放弃率与方差降低（最强证据）

- **放弃率大幅下降**：全部 12 个模型×任务分层上，Solo 放弃概率的 CMH 公共 OR 为 13.7（95% CI [3.9, 48]，p < 10⁻⁵，Tarone 齐性 p=0.92）。汇总计数：Solo 40/131（31%）→ AgentRoom 5/94（5%）。
- **个别显著性**：T4 Haiku 12/35 → 1/17（p=0.025）；T4 Codex 9/17 → 2/21（p=0.005）；T4 Sonnet 6/33 → 0/17（p=0.070）。
- **方差收缩**：AgentRoom ×2 将运行间标准差降低约 30–45%（Sonnet 0.23→0.14，Haiku 0.25→0.17，Codex 0.27→0.15）。

### 6.2 Tier II：匹配计算量消融排序

- **T4 Sonnet 六条件单调排序**：ChatDev-style（0.333）< parallel-merge（0.456）< Solo（0.544）< Shared-only（0.575）< Shared + prompt noMCP（0.588）< AgentRoom ×2（0.669）。
- **关键对比**：AgentRoom 比 parallel-merge 高 +0.213（Welch t=3.35, p=0.003）。无协调的并行合并甚至低于 solo，因为第二个智能体的 server.ts 会静默覆盖第一个智能体的文件。
- **与串行管线对比**：ChatDev-style（n=6 有效运行）均分 0.333，AgentRoom ×2 为 0.669（p=0.006）；串行管线在每个阶段边界放大了单智能体放弃模式。

### 6.3 组件剥离与机制归因

- 保留 CRDT + 协作提示、移除 MCP 工具面后仅比 shared-only 高 +0.013；加上 MCP 协调层进一步 +0.081——**最大观察步骤来自显式协调通道**，而非 CRDT 基质或提示。
- 结论：协调负担权重最大；并行性或 CRDT 合并本身不是主要贡献者。

### 6.4 其他发现

- **智能体数量最优为 2**：T4 Sonnet 质量在 ×2 达峰（0.669），×3（0.553）与 ×4（0.489）下降；广播流量在 ×3 后超线性上升。
- **成本等价对比**：2×Haiku AgentRoom（0.662, n=17）以约一半美元成本击败 1×Sonnet（0.544, n=32），p=0.036，提示配对较小模型在 Pareto 前沿有竞争力。
- **结构化状态优于自由文本聊天**：T5 上 MCP-chat 后端（n=2）1/2 失败（因两 agent 同时以自由文本广播声明且均未检测冲突），CRDT-state 的 room_claim 返回系统级冲突错误，7/7 成功。
- **跨语言方向性复现**：Python DevBench 8/10 通过（Solo 为 7/10）；Rust+axum 上 ×2 与 Solo 持平（0.740 vs 0.714，描述性）。

## 7. 优点

1. **清晰的问题定位**：将多智能体编码的瓶颈明确归结为协调问题，并通过匹配计算量的消融设计（parallel-merge vs AgentRoom）干净地分离了“并发”与“协调”的贡献。
2. **完善的形式化动机**：碰撞率公式与信息密度推导为协调层提供了理论基础；CRDT 的 SEC 与 claim 原语的角色划分清晰。
3. **多评分器交叉验证**：LLM-judge、regex、AST 三类评分器相关性与排序一致性较好，并针对同族偏好偏差引入了跨厂商 judge。
4. **统计严谨性好**：CMH 分层检验、Tarone 齐性检验、bootstrap CI、阈值敏感性扫描和池敏感性分析齐备；对多个结果主动给出“探索性”降级标注。
5. **透明与可审计**：提供完整 agent 日志示例、阈值代码簿、release bundle；对 Gemini CLI 非兼容、Codex-mini 崩溃等部署问题做了根因分析并修复验证。
6. **研究边界诚实**：不声称 bit-for-bit 复现，不夸大跨语言泛化，明确区分证据层级（Tier I/II/III）。
7. **与现有系统定位区分度高**：明确对比 CodeCRDT 的隐式协调、ChatDev 的串行角色阶段，并指出二者互补（CodeCRDT 字符级合并可用于 AgentRoom 的已声明文件内编辑）。

## 8. 不足与局限

1. **实验覆盖偏窄**：主结果全部基于单个 Express.js/TypeScript 运行时；Rust/Python 检查样本小（n≤10 个任务），只能作为方向性证据，不能证明跨语言量级泛化。
2. **无真值测试套件**：任务是“自由构建”，智能体自行编写 vitest 套件；缺少 held-out 正确性集，质量评估依赖 LLM-judge 综合分，尽管用多个 scorer 交叉验证，但无法声称执行级正确性。
3. **统计功效不均**：多个关键单元 n 仅 5–17，例如 MCP-chat 对比只有 n=2、异质配对 n=1–4、Gemini 只有 5+5；部分结论（如组件步长）的置信区间跨越零，只能解读为排序。
4. **捆绑设计无法完全解耦**：CRDT、协作提示、MCP 工具面是协同设计的，组件探针只能部分分离；提示与通道对 Haiku 的效果无法分开识别（提示兼作工作流脚手架）。
5. **托管模型不可复现性**：厂商托管 API 可服务端更新，不做 bit-for-bit 复现；只能在“匹配 CLI + 匹配预算”条件下保证对比有效性。
6. **模型异质性结果不稳定**：Codex 在多智能体配对中一致退化（与单体架构先验相关）；Sonnet+Codex 在 LLM-judge 上最高但测试通过率低于同质配对，模型间结论不一致。
7. **可扩展性问题未解决**：×3、×4 质量下降与广播流量超线性增长相关，但未做多通道消融，无法归因于广播通道饱和；N=2 是最优工作点，大 N 场景尚不清晰。
8. **质量定义有限**：综合分只覆盖四维度，不测可维护性、安全性、长期演进成本；不能直接解读为软件质量整体。
9. **潜在偏差**：成本等价跨模型对比暴露了价格/能力不等价的偏差风险；同族 judge 虽经跨厂商验证，但“完全独立第三方 judge”仍未实现。
