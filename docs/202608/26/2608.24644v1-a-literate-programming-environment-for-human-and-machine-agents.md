## 摘要
本文介绍了一个环境，用于与语言感知的机器代理协同构建文学程序。该环境包括一个可执行程序散文的语法、一个将名称视为一等对象的解析器、一个连接散文、名称与可执行工件的内部名称图，以及一个用于现有语言和测试工具集的绑定机制。这支持将代码与其最相关的自然语言和结构化数据上下文共同定位，从而更好地利用大型语言模型（LLM）的上下文窗口。它还为LLM编码代理提供了一套工具，更类似于人类程序员面对的集成开发环境（IDE）中可用的符号感知搜索和使用信息。我们描述了一个工作实现，它绑定到三种已建立的编程语言，并提供了几个示例程序。

## Abstract
This paper introduces an environment for constructing literate programs in concert with language-aware machine agents. This environment includes a grammar for executable program essays, a parser that treats names as first-class objects, an internal name-graph which relates prose, names and executable artifacts, and a binding mechanism for existing languages and testing toolsets. This supports co-location of code with its most relevant natural language and structured data context, making better use of Large Language Model (LLM) context windows. It also provides LLM coding agents with a toolset more analogous to the symbol-aware search and usage information available in human programmer-facing Integrated Development Environments (IDEs). We describe a working implementation with bindings to three established programming languages, and several example programs.

  - **上下文窗口（Context Window）的影响占据主导地位**：LLM 在推理过程中不学习，会话记忆完全依赖将符号重新注入上下文窗口。
- **理论对立**：Peter Naur 认为"编程即理论构建"，理论主要存在于程序员脑中而非代码工件中。而 Knuth 的文学编程（Literate Programming）认为程序理论可以通过书写工件有效传达，精良的自然语言是高效载体。
- **核心问题**：当编程从"人机对话"转向"人-LLM 协作"时，编程语言与环境应当如何设计，使 LLM 编码代理拥有类似人类程序员 IDE 中的符号感知搜索与使用信息，同时充分利用有限的上下文窗口？

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- 借鉴文学编程传统，将程序组织为**可执行的"程序散文"（program essays）**，使自然语言、代码和验证检查共置（co-location）于单一源工件中，而非像规格驱动开发（SDD）那样将规格置于代码生成流水线的上游。
- 设计目标是让**人类和机器代理共同阅读**这些"散文"及其中的可执行代码。

### 关键技术细节

- **语言语法（notlob）**：
  - 宏观结构仿照技术报告：正文（body）+ 补充文本（post text），补充文本以 `---` 分隔符开始。
  - Markdown 风格的 `#` 标题与 `##` 子标题，标题在语法中是一等结构。
  - 可执行块通过缩进标记；语法由语言绑定决定。
  - 使用 `~` 前缀关键字（sigil）区分可执行块类型：`~property`（性质测试）、`~example`（示例）、`~test`（单元测试）、`~run`（执行入口）、`~language`/`~external`/`~on-build`/`~keep-generated-src`（绑定配置）。
  - 词法分析使用歧义正则文法，通过规则优先级和最大匹配（maximal munch）消歧，散文回退优先级最低。

- **语义与名称图（Name-Graph）**：
  - **名称被视为一等对象**，标题和子标题是语法的一部分，可被解析与引用。
  - 解析树可构建**名称图**：连接散文、名称、概念与代码的图结构，节点包含源文件位置，支持精确定位。
  - 提供两种相邻性（adjacency）：**文件相邻性**（同一文本块中的邻近）和**概念相邻性**（图中短路径连接），均可供人类和机器代理廉价访问。
  - 名称图还用于跨代码库的一致性检查（包括散文本身），是 Knuth 索引的非线性数据结构的现代对应物。

- **绑定机制（Bindings）**：
  - 绑定定义了编程语言、单元测试库、属性测试库和 linter（如 Haskell 绑定使用 stack-ghc、hunit、quickcheck、hlint）。
  - 通过绑定支持三种既有语言：Haskell、Python、TypeScript（另有实验性 Rust 绑定）。
  - 各 sigil 有语义限制：`~example` 限于正文作为概念阐述；`~test` 限于补充部分的 `#Tests` 区作为事实陈述；`~property` 期望在正文中靠近解释性散文。

- **工具链**：
  - 提供 `run`、`test`、`build`、`weave`（渲染 Markdown）、`graph`（导出名称图 JSON/RDF）、`query`（图查询）、`check`（一致性检查）、`mcp`（MCP 服务器）等命令。
  - 文件系统布局有确定性规则：标题中每个词对应一个子目录（如 `#Roman Numerals` → `roman/numerals.lob`）。
  - `check` 命令将缺失导入和未使用引用视为错误；近似名称拼写不一致等问题给出信息级警告。

## 6. 主要结论与发现

- notlob 作为面向"人-LLM 协作"的文学编程环境**在技术上是可行的**：已实现支持三种语言的完整工具链和多个可运行示例程序。

- 在 Pleiades 项目中，代理生成的代码和散文高度贴合设计草图，能主动发现类型签名不一致、建议新模块（如 BCE 日期处理），但也传播了人类输入的错误拼写和未被审视的假设。
- 设计批评会话发现的常见问题包括：散文与代码漂移、隐含原则未被提升为可检查的 `~property` 块、代理倾向忽略支撑其工作的声明性工件（声明性工件被忽视现象在多种工件类型中重复出现）。
