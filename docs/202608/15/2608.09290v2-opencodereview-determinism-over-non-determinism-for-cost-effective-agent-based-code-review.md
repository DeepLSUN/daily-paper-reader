## 摘要
基于LLM的代码审查代理承诺提供可扩展、始终在线的审查，但现有系统存在两个相互交织的弱点：(1) 非确定性——无界的工具使用使审查结果不稳定；(2) 上下文局部性——审查者的访问仍局限于差异(diff)，限制了可发现问题的深度。两者共同引发了三个挑战：上下文检索错位、多文件拉取请求中的连贯性与效率权衡，以及侵蚀信任的幻觉评论。为解决这些问题，我们提出了OpenCodeReview，其构建于针对不确定代理的确定性工程之上：不是赋予最大自由度，而是在三个精心设计的流水线节点注入确定性。规则引导调度(Rule-Guided Dispatch)使用多层规则系统确定性地选择文件和审查标准，消除代理驱动分类的变异性。基于实地的文件审查(Grounded File Review)用通过ReAct循环暴露的精选工具集取代自由探索，同时文件级并行子代理(SubAgents)在上下文连贯性与效率之间取得平衡，并按需恢复跨文件依赖。独立反思(Independent Reflection)引入了一种在非对称信息边界下的先证伪过滤器——反射器仅看到差异，而不见代理的工具增强探索——从而在无自我强化偏差的情况下移除幻觉评论，提高精确率同时保持召回率。在AACR-Bench（200个真实PR，10种语言，1,505条专家验证评论）上，OpenCodeReview在六个LLM后端上优于主流编码代理（如Claude Code和Codex），SEM-F1最高提升2.17倍（25.10%对11.57%），同时消耗的令牌数减少5–15倍。我们在https://github.com/alibaba/open-code-review开源了OpenCodeReview。

## Abstract
LLM-based code review agents promise scalable, always-on review, yet current systems suffer from two intertwined weaknesses: (1) non-determinism--unbounded tool use makes review outcomes unstable, and (2) context locality--the reviewer's access remains bounded to the diff, capping discoverable issue depth. Both give rise to three challenges: misaligned context retrieval, a coherence-efficiency trade-off in multi-file pull requests, and hallucinated comments that erode trust. To address these, we introduce OpenCodeReview, built on deterministic engineering for uncertain agents: rather than granting maximal freedom, we inject determinism at three deliberate pipeline points. Rule-Guided Dispatch uses a multi-layer rule system to deterministically select files and review criteria, eliminating variability of agent-driven triage. Grounded File Review replaces free-form exploration with a curated tool set exposed through a ReAct loop, while file-level parallel SubAgents balance context coherence against efficiency and recover cross-file dependencies on demand. Independent Reflection introduces a falsification-first filter under an asymmetric information boundary--the reflector sees only the diff, not the agent's tool-augmented exploration--removing hallucinated comments without self-reinforcing bias, improving precision while preserving recall. On AACR-Bench (200 real-world PRs, 10 languages, 1,505 expert-verified comments), OpenCodeReview outperforms mainstream coding agents (e.g., Claude Code and Codex) across six LLM backends, achieving up to 2.17x higher SEM-F1 (25.10% vs. 11.57%) while consuming 5-15x fewer tokens. We open-source OpenCodeReview at https://github.com/alibaba/open-code-review.

# OpenCodeReview 论文总结

## 1. 论文的核心问题与整体含义

**研究动机与背景：**

- 代码审查是软件质量保证的基石，但人工审查成本高昂（时间、认知负荷、周转延迟），难以规模化。
- LLM 的进步使"可扩展、始终在线"的自动代码审查成为可能，主流编码代理（Claude Code、Codex、Cursor、OpenCode）已内置审查功能。
- 然而，现有基于 LLM 的代码审查代理存在**两个相互交织的根本弱点**：
  - **非确定性（Non-determinism）**：无界的工具使用和庞大的动作空间导致跨运行审查结果不稳定、不可复现。
  - **上下文局部性（Context locality）**：审查者的有效访问范围仍然局限于 diff 本身，无法深入探索仓库级上下文，限制了可发现问题的深度（如跨文件的数据流缺陷、破坏远端调用方的回归等）。
- 两个弱点共同引发了三大挑战：
  1. **上下文检索错位**：检索策略失衡，要么污染上下文（无关代码稀释信号），要么回到局部受限的窠臼。
  2. **多文件 PR 的连贯性-效率权衡**：单代理共享上下文保持全局视野但成本随变更规模爆炸；过度细分的并行代理则割裂变更的连贯性。
  3. **幻觉评论**：多步代理容易产生与 diff 证据相悖的评论，侵蚀信任并施加额外筛选成本。

**核心含义**：论文主张，对于代码审查这类范围明确、重复性的任务，**非确定性不是 LLM 代理的固有属性，而是设计缺陷**，可以通过在任务验证的维度上约束代理行为来消除——即"确定性工程"（Deterministic Engineering）范式。

## 2. 方法论：核心思想与关键技术细节

### 核心思想：确定性工程（Deterministic Engineering for Uncertain Agents）

- 不授予代理最大自由，而是在审查流水线的**三个关键节点**主动注入确定性，兼顾审查深度、输出可靠性和成本效率。

### 关键技术细节

**（1）Rule-Guided Dispatch（规则引导调度）**

- **规则概念**：规则是自然语言审查准则文档，通过 glob 路径模式确定哪些文件在范围内，通过结构化检查清单（正确性、安全性、性能、可维护性、测试覆盖）指定审查标准。
- **四层规则优先级链**：
  - 第 1 层（最高）：调用时提供的临时规则（Ad-hoc）
  - 第 2 层：仓库中版本控制的项目级规则（Project-level）
  - 第 3 层：用户主目录的跨项目全局规则（User-global）
  - 第 4 层（最低）：内置系统规则（Built-in，覆盖主流语言和配置文件格式）
  - 支持 **替换模式（Replace，默认）** 与 **合并模式（Merge）**；采用首次匹配优先语义，确定性映射文件到规则。
- **文件过滤与调度**：多级过滤（排除二进制文件、应用用户排除/包含模式、扩展名白名单、排除测试夹具和生成代码、过滤 diff 超过模型上下文窗口 80% 的文件），然后为每个文件并行启动一个独立的 SubAgent。
- **效果**：同一 PR 始终产生相同的文件分配和审查标准，消除了代理自主文件分类的随机性。

**（2）Grounded File Review（接地文件审查）**

- **ReAct 代理循环**：每个 SubAgent 执行标准的 Thought-Action-Observation 循环，默认最大迭代次数为 30；包含**空轮检测**（连续三轮无工具调用则强制行动或终止）和**上下文压缩**（60% 上下文利用率时异步压缩，80% 时同步强制压缩中间区域，采用"冻结-压缩-活跃"三区域策略缓解 token 雪球效应）。
- **精选工具集**（替代通用 bash shell）：
  - `file_read`：读取文件内容（最多 500 行/次）
  - `file_find`：按名称关键字定位文件（最多 100 个结果）
  - `code_search`：跨仓库文本模式搜索（最多 100 个匹配，10 秒超时）
  - `file_read_diff`：查看其他变更文件的 diff（审查多文件 PR 时特有）
  - `code_comment`：提交审查评论
  - `task_done`：结束循环
  - 工具设计基于人类专家审查者导航仓库的真实模式，输出边界有硬性约束，既有跨文件探索能力又避免上下文膨胀。
- **评论生成与行号解析**：三级回退机制定位行号——
  1. 将 `existing_code` 与 diff 新侧 hunk 匹配；
  2. 失败则在完整文件内容中搜索；
  3. 仍失败则调用 LLM 辅助重新定位。

**（3）Independent Reflection（独立反思过滤）**

- **非对称信息边界（Asymmetric Information Boundary）**：反思器只看到 diff，不看到 SubAgent 的工具增强探索结果。这打破了同模型自我批评的自我强化偏差。
- **证伪优先（Falsification-First）原则**：反思器执行两步评估——
  - **事实检查（否决规则）**：仅当 diff 包含直接反驳评论核心主张的证据时标记删除；评论引用 diff 外上下文时不标记。
  - **问题分类**：检查评论是否错误描述代码性质。
- **纯过滤设计**：反思器只能删除评论，不能生成新评论；解析失败时保持所有评论（故障开放），优先保证召回率。

## 6. 主要结论与发现

1. **系统性优势**：OpenCodeReview 在所有 6 个 LLM 后端上取得最高 SEM-F1（17.90%–25.10%），而 Claude Code 为 10.93%–14.13%，Codex 为 8.36%。最弱配置（Deepseek-V4-Pro，17.90%）仍超过最强 Claude Code 配置（14.13%）。
2. **同模型对比显著提升**：Claude-4.6-Opus 在 OpenCodeReview 下 SEM-F1 为 25.10%，在 Claude Code 下仅为 11.57%——**2.17 倍提升完全归因于系统设计**。模型在 OpenCodeReview 中排名第一，在 Claude Code 中却接近垫底。
3. **优势来自精度而非召回率膨胀**：OpenCodeReview 精度 25.20%–37.80% vs. Claude Code 7.23%–15.93%。Claude Code 的高召回率（28.90%）是靠生成海量评论（4,580 条）换来的，这正是文献中记录的低信噪比问题。
4. **成本效率突破**：OpenCodeReview 消耗 **5–15 倍更少的 token**，同时实现 **1.3–2.2 倍更高的 SEM-F1**。token 节省来源于规则引导调度（避免探索性分类开销）、有界输出工具（防 token 雪球）、文件级并行与上下文隔离。
5. **系统设计比模型选择更重要**：性能差异主要由系统架构驱动，而非底层模型。
6. **信息边界而非模型边界实现反思独立性**：非对称信息边界的证伪优先过滤器比同模型自我批评更有效。

## 7. 优点

- **创新性思想**："确定性工程"明确挑战了"更多自主性→更好结果"的主流假设，为代理设计提供了新范式——通过任务验证约束维度来控制不确定性。
- **工具设计有据可依**：精选工具集基于人类审查者真实导航模式的观察，而非随意借用程序修复或代码搜索的工具，实现了信息需求与工具模式的对齐。
- **巧妙的信息边界设计**：反思器使用相同 LLM 但只看 diff（比代理看更少），有效打破自我强化偏差，设计优雅且具有通用潜力。

- **报告完整度高**：提供了精确率、召回率、token 消耗、运行时间等多维度数据，成本-质量联合分析详实。
- **开源可用**：代码已开源，便于复现和后续研究。
