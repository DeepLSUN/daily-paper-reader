## 摘要
基于LLM的代码审查智能体承诺提供可扩展、始终在线的审查，但现有系统存在两个相互关联的弱点：(1) 非确定性——无限制的工具使用导致审查结果不稳定；(2) 上下文局部性——审查者的访问范围仅限于diff，限制了可发现问题的深度。这两者引出了三个挑战：上下文检索错位、多文件拉取请求中的连贯性与效率权衡，以及侵蚀信任的幻觉评论。为解决这些问题，我们提出了OpenCodeReview，它建立在针对不确定智能体的确定性工程之上：我们不是赋予最大自由度，而是在三个精心设计的流水线节点注入确定性。规则引导调度（Rule-Guided Dispatch）使用多层规则系统来确定性地选择文件和审查标准，消除了智能体驱动的分诊变异。接地文件审查（Grounded File Review）通过ReAct循环公开一组精选工具，取代自由形式的探索，而文件级并行子智能体（SubAgents）在上下文连贯性与效率之间取得平衡，并按需恢复跨文件依赖。独立反思（Independent Reflection）在非对称信息边界下引入先证伪过滤器——反射器仅可见diff，而非智能体的工具增强探索——从而去除幻觉评论而不会自我强化偏差，在保持召回率的同时提高精确率。在AACR-Bench（200个真实PR、10种语言、1,505条专家验证评论）上，OpenCodeReview在六个LLM后台上优于主流编码智能体（如Claude Code和Codex），SEM-F1最高提升2.17倍（25.10%对比11.57%），同时消耗5-15倍更少的令牌。我们在https://github.com/alibaba/open-code-review开源了OpenCodeReview。

## Abstract
LLM-based code review agents promise scalable, always-on review, yet current systems suffer from two intertwined weaknesses: (1) non-determinism--unbounded tool use makes review outcomes unstable, and (2) context locality--the reviewer's access remains bounded to the diff, capping discoverable issue depth. Both give rise to three challenges: misaligned context retrieval, a coherence-efficiency trade-off in multi-file pull requests, and hallucinated comments that erode trust. To address these, we introduce OpenCodeReview, built on deterministic engineering for uncertain agents: rather than granting maximal freedom, we inject determinism at three deliberate pipeline points. Rule-Guided Dispatch uses a multi-layer rule system to deterministically select files and review criteria, eliminating variability of agent-driven triage. Grounded File Review replaces free-form exploration with a curated tool set exposed through a ReAct loop, while file-level parallel SubAgents balance context coherence against efficiency and recover cross-file dependencies on demand. Independent Reflection introduces a falsification-first filter under an asymmetric information boundary--the reflector sees only the diff, not the agent's tool-augmented exploration--removing hallucinated comments without self-reinforcing bias, improving precision while preserving recall. On AACR-Bench (200 real-world PRs, 10 languages, 1,505 expert-verified comments), OpenCodeReview outperforms mainstream coding agents (e.g., Claude Code and Codex) across six LLM backends, achieving up to 2.17x higher SEM-F1 (25.10% vs. 11.57%) while consuming 5-15x fewer tokens. We open-source OpenCodeReview at https://github.com/alibaba/open-code-review.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：代码审查是软件质量保障的基石，但人工审查成本高昂（审查者时间、认知负荷、交付延迟），在大规模项目中成为瓶颈。LLM 的进步使得自动化、可扩展、全天候的代码审查成为可能，主流编码代理（如 Claude Code、Codex、Cursor、OpenCode）已内置代码审查功能。
- **核心问题**：现有 LLM 代码审查智能体存在两个相互关联的弱点：
  1. **非确定性（Non-determinism）**：无限制的工具使用和庞大的动作空间导致审查结果在多次运行间不稳定。
  2. **上下文局部性（Context locality）**：审查者的有效访问范围仅限于 diff 本身，无法深入仓库，限制了可发现问题的深度（如跨文件控制/数据流缺陷、破坏远端调用者的回归、仓库级规范违反）。
- **由此引发的三个挑战**：
  1. 上下文检索策略错位：自由扩展上下文会导致上下文污染，过度保守则退回局部性受限状态；通用工具（如 bash）与真实审查信息需求不匹配。
  2. 多文件 PR 中上下文连贯性与执行效率的权衡：单体代理成本高，过于细粒度的划分会碎片化变更。
  3. 幻觉评论：多步智能体倾向于捏造不存在的证据或发明无根据的问题，侵蚀信任并增加人工核验成本；现有自反思机制存在自我强化偏差。
- **核心论点**：LLM 智能体的非确定性并非固有属性，而是可以通过**确定性工程**（在任务验证的轴上约束动作空间）被工程设计消除。OpenCodeReview 通过"对不确定智能体进行确定性工程"这一原则，在三个关键节点注入确定性，同时提升审查深度、可靠性和效率。

## 2. 方法论：核心思想、关键技术细节

**总体设计哲学**：确定性工程——不给智能体最大自由，而是沿与审查真实信息需求对齐的轴注入确定性。

**三大核心模块**：

1. **规则引导调度（Rule-Guided Dispatch）**
   - **规则概念**：自然语言文档，包含 glob 路径模式（决定文件范围）和结构化审查清单（正确性、安全、性能、可维护性、测试覆盖）。
   - **四层优先级规则链**：Ad-hoc（调用时提供）> 项目级（仓库内、版本控制）> 用户全局（跨项目）> 内置系统规则（按语言/文件类型默认）。
   - **替换/合并模式**：用户规则可完全替换或合并追加到系统规则。
   - **文件过滤与调度**：多阶段过滤（排除二进制文件、用户排除/包含模式、扩展名允许列表、排除测试夹具和生成代码、diff 超过上下文窗口 80% 过滤），每个文件分配一个独立 SubAgent 并行运行。
   - **效果**：相同 PR 始终产生相同的文件与标准分配，消除代理驱动文件分诊的变异性。

2. **接地文件审查（Grounded File Review）**
   - **ReAct 循环**：Thought→Action→Observation，默认最大 30 轮迭代。
   - **循环控制机制**：
     - 空轮检测：连续三轮无工具调用则提示行动或终止。
     - 上下文压缩：60% 利用率触发异步后台压缩，80% 触发同步强制压缩（冻结-压缩-活跃三区域策略），缓解 "token snowball" 效应。
   - **精选上下文工具集（6个工具，输出有界）**：
     - `file_read`：按路径和行号范围读取文件，最大 500 行/次。
     - `file_find`：按文件名关键字定位，最大 100 结果。
     - `code_search`：跨仓库搜索文本模式，最大 100 匹配，10 秒超时。
     - `file_read_diff`：查看另一个变更文件的预计算 diff（多文件 PR 场景特有的工具）。
     - `code_comment`：提交审查评论（解析后异步收集）。
     - `task_done`：发出任务完成信号，终止循环。
   - **严格聚焦规则**：系统提示明确其他文件的发现不得成为评论主题，只审查当前文件 diff。
   - **评论行号解析**：三阶段回退——(1) 匹配 `existing_code` 到 diff 新侧 hunks；(2) 搜索完整文件内容；(3) LLM 辅助重新提取引用片段。

3. **独立反思（Independent Reflection）**
   - **非对称信息边界**：反思器只接收文件 diff 和评论列表，看不到 SubAgent 的完整工具增强探索上下文；不同于内在自我反思（同模型相同上下文，继承自我强化偏差）。
   - **证伪优先原则（Falsification，而非 Verification）**：
     - 事实检查（否决规则）：若 diff 包含与评论直接矛盾的证据，则标记删除；若评论引用 diff 不可见的上下文，不标记。
     - 问题分类：检查评论是否曲解代码（如将正常代码标记为缺陷）。
   - **只过滤不生成**：反思器只能删评论、不能生成新评论，保守地只降低假阳性、不引入新误报；解析失败时 fail-open（保留所有评论）。

## 6. 主要结论与发现

1. **系统性超越**：OpenCodeReview 在所有 6 个 LLM 后端上均取得最高 SEM-F1（17.90%~25.10%），Claude Code 为 10.93%~14.13%，Codex 为 8.36%；最弱配置（Deepseek-V4-Pro，17.90%）超过最强 Claude Code 配置（14.13%）。
2. **模型内增益**：Claude-4.6-Opus 在 OpenCodeReview 下为 25.10% SEM-F1，在 Claude Code 下仅 11.57%，提升 2.17 倍——纯粹由系统设计带来。模型质量不是主导因素，系统设计贡献更大。
3. **优势来自精确率而非召回率膨胀**：OpenCodeReview 精确率 25.20%~37.80% vs. Claude Code 7.23%~15.93%。Claude Code 靠大量生成评论（4,580 条 vs. 465~1,096 条）达到高召回率，但精确率严重退化，即"低信噪比"问题。
4. **成本效率**：OpenCodeReview 比 Claude Code 少消耗 5~15 倍 token，同时 SEM-F1 提升 1.3~2.2 倍；比 Codex（同 GPT-5.5）SEM-F1 高 2.5 倍，token 消耗相当。
5. **精确率-召回率权衡**：OpenCodeReview 聚类在高精确率、中等召回率区域；Claude Code 分为高召回低精确（Claude-4.6-Opus、Qwen3.7-Max）和中精确低召回（Claude-4.8-Opus）两类；Codex 处于极低召回（5%）中精确（28%）区域。
6. **确定性工程的价值**：结构化的探索（而非消除探索）同时提升质量和降低成本；非对称信息边界比模型身份更能实现反思独立性。

## 7. 优点

1. **设计理念创新**："确定性工程"原则具有普适启发性——不是盲目追求智能体自主性，而是识别任务关键轴并注入确定性，挑战了 LLM 代理研究中"更多自主=更好结果"的主流假设。
2. **三个模块设计各有亮点**：
   - 规则引导调度的四层优先级链和替换/合并模式兼顾确定性（首选匹配）与灵活性（用户可定制）。
   - 精选工具集基于数据驱动的审查者信息需求分析，每个工具输出有界、有超时，从设计上防止 token 雪球效应。
   - 独立反思的非对称信息边界是新颖设计：反射器看到更少而非更多，打破自反思的自我强化偏差，且只过滤不生成保证保守性。
3. **实验设计严谨**：6 个模型后端 × 3 个系统的多配置对照，同一模型在多系统下的对比排除了模型能力混淆；通过"AI 辅助+专家验证"的三轮交叉验证真值保障基准质量；LLM judge 多次运行取均值缓解非确定性。
4. **实际部署导向**：平均每样本 1~7 分钟、35 万~74 万 token 的成本在工业规模下可行，具有直接落地价值。
5. **开源贡献**：完整开源系统，便于复现和后续研究。

## 8. 不足与局限

1. **缺乏消融实验**：这是最显著的实验设计缺陷。无法得知规则引导调度、精选工具集、文件级并行、独立反思各自对 SEM-F1 提升的独立贡献程度，也无从判断哪些设计最为关键。
2. **基线覆盖不足**：
   - 仅对比两个工业基线（Claude Code、Codex），未与学术代理系统（如 CodeAgent、CodeReviewer）或其他 RAG 方法对比，难以在更广的学术谱系中定位性能。
   - Codex 仅用一个模型（GPT-5.5），且该配置召回率极低（4.92%），其能力可能被低估。
   - 未与人工审查者对比，无法说明相对于人类审查的差距。
3. **benchmark 覆盖面有限**：AACR-Bench 虽含 10 种语言、50 个仓库，但主要为开源项目，不包含领域特定语言或结构非常规的工业代码库。
4. **指标有效性**：SEM-F1 基于语义匹配，无法捕捉评论的实际可操作性、清晰度、严重性等实用维度；对真值未覆盖但可能有效的评论会误判为假阳性。
5. **内部有效性威胁**：LLM 代理固有非确定性虽经设计缓解，但 5 次 judge 的均值仍可能掩盖较大方差；不同系统的绝对性能数值在完全可重复性上仍存疑。
6. **未披露算力资源**：缺少 GPU 型号、数量、总体计算成本等关键复现信息；同时 token 消耗比较未按模型供应商或模型规模分层分析，token 与成本的关系可能因定价差异而不完全对称。
7. **规则维护成本**：四层规则系统需要人工编写和维护内置规则与项目规则，自动化规则发现的未来工作未在本文实现，真实部署时的规则维护开销可能抵消部分效率收益。
