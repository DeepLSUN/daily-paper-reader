## 摘要
真实世界的软件开发要求编码智能体在共享工作空间中操作，其中用户可能在任务进行中检查和修改代码，然而现有的仓库级基准测试通常评估智能体单独工作或将用户参与限制为消息。这引导我们提出一个问题：编码智能体如何理解并响应共享工作空间中的代码变化？我们引入了SWE-Touch，一个通过验证的反编辑（Counter-Edits）来压力测试该设置的框架：反编辑是对任务相关代码的合理改动，但与任务完成相冲突。SWE-Touch从多条修复轨迹中挖掘任务关键区域，使用独立的用户补丁生成器构造编辑，并在智能体到达相关代码时注入带有上下文信息的用户消息。我们在SWE-bench Verified上评估了九个编码模型，并在SWE-Bench Pro和DeepSWE的更长周期任务上进行了额外实验。反编辑使SWE-bench Verified上的平均解析率降低了7.7个百分点，在更长周期基准上的退化也持续存在。轨迹分析将这些失败与对不断演进的工作区的有限感知联系起来：智能体可能保留冲突代码，或者在没有充分重新检查仓库并使用有针对性的测试验证修改后代码的情况下替换它。这些发现表明，强大的自主性能尚不足以确保共享工作区协作所需的状态感知和自适应行为，并指出检测工作区变化、协调冲突编辑与任务以及验证受影响行为是未来优化的关键能力。

## Abstract
Real-world software development requires coding agents to operate in shared workspaces where users may inspect and modify code during an ongoing task, yet existing repository-level benchmarks typically evaluate agents working alone or restrict user participation to messages. This leads us to ask: how do coding agents understand and respond to code changes in a shared workspace? We introduce SWE-Touch, a framework that stress-tests this setting through validated Counter-Edits: plausible edits to task-relevant code that conflict with task completion. SWE-Touch mines task-critical regions from multiple repair trajectories, uses a separate User Patch Generator to construct the edits, and injects them with contextual user messages when agents reach the relevant code. We evaluate nine coding models on SWE-bench Verified, with additional experiments on longer-horizon tasks from SWE-Bench Pro and DeepSWE. Counter-Edit lowers average resolve rate by 7.7 percentage points on SWE-bench Verified, with degradation also persisting on both longer-horizon benchmarks. Trajectory analysis links these failures to limited awareness of the evolving workspace: agents may retain conflicting code or replace it without sufficiently re-inspecting the repository and validating the revised code with targeted tests. These findings show that strong autonomous performance does not yet ensure the state awareness and adaptive behavior needed for shared-workspace collaboration, and point to detecting workspace changes, reconciling conflicting edits with the task, and verifying the affected behavior as key capabilities for future optimization.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：真实软件开发中，编码智能体（Coding Agent）需要在共享工作区（Shared Workspace）中与用户协作。用户不仅通过消息交流，还会直接检查和修改正在任务执行中的代码。
- **核心痛点**：现有仓库级编码基准（如 SWE-bench、Terminal-Bench）普遍采用“静态公式化”评估——智能体接收任务说明和初始代码库后独立工作，最终用可执行测试评分，完全忽略了用户在任务进程中修改代码这一常见交互方式。
- **实证动机**：作者对 SWE-chat 数据的分析发现，**59.0% 的会话包含用户发起的仓库变更**，证明代码编辑是除消息之外的重要交互通道。
- **核心研究问题**：当用户修改共享代码库时，编码智能体如何理解并响应这些代码变化？强自主性能是否意味着共享工作区中的鲁棒协作能力？

## 2. 方法论

### 核心思想
SWE-Touch 是一个基准测试框架，通过向正在进行的智能体修复轨迹中注入**经过验证的、与任务冲突的 Counter-Edits**（合理的用户编辑，但与任务完成相冲突），压力测试智能体在共享工作区中的状态感知和自适应能力。

### 三大技术组件

**（1）任务关键区域挖掘（Mining Task-Critical Regions）**
- 将代码区域表示为三元组：r = (p, s, e)，其中 p 为仓库相对路径，[s, e] 为行区间。
- 使用三个不同系列模型（GPT 5.5、GLM 5.1、MiniMax M2.7）在每项任务上生成完整修复轨迹。
- 对不同轨迹的 Read（读取区域）和 Edit（编辑区域）覆盖进行**交集运算**，提取任务关键区域：
  - C(X)_i = ∩ L(X(τ))，X ∈ {Read, Edit}
- 按优先级选择：编辑证据 > 读取证据，实现文件 > 测试文件，每任务最多保留 8 个区域。

**（2）Counter-Edit 构建（User Edit Construction）**
- 使用独立的 **User Patch Generator**（GPT 5.5 驱动的编码智能体）生成小而合理的错误编辑，编码对任务行为的“错误信念”。
- 编辑仅针对实现代码，禁止修改测试或元数据，平均仅改动 7.0 行/1.04 个文件（SWE-bench Verified）。
- **三重验证条件**：
  - V_Fi(R⁻) = 0：用户编辑单独不解决问题
  - V_Fi(R⋆) = 1：参考补丁单独解决问题
  - V_Fi(R⁻⋆) = 0：两者组合仍然失败
  - 确保编辑既不能单独解决任务，也不能与正确修复简单地组合通过。

**（3）共享工作区评估（Deterministic Delivery Rule）**
- 运行时监控智能体动作，当智能体访问与补丁区域重叠的代码时自动触发注入（默认 K=3 次）。
- 每次交付时，运行时通过上下文匹配将补丁应用到当前仓库状态，并生成情境化的自然语言用户消息（由 GPT-4o 生成，模拟“过度自信但错误信念”的用户）。
- 消息生成器绝不接收参考补丁或验证器信息，保证公平性。

## 6. 主要结论与发现

1. **一致的性能下降**：Counter-Edit 使 SWE-bench Verified 平均解决率下降 **7.7 个百分点**（每模型均为负向变化，范围 1.3–16.5 点），长周期基准同样持续下降（SWE-Bench Pro −4.9、DeepSWE −3.4）。
2. **排名震荡**：解决率排序被显著重排——MiniMax M2.7 从第 3 名跌至第 8 名，GLM 5.1 从第 7 升至第 4。自主性能不能预测共享工作区鲁棒性。
3. **最强的自主模型最稳定**：Claude Opus 4.8（−1.8）和 GPT 5.5（−1.3）损失最小，保留率分别达 96.0% 和 95.0%；Qwen3-Coder-480B 损失最大（−16.5，保留率仅 60.8%）。
4. **失败机制分布**：63.3% 的失败运行仍然保留用户的冲突代码；13.9% 错误替换；11.6% 不完全协调；5.5% 偏离目标。
5. **修订率与性能强相关**：模型对用户编辑的“对抗/修订”比率与 Counter-Edit 性能变化呈 Spearman ρ = 0.80 正相关，但挑战编辑并不保证恢复——28% 对抗编辑的轨迹仍失败。
6. **关键结论**：自主解决率不是共享工作区协作能力的可靠代理；开放权重模型在静态排行榜上表现竞争力强，但在交互条件下显著退化，说明针对静态基准的优化不能转化为对动态演进仓库状态的鲁棒处理。

## 7. 优点

- **填补关键空白**：首次系统评估编码智能体在用户直接修改代码（而非仅发送消息）的共享工作区中的表现，拓展了交互式基准的维度。
- **控制严谨的合成方法**：Counter-Edit 经过三重验证（单独不解、参考解、组合不解），确保注入的冲突是真实且非平凡的；Co-Edit 控制组有效排除了“任何外部干扰都会伤性能”的替代假设。
- **多层次的丰富分析**：从聚合指标（解决率/保留率）到过程级行为（修订率、测试频率）再到细粒度失败机制（7 类标签），提供了可操作的洞察。
- **资源效率数据**：详尽报告 token 消耗与成本，揭示了“额外调用不带来恢复”的投入产出倒挂现象。
- **可复现性设计**：冻结任务列表、公开数据与代码、详细标注协议，支持后续研究。

## 8. 不足与局限

- **合成 vs 真实用户编辑**：Counter-Edits 由语言模型生成的模拟错误信念构造，不代表真实用户编辑的完整分布（真实用户可能提供部分正确、互补性的修改，或需求变更）。作者在局限部分也明确承认了这一边界。
- **干预方式的受控性限制生态效度**：主评估使用区域触发式注入、长任务使用固定百分比时间表，虽然保证了可比性，但不同于真实协作中用户自适应决定“何时、是否”介入的行为模式。
- **单一代理接口**：所有模型通过 Mini-SWE-Agent 外壳交互，结论可能不直接推广到其他工具使用范式。
- **GPT-5.5 既是挖掘/生成器又是被评估模型**：GPT-5.5 作为 region-mining 和 patch-generation 的对象之一，可能存在潜在的选择偏差（虽然作者将 User Patch Generator 与评估模型解耦，且生成时未使用验证器信息）。
- **默认 K=3 的选取**：主结果对编辑频率选择的敏感性存在模型间异质性（部分模型 K 增长持续下降，部分趋于平稳），默认值在不同设置下的代表性有待进一步论证。
- **“保留冲突代码”与“智能体判断”的边界**：63.3% 保留冲突的失败中，无法完全区分智能体是盲目接受用户代码，还是主动判断后选择保留（后者在真实协作中可能合理地相信用户）。
