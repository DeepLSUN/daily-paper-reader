## 摘要
搜索智能体现在能够回答需要数十次搜索才能解决的问题，然而这些智能体如何阅读页面所受到的关注远不如如何找到页面。几乎所有的搜索智能体都使用两种文档接口之一，而这两种接口都将页面与其被打开的时刻绑定。\emph{访问并阅读}在获取时将页面的阅读注入消息历史，在智能体知道需要哪个事实之前就固定了该阅读。有状态的\emph{浏览}则按需从当前页面提取，但一次只持有一个页面，一旦智能体打开另一个页面便立即释放该页面。无论哪种方式，一个在多个回合后才被证明重要的页面，都必须重新获取并渲染到上下文中。我们提出\textbf{先取后探}，将页面选择与证据提取分离，并保留所选择的内容：页面被记录在文件系统上的每问题工作区中，而不是上下文窗口或临时会话中，之后按需从中提取证据。选择几乎变得免费，提取可以等到智能体知道要寻找什么时再进行，并随着其假设的细化而重复，页面也不会在智能体继续前进时被释放，因此证据在轨迹中不断积累。在一个具有固定搜索的统一ReAct框架中，我们将先取后探与仅摘要、访问并阅读以及浏览基线在BrowseComp和WideSearch两个开放网页基准上，跨三个智能体主干进行比较。它在每个主干上的BrowseComp准确率均领先，并在WideSearch上通常达到或超过基线，行为分析将收益归因于工作区的决定性动作：在离开页面后返回该页面，这比任何临时接口都频繁得多，因此首次遗漏的证据仍可在之后恢复。

## Abstract
Search agents now answer questions that take dozens of searches to settle, yet how such an agent reads a page has drawn far less attention than how it finds one. Nearly all of them use one of two document interfaces, and both tie a page to the moment it is opened. \emph{Visit-and-read} injects a reading of the page into the message history at fetch time, fixing that reading before the agent knows which fact it will need. Stateful \emph{browsing} instead extracts on demand from the page in hand, but holds one page at a time and releases it as soon as the agent opens another. Either way, a page that turns out to matter many turns later has to be fetched and rendered into context all over again. We propose \textbf{Fetch-then-Explore}, which separates page selection from evidence extraction and keeps what it selects: pages are recorded in a per-question workspace on the filesystem rather than the context window or a transient session, and evidence is pulled from them on demand later. Selection becomes almost free, extraction can wait until the agent knows what to look for and be repeated as its hypothesis sharpens, and pages are not released when the agent moves on, so evidence accumulates across the trajectory. In a unified ReAct harness with fixed search, we compare Fetch-then-Explore against snippet-only, visit-and-read, and browsing baselines on two open-web benchmarks, BrowseComp and WideSearch, across three agent backbones. It leads BrowseComp accuracy at every backbone and generally matches or exceeds the baselines on WideSearch, and a behavioral analysis traces the gains to the workspace's defining move: returning to a page after leaving it, which it does far more than any transient interface, so evidence missed on a first pass can still be recovered later.

## 1. 核心问题与整体含义（研究动机和背景）

- **研究背景**：长程搜索智能体（deep-research agents）已成为开放网络环境下处理多源证据收集任务的主流方案，其底层几乎都采用 ReAct 式架构。然而，大量研究聚焦于如何优化"搜索"这一环节，对智能体**如何阅读页面**这一文档访问机制关注甚少。
- **现有接口的根本缺陷**：目前部署的搜索智能体几乎都使用两种文档接口中的一种，二者都将页面与其被打开的时刻绑定：
  - **访问并阅读（Visit-and-read）**：在获取（fetch）时立即将页面的摘要、截断窗口或目标分块渲染注入消息历史。这一渲染发生在智能体知道最终需要哪个事实之前，因此是"一次性"的——遗漏的信息除非重新获取页面，否则无法恢复。
  - **有状态浏览（Stateful browsing）**：先打开页面再在页面内查找，实现了选择与提取的解耦，但会话一次只持有一个页面，一旦打开新页面即释放旧页面，证据无法跨页面积累。
- **核心问题**：一个在多个回合后才被证明重要的页面，在上述两种接口下都必须重新获取并重新渲染进上下文，造成显著的重复成本和证据丢失风险。
- **论文主张**：将页面选择（selection）与证据提取（extraction）完全解耦，并把所选页面持久保存在文件系统上的"每问题工作区"中，使提取可以延迟、重复执行，且证据随轨迹持续积累，从根本上限定了文档接口在持久性这一维度上的缺失。

## 2. 方法论：核心思想、关键技术细节

### 2.1 核心思想

Fetch-then-Explore（FTE）基于两条原则：
1. **解耦**：选择页面的动作（fetch）与从页面中提取证据的动作（grep/read）完全分离；
2. **持久保留**：被选中的页面不进入上下文窗口，也不随会话切换而释放，而是存储在文件系统上的持久工作区中，在整个轨迹内保持可查询。

### 2.2 工具集（关键技术细节）

FTE 定义了唯一的文档访问工具集：`A_doc = {fetch, grep, read, list_fetched}`，操作一个每问题缓存 `C_q`（一个临时目录，每个资源一个纯文本文件）：

| 工具 | 功能 | 关键设计 |
|------|------|----------|
| **fetch(url)** | 下载页面、规范化为纯文本、存入缓存，返回轻量记录（路径、字符数、是否新获取） | 页面正文**绝不进入上下文**；文件名由 URL 确定性哈希生成，重复获取自动短路，不重复下载 |
| **grep(pattern, path, context)** | 大小写不敏感的正则搜索；不指定 path 时**跨全部缓存文件**搜索；最多 20 个匹配，按文件分组，每匹配带 ±context 行 | 支持缓存级查询范围，这是会话型接口无法提供的 |
| **read(path, offset, limit)** | 从 1 起始的行号偏移读取最多 200 行，带行号前缀和继续偏移提示 | 偏移基于行号，grep 返回的行号可直接用作 read 的偏移，形成"定位-展开"两步模式 |
| **list_fetched()** | 枚举缓存内容 | 辅助工具 |

### 2.3 与其设计空间中的定位

论文用三个维度刻画文档接口的设计空间，并将各方法置入其中：

| Profile | Substrate（基板） | Extraction（提取方式） | Query Scope（查询范围） |
|---------|-------------------|----------------------|------------------------|
| SNIPPET-ONLY | — | — | — |
| VISIT-SNIPPET | 上下文窗口 | 获取时固定渲染 | — |
| VISIT-SUMMARY | 上下文窗口 | 获取时固定渲染（摘要模型） | — |
| OPEN+FIND | 临时会话（单页） | 按需（有界） | 单页 |
| **FTE（本文）** | **外部持久缓存 C_q** | **按需（有界、可重复）** | **全缓存** |

- 对比逻辑：VISIT 系列检验"解耦是否有帮助"；OPEN+FIND 已解耦但瞬时，隔离出"持久+跨文档工作区"的增量价值。

### 2.4 统一智能体框架

所有范式均嵌入同一 ReAct 智能体中，动作集 `A = A_search ⊔ A_doc ⊔ {a⊥}`；固定搜索工具集 `A_search` 是关键设计决策——它限定了任何文档访问机制可能恢复的证据上界，避免"证据存在哪里"与"证据如何被找到"的混淆。

## 6. 主要结论与发现

### 6.1 主实验结果

- **BrowseComp（准确率）**：FTE 在所有三个骨干上均取得最高准确率（44.5 / 52.5 / 70.5），超过原始 VISIT-SNIPPET 7-14 pp，超过次优配置 2-4.5 pp；排序在各骨干上一致为 FTE > OPEN+FIND > VISIT-SUMMARY > VISIT-SNIPPET > SNIPPET-ONLY。
- **WideSearch（Row-F1）**：FTE 在 Qwen3.5-122B-A10B 上领先，在 DeepSeek-V4-Pro 上差距仅 0.1 pp；唯一被明显超过的单元是最弱骨干（VISIT-SUMMARY 领先 1.2 Row-F1）。
- **FTE vs. OPEN+FIND**：FTE 在每个单元均胜出（BrowseComp +2.0 至 +4.5 pp），证明持久、跨文档工作区的增量价值。
- **工具预算分析**：SNIPPET-ONLY 搜索次数最多；两种按需提取配置搜索次数少于获取时渲染的 VISIT 家族；文档访问与搜索是**替代关系**而非叠加成本。

### 6.2 行为分析发现

- **回归率（Revisit Rate）**是持久工作区与瞬时接口最尖锐的行为分界：
  - BrowseComp：FTE 回归 12-20% 文档，瞬时接口仅 3-10%
  - WideSearch：FTE 回归 **67-76%** 文档，瞬时接口低于 9%，差距达 **8-12 倍**
- **工具使用模式**：grep:read 比随骨干能力上升（强骨干接近或超过 1:1，弱骨干低至 0.62）；缓存规模 5-15 个文档；跨缓存 grep 使用率低（1-10.5% 的问题），但消融证明其贡献关键。
- **消融结论**：
  - 去掉 grep 代价最大（BrowseComp -7.5 pp），说明**定位能力**比窗口大小更稀缺
  - 去掉 read 代价次之（-5.0 pp），提取工具的角色不可互相替代
  - 限制 grep 为单文件（FTE\x-cache）与去掉一个提取工具几乎同价（BrowseComp -5.0 pp、WideSearch -5.1 Row-F1），且 BrowseComp 搜索调用增加 8.3 次/问题——持久化与跨缓存范围是**同一机制的两半**，单独保留持久性反而可能带来负面效果（低于瞬时的 OPEN+FIND）

## 7. 优点

- **控制变量的实验设计**：在所有混杂因素（框架、搜索后端、骨干、提示）固定的前提下，仅变化文档访问工具集，使端到端差异可严格归因于文档接口，这是现有文献中少见的干净对比。
- **设计空间的正规化**：用"基板 × 提取方式 × 查询范围"三维度将各方法置于统一格栅中，并通过消融（FTE\x-cache）填补格栅空隙，论证逻辑严密。
- **行为层面的深入归因**：不仅报告端到端指标，还通过回归率、工具调用分布、n-gram 序列等行为分析，揭示收益的真正来源（离开后返回页面）而非表面机制（更多获取）。
- **跨骨干泛化验证**：三个能力层级（35B MoE → 122B MoE → 前沿 API 模型）骨干上的一致结论显著增强了结果的稳健性。
- **实用的工程设计**：确定性文件名哈希避免重复下载、行号偏移衔接 grep/read、观察大小独立于文档长度等设计直接降低了上下文成本。
- **代价度量细致**：拆分 #Select/#Extract，清晰展示了各配置的工具预算分配，并揭示文档访问与搜索的替代关系。

## 8. 不足与局限

- **算力资源未披露**：未说明 GPU 型号与数量、运行时长、总计算成本，影响可复现性和成本评估。
- **基准采样偏差风险**：BrowseComp 只采样 200/1,266 问题，即使固定种子，样本可能无法完全代表原基准的难度分布；BrowseComp-Plus 分析仅运行在一个骨干上。
- **运行次数有限**：每单元仅 3 次取最佳，对随机性较强的智能体 rollout 而言统计功效有限；未报告方差或置信区间。
- **WideSearch 优势不明显**：在最强骨干上仅与 VISIT-SUMMARY 打平（差距 0.1 pp），在弱骨干上甚至被反超；论文将原因归于 WideSearch 奖励高覆盖提取而非重试能力，但这同时说明 FTE 的收益具有任务类型依赖性。
- **跨缓存 grep 使用率极低**：仅 1-10.5% 的问题使用过全缓存 grep，说明未训练的骨干很少主动利用 FTE 的核心跨文档能力；其贡献是通过消融（FTE\x-cache 大幅下降）间接证明的，而 FTE\x-cache 的约束同时引入了拒绝调用等混杂因素。
