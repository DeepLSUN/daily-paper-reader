## 摘要
编码代理已迅速成为AI辅助软件开发的主要界面。然而，尽管其应用日益广泛，对其内部架构的了解却相对较少，目前还没有类似于编译器或操作系统那样的系统性架构描述。本文通过记录编码代理的主要架构组件，解释其职责、交互和执行流程，填补了这一空白。为支持这项工作，我们还推出了Ark（Agent Research Kit），一个极简的开源编码代理，专为研究和教育设计，在保持现代编码代理基本架构机制的同时，强调简洁性和清晰性。我们还引入了ArkBench，一个包含十个代表性软件维护与演化任务的轻量级基准。使用gpt-5.4-mini，Ark成功解决了10个任务中的8个，同时保持了适度的令牌消耗。最后，我们使用最近提出的架构分类法，将Ark的架构与最先进的编码代理进行了比较。我们希望Ark和ArkBench能为编码代理的教学、研究和实验提供实用基础。

## Abstract
Coding agents have rapidly emerged as the primary interface for AI-assisted software development. However, despite their growing adoption, relatively little is known about their internal architecture, and no systematic architectural description comparable to those available for compilers or operating systems currently exists. This paper addresses this gap by documenting the main architectural components of coding agents, explaining their responsibilities, interactions, and execution flow. To support this effort, we also present Ark (Agent Research Kit), a minimal open-source coding agent designed for research and education that preserves the essential architectural mechanisms of modern coding agents while emphasizing simplicity and clarity. We also introduce ArkBench, a lightweight benchmark comprising ten representative software maintenance and evolution tasks. Using gpt-5.4-mini, Ark successfully solved 8 of the 10 tasks while requiring modest token consumption. Finally, we compare the architecture of Ark with those of state-of-the-art coding agents using a recently proposed architectural taxonomy. We hope that both Ark and ArkBench provide a practical foundation for teaching, research, and experimentation on coding agents.

## 2. 方法论

### 2.1 核心思想
- 采用**自研代理 + 文献驱动 + 迭代实现**的方法。最初遵循 ReAct 模式，并参考 OpenAI Codex 与 Anthropic Claude Code 的技术文档，逐步重构出清晰架构。
- 开发过程中使用 **Codex** 辅助生成代码，作者对全部生成代码进行人工审查；提交统计显示 37% 提交用于重构、32% 用于文档维护，表明即便 LLM 生成代码，仍需大量工程工作确保质量。

### 2.2 架构组件（Ark 中实现）
- **Agentic Loop**：以 ReAct 范式循环运行，每轮调用 LLM 获取下一次工具请求，执行工具后记录进记忆，直至 LLM 输出 `finish` 或达到迭代上限。核心代码仅 18 行。
- **系统提示（System Prompt）**：定义 LLM 的角色、交互协议（Thought/Action/Action Input）、允许的工具、约束（先读后改）和终止条件；提示需随每次请求发送，长度直接影响 token 成本。
- **工具集**：仅提供 5 个工具——`list_files`、`read_file`、`find_text`、`run_tests`、`finish`；所有工具直接用 Python 实现，限制规避能力和攻击面。
- **记忆（Memory）**：记录每轮工具调用与输出，用于构建上下文；为防止超出上下文窗口，仅保留最近 4 轮迭代记录。
- **上下文管理**：包含系统提示、用户任务描述（`prompt.txt`）、工作区说明（`AGENTS.md`）、自动生成的状态摘要及最近交互历史。
- **错误处理**：分为两类——ReAct 协议格式错误（自动返回修复提示，仅重试一次）、补丁错误（用 `git apply --check` 验证，自动重算 hunk 行数修复后应用）。
- **安全机制**：在临时目录创建项目副本，全部操作隔离在工作区内；限制路径；固定测试命令为 `pytest`；补丁应用前需用户批准。
- **追踪（Tracing）**：记录 LLM 请求/响应、验证错误、修复尝试和补丁处理事件到 `agent_trace.log`。
- **LLM 集成**：模块化封装，兼容 OpenAI API，支持配置模型、端点、API Key 环境变量。

## 3. 实验设计

- **基准：ArkBench**——一个基于小型电商应用（纯 Python 实现）的维护与演化基准，包含 10 个独立任务：
  - 3 个 bug 修复（分页 off-by-one、订单校验、折扣阈值）
  - 3 个重构（提取重复函数、移动函数、重命名公共函数）
  - 4 个功能实现（价格筛选、排序、CSV 导出、按类别分组）
  - 每个任务拥有独立项目副本、公开测试和隐藏评估测试（包括结构验证脚本）。
- **评估模型**：最终使用商业 LLM `gpt-5.4-mini`。开发前期尝试了 Qwen2.5-coder:14b 和 Qwen3-coder:30b 本地模型，但性能不佳，尤其在协议遵循和补丁生成上，故被替换。
- **评估指标**：任务成功与否、token 消耗、执行时间、工具调用次数。
- **对比方法**：未进行定量性能对比。而是采用 Rombaut 提出的架构分类法（三层十二维度），将 Ark 与 **Codex CLI**（商业代表）和 **OpenCode**（开源代表）进行**架构特征比较**。

## 4. 资源与算力

## 5. 实验数量与充分性

- **实验规模较小**：仅 10 个任务，且每个任务只执行一次（单次运行），未进行多次重复实验以处理 LLM 非确定性。
- **无消融实验**：未系统比较不同系统提示长度、上下文策略（如滑动窗口大小）、工具集等设计选择的效果。
- **无基线对比**：论文明确表示目的不是与前沿代理比较，因此缺少 Codex CLI、OpenCode 等在 ArkBench 上的量化结果，难以评估 Ark 的相对能力水平。
- **数据生成存在人工偏差风险**：ArkBench 由 ChatGPT 自动生成，作者人工审查；任务设计可能偏向 Ark 的能力范围，仍具一定主观性。
- **积极之处**：每个任务包含公开与隐藏测试（含结构验证），可有效防止“过拟合公开测试”的作弊行为；且明确报告了失败案例，分析较诚实。
- **总体充分性评价**：作为“探索性研究”和“架构教学原型”是充分的，但作为能力验证或科学基准评估则不够充分。

## 6. 主要结论与发现

- **Ark 成功解决 8/10 任务（80% 成功率）**：其中 4 个功能实现全部成功，2/3 的 bug 修复和 2/3 的重构成功。平均 7.1 次工具调用、23.5 秒/任务，证明“简洁架构 + 现代 LLM”足以处理中等复杂度维护任务。
- **失败案例分析富有洞察**：
  - `bugfix-02`：修复不完整，公共测试通过但隐藏测试抛错（异常类型错误），反映 LLM 对边界条件覆盖不足。
  - `refactor-03`：主变换正确但未传播所有调用点/导入，导致隐藏评估失败；说明 LLM 在重构任务中容易遗漏次级依赖，产生不完整补丁。
- **架构对比结论**：Ark 与 Codex CLI、OpenCode 共享 ReAct 控制循环和 LLM 驱动范式；主要差异在工具集规模（5 vs 18+/20+）、动态工具发现、上下文压缩策略（截断 vs LLM 摘要）、持久化记忆（无 vs 有）和模型路由（单模型 vs 多模型）。这些差异是**有意简化**，目的是保证教育性和可读性。
- **开发过程发现**：用 LLM 生成代理代码是可行的，但其产出需大量重构和文档化才能达到高质量，37% 的提交用于重构、32% 用于文档，表明“架构清晰”需要主动工程干预。

## 7. 优点

- **开源与可复现**：Ark（MIT 协议）和 ArkBench 均公开于 GitHub，附带 50 个单元测试，行覆盖率达 100%，便于他人学习、扩展与复现。
- **架构极简**：13 个 Python 文件、1471 行代码、仅两个外部依赖，是迄今最清晰的编码代理参考实现之一。
- **文档与代码并重**：提供完整架构图、Agentic Loop 源码和 System Prompt 全文，降低了理解门槛。
- **教学价值高**：类似于 Minix 对操作系统的意义，Ark 可作为编码代理的“教学内核”。
- **安全性设计务实**：临时工作区隔离、路径校验、固定测试命令、用户审批补丁，虽简化但覆盖了关键风险。
- **基准轻量而有效**：ArkBench 任务真实，覆盖三类型维护活动，带隐藏测试避免简单过拟合；总成本不足 0.5 美元，适合快速验证。
- **使用架构分类法进行定位**：将 Ark 与主流代理的对比建立在已有分类法之上，增强了讨论的结构性和说服力。

## 8. 不足与局限

- **实验数量与深度不足**：10 个任务、单次执行，无法统计可信的成功率波动；缺乏消融实验、参数敏感性分析和多模型测试（仅验证了 gpt-5.4-mini）。
- **缺乏定量基线对比**：未在相同基准上与 Codex CLI、OpenCode 等代理对比，能力评估缺少参照系；架构对比也仅基于二手分类法，未直接分析对方代码。
- **Ark 自身的简化短板**：
  - 仅 5 个静态工具，未支持动态工具发现或 MCP 插件；
  - 上下文管理采用硬截断（最近 4 轮），可能丢失远期关键信息；
  - 无持续记忆，无法跨会话复用知识；
  - 单模型驱动，无安全校验模型或任务路由；
  - 本地 shell 执行模式不及 Codex CLI 的沙箱隔离安全。
- **ArkBench 规模与代表性有限**：基于小型电商应用（纯 Python、无数据库），任务文件规模小（修改 2-4 个文件），不能代表大型真实代码库中的复杂依赖、异构技术和长流程任务。
- **潜在偏差风险**：LLM 生成基准任务，可能隐式偏好类似架构的代理；作者是导师兼开发，可能存在“自我验证”偏向；失败分析为定性说明，无系统性多轮验证。
- **适用范围**：Ark 定位于教育与研究“最小内核”，不适用于生产级使用；对大规模仓库修复、复杂重构、API 迁移等真实工程任务尚无证据支撑。
