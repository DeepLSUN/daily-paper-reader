## 摘要
大语言模型（LLMs）正在改变数据库交互范式，从简单的查询转换器演变为自主的数据库管理员（DBA）。然而，当前的评估基准仍不成比例地专注于Text-to-SQL任务，忽视了从初始模式设计到部署后维护的完整数据库生命周期。这种狭隘的视角未能捕捉现实世界数据库管理所需的各种能力。为弥补这一差距，我们引入了DBLifeBench，这是首个在五个关键生命周期阶段评估LLMs的基准：设计、实现、操作、调试和维护。此外，针对模糊自然语言与复杂SQL逻辑之间的认知不匹配问题，我们提出了渐进式Text2SQL（Progressive-Text2SQL），一种新颖的任务，利用结构化推理图模拟人类的迭代问题解决过程。我们广泛的评估揭示了一个关键见解：虽然通用模型表现出均衡的性能，但专门的Text-to-SQL模型在设计和维护等非编码阶段遭受“灾难性遗忘”。DBLifeBench作为评估和构建真正全栈数据库智能的基础性一步。

## Abstract
Large Language Models (LLMs) are transforming database interaction paradigms, evolving from simple query translators to autonomous database administrators (DBAs). However, current evaluation benchmarks remain disproportionately fixated on Text-to-SQL tasks, neglecting the holistic Database Lifecycle-from initial schema design to post-deployment maintenance. This narrow focus fails to capture the diverse capabilities required for real-world database management. To bridge this gap, we introduce DBLifeBench, the first benchmark to evaluate LLMs across five critical lifecycle phases: Design, Implementation, Operation, Debugging, and Maintenance. Furthermore, addressing the cognitive mismatch between ambiguous natural language and complex SQL logic, we propose Progressive-Text2SQL, a novel task utilizing structured reasoning graphs to mimic human iterative problem-solving. Our extensive evaluation reveals a critical insight: while general-purpose models demonstrate balanced performance, specialized Text-to-SQL models suffer from ``catastrophic forgetting'' in non-coding phases like design and maintenance. DBLifeBench serves as a foundational step toward evaluating and building true full-stack database intelligence.

## 2. 论文提出的方法论

**核心思想**：提出 DBLifeBench——第一个覆盖数据库完整生命周期的基准，将生命周期映射为 LLM 的五种认知能力，并引入 Progressive-Text2SQL 任务解决自然语言与复杂 SQL 之间的认知鸿沟。

**五个生命周期阶段的评测任务**：

- **设计（P1: Abstraction & Modeling）**：给定自然语言需求，模型需构建 schema S = (E, D, K)，包含实体、数据类型、外键依赖，测试高层逻辑建模能力。
- **实现（P2: Syntax Precision）**：将概念 schema 转换为可执行的 SQL DDL 语句，要求严格语法精度。
- **操作（P3: Logic Translation & Reasoning）**：将操作需求转换为 DML 语句，包括标准 Text2SQL 与创新的 Progressive-Text2SQL。
- **调试（P4: Diagnosis & Correction）**：给定错误 SQL 和错误信息，模型需识别根因（语法或语义）并生成修正语句，支持单轮和多轮调试。
- **维护（P5: System Management）**：模拟 SRE/DBA 角色，分为故障分诊（Assigner，从错误日志分配专家）和专家执行（Expert，调用模拟 API 如 check_metric、io_match_diagnose_knowledge 等诊断并修复系统异常）。

**Progressive-Text2SQL 的关键技术细节**：

- 定义**推理图 G = (V, E)**：节点 V 表示子任务（如"按日期过滤""连接表"），包含局部自然语言描述和对应 SQL 片段；边 E 表示逻辑依赖关系，模拟人类专家的链式思维（Chain-of-Thought）过程。
- **图构建流程**：收集 Text2SQL 中难度较高且自然语言与 SQL 错位明显的样本；使用多种 LLM（GPT-4o、Claude、Gemini、DeepSeek-R1）独立生成候选图结构以减少单模型偏差；再为每个 SQL 节点生成自然语言描述。
- **两阶段数据验证**：先在 SQLite 中执行所有 SQL 节点，丢弃执行失败的；再由三名数据库方向研究生仅凭 SQL 和自然语言描述独立重建图边，与原结构计算 Jaccard 相似度，保留共识度 >80% 的样本。Fleiss' kappa 为 0.8173，表明标注者间高度一致。

**评估指标**：

- **设计阶段**：实体名准确率（ACC i-Entity）、数据类型准确率（ACC i-Data）、外键依赖准确率（ACC i-Key）。
- **实现阶段**：表级准确率（T-Level）和字段级准确率（F-Level），指标函数 I(·) 判断语义一致性。
- **操作阶段**：标准 Text2SQL 用执行准确率（EX）；Progressive-Text2SQL 用图执行准确率（G-EX），即各节点 EX 的平均值。
- **调试/维护阶段**：基于 SQL 执行结果和 API 调用正确性评估。

## 6. 论文的主要结论与发现

- **通用模型整体更强**：GPT-4o 和 GPT-4o-mini 在几乎所有阶段表现领先，展示出较全面的数据库能力。
- **"专业化的诅咒"（curse of specialization）**：专门针对 SQL 微调的模型（如 SQLCoder）在设计与维护等非编码阶段表现严重退化，SQLCoder 在实现阶段 T-Level 仅 10.00、维护阶段 Assigner/Expert 均为 0。SQL 微调产生的过拟合损害了模型的泛化能力。
- **P-Text2SQL 有效提升复杂 SQL 生成**：推理图显著提升所有模型在执行准确率上的表现，且任务越复杂（Challenging 级别）提升率越大。
- **P-Text2SQL 增强模型对 schema 变化的鲁棒性**：变异系数更小，表明推理图帮助模型更好地适应数据模型变化。
- **多轮调试能力模型间差异大**：Llama3、Mistral 能从多轮反馈中学习并改进，而 DeepSeek 单轮与多轮无差异，缺乏相应能力。
- **工具使用是瓶颈**：所有模型在维护阶段的 Expert 任务中分数均偏低，说明 LLM 不擅长调用数据库诊断工具。
- **过度规范化反而不利**：v3（最高规范化）因语义对齐更好而表现最优，v2 因别名冲突和 UNION 冗余表现最差，建议重视语义对齐、避免过度规范化。

## 7. 优点

- **全局视角**：首次以数据库生命周期为主线构建评测体系，突破 Text-to-SQL 单任务局限，更贴近真实 DBA 工作场景。
- **任务创新**：Progressive-Text2SQL 将 SQL 生成转化为结构化推理过程，模拟人类逐步求解，兼具方法论价值和应用价值。
- **数据集质量保障**：需求分析采用"人机协作多轮迭代"流程；推理图采用多模型生成+两阶段验证（执行验证+人工重建），并报告 Kappa 一致性系数，严谨性较高。
- **评估指标多维**：不同阶段配以不同粒度指标（实体级、表级、字段级、执行级），避免单一 EX 指标无法衡量结构性推理的缺陷。
- **实验分析深入**：包含鲁棒性测试、schema 变体影响、需求质量迭代影响、模型排名重构等多个分析角度，洞察丰富。
