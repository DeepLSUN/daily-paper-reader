## 摘要
代码代理的大部分精力仅仅花在定位仓库中的正确代码上。目前有两种方法主导着实践。在语义搜索中，代理从预先根据仓库构建的向量索引中检索代码块。在深度代理搜索（也称为子代理的grep搜索）中，规划代理将探索任务委托给一个独立的子代理，该子代理在隔离的上下文窗口中工作，并仅返回精简的结果。第二种设计被认为是一种良好的上下文工程实践，其存在是为了保护主代理免受上下文污染（也称为上下文腐烂）的影响，即随着不相关材料在上下文窗口中积累而导致的准确性损失。最近的代码代理（如 Claude Code、Codex、Antigravity 等）迅速采用了这种方法，但关于它是否能产生更好的答案，几乎没有证据。我们在 SWE-QA（一个用于仓库级代码问答的基准测试）上比较了这两种方法。语义搜索正确回答了65.2%的问题，而深度代理搜索为46.2%，并且语义搜索产生每个正确答案的成本不到深度代理搜索的一半。为了解释这一差距，我们随后将每次失败的运行进行了故障模式分类。该分类显示，深度代理搜索并没有消除失败，而是引入了一类新的失败：其中最大的一部分失败（占41.8%）发生在规划器与其子代理之间的交接处，而这些失败通常是无声的，最终以流畅而自信的错误答案结束。深度代理搜索解决了一个实际问题，现已成为许多代码代理的首选设计。然而，我们的结果表明，它提供的保护可能不是免费的，并且对于可索引的仓库上的只读问题，检索是更强大且更便宜的选择。

## Abstract
Code agents spend much of their effort simply locating the right code inside a repository. Two approaches dominate current practice. In Semantic Search, the agent retrieves code blocks from a vector index built from the repository in advance. In Deep Agentic Search (also known as grep-search by subagent), a planning agent delegates the exploration to a separate subagent that works in an isolated context window and returns only a condensed result. The second design, which is considered good context engineering practice, exists to protect the main agent from context pollution (also known as context rot), the loss of accuracy that occurs as unrelated material accumulates in the context window. Recent code agents (such as Claude Code, Codex, Antigravity, etc) have adopted it quickly, but there is little evidence on whether it produces better answers. We compare the two approaches on SWE-QA, a benchmark for repository-level code question answering. Semantic search answered 65.2% of questions correctly against 46.2% for deep agentic search, and it produced each correct answer at less than half the cost. To explain the gap, we then coded every failed run into a taxonomy of failure modes. The taxonomy shows that deep agentic search did not remove failures but introduced a new class of them: the single largest share of its failures, 41.8%, occurred at the hand-off between the planner and its sub-agent, and these were usually silent, ending in a fluent and confident answer that was wrong. Deep agentic search addresses a real problem and is now the preferred design in many code agents. However, our results show that the protection it offers may not be free, and that for read-only questions over a repository that can be indexed, retrieval was the stronger and cheaper option.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：在大型存储库（repository）中进行代码问答时，代码代理（Code Agent）需要耗费大量精力去定位正确的代码。当前实践中两种主流范式——基于向量索引的**语义搜索（Semantic Search）** 与基于子代理委派的**深度代理搜索（Deep Agentic Search）**——究竟哪一方在准确性、成本和效率上更优，此前缺乏实证证据。
- **研究背景**：
  - 代码代理已成为软件开发的主要交互界面，仓库级代码问答（Repository-level Code Question Answering）是其中最具挑战性的任务，因为所需信息往往分散在多个文件中。
  - 代理的上下文窗口有限，且随着无关材料在上下文中积累会出现**上下文污染（context pollution / context rot）**，导致准确性下降。
  - 深度代理搜索是一种新兴的"上下文工程（context engineering）"实践：规划代理（planner）将探索任务委派给在隔离上下文窗口中工作的子代理（sub-agent），仅返回精简的结果，以保护主代理的上下文免受污染。
  - 尽管 Claude Code、Codex、Antigravity 等前沿代码代理已快速采用深度代理搜索设计，但对其是否真正优于传统语义搜索，几乎没有实证研究。
  - 该研究与现有基准测试（如 SWE-QA 本身仅对比检索与平面单代理）以及现有对比研究（如 SWE-Explore、StackRepoQA）的关键区别在于：首次将**委派式深度代理**（而非平面单代理）作为代理端，与语义搜索进行直接、系统的对比。

## 2. 论文提出的方法论

论文不提出新方法，而是对两种现有范式进行受控实证对比：

- **范式一：语义搜索（Semantic Search, 即 RAG 式检索）**
  - 由 **ReAct 代理**实现（使用 LangChain 的 ReAct harness），仅配备三个工具：
    - 仓库结构查找（get_repo_structure）
    - 向量索引检索（search_rag）
    - 文件读取（read_file）
  - 建索引方式：将仓库按 500 token 块（50 token 重叠）切分，用 `text-embedding-3-small`（1536 维）嵌入，存入 Chroma 向量数据库；检索时取 top-10 块（余弦相似度）。
  - 思想：预建索引，查询时仅将最相关的紧凑文本块放入上下文。

- **范式二：深度代理搜索（Deep Agentic Search）**
  - 由 **Deep Agent** 实现（使用 LangChain 官方 `langchain-deep-agents` 库的默认工具集）：
    - 任务列表规划（write_todos）
    - 子代理委派（task）
    - 文本搜索（grep）、文件列举与通配（ls、glob）、文件读取（read_file）
  - 思想：不建索引，代理以终端命令实时探索仓库；探索过程交由隔离上下文窗口的子代理执行，子代理只返回精简结论给主规划器。
  - 关键架构差异：Deep Agent 具备规划、虚拟文件系统和子代理委派能力，而 ReAct 代理没有这些；二者不可进行工具级"均等化"——工具差异正是构成范式差异本身。

- **评估方法论**：
  - 由独立第三方模型 Claude Sonnet 4.6（不同提供商、不同模型家族）作为 LLM 评判员，从正确性、完整性、相关性、清晰度、推理五个维度打分（0–100），并映射为 Pass/Partial/Fail 三档（Pass≥70，Partial 50–70，Fail<50）。
  - 所有对比均为**模型内配对比较**（同模型对比两种范式），使用 McNemar 精确检验（Pass 率）、Wilcoxon 符号秩检验（分值）、Cliff's delta 与 dz 效应量，并进行 Benjamini-Hochberg FDR 校正。
  - 对每一次失败运行进行双轴失败分类：**机制轴**（根因行为）和**症状轴**（答案错误形态）。

## 6. 论文的主要结论与发现

- **（RQ1）准确性：语义搜索全面优于深度代理搜索**
  - 池化四模型：语义搜索 Pass 率 **65.2%** vs 深度搜索 **46.2%**；Fail 率 21.9% vs 34.4%。
  - 每个模型均一致地支持语义搜索，幅度从 Gemini 2.5 系列的约 5.6–10.0 个百分点，到 Qwen3-235B 的 10.6 个百分点，再到 Gemini 3 Flash 的 **49.6 个百分点**。
  - 所有配对检验经 FDR 校正后仍然显著；Gemini 3 Flash 的 Cliff's delta 达 0.760（大效应）。
  - 语义搜索在全部五个质量维度、全部四类问题类型、14/15 个仓库上均占优（唯一例外是 django 仓库）。
  - 优势随仓库规模增大而收窄（Spearman ρ = −0.69, p=0.004），但在所研究的范围内始终未逆转。

- **（RQ2）成本与效率：深度搜索更贵且不更高效**
  - 深度搜索在每个模型下都消耗更多输入 token、更高的每问题美元成本和更高的**每个正确回答（Pass）成本**。
  - 池化来看，语义搜索每 Pass 成本 0.32 美元 vs 深度搜索 0.74 美元（约 2.3 倍差距）。
  - 额外努力换不来更高准确性：每问题得分与 token 消耗/工具调用数量的拟合斜率平坦至为负。
  - 延迟方面两者无一致排序，论文将其列为次要指标。

- **（RQ3）行为与失败模式：深度搜索引入了一类全新且占比最大的静默失败**
  - **语义搜索的失败签名**：以"检索/定位未命中"（53.6%）为主，属于高努力失败（平均 12.6 次工具调用仍未找到正确文件）；其次是"证据不足即作答"（18.1%）和"误读证据"（17.1%）。
  - **深度搜索的失败签名**：最大失败类别为**协调失败（coordination breakdown），占 41.8%**，在平面检索代理中没有对应物；另有 13.5% 为非终止循环。
  - **最关键的发现**：协调失败中 **91% 是静默失败**——代理仍返回流畅自信但错误的答案，而不是报告内部出错；深度搜索还更频繁地"无答案"（24.2% vs 12.7%）。
  - 结论：深度代理搜索并未消除失败，而是新增了一类由规划器-子代理交接产生的、往往不可见的失败，其代价超过了它试图防止的上下文污染问题。

## 7. 优点

- **研究定位精准且填补空白**：首次将"委派式 Deep Agent"与"索引式 ReAct 代理"在仓库级代码问答上进行直接实证对比，填充了现有文献中的明确空白（Table 1 的定位表清晰有力）。
- **实验设计严谨、公平**：
  - 模型内配对比较（paired within-model），消除了跨模型混杂；
  - 统一基于 LangChain 生态（ReAct harness 与 deep-agents harness），避免用研究实现对比商业产品的偏倚；
  - 评价器使用来自不同提供商、不同模型家族的 LLM，并进行独立人工小组验证（Fleiss κ=0.81，人机 Cohen's κ=0.74），保障了评估可信度；
  - 温度 0.0 确定性解码，支持可复现性。
- **多层次分析框架**：准确性、成本（token+美元+每 Pass 成本+有效前沿）、行为（工具分布+轨迹长度）和失败模式（机制×症状双轴分类）四位一体，远超单纯报告准确率的同类研究。
- **失败分析深入且有洞察力**：区分"机制"（产生原因）与"症状"（答案形态），揭示了深度搜索失败大多发生于规划器-子代理交接处且以"流畅但错误"的答案形式静默出现——这对理解多代理系统脆弱性有重要启示。
- **稳健性检验丰富**：Pass 阈值扫描、仓库级 bootstrap 重采样、按仓库来源的泄漏检查、成本-精度平面分析等多重验证增强了结论的可信度。
- **边界条件讨论诚实透彻**：明确指出结果适用于"可索引仓库上的只读单轮问答"，不适用于多轮/多任务会话、不可索引环境或代码执行任务。

## 8. 不足与局限

- **范式代表性有限**：每种范式仅通过一个 harness 实现（LangChain），未涵盖其他主流实现（如 OpenHands SDK 等），也未做跨 harness 敏感性分析；不同实现可能在提示词措辞、子代理摘要方式、最大步数等方面影响结果幅度。
- **外部效度受限**：
  - 单一基准（SWE-QA）、单一语言（Python）、四个模型；
  - 单轮只读问答场景无法捕捉深度代理搜索在长会话上下文卫生（context hygiene）方面的潜在优势；
  - 无计算匹配基线（compute-matched baseline），未将 token 预算均等化以分离"搜索策略"与"消耗算力"的效应。
- **数据泄露风险未完全排除**：论文做了描述性检查（语义搜索在三个较新的 SWE-bench-Live 仓库上优势反而更大），但这不能完全排除训练数据中包含已发布仓库代码的污染，仅表明未发现不对称效应。
- **规模趋势不确定**：语义搜索优势随仓库规模增大而收窄，但未在超过 86 万行级别的仓库上测试，无法确证是否存在逆转点（crossover）。
- **多代理超参数未探索**：协调失败主导深度搜索的失败，但论文未系统变化代理间交接协议、子代理模型、摘要粒度等超参数来探究其影响。
- **延迟测量受环境干扰**：论文承认延迟重尾且受执行环境影响，因此未基于延迟做任何结论。
- **人类标注仅覆盖 800/5,760 个回答**：占约 14%，虽然作为验证子样本合理，但自动评判仍可能存在未被样本捕捉的系统性偏差。

总体而言，这是一项设计严谨、分析深入、结论明确的实证研究。它用数据挑战了当前业界的默认偏好，指出深度代理搜索的上下文保护"并非免费"，在可索引仓库的只读问答场景下，语义检索依然是更强大且更经济的选择——同时也坦诚地划定其结论的适用边界，为后续混合路由设计和跨 harness 验证留下了明确的研究方向。
