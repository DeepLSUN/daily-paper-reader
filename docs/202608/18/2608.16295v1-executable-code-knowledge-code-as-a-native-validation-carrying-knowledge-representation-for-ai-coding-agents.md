## 摘要
AI编码代理不仅需要相关片段，还需要业务语义、验证证据、关系以及确保其上下文是最新的。现有系统通常通过检索、摘要、图、规则或反向规范来推断或外化这些知识。我们研究了一种互补的表示方式，其中选定的代码单元直接携带代理可用的知识。我们引入了可执行代码知识（ECK），并将可执行代码知识单元（ECKU）定义为一种源绑定对象，结合了稳定身份、语义、可执行行为、契约、证据、关系、来源、验证状态和查询接口。我们的Python原型支持代码本地编写、清单导出、证据执行、精确变更行影响、新鲜度检查以及面向代理的投影。在三个真实Python仓库和26个受控补丁任务中，直接ECK为11/11个证据承载任务提供了可执行测试覆盖，并为9/11提供了精确选择器；隐藏声明证据会将精确恢复降至1/11（配对精确McNemar p=0.0078）。从ECK派生的规则恢复了11/11个精确选择器，表明规则是有效的交付制品，而ECK提供了源绑定、验证状态、影响和新鲜度。精确变更行影响与所有26个补丁上独立撰写的标签匹配（12个单位链接；精确率、召回率和F1均为1.000）。AST边界指纹正确分类了50个正向更改和17个无关的同文件控件，而静态规则快照无法检测50个过期案例中的任何一个。模型支持的补丁审查和跨层研究衡量了投影保真度，而非独立的影响发现。这些结果支持一种混合架构：检索用于覆盖，ECK用于源和证据治理，投影用于交付。

## Abstract
AI coding agents need more than relevant snippets: they need business semantics, validation evidence, relations, and assurance that their context is current. Existing systems usually infer or externalize this knowledge through retrieval, summaries, graphs, rules, or reverse specifications. We investigate a complementary representation in which selected code units directly carry agent-usable knowledge. We introduce Executable Code Knowledge (ECK) and define an Executable Code Knowledge Unit (ECKU) as a source-bound object combining stable identity, semantics, executable behavior, contracts, evidence, relations, provenance, validation state, and a query interface. Our Python prototype supports code-local authoring, manifest export, evidence execution, exact changed-line impact, freshness checking, and agent-facing projections. Across three real Python repositories and 26 controlled patch tasks, direct ECK provides executable test coverage for 11/11 evidence-bearing tasks and exact selectors for 9/11; hiding declared evidence reduces exact recovery to 1/11 (paired exact McNemar p=0.0078). ECK-derived rules recover 11/11 exact selectors, showing that rules are effective delivery artifacts while ECK supplies source binding, validation state, impact, and freshness. Exact changed-line impact matches independently authored labels on all 26 patches (12 unit links; precision, recall, and F1 all 1.000). AST-bounded fingerprints classify 50 positive changes and 17 unrelated same-file controls correctly, whereas static rules snapshots detect none of the 50 stale cases. Model-backed patch-review and cross-layer studies measure projection fidelity rather than independent impact discovery. These results support a hybrid architecture: retrieval for coverage, ECK for source and evidence governance, and projections for delivery.

### 1. 论文的核心问题与整体含义

- **研究背景**：AI 编码代理在仓库级问题解决、代码检索、工具使用和基于测试的验证方面越来越受重视。然而现有系统通常将代码视为“可挖掘的文本”，通过检索、摘要、静态图谱、规则或反向规范等**后处理流水线**来构造知识，这种范式存在明显的**权威性问题**：
  - 检索到的片段只能提示“去哪看”，无法告诉代理哪个测试是权威的验证证据；
  - 静态图谱暴露结构，但无法区分领域不变量与偶然调用关系；
  - 生成的摘要和反向规范需要追溯、验证和保鲜，但往往缺乏这些机制。
- **核心研究问题**：代码本身能否直接表示为代理可用的知识对象，而不仅仅作为待挖掘的文本？论文针对**特定高价值代码单元**（业务规则、安全策略、数据转换、API 行为、解析器不变量、工作流转换、兼容性契约等）给出肯定回答。
- **整体含义**：提出了一种补充性的知识表示范式——**可执行代码知识（Executable Code Knowledge，ECK）**，它不是“RAG 但更好”，而是提供检索无法提供的**验证承载与时效性治理**能力，最终倡导“检索保覆盖、ECK 保源头与证据、投影保交付”的混合架构。

### 2. 论文提出的方法论

#### 核心思想
- 定义**可执行代码知识单元（ECKU）**为源码绑定对象，形式化表示为九元组：
  ```
  ECKU = <I, S, B, C, E, R, P, V, Q>
  ```
  其中：
  - **I** (Identity)：稳定身份标识
  - **S** (Semantics)：领域语义
  - **B** (Body)：可执行函数体
  - **C** (Contract)：前置/后置条件契约
  - **E** (Evidence)：可执行验证证据（测试命令等）
  - **R** (Relations)：到 API、数据实体、测试、文档或其他单元的关联
  - **P** (Provenance)：来源与溯源信息
  - **V** (Validation)：验证状态与新鲜度
  - **Q** (Query)：查询与组合接口

#### 关键技术细节
- **作者方式**：开发者通过装饰器（`@knowledge_unit`、`@contract`、`@evidence`）直接在源码中编写 ECKU，原始函数保持为可执行源码跨度（而非包装器）。
- **验证与新鲜度**：
  - 定义了四个哈希：`SourceHash`（源码指纹，AST 限定的函数边界）、`KnowledgeHash`（代理可见知识指纹，排除装饰器）、`ContractHash`（契约指纹）、`EvidenceHash`（证据指纹）。
  - `Fresh(u, t)` 要求四个哈希均与上次验证时一致；`Valid(u)` = `Fresh(u)` 且所有可执行证据通过。
  - 改变行影响分析：精确跟踪统一 diff hunk 内**新增/删除行的精确位置**，与 ECKU 的 AST 跨度求交集（消除了 whole-hunk 在 `slugify_params` 与 `main` 边界处的误报）。
- **查询与组合接口**：`build/query/show/validate/freshness/impact/context` 等操作；关系组合（API→业务规则→数据字段→测试→策略）标记为未来工作。
- **系统分层**：作者层（装饰器）→ 发现与清单层（导出 JSONL/manifest）→ 验证层（执行证据命令）→ 新鲜度层（指纹比对）→ 代理上下文层（生成紧凑类型化上下文包）。

### 6. 论文的主要结论与发现

1. **显式证据是精确验证选择的关键**：隐藏证据后，精确选择器恢复从 9/11 骤降至 1/11（p=0.0078），覆盖率从 1.000 降至 0.636；BM25 定位文件往往成功但精确选择器失败。
2. **规则是有效的交付媒介**：Rules Context 取得 11/11 精确选择器恢复，证明规则/记忆/AGENTS.md 等格式可有效传递验证提示；但规则没有源码绑定、影响操作、验证状态或新鲜度——在 50 个过期场景中，规则快照全部失效（0/50），ECK 全部检测到（50/50）。
3. **ECK 定位为“认证层”而非“更好的 RAG”**：BM25 和 Direct ECK 文件召回均为 0.981，但 ECK 的差异化价值在于验证承载能力与新鲜度治理，而非通用检索效果。
4. **直接源跨度影响分析是确定性的、准确的**：精确变更行影响在 12 个单元链接上达到 1.000 精度/召回/F1，且精确行跟踪修复了 whole-hunk 的边界误报。
5. **类型化报告和任务特定投影是可靠的交付格式**：Direct ECK Patch 报告在消费测试中达到 1.000 ECK-ID/验证命令召回，但论文明确反对将其解读为独立影响发现证据。
6. **混合架构是最佳设计**：提取/检索保覆盖、ECK 保源码与证据治理、规则或投影保交付。

### 7. 优点

- **问题框架清晰**：将“代码定位—验证证据—新鲜度治理”三个维度分离，并给出对应的实验证据，界定了“覆盖率-权威性前沿”（coverage-authority frontier）。
- **形式化定义严谨**：ECKU 九元组和四个哈希的验证/新鲜度定义精确，支持不一致状态的分类检测（`never_validated`、`source_changed` 等），避免含糊的“文档过期”表述。
- **消融实验设计出色**：关键对照（有/无证据、有/无 ID、规则 vs 直接 ECK、BM25 vs 测试选择基线）有效隔离了每种表示成分的真实贡献。
- **诚实的局限声明**：论文多处主动区分“投影保真度”与“独立影响发现”，不夸大模型在补丁审查中的能力，这种严谨性在同类论文中较突出。
- **工程化程度高**：提供可复现的 CLI（CPU 即可跑通核心流程）、公开 artifact 仓库、保存的原始模型输出，可直接重评分，威胁有效性分析透彻。
- **对规则/记忆系统的兼容态度**：没有全盘否定现有规则系统，而是将其定位为 ECK 的投影交付层，给出实操性的迁移路径（提取→LLM 提议→人工审批→CI 验证→代理消费）。

### 8. 不足与局限

- **样本规模有限**：3 个小仓库、17 个 ECKU、26 个受控补丁，概括性有限；不足以支撑跨语言、跨规模仓库的结论。
- **任务构造偏差**：即使请求描述与补丁文件名独立，但任务仍由已知补丁事后构造，缺少自然问题报告基准（如 SWE-bench 风格）。
- **标注偏差**：影响 gold 标签仅 1 名标注者，无一致性检验；跨层案例的合成性质进一步限制生态效度。
- **投影保真度的构造性偏差**：补丁审查和跨层评估中，目标本身由确定性影响引擎生成，模型只是“消费报告”，满分类别不构成端到端性能证明。
- **模型覆盖窄**：仅 Qwen2.5 家族（7B/32B）两个模型，未见 GPT/Claude/DeepSeek 等更广泛验证。
- **新鲜度研究局限**：扰动是合成的，不包括开发者自然编辑；哈希变化是治理信号而非语义等价性的证明，可能出现“无害编辑触发失效”或“语义变化但哈希未变”的情况。
- **缺少端到端修复评估**：不涉及补丁生成成功率和真实代码修复效果，无法证明 ECK 提升 SWE-bench 式任务解决率；这正是未来以 SWE-Skills-Bench 的版本错配结果为导向的验证方向。
- **领域与语言局限**：原型仅支持 Python；关系组合（compose）为未来工作，关系扩展影响尚未实现；对多语言仓库、大型单体仓库的适应性未验证。
