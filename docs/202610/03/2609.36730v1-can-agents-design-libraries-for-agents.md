## 摘要
智能体越来越多地基于其他智能体编写的代码进行构建，并且倾向于重新实现而非复用，这使得后续智能体必须处理的代码库不断膨胀。为了衡量智能体为其他智能体设计程序库的效果，我们提出了 LibraryDesignBench，这是一个两阶段基准：其中一个智能体根据一份规范实现一个功能完备的程序库，该规范定义了所需能力和潜在用例，但不规定设计。我们通过来自不同模型系列的三个用户智能体所编写程序的正确性和简洁性来评估该程序库。该基准涵盖四种语言中的 15 个程序库设计任务，共 242 个经专家验证的编程问题。在 15 个任务中的 11 个上，作为设计者的智能体复现了人类编写的生产级程序库中的抽象。下游智能体同样会采用智能体编写和人类编写的程序库，但对其利用不足，会重新实现程序库已经提供的功能。我们的失败分析发现，下游智能体编写额外代码，主要是因为智能体编写的程序库僵化或难以使用，而不是因为功能缺失。我们还进行了实验：为设计者提供更具规定性、以智能体为先的指导，并让它们用子智能体测试其程序库；这提高了下游得分，并产生了更简单的程序。LibraryDesignBench 既提供了一个测试平台，用于评估面向智能体用户的程序库设计实践，也提供了一个可改善下游复用的初始设计基线。

## Abstract
Agents increasingly build on code written by other agents, and they reimplement rather than reuse, growing the codebases later agents must work in. To measure how well agents design libraries for other agents, we introduce LibraryDesignBench, a two-phase benchmark in which an agent implements a full-featured library from a specification that defines required capabilities and potential use cases without prescribing the design. We evaluate the library through the correctness and simplicity of programs written by three user agents from different model families. The benchmark spans 242 expert-validated programming problems across 15 library-design tasks in four languages. On eleven of the fifteen tasks, agent designers reproduce the abstractions of the human-written production library. Downstream agents adopt agent- and human-written libraries alike but underuse them, reimplementing capabilities the library already provides. Our failure analysis finds that downstream agents write extra code mainly because agent-written libraries are rigid or hard to use, not because capabilities are missing. We also experiment with giving designers more prescriptive, agent-first guidance and having them test their library with subagents; this improves downstream scores and yields simpler programs. LibraryDesignBench provides both a testbed for evaluating library-design practices for agent users and an initial design baseline that improves downstream reuse.

## 1. 核心问题与整体含义

- **研究动机**：智能体越来越多地基于其他智能体编写的代码构建，但倾向于"重新实现"而非"复用"，导致后续智能体必须处理的代码库持续膨胀，增加人工修复成本。软件工程史上，人类工程师通过设计库、框架、SDK 的"有主见的设计决策"来降低后续工作难度。如今面临一个拐点：智能体使用的代码将更多来自其他智能体而非人类工程师。
- **核心问题**：**智能体能否为其他智能体设计出可被有效利用的程序库？**
- **关键难点**：评估生成的库非常困难。传统测试只能检验库的*正确性*，无法衡量其对使用者的*帮助程度*；按规范评分接口需要签名或构造，这恰恰"规定了"我们要测量的设计自由度；智能体验证与静态指标只评实现、不评可用性；人工评审衡量的是人类偏好而非智能体需求。
- **根本洞察**：**唯一忠实的评估方式，是观察智能体如何使用它。** 面向智能体的库设计与面向人类的库设计存在本质差异，且仍是一个开放问题。

## 2. 方法论

### 2.1 核心思想：两阶段基准 LibraryDesignBench

- **设计阶段（Design Phase）**：被评估的设计者智能体 πθ 根据指令 I 实现库 L。指令列出必须支持的功能能力与 2–3 个示例用法（"可见问题"），但**不规定接口与抽象**，迫使智能体自行推理需要哪些抽象。同时要求：主要用户是编码智能体、资深工程师会审阅、需按语言特定的包管理器打包（提供 `pyproject.toml`/`package.json`/`Cargo.toml`/`.cabal` 等布局要求）。
- **评估阶段（Evaluation Phase）**：多个能力较弱的用户智能体 πu 使用该库实现下游程序。问题必须"有无库均可解"，实现者被明确要求写出"薄适配器"（thin adapter）并阅读文档，以诱发库被最大程度利用。

### 2.2 评分函数

总分 = 正确性与简洁性的乘积：

$$
\text{score}(L)=\frac{1}{|P|\cdot|U|}\sum_{u\in U}\sum_{x_i\in P} q_i(y_i)^2\cdot\rho_i(y_i),\quad y_i\sim\pi_u(x_i\mid L)
$$

- $q_i(y_i)\in[0,1]$ 为通过的测试比例，**取平方**以优先保证正确性，同时保留部分正确程序的梯度得分（80% 通过、参考大小 → 0.64；全部通过、1.5 倍大小 → 0.67）。
- 若库无法安装，得分恒为 0。

**简洁性** $\rho_i$ 定义为参考解与生成解在多个静态指标上的比值均值（上限截断为 1）：

$$
\rho_i(y_i)=\frac{1}{|M|}\sum_{m\in M}\min\left\{\frac{m(y_i^*)}{m(y_i)},1\right\}
$$

- $M=\{$圈复杂度、认知复杂度、Halstead 体积、源码行数（SLOC）$\}$，避免依赖单一指标；格式化后测量，排除注释与空行。
- **参考解** $y_i^*$：使用成熟生产库 $L^\star$ 编写并针对惯用抽象优化的固定程序（非"代码高尔夫"），由库专家借助智能体开发优化。

### 2.3 聚合与统计

- 每个任务独立重复设计阶段 $K=3$ 次，每个库用固定实现者集合评估；任务等权聚合：$\hat{S}=\frac{1}{TK}\sum_p\sum_k S_{p,k}$。
- 采用**分层（按任务）重跑标准误**，保留库内部相关性（同一架构缺陷可能同时影响多个问题/实现者），给出 Welch–Satterthwaite 自由度下的 Student-t 95% 置信区间。描述性指标（通过率、简洁性、成本）使用按任务聚类的标准误。

### 2.4 实验干预（Prompting Interventions）

- 向设计者追加**面向智能体的显式指导提示**（称为 neuralese 风格）：先写 10–15 个消费者程序草图（SKETCHES.md），再据此设计 API、实现、用无记忆子智能体测试、冻结为可运行示例、写 README、打包。

## 6. 主要结论与发现

- **RQ1（智能体能否设计出改善其他智能体的库？）**：能。Opus 5.5 得分最高 **48.9**，比生产库基线（46.6）高 **2.3 分（相对 4.9%）**；但设计者在 **15 个任务中的 11 个**复现了生产库的抽象（如 `clirs` 中复制 clap 的 builder 而非更短的 derive 宏）。下游正确率在各设置间几乎无差异（84.1%–86.6%），无库条件也达 86.4%，**得分差异主要来自简洁性**。DeepSeek V4 Pro 的库比无库还低 9.2%；Haskell 中约 70% 的（设计者, 任务）对低于无库。
- **RQ2（为何智能体使用库时挣扎？）**：抽样中 **82%** 的主要过度代码归因于库的局限，其中 **Rigidity + Verbosity 占 64%**，而 **Coverage（功能缺失）仅占 14%**。典型模式：库只实现规范字面点名的核心功能（如 33 个 `clirs` 库中 24 个不支持长选项前缀推断，相关问题上低 16.7 分）。
- **RQ3（实现者如何更好利用库？）**：更规定性的提示与更高推理努力分别带来 **23% 与 63%** 的相对提升——**提示驱动库使用，努力驱动正确性**；即使如此，解仍远长于参考。仅用生产库时，8 个实现者最高分仅 66.9（Opus 5.5），说明**部分差距来自实现者而非设计**。最小提示下 24% 的试验从不打开库，36% 的参考库符号从未被看到。
- **RQ4（智能体式设计模式是否有效？）**：显式指导提示使得分从 44.1 升至 **46.4**（仍略低于生产库 46.6 与 Opus 5.5 的 48.9），主要来自 **6.8% 的简洁性提升**（+2.5 分来自简洁性，−0.9 来自正确性），与生产库的导出名重叠从 19.4% 降至 13.4%，但设计成本近乎翻倍（$8.24 vs $4.51）。
- **搜索行为发现**：智能体倾向"验证记忆中的 API"——64–87% 的 grep 是标识符形状，仅 16–20% 与任务用词相关；92% 跳过读库的解仍凭记忆 import 库。

## 7. 优点

- **评估范式创新**：首次以"下游智能体真实使用"来度量库设计质量，而非测试正确性或接口合规性，把用户研究方法（固定任务观察开发者）迁移到智能体用户并替换为正确性 + 代码量。
- **评分设计精巧**：正确性平方 × 简洁性的乘积、四指标平均且截断、任务等权聚合，兼顾梯度与稳健性；为"智能体对智能体"评估提出分层重跑标准误与置信区间。
- **基准构建严谨**：多阶段智能体流水线 + 双重专家审计；问题要求"无库也可解"以保证公平；参考解为惯用优化而非代码高尔夫。
- **失败分析深入**：五类十叶的细粒度分类学，揭示"僵化/难用"而非"功能缺失"是主因，对后续设计有直接指导意义。
- **可操作的设计干预**：显式"neuralese"指导（消费者先行草图 + 可运行示例 + 子智能体测试）被验证有效，并公开代码与数据。

## 8. 不足与局限

- **评估范围受限**：仅衡量指定任务、消费者配置与预算下的下游效用，**不构成与消费者无关的库排序**；不评估完整正确性、安全性、运行时效率或可维护性。
- **参考解非唯一最优**：参考程序只是归一化基准，不代表唯一最优解；基准偏向存在复用机会的工作负载。
- **统计泛化有限**：置信区间只覆盖固定任务集的重跑波动，每任务仅 3 次生成，名义覆盖率无保证；不保证泛化到所有库领域。
- **审计主观性风险**：失败分类由单一模型（与某实现者同族）完成，无人工标签与一致性检验，且基于"最佳路径"推理而非实际执行，可能存在系统性偏差。
- **设计自由度与可测性的张力**：规范虽不规定接口，但"必须支持的能力列表"仍可能引导设计；不同 harness（如 mini-SWE-agent vs Claude Code）导致分数差异显著（Fable 5.1：47.5 vs 39.9），需分别报告。
- **应用限制**：超时/安装失败占 2.3% 仍按现状计分；离线环境与包管理约束可能不反映真实开发条件。
