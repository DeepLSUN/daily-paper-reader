## 摘要
大语言模型智能体正越来越多地被部署于数据密集型工作，然而可靠的数据分析所需的不仅仅是通用推理和临时性的工具增强。配备工作流执行框架的数据智能体，为自动化端到端数据科学生命周期提供了一种有前景的范式。本文从以工作流执行框架为中心的视角审视数据智能体。首先，我们介绍数据智能体及相关数据环境的分类体系，并围绕五个功能阶段组织文献：感知、规划、执行、验证和修复。其次，我们分析每个阶段中的关键技术路线，识别出从数据结构探测到数据状态重建的15种不同方法。第三，我们指出四个尚未解决的可靠性问题：语义校准未激活、澄清缺失、经验迁移缺失以及验证-修复仓库缺失。这些问题解释了为何即使单个组件运行正常，静默失败仍会持续存在，并凸显了对严格的工作流执行框架和共享可靠性资源的需求。最后，我们总结数据智能体的横向任务族，考察其纵向应用场景及评估基准，同时维护配套仓库：https://github.com/DEEP-PolyU/Awesome-Data-Agents。

## Abstract
Large language model agents are increasingly deployed for data-intensive work, yet reliable data analysis requires more than general-purpose reasoning and ad hoc tool augmentation. Data Agents, equipped with workflow harnesses, offer a promising paradigm for automating the end-to-end data science lifecycle. This paper examines Data Agents from a harness-centric perspective. First, we introduce a taxonomy of Data Agents and associated data environments, organizing the literature around five functional stages: perception, planning, execution, verification, and repair. Second, we analyze the key technical routes within each stage, identifying 15 distinct approaches ranging from data structure probing to data state reconstruction. Third, we identify four open reliability problems: inactive semantic calibration, missing clarification, missing experience transfer, and the missing verification-repair repository. These problems explain why silent failures can persist even when individual components function correctly, highlighting the need for rigorous workflow harnesses and shared reliability resources. Finally, we summarize the horizontal task families of Data Agents, examine their vertical application settings, and benchmarks for evaluation, while maintaining a companion repository at https://github.com/DEEP-PolyU/Awesome-Data-Agents.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体已成为数据密集型工作的主要接口，擅长任务分析、生成计划、把自然语言翻译成 SQL/Python。但"通用推理能力强"并不等于"分析结果可靠"。
- **核心矛盾**：在真实、不完美的数据环境中，智能体可能**不报错地给出错误答案**——即所谓**静默失败（silent failure）**：任务正常终止、结果看似合理，但建立在错误假设之上。
- **五个反复出现的环境性挑战**：
  1. **数据真实语义未被表层上下文充分表达**：原始格式/表格布局/特征定义只提供部分语义，字段间语义关系、数据生成分布等关键信息缺失。
  2. **解空间严重欠定**：同一任务与数据环境几乎没有唯一标准解法，策略数量巨大。
  3. **工具执行本质上是动态的**：最优下一步依赖上一步执行后才出现的中间观测，无法预先确定完整执行序列。
  4. **失败信号稀疏且非局部**：错误常在多步之后才以下游症状形式暴露，难以定位真正的致因步骤。
  5. **修复与局部数据上下文纠缠**：修复代码与 schema、表格布局、数值分布强绑定，难以复用。
- **核心论点**：问题不在于"工具不够多、推理不够强"，而在于缺少一套**纪律化的工作流执行框架（workflow harness）**。作者提出从"能力集合"转向"受治理的分析流程"，把一次性答案生成器改造为可靠的 **AI Data Scientist**。
- **重要概念区分**：
  - **Workflow（工作流）**：智能体与数据环境交互产生的任务特定轨迹（动作、观测、数据状态的序列）。
  - **Workflow Harness（工作流执行框架）**：治理这条轨迹**如何被构造、监控与修正**的控制结构——不规定固定操作序列，而是决定智能体如何解读当前数据状态、选择动作、评估结果、并在偏离目标时响应。
  - 与传统编排器（如 Airflow 执行开发者指定的 DAG）不同：Data Agent 随数据状态演化而**选择、评估、修订**分析动作。

## 2. 方法论：以 Harness 为中心的分类体系

### 2.1 形式化基础

- **数据环境**：$\mathcal{D} = \{d_1, d_2, \dots, d_m\}$，每个数据源 $d_j = \langle X_j, \tau_j, \Sigma_j, \Pi_j \rangle$：
  - $X_j$：数据载荷（CSV 单元格、数据库行、图表像素、文档文本）；
  - $\tau_j$：结构类型（结构化 / 半结构化 / 非结构化）；
  - $\Sigma_j$：数据结构（列 schema、JSON 嵌套键路径、表头与布局位置）；
  - $\Pi_j$：数据属性（唯一约束、公式依赖、统计分布）。
  - $\Sigma_j$ 与 $\Pi_j$ 共同构成智能体必须导航的**数据上下文**；所有数据源的当前配置构成**数据状态**。
- **三类数据环境的差异**：
  - 结构化（关系库、时序）：$\Sigma_j$ 显式、$\Pi_j$ 由完整性约束定义，可确定性查询；
  - 半结构化（表格、HTML、JSON）：$\Sigma_j$ 部分可观测（表头缺失、嵌套任意），需先推断结构；
  - 非结构化（PDF、图像、文本）：$\Sigma_j$ 缺失、$\Pi_j$ 潜在，载荷 $X_j$ 是唯一信息来源，需主动抽取构造任务相关表示。
- **Data Agent 定义（Def. 2.1）**：LLM 驱动、通过多步交互与持久数据环境协作，把数据转化为可验证分析产物（清洗后数据集、可视化、报告、训练好的模型）。
- **操作化形式化**：给定任务 $T$、初始环境 $\mathcal{D}_0$、执行环境 $\mathcal{E}$（动作空间 $A_\mathcal{E}$、观测空间 $O_\mathcal{E}$）、推理核心 $M$，智能体映射为一条有限轨迹：
  $$A(T, \mathcal{D}_0, \mathcal{E}, M) \rightarrow \big((a_1,o_1,\mathcal{D}_1), (a_2,o_2,\mathcal{D}_2), \dots, (a_n,o_n,\mathcal{D}_n), R\big)$$
  其中 $a_i$ 为数据中心动作，$\mathcal{D}_i$ 为更新后的数据状态，$o_i$ 为环境返回的**部分视图**，历史 $h_i$ 条件化下一步决策。
- **研究范围界定**：涵盖（1）数据分析任务（剖析、可视化、数据操纵/表格编辑）与（2）ML 导向任务（特征工程、模型选择、训练）；区别于一次性预测或单次生成系统。

### 2.2 五个功能阶段与 15 条技术路线（每条路线按结构化 / 半结构化 / 非结构化分别论述）

| 阶段 | 功能目标 | 三条技术路线 | 驱动机制 |
|---|---|---|---|
| **感知 Perception** | 从原始异构源构建"置信度校准的数据状态" | ① 数据结构探测 ② 跨源数据对齐 ③ 置信度校准的状态打分 | 探索驱动 / 语义+溯源驱动 / 不确定性驱动 |
| **规划 Planning** | 把感知状态转为可执行蓝图 | ① 树搜索（MCTS/PUCT）② 启发式搜索（beam、进化、代价引导）③ 策略路由 | 价值回传驱动 / 局部打分驱动 / 状态到策略映射驱动 |
| **执行 Execution** | 把计划转为可靠工具调用 | ① 工具能力边界学习 ② 组合式工具推理 ③ 反馈自适应工具调用 | 三类信号：工具需求信号 / 工具规格信号 / 工具反馈信号 |
| **验证 Verification** | 常规化校验中间状态以定位静默失败 | ① 过程分数估计 ② 规则化约束检查 ③ 轨迹级可解释归因 | 打分驱动 / 约束驱动 / 轨迹分析驱动 |
| **修复 Repair** | 从验证信号出发恢复并沉淀可复用经验 | ① 数据状态重建 ② 搜索引导的干预式修复 ③ 可复用记忆技能 | 恢复驱动 / 搜索驱动 / 经验驱动 |

- **阶段间的三条核心问题**：
  - 感知三问："数据环境长什么样？"（探测）"哪些数据对象应归在一起？"（对齐）"这个状态该被信任多少？"（打分）。
  - 规划三问："哪些分支值得继续探索？"（树搜索）"哪些候选值得保留？"（启发式搜索）"哪种既有策略最适配当前状态？"（路由）。
  - 执行三问："这个工具能否可靠满足当前需求？"（能力边界）"多个工具操作应如何连接？"（组合推理）"观测到的执行是否说明需要改？"（反馈自适应）。
  - 验证三问："这个中间步该怎么评？""是否满足显式条件？""哪个动作导致失败、为什么？"
  - 修复三问："从何处恢复？""如何修正？""保留什么？"
- **关键设计思想**：五阶段**不是一次性执行的固定流水线**，而是按演化中的数据状态**按需迭代调用**，可回溯与往返。
- **五大互联目标**：深度语义落地、高效解空间导航、动态工具编排、常规可验证性、泛化修复。
- **四类开放可靠性问题（本文核心贡献之一）**：
  1. **语义校准失活（Inactive Semantic Calibration）**：感知阶段产生的置信度/概率评估**不向下游传播**，智能体把概率性感知坍缩为单一确定性假设；因语法合法而不触发异常，错误被静默放大。
  2. **澄清缺失（Missing Clarification）**：任务意图本身模糊（"增长""风险""区域表现"有多种合理解读）时，智能体默认取统计上最可能的解释而非停下询问；且缺少"什么是有用的分析性追问"的标准与停止准则，导致要么问太少（幻觉假设）、要么问太多（用户疲劳）。
  3. **经验迁移缺失（Missing Experience Transfer）**：修复经验的复用高度依赖任务表面相似性（相似 schema / 分布），跨结构或分布迁移时易发生**负迁移**——把含偶然性步骤的修复模板套用到新环境。
  4. **验证-修复仓库缺失（Missing Verification-Repair Repository）**：缺乏大规模、标准化的失败-修复语料，各系统只能自建狭窄的失败案例集，难以训练识别多样失败模式、验证中间状态并泛化修复策略。

### 2.3 横向任务族、纵向应用与评测框架

- **横向分析任务族（5 类，回答"做什么"）**：数据采集与获取；数据准备与转换；数据查询与信息检索（Text-to-SQL、Table QA、表格推理）；数据分析与预测（时序预测/分类、异常检测）；数据解读与多模态推理（EDA、可视化与洞察生成、文档/多模态推理）。该视角与工作流视角正交：同一目标可跨多阶段，同一操作可服务不同目标。
- **纵向应用场景（4 类，回答"能力如何组合"）**：
  1. **交互式数据辅助**：Fabi Analyst Agent、V7 AI Spreadsheet Analysis Agent；
  2. **协作式分析工作**：GPT for Work（嵌入 Excel/Google Sheets）、Codex；
  3. **自主数据工作流**：Snowflake CoCo / Cortex Agents、Databricks Genie Code、Manus；
  4. **知识密集型发现**：Manus 多步研究、Pelayar Spreadsheet Agent（PDF/发票/图像→结构化表格）、金融与商业分析。
- **评测框架四维**：评测目标与任务覆盖；数据/环境/任务复杂度（数据复杂度、知识需求、交互复杂度、环境不确定性）；评测准则（执行准确率、意图忠实度、证据相关性/充分性、视觉落地、过程质量、效率与鲁棒性、失败归因）；当前基准的局限。

## 6. 主要贡献与核心结论

### 6.1 论文自述的四项贡献

1. **概念贡献**：首次系统区分 **Workflow** 与 **Workflow Harness**，把"数据智能体可靠性"问题从"能力叠加"重新表述为"流程治理"问题。这一区分是全文的理论锚点——它解释了为何单纯增加工具或提升基座模型推理能力无法根治静默失败。
2. **形式化贡献**：给出数据环境 $\mathcal{D}$、Data Agent、交互轨迹 $A(T,\mathcal{D}_0,\mathcal{E},M)$ 的形式化定义，为后续工作提供了可复用的符号体系与任务边界（明确排除一次性预测与单次生成系统）。
3. **分类贡献**：构建"**五阶段 × 三数据形态 × 十五技术路线**"的三维分类体系，并把感知、规划、执行、验证、修复各自细分为三条驱动机制明确的技术路线，使庞杂文献获得可比对的坐标。
4. **问题贡献**：提炼出**四类开放可靠性问题**（语义校准失活、澄清缺失、经验迁移缺失、验证-修复仓库缺失），为后续研究指明可攻击的具体缺口。

### 6.2 论文隐含的核心结论

- **可靠性瓶颈的定位转移**：静默失败的根因不在单步推理质量，而在**跨阶段的信息衰减**——尤其是感知阶段产出的概率性/置信度信息在向下游传递时被坍缩为确定性假设（对应"语义校准失活"）。
- **验证与修复是当前体系最薄弱的环节**：相比感知与执行已有较多工作，验证（尤其是过程级验证与轨迹级归因）与修复（尤其是跨任务可复用经验的沉淀）在文献中覆盖最稀疏，且缺少标准化的失败-修复语料。
- **阶段划分的实践含义**：五阶段不是流水线，而是**可迭代、可回溯的调用集合**；一个成熟 harness 应能根据数据状态决定"此刻该回到感知、还是进入修复"。
- **任务视角与工作流视角正交**：同一分析目标（如"预测"）可横跨多个阶段，同一操作（如"查询"）也可服务不同目标——这意味着评测不应只按任务族切分，还需覆盖过程质量。

## 7. 局限性与未来方向

### 7.1 论文自身承认或隐含的局限

- **无实证验证**：所有关于"harness 能提升可靠性"的论断均为文献归纳所得，未经受控实验或消融验证，因此其因果主张属于**假说而非结论**。
- **分类边界模糊**：作者自述各技术路线"互补而非互斥"，导致同一工作可能同时符合多条路线，削弱了分类的判别力。
- **覆盖偏向**：约 150 篇文献以 2024–2026 年预印本与工业系统为主，可能对早期经典工作（如传统 EDA 自动化、数据清洗理论）覆盖不足。
- **配套资源不可验证**：GitHub 仓库的条目数、更新频率、与正文分类的对应关系均未报告，读者无法核对其完整性。

### 7.2 论文指出的未来方向

- **置信度传播机制**：如何让感知阶段的不确定性评估贯穿规划、执行、验证，避免过早坍缩为确定性假设。
- **澄清标准与停止准则**：建立"何种模糊性值得追问""追问到什么程度停止"的规范，平衡幻觉风险与用户负担。
- **抗负迁移的修复经验表示**：寻找与表面相似性解耦的经验抽象方式，使修复策略在跨 schema、跨分布时仍可安全复用。
- **构建验证-修复语料库**：收集大规模、标注规范的"失败-诊断-修复"三元组，作为训练与评测的共同基础设施。
- **面向过程的评测基准**：从结果正确率转向对中间状态可信度、归因质量、修复效率的度量。

## 8. 对研究与实践的启示

- **对系统设计者**：与其继续堆叠工具与提示技巧，不如优先建设 harness 层的三件事——(1) 感知结果的可信度标注与传递；(2) 过程级验证钩子；(3) 可检索的修复经验库。三者的缺失正是静默失败的主要温床。
- **对评测设计者**：现有基准多以最终答案准确率为主指标，难以捕捉"过程合法但假设错误"的失败。可考虑引入**中间状态核查**、**假设显式化要求**、**失败归因得分**等维度。
- **对研究者**：四类开放问题中，"语义校准失活"与"验证-修复仓库缺失"最具可操作性——前者是机制设计问题，后者是数据基础设施问题，二者都可产出可复现的独立贡献。
- **对读者的阅读建议**：本文宜作为**地图**而非**证据**使用——用其分类体系定位自己的研究坐标、用其开放问题清单寻找选题缺口，但不应将其分类结论当作已证实的经验规律。
