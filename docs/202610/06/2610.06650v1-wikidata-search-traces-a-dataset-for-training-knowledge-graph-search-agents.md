## 摘要
Wikidata 是最大的开放知识库之一，但在其上回答一个复杂问题仍需编写 SPARQL 查询，正确命名实体与属性并串联它们之间的关系。语言模型提供了自然语言的替代方案，但主要依赖记忆作答，对不太知名的实体而言最为不可靠。我们研究通过探索图来作答的智能体，并认为有两个障碍限制了它们：缺乏记录求解器如何探索的训练数据，以及会将大量图结果直接加入模型上下文的接口。我们检验三个假设：图搜索的难度可以通过问题的结构来控制，而不仅仅通过冷僻实体或措辞；长程搜索中的大部分失败源于检索证据的管理方式，而非模型本身；在合适的环境中，开放权重模型能够匹敌商业闭源模型。我们通过在冻结的 Wikidata 快照上将命名实体替换为嵌套条件来构建多跳问题，并在每次扩展后检查目标仍然唯一、且每个新条件都是必要的。我们发布了 10,235 条针对单实体与多跳问题的求解轨迹，以及产生这些轨迹的递归语言模型（RLM）框架；在该框架中，模型批量执行图调用，将结果保存在持久的 Python 状态中，并通过子调用解读选定的证据。在 100 个问题上，与在相同函数上直接调用工具相比，该框架在两种接口下均提升了我们运行的两个模型：gpt-6-luna 从 49 个正确答案提升到 61 个，多跳准确率翻倍；而 Qwen3.8-27B——一个在单张 GPU 上服务的开放权重模型——则从 60 提升到 74。

## Abstract
Wikidata is one of the largest open knowledge bases, yet answering a complex question over it still requires a SPARQL query that names the right entities and properties and chains their relations. Language models offer a natural-language alternative but answer largely from memory, which is least reliable for less prominent entities. We study agents that instead answer by exploring the graph, and argue that two obstacles limit them: the lack of training data recording how a solver explores, and interfaces that add large graph results directly to the model's context. We test three hypotheses: that the difficulty of graph search can be controlled through the structure of a question rather than only through obscure entities or wording; that much of the failure on long-horizon search comes from how retrieved evidence is managed rather than from the model itself; and that, in a suitable environment, open-weight models can match commercial closed ones. We construct multi-hop questions on a frozen Wikidata snapshot by replacing named entities with nested conditions, checking after each expansion that the target remains unique and that every new condition is necessary. We release 10,235 solving traces over single-entity and multi-hop questions, together with the recursive language model (RLM) harness that produced them, in which models batch graph calls, keep results in persistent Python state and interpret selected evidence through sub-calls. On 100 questions, the harness improves both models we ran under both interfaces compared with direct tool calling over the same functions: gpt-6-luna rises from 49 to 61 correct answers, doubling its multi-hop accuracy, and Qwen3.8-27B, an open-weight model served on a single GPU, from 60 to 74.

- **背景**：Wikidata 是最大开放知识库之一，但复杂问答仍依赖 SPARQL，需要正确识别实体、属性并串联关系。

- **核心主张**：应让智能体通过“探索图”来回答，而非凭记忆回答。但当前存在两个障碍：
  - 缺乏记录“求解器如何探索知识图谱”的训练数据；
  - 常见工具调用接口会把大量图查询结果直接塞入模型上下文，导致长程搜索失败。
- **三个假设**：
  - **H1 结构**：图搜索难度可由问题结构控制，如嵌套依赖数量、条件歧义度，而不仅靠冷僻实体或晦涩措辞。
  - **H2 证据管理**：长程图搜索的许多失败源于模型如何管理检索证据，而非模型知识或推理能力不足。
  - **H3 开放模型**：在合适环境中，单卡服务的开放权重模型可匹敌商业闭源模型。
- **整体意义**：论文发布 10,235 条求解轨迹与递归语言模型（RLM）框架，推动可训练、可审计、可本地运行的知识图谱搜索智能体研究。

## 2. 方法论：核心思想与关键技术细节

- **问题表示**：
  - 知识图谱记为 \(G \subseteq E \times P \times E\)，事实为 \((u,p,v)\)。
  - 条件可写成知识投影：\(R_p(S)=\{x \in E:\exists y\in S,(x,p,y)\in G\}\)，反向投影为 \(R_p^{-1}(S)\)。
  - 目标集合 \(T\) 是所有条件候选集的交集，要求 \(T=\{s\}\)，其中 \(s\) 是已知答案实体 seed。
  - 条件歧义度用“候选数量”衡量，例如“参与勒芒 24 小时耐力赛”候选数为 2,331。

- **长程问题构造**：
  - 围绕已知答案实体，将命名实体逐步替换为“隐藏实体 + 嵌套条件”。
  - 两个算子：
    - **SELECT**：选择下一个要隐藏的命名实体。
    - **EXPAND**：用 1–3 个条件组成的 bundle 替换该实体，形成嵌套依赖。
  - 根扩展描述 seed 本身并定义 \(T\)，后续扩展引入 \(V_1,V_2,\dots\) 等隐藏中间实体。
  - 示例：将“摩纳哥赛道”隐藏为“街道赛道 + 赛车运动”的条件组合，使问题必须多跳求解。

- **认证与必要性检查**：
  - 对每个扩展 bundle \(B\)，要求：
    - **认证**：\(T_B=\{s\}\)，即完整问题图只识别出唯一 seed。
    - **必要性**：对每个条件 \(c\in B\)，\(|T_{B\setminus\{c\}}|\ge 2\)，即删除任一新增条件都会出现其他可能答案。
  - 还拒绝泄露隐藏实体名称的线索，并要求每个条件至少匹配两个候选，避免单条件直接锁定答案。
  - 重复 SELECT/EXPAND，要求至少 3 次扩展、深度 3，最多 10 次扩展、深度 7。

- **问题生成**：
  - 将问题图转为 Mermaid 式文本，命名实体为可读节点，隐藏实体为变量节点，条件为带属性标签的有向边。
  - 问题类型包括：identity、year、quantity、group、count、argmax、argmin。
  - 由 writer LLM 生成自然语言问题，critic LLM 检查条件完整性、答案类型、自然度与答案泄露。
  - 机械检查拒绝包含标识符、隐藏实体名或答案的问题。
  - 另生成单实体问题：直接命名目标，询问某个事实，不进行图增长。

- **求解轨迹与 RLM 框架**：
  - 求解轨迹记录模型在 RLM harness 中回答问题的过程。
  - RLM harness 提供持久 Python REPL，模型可：
    - 批量执行图函数调用；
    - 将中间结果存入变量；
    - 选择性打印证据，避免上下文爆炸；
    - 使用 `llm_query` / `llm_map` 对选定证据进行子调用解读；
    - 通过 `FINAL(value)` 或 `FINAL_VAR(value)` 提交答案。
  - 共提供 13 个图函数：`search_entity`、`search_property`、`claims`、`references`、`describe`、`labels`、`label`、`descriptions`、`edges`、`count_edges`、`degree`、`name`、`has`。
  - 使用冻结的 2026 年 2 月 Wikidata 快照，约 4,800 万实体、2.62 亿事实。

- **seed 选择**：
  - 覆盖不同实体类型、语言和知名度。
  - 排除 Wikimedia 维护实体，限制入度/出度。
  - 使用长尾分数 \(L(e)=1-\frac{r(d_{in}(e))+r(q(e))}{2}\)，采样 popular、moderate、rare 三类 seed。
  - 部分 seed 仅用阿拉伯语、俄语或中文描述，以增加语言覆盖。

## 3. 实验设计：数据集、Benchmark 与对比方法

- **Benchmark/评估集**：
  - 主评估包含 100 个问题：50 个单实体问题 + 50 个多跳问题。
  - 评估时不给模型任何收集阶段使用的图派生线索。
  - 使用精确答案评分。

- **对比接口**：
  - **RLM harness**：模型在持久 Python REPL 中调用相同图函数，批量查询、保存状态、选择性解读。
  - **直接工具调用 agent**：将相同 13 个图函数作为工具，结果作为对话消息返回，使用 OpenAI Agents SDK，其他提供商用 LiteLLM。

  - Agent 最多 100 次模型调用，每题成本上限 0.50 美元，本地 Qwen 不适用成本上限。

  - 两者可见输出截断为 10,000 字符。
  - 但图调用次数未匹配：Python 单元可一次执行大量图调用。

## 5. 实验结果与分析

> 说明：以下分析围绕论文提出的三个假设（H1 结构、H2 证据管理、H3 开放模型）展开，结论方向与论文报告一致。

- **接口对比是主实验**：在相同的 13 个图函数、相同指令、相同预算上限下，仅改变“结果如何进入模型”这一点，即对比 RLM harness（持久 REPL + 变量存储 + 选择性打印）与直接工具调用 agent（每条工具结果作为对话消息返回）。因此该对比直接检验 H2。
- **单实体问题 vs 多跳问题**：
  - 单实体问题中位仅需 1 轮，答案通常来自一次 `claims` 或 `describe` 调用，两种接口差距较小；主要失败来自属性歧义（同一属性标签对应多个 PID）与语言标签不匹配。
  - 多跳问题中位约 10 轮，是差距的主要来源。直接工具调用 agent 在多跳后段常出现上下文饱和：早期批次返回的大量实体/边挤占上下文，导致模型丢失原始约束或遗忘已确认的中间实体。
- **H2 的关键证据**：失败并非集中在“模型不知道某实体”，而是集中在证据管理——即模型把哪些中间结果保留在上下文中、哪些丢弃、哪些需要再解读。RLM 允许把中间结果赋给变量、只打印计数或标签，从而把上下文占用从“与检索量成正比”变为“与决策所需信息量成正比”。
- **H1 的结构控制**：
  - 因为问题由 seed 出发、经 SELECT/EXPAND 认证构造，嵌套深度与条件歧义度（候选集合大小）是可控变量，可与实体知名度解耦。
  - 论文据此可以区分“问题难在结构”与“问题难在冷僻实体”，从而检验 H1：即性能下降是否随嵌套深度和单条件候选数单调变化，而非仅随 seed 长尾分数变化。
- **H3 的检验**：Qwen3.8-27B 以 FP8 + vLLM 在单张 H100 上服务，若在 RLM harness 下接近同时运行的商业模型，则支持“合适环境中开放权重模型可匹敌闭源模型”。估计 batched serving 成本约 0.04 美元/问题，与 0.50 美元/题的商业上限形成对比。
- **预算的公平性注意点**：两者模型调用次数上限相同（100 次），但图调用次数未对齐——Python 单元一次可执行大量图调用，而工具调用每次只返回一个结果。因此 RLM 的优势部分是“单位模型调用能携带更多图查询”，论文据此把它归因于接口而非模型能力。
- **失败模式分类（论文层面）**：
  - 检索失败：未找到正确实体或属性（受标签语言、别名、模糊匹配影响）。
  - 推理/组合失败：找到中间实体但未正确求交集或未满足唯一性。
  - 证据管理失败：上下文丢失、重复检索、误读子调用结果。
  - 提交失败：格式或答案类型不匹配（如 year 题给出实体名）。
- **轨迹数据的价值**：发布的 10,235 条轨迹（多跳 672、单实体 9,563）记录了模型如何探索图，可用于训练“会搜索”的智能体，而不仅是评估；这呼应 H2——证据管理是可学习的行为，而非仅靠加大模型规模解决。

## 6. 局限与未来工作

- **快照与时序**：使用冻结的 2026 年 2 月 Wikidata 快照（约 4,800 万实体、2.62 亿事实），答案与候选集随时间变化，评测不可直接复用于未来快照。
- **评测规模有限**：主评估仅 100 题（50 单实体 + 50 多跳），虽然用于假设检验足够，但不足以覆盖 Wikidata 全部属性语义与语言。
- **生成偏差**：问题由 LLM writer 生成、critic 检查，并用机械规则拒绝答案泄露；但自然度与真实用户提问分布仍可能有差距。
- **预算不对称**：图调用次数未在两种接口间匹配，RLM 的批量执行优势可能被高估，或反之被低估，取决于如何定义“公平预算”。
- **未训练新模型**：论文核心贡献是数据构造、RLM 框架与推理评估，未报告训练算力、总 GPU 小时或能耗；开放权重模型的可训练性有待后续工作验证。
- **语言覆盖**：虽然部分 seed 仅用阿拉伯语、俄语或中文描述，但整体仍以英文 Wikidata 标签为主，多语言检索与跨语言别名匹配仍是未充分探索的方向。

## 7. 结论与意义

- **核心结论**：让智能体通过“探索图”而非“凭记忆”回答，是可训练、可审计、可本地运行的路线；其瓶颈更多在证据管理接口，而非模型知识或推理能力。
- **方法论贡献**：
  - 用认证与必要性检查自动构造结构可控、答案唯一的多跳问题，把难度从“冷僻实体”解耦为“嵌套深度与条件歧义度”。
  - 提出 RLM harness：以持久 Python REPL 承载图函数，允许批量查询、变量存储与选择性解读，抑制上下文爆炸。
