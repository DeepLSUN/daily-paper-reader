## 摘要
可执行环境对于在需要工具使用和多步交互的任务上对智能体进行后训练至关重要，但将可执行任务与其环境一并构建仍然难以规模化。技能提供了可复用的领域知识、操作流程和工具使用说明，但技能所包含的信息与一个具有完整可执行环境的具体且具有挑战性的任务之间仍存在显著差距。为弥补这一差距，我们提出 Skill2Env，一个面向能力的框架，它从技能出发，并利用智能体能力需求来指导任务与环境合成。Skill2Env 通过可复用的难度模式来表示这些需求，并将其实例化为任务蓝图，用以规定目标、挑战、环境事实、信息边界和验收标准。这些蓝图指导围绕源技能联合构建任务指令、执行基底、工作空间以及基于评分量规的评估器。我们进一步提出迭代式任务强化（Iterative Task Hardening），它利用求解器的执行证据来识别挑战性不足的任务设计，强化或扩展其难度模式实例，并修订相应的蓝图与环境。使用由 Skill2Env 环境生成的 1.5K 条高分轨迹进行监督微调后，我们在广泛的智能体基准上观察到一致提升，表明面向能力的环境合成对智能体后训练是有效的。

## Abstract
Executable environments are critical for post-training agents on tasks that require tool use and multi-step interaction, but constructing executable tasks together with their environments remains difficult to scale. Skills provide reusable domain knowledge, operational procedures, and tool-use instructions, but a substantial gap remains between the information contained in a skill and a concrete, challenging task with a complete executable environment. To address this gap, we introduce Skill2Env, a capability-oriented framework that starts from a skill and uses agent capability demands to guide task and environment synthesis. Skill2Env represents these demands through reusable difficulty patterns and instantiates them into task blueprints that specify objectives, challenges, environment facts, information boundaries, and acceptance criteria. These blueprints guide the joint construction of task instructions, execution substrates, workspaces, and rubric-based evaluators around source skills. We further propose Iterative Task Hardening, which uses solver execution evidence to identify insufficiently challenging task designs, strengthen or extend their difficulty-pattern instantiations, and revise the corresponding blueprints and environments. Using 1.5K high-scoring trajectories generated from Skill2Env environments for supervised fine-tuning, we observe consistent improvements across a broad range of agent benchmarks, demonstrating the effectiveness of capability-oriented environment synthesis for agent post-training.

## 1. 核心问题与研究动机

- **背景**：随着 LLM 被部署到需要工具调用与多步交互的真实任务中，可执行环境成为智能体后训练（post-training）的关键基础设施。但构建可执行任务不仅需要生成指令，还需配置可用工具、准备工作区资源与状态、建立与任务目标对齐的评估机制，逐任务人工构建难以规模化。
- **核心痛点**：技能（skill）封装了领域知识、操作流程与工具使用说明，甚至包含脚本、模板与参考资源，本可作为环境合成的起点；但**技能所包含的信息**与**一个具体、有挑战性且环境完整的可执行任务**之间仍存在巨大鸿沟。
- **已有工作的不足**：SkillSynth（技能图采样工作流路径）、Terminal-World（技能联合驱动指令与环境构建）、FACET（跨技能场景重建保证一致性）等虽已探索技能驱动的环境合成，但都未显式回答：*给定一个技能，如何依据智能体的能力需求来构造可执行任务及其环境？*
- **论文的整体含义**：提出 **Skill2Env**——一个以能力需求为导向的框架，把"智能体应被考验哪些能力"作为环境合成的组织原则，而非仅仅扩大技能/任务覆盖度；配合 **Iterative Task Hardening**（迭代式任务强化），使环境可随智能体能力提升而持续加难。最终产出 2,963 个可执行任务，并用其生成的高分轨迹做 SFT，验证监督信号可跨基准迁移。

## 2. 方法论

### 2.1 形式化基础（预备定义）

- 技能 κ：可复用的过程性指令包（含可选支撑资源）；执行基底 X 提供工具与运行时；工作区 W 为任务专属本地资源与组织方式。
- 环境与任务实例：**E = (X, κ, W₀)，T = (g, E, V)**，其中 g 为任务指令，V 为评估器。
- 交互过程：状态 s_t 含当前工作区 W_t 与运行时状态，智能体接收部分观测 o_t，依策略 π 产生动作 a_t ~ π(·|g, h_t)，环境转移 s_{t+1} ~ P_E(·|s_t, a_t)；执行 L 步得到 rollout τ，评估器给出 r = V(s_L) ∈ [0,1]。

### 2.2 技能筛选（Skill Curation）

- 从 ClawHub 下载 **47K+** 公共技能文件夹，按三条标准筛选：**Practical Utility**（明确实质性用途）、**Runtime Compatibility**（硬件/OS/权限/算力与 Linux 沙箱兼容）、**Setup Feasibility**（输入、依赖、数据、服务可被可行地供给）。
- 保留 **3K+** 技能文件夹进入环境合成。

### 2.3 从能力需求到难度模式

- 提炼 **5 类核心能力需求**：
  - **环境理解**（识别任务相关事实、目标与约束）
  - **规划**（识别操作依赖并随状态演化调整计划）
  - **技能使用**（按任务要求正确套用技能中的工具指令与流程）
  - **长程一致性**（多步执行中持续追踪状态、保持中间结果与环境一致）
  - **错误恢复**（利用执行反馈定位错误、调整操作并继续推进）
- 引入**难度模式（difficulty patterns）**：每个模式描述一类可复用的任务挑战及其构造方式。初始模式池 **P 含 100 个模式**，按五个能力维度各 20 个组织（附录 B：U01–U20、P01–P20、S01–S20、L01–L20、R01–R20），并给出"加固控制变量"（如来源数量、依赖深度、预算紧度、掩蔽深度等）。
- 应用时，合成智能体先识别技能支持的工作流，再选择**兼容子集 P_κ ⊆ P**（要求挑战能自然融入同一任务目标、技能支持所需操作）；不同模式组合让同一技能支撑不同能力需求的任务。

### 2.4 蓝图引导的环境构建

- 合成智能体先起草**任务蓝图 B**，作为"作者侧契约（author-side contract）"，规定：任务目标、挑战、支撑事实与推导、验收标准、执行需求、信息边界。
- **信息边界**明确区分：指令中给出的、求解器须在工作区中发现的、须推断的三类信息；解题所需事实对求解器可见，参考答案与推导保留在作者侧。
- 由 (κ, B) 合成出 **T = (g, (X, κ, W₀), V)**；工作区构建融合合成材料与检索到的真实材料；蓝图与环境构建**迭代进行**（先修蓝图、再更新受影响组件）。
- **评分量规评估**：验收标准转为一组 rubric 项 C，每项权重 w_c > 0 且 Σw_c = 1，得分 q_c ∈ [0,1]；可程序化检查的用确定性验证（通常二值），其余用 LLM judge 给连续部分分；**任务奖励 r = Σ_{c∈C} w_c · q_c(s_L)**。
- **一致性校验**：rollout 后由校验智能体比对任务条件与 rubric 结果和蓝图、执行证据；需改契约的问题通过蓝图+组件的协同更新解决，仅实现层问题按原蓝图修正；因任务条件不一致或评估器错误导致的证据**被排除出能力诊断**。

### 2.5 迭代式任务强化（Iterative Task Hardening）

- **执行驱动诊断**：第 j 轮，求解器执行 T⁽ʲ⁾ 得到轨迹 τ⁽ʲ⁾ 与 rubric 结果 q⁽ʲ⁾；以奖励作为**加固触发器**（阈值 0.7）——高于阈值的任务进入加固，其余保留。诊断智能体检查求解器如何处理已实例化的难度模式、是否通过捷径绕过挑战、残余失败点在哪里，得 D⁽ʲ⁾ = Diagnose(B⁽ʲ⁾, τ⁽ʲ⁾, q⁽ʲ⁾)。
- **模式池扩展**：若诊断揭示当前池中未表示的可泛化挑战，则抽象为新难度模式加入 P。
- **加固提案与任务修订**：H⁽ʲ⁾ = ProposeHardening(κ, B⁽ʲ⁾, D⁽ʲ⁾, P)（增强已有模式实例强度，或引入兼容的新模式）；B⁽ʲ⁺¹⁾ = ReviseBlueprint(B⁽ʲ⁾, H⁽ʲ⁾)；T⁽ʲ⁺¹⁾ = Construct(κ, B⁽ʲ⁺¹⁾)，协同更新指令、执行基底、工作区与评估器。
- 完整流水线产出 **2,963 个可执行任务**。
