ABSTRACT 

Frameworks that use large language models for scientific discovery typically rely on a fixed, human-designed algorithm that decides what the model sees at each step, leaving the model only the role of proposer. The model knows nothing of the search beyond what it is shown. As models grow more capable, a question arises: does a search strategy chosen by a human before the run scale better than promoting the model from proposer to planner and letting it own the search? The Bitter Lesson suggests that choosing the strategy in advance is the kind of hand-designed structure that general methods eventually outscale. We introduce AgentDiscover, in which a coding agent plans the search using its context as working memory, runs experiments, and records every attempt in a database of ideas, candidates, and their relations. This database serves as the agent’s long-term memory and is structured so that the selection rules of classical algorithms such as MAP-Elites and Monte Carlo tree search each reduce to a single query, which the agent is free to use, combine, or replace. A server maintains the database and steers the agent after every submission, keeping it on course over long runs. In our experiments, AgentDiscover is more cost-efficient than existing frameworks, reaching better scores at lower cost. On tasks in kernel engineering, biology, algorithm design, and mathematics, AgentDiscover outperforms prior discovery frameworks. Its programs would have placed first among human competitors in seven past AtCoder heuristic contests, and on eleven mathematical and systems optimization tasks it matches or exceeds every baseline that uses the same model. 1 Introduction 

Large language models (LLMs) are increasingly capable problem solvers, but their solutions must be verified. Returning each verdict to the model lets it improve its solutions, closing a loop of proposal and verification. When both the candidate solution and its evaluator are programs, this loop needs no human intervention: the model writes a program that either encodes a solution or searches for one, and an evaluator program runs it and scores the result. This recipe, typically run as an evolutionary search, has already produced genuine mathematical and scientific discoveries. For instance, FunSearch (Romera-Paredes et al., 2024) found new constructions in extremal combinatorics, and AlphaEvolve (Novikov et al., 2025) improved the best known results on roughly a fifth of more than fifty open mathematical problems. A growing family of open systems follows the same recipe (Sharma, 2025; Lange et al., 2026; Cemri et al., 2026; Liu et al., 2026a), and some go further by training the model on each problem at test time (Wang et al., 2025; Yuksekgonul et al., 2026). These systems share a common architecture with three roles. A search algorithm selects past candidates for the model’s context, a proposer , a language model, writes a new candidate from them, and an evaluator scores it; the result will then be recorded, typically in an archive of past candidates. In most implementations, the selection rule is designed by humans and fixed before the run: AlphaEvolve combines MAP-Elites (Mouret & Clune, 2015) with island models, ShinkaEvolve (Lange et al., 2026) extends a prescribed population loop with novelty filtering, and MCTS-AHD (Zheng et al., 2025) organizes candidates in a tree and selects among them with the upper confidence bound for trees (UCT) (Kocsis & Szepesvári, 2006). More recent systems adapt this rule during a run, but only within a space prescribed beforehand by their designers (Cemri et al., 2026; Liu et al., 2026a). In every case, the search is run by a human-designed algorithm and the LLM only proposes: it sees the candidates that the algorithm puts in its context, but has no say in which ones those are. Leaving the search to a fixed human-designed algorithm becomes harder to justify as LLMs improve. In The Bitter Lesson , Sutton observes that methods built on human knowledge are eventually overtaken by general methods that exploit growing computation (Sutton, 2019). Choosing the search strategy before the run is such a use of human knowledge; it bets that the designer understands the problem better than the language model will. The LLM, meanwhile, could run the search itself: classical algorithms such as MAP-Elites and UCT are well documented in the text it is trained on, and coding agents , which let an LLM write and run code with tools, can implement them when needed. Knowing the alternatives matters because no single search strategy is best across problems (Wolpert & Macready, 1997). In automated evolutionary discovery specifically, a budget-matched comparison of 30 fixed search strategies (“harnesses”) found none reliably better than a simple baseline across models and problems, and the full OpenEvolve recipe ranked last (Gupta et al., 2026). The best strategy can also change within a run (Cemri et al., 2026; Liu et al., 2026a); fixing one for the whole search leaves the model’s knowledge of the alternatives unused. This raises a natural question: can coding agents fill both roles, one planning the search and another proposing candidate solutions with minimal human-engineered search heuristics? 

Handing the search to a coding agent is not enough on its own. The agent must remember what it has tried long after those attempts have left its context, retrieve the relevant part of that history cheaply, stay on course over hours of work, and do all of this without being able to tamper with the evaluator that scores it. Without a structured memory, the agent must reconstruct the state of the search from raw logs before it can apply any strategy to it. Storing such a memory is cheap; reading it is not. Every attempt can be recorded, with its score, its lineage, and the ideas it builds on, at negligible cost next to the compute a run already spends, but an agent pays in context for every record it reads. Databases have long addressed this: a query states what is wanted, and indexes and a query planner find it, so the reader receives only the answer. This raises a second question: can the history of a search be kept so that the agent retrieves only what it needs, at the cost of a query? 

We answer these questions affirmatively by developing AgentDiscover, a novel framework for scientific discovery in which a coding agent both directs the evolutionary search and proposes its candidates, with every past attempt one query away in a graph database (Figure 2b, §3). A coding agent works on the problem inside a sandbox, and its context is its working memory: it runs experiments, writes candidates, and decides what to try next. Each agent session eventually ends and a fresh one takes over, for two reasons: a fresh agent is not conditioned on its predecessor’s reasoning; and beyond some length, re-reading an ever longer context at every step costs more than starting over. What a session learns outlives it in a long-term memory: a graph database of ideas and candidates. Because the graph makes each candidate’s ideas and lineage explicit, the selection rule of a classical algorithm becomes a single query: the best candidate per idea for MAP-Elites, or visit counts and values over the candidate lineage for Monte Carlo tree search. The agent can use these rules, combine them, or replace them. Because the search strategy is not fixed in advance, a stronger model improves not only the candidates but also the search that produces them, whereas under a fixed search algorithm it can improve only the candidates. 2 Related Work 

LLM-based evolutionary search. A first line of work couples an LLM with an evolutionary search loop for scientific and algorithmic discovery. FunSearch (Romera-Paredes et al., 2024) established the recipe, evolving programs inside a fixed island-based loop and discovering new constructions in extremal combinatorics. AlphaEvolve (Novikov et al., 2025) then shifted the landscape, improving the best known results on roughly a fifth of more than fifty open mathematical problems with a fixed archive and population policy combining MAP-Elites and island models. ShinkaEvolve keeps a prescribed population outer loop but adds novelty filtering and bandit-based model selection, while MCTS-AHD replaces population evolution with a fixed UCT-organized tree (Lange et al., 2026; Zheng et al., 2025). SimpleTES designs parallel trajectories, refinement, and history selection, and sets new best-known values with an open model (Ye et al., 2026). Fine-tuning variants keep the same loop: ThetaEvolve and TTT-Discover update the model parameters themselves at test time (Wang et al., 2025; Yuksekgonul et al., 2026). In all these systems the search algorithm is designed in advance and stays fixed; they differ mainly in which algorithm they fix. A few go a step further and adapt the algorithm at runtime: AdaEvolve adjusts within-island exploration, cross-island allocation, and stagnation-triggered guidance through a prescribed three-level controller (Cemri et al., 2026); Gupta et al. (2026) run several fixed harnesses side by side and shift the remaining compute to those whose early scores lead; and EvoX 3AgentDiscover: Autonomous Discovery with Minimal Search Scaffolding evolves an explicit parent-selection, inspiration, and variation policy, but only when a fixed progress monitor triggers replacement (Liu et al., 2026a). Even here, adaptation remains confined to a predefined space. 

Coding agents as proposers. A few systems instead hand the search to a coding agent. AlgoEvo lets an agent decide when to inspect, diagnose, edit, or evaluate code, but a fixed upper-confidence rule still chooses which earlier design guides each step (Qiu et al., 2026). Vesper gives repository-level coding agents direct database access, but its fixed island-model policy samples the parent and seeds the worktree before the agent is invoked (Ishibashi et al., 2026). Meta-Harness removes the selection rule entirely: a coding agent reads every earlier harness with its scores and traces and decides what to change next, though its object is the harness around a model rather than the solution to a discovery task (Lee et al., 2026). CORAL is the closest work to ours: its long-running agents control retrieval and search direction across shared persistent state (Qu et al., 2026). AgentDiscover differs mainly in how it manages context, which lowers its cost. First, AgentDiscover periodically resets the agent’s context, which avoids paying for an ever longer history and helps the agent find new ideas. Second, where CORAL shares attempts, notes, and skills as file-system artifacts, AgentDiscover keeps its long-term memory in a graph database of ideas and candidate lineage: a fresh agent re-explores the search cheaply through queries, and the selection rule of a classical algorithm is a single query. Third, AgentDiscover lets the agent write its own tools and run experiments before it submits a candidate, and an optional meta agent turns past sessions into skills for later ones. Finally, CORAL interrupts and restarts the session on a heartbeat, whereas AgentDiscover’s server steers the running session with a message after every submission. 

Adapting prompts, scaffolds, and memories. A third group adapts artifacts other than the candidate program. With frozen weights, GEPA adapts prompts, BES searches over reasoning trajectories at inference time, SICA recursively edits its coding-agent scaffold, and SkillOpt applies bounded updates to skill documents (Agrawal et al., 2025; Xu et al., 2026; Robeyns et al., 2025; Yang et al., 2026). Others persist semantic search state: SeaEvo clusters and retrieves strategy descriptions and PACEvolve decouples idea generation from code evaluation (Luo et al., 2026; Yan et al., 2026). 

Autonomous research agents. A fast-growing line of work gives LLM agents autonomy over research itself. The AI Scientist automates the cycle from idea to paper (Lu et al., 2024; Yamada et al., 2025); the AI co-scientist and the Virtual Lab organize agents as a research group (Gottweis et al., 2026; Swanson et al., 2025); and long-running systems combine literature search and data analysis to reach new findings (Ghareeb et al., 2026; Mitchener et al., 2025). Agents are also changing how research is shared: Paper2Agent turns papers into agents (Miao et al., 2025), AgentRxiv lets agents build on each other’s reports (Schmidgall & Moor, 2025), and concurrent projects run coding agents autonomously on optimization targets (Karpathy, 2026; Chen et al., 2026). These systems target open-ended research judged by humans or experiments. AlphaEvolve-style methods instead perform verifier-driven program evolution, but the LLM only proposes candidates inside a fixed, human-designed search loop. AgentDiscover combines the two: an autonomous agent that owns the search, scored by a verifier. 

3 Methodology 

3.1 Problem Formulation and Motivation 

LLM-driven scientific discovery casts a research problem as a search over programs. The problem is stated in natural language, and each candidate is a program x: a representation the LLM can read and revise, and a machine can execute and score. A fixed evaluator E scores each candidate with a scalar fitness E(x), oriented so that higher is better, and reports any auxiliary metrics the problem defines. The goal is a candidate of high fitness within a budget of evaluations, found by an LLM that revises candidates iteratively in light of what has already been tried. Existing systems (e.g., Romera-Paredes et al., 2024; Novikov et al., 2025; Lange et al., 2026; Ye et al., 2024) fix this iteration before the run: an evolutionary algorithm decides which past candidates the LLM sees, and the LLM only proposes the next one. This design is ironic: these systems aim to surpass human design, yet their search procedure is human-designed, and the LLM, the one component meant to outdo human design, has no say in it. Committing the whole run to one such procedure is hard to justify when no single strategy is best across problems (§1). We therefore replace the LLM proposer with a coding agent. The agent queries past attempts to build its own context, runs its own experiments, and records what it tries in a memory that outlives its context. Which candidates to revisit, which directions to abandon, and which strategy to follow become decisions the agent makes, and revises, during the run; in the terms of metacognition, it takes over the monitoring and control of its own search (Flavell, 1979). 3.2 The AgentDiscover Framework 

AgentDiscover has three components. The search agent is a coding agent that studies previous attempts, plans, runs experiments, and proposes new candidates. The long-term memory is a graph database that keeps every idea and candidate tried so far. The optional meta agent is another coding agent that reflects on the search agents’ reasoning logs and writes what it learns as skills for them. We designed these components with two properties in mind, and show below how they achieve them. First, flexibility : no search strategy is hard-coded, and the agent decides what to read, what to try, and when to change course. Second, efficiency over long horizons : a search runs for hours, so the agent must stay on course, retain what it learns beyond its context, and keep its token cost under control. 

Search agent: The search agent is a coding-agent CLI, such as Claude Code, sandboxed in a version-controlled worktree. It starts from an instruction file that describes the task, summarizes the database, and explains how to access it through a Model Context Protocol (MCP) server; the worktree also holds tools and skills folders, both empty in the first session. At each step, the agent chooses whether to query the database, plan, write or run tools, or submit a candidate, and it reflects on each evaluation and plans further. When the agent finds that it has stalled, or that carrying its context costs more than starting afresh, it records a lesson in the database, including experiments that never became candidates, and terminates, ending the session . A new session then starts a fresh search agent that inherits the long-term memory, tools, and skills. Figure 3 walks through a session on a toy task. 

Long-term memory: The long-term memory is a graph database of all ideas, candidates, sessions, and lessons, and the relations among them. It sits on the MCP server alongside the evaluator: the agent reads it with any query but writes only through MCP tools that validate their input arguments, keeping the database consistent. The server scores each submitted candidate and sends the agent a steering message that reports the fitness and the number of candidates left, keeping the agent on course over the long horizon. The graph also makes classical strategies native: MAP-Elites, which keeps the best candidate per niche, is one query returning the best candidate for each idea. 

Meta agent: The meta agent is another coding-agent CLI, but with a different task and a different view of the database. It runs after each search-agent session and focuses on how the search was done rather than on what it found. It reads the session transcripts, including the search agents’ reasoning traces, and relates them to the outcomes recorded in the long-term memory to find which ways of reasoning paid off and which did not. It then consolidates its conclusions into skill files that later sessions draw on. 5AgentDiscover: Autonomous Discovery with Minimal Search Scaffolding The agent accumulates a long context, which causes three problems. (i) Each LLM call re-reads the full context, so past some length a new session is cheaper than continuing, even with the reduced cost of cached tokens. (ii) The agent also becomes anchored to its earlier reasoning, which makes it harder to change ideas and more likely to get stuck in a local optimum. (iii) It is more likely to lose track of the task. Fresh agents and the database together address the first two problems. The new agent explores the database from scratch and can form a new perspective on the search; we expect this to produce new ideas more reliably than prompting the old agent to try something else while its context stays the same. Restarting is cheap because retrieval is a query. Without the database, the agent would read past attempts from files: the Meta-Harness (Lee et al., 2026), for example, reads a median of 82 files per iteration, each read costing an LLM call and consuming context the agent cannot get back. For the third problem, the server answers every submission with a steering message that tells the agent where the search stands and keeps it on course. 

4 Experiments

Anthropic kernel builder. Finally, we test how solution quality improves with model spend on Anthropic’s Original Performance Take-Home (Anthropic, 2026) (Table 4). Meta-agent guidance. To isolate the effect of the meta agent, we run transaction scheduling five times without a meta agent. We then fork each run three times, after its first, second, and third iteration. A fork copies the run’s database and workspace at that point, adds a single meta pass, and continues for two more iterations with no further guidance; the original run continues from the same point without guidance. A fork and its original therefore start from the same state, and the only difference between them is whether the next search agent has read the meta agent’s guidance. This removes most of the run-to-run randomness from the comparison. Across the 15 forks, guidance helps the new agent make progress sooner: it beats the best fitness found before the fork within its first two candidates in 73% of the forks, against 33% without guidance, and within ten candidates in 87% against 53% (Figure 5c). Guidance also raises the quality of what the agent proposes, not only of its best candidate: across all candidates proposed in the two iterations after the fork, the median fitness rises from 0.801 to 0.832 (Figure 5d). At the end of these two iterations, the guided run has the higher best fitness in 10 of the 15 forks, the same in 2, and a lower one in 3. We use Claude Haiku 4.5 as the search agent and Claude Opus 4.6 as the meta agent, with ten candidates per iteration and five iterations per run. 

5 Conclusion 

We asked whether a search strategy chosen by a human before the run scales better than promoting the model from proposer to planner and letting it own the search. Our results favor the agent. The agent reached better scores at lower cost than the frameworks we compared against, would have placed first among human competitors in seven past AtCoder contests, and improved the best published bound on the first autocorrelation inequality. The improvement over fixed search algorithms comes, in our view, from the agent seeing the whole search rather than the few candidates a fixed algorithm would hand it, and from reasoning and experimenting over many steps rather than proposing each candidate in one shot. The improvement over CORAL, where an agent also runs the search, comes from managing context more efficiently over the long horizon. We showed that resetting the agent’s context kept the cost of each call low and made it more likely to escape a stall, and that a meta agent helped further. A graph database let each fresh agent re-explore the search cheaply, while the agent wrote its own tools and ran experiments before submitting. Together, these made AgentDiscover more cost-efficient than CORAL and other frameworks we compared against (see Appendix E for more tasks and figures). Along the way, we found that several evaluators inherited from prior work admit reward hacking, and corrected them (Appendix C). 

Limitations. Each entry in our main tables is a single run, so we report no variance; small margins between methods should be read cautiously. Additionally, we ran AgentDiscover with Claude models and, on some tasks, GPT-6 Sol; the framework supports other coding agents, but we have not varied the backbone model on a fixed task. Finally, we have not analyzed which search strategies the agents actually use: whether they rediscover classical rules such as MAP-Elites and UCT from the provided queries, or synthesize new ones. 9AgentDiscover: Autonomous Discovery with Minimal Search Scaffolding

A Implementation Details 

This appendix adds implementation details to the components of §3.2. Prompt templates and tool descriptions are in Appendix B, and the settings of our experiments in Appendix D. 

A.1 Architecture and Run Lifecycle Processes and setup. The trusted side is the orchestrator, a Neo4j database whose data persists between runs, and the MCP server, a host process. Only this trusted code holds the database password, and the database and the server listen on loopback only. Containers are started through one sandbox module that supports Docker, Podman, Apptainer/Singularity, and Enroot. Before any agent starts, the orchestrator starts the database and the MCP server and builds the evaluation environment. Each branch takes its starting iteration from the database, so a new invocation continues a branch where it stopped. A new branch’s worktree (its workspace in §3.2) is a fresh git repository, not connected to the main repository’s history, holding a copy of the problem’s solution.py and empty tools/ and skills/ folders. 

Iterations. Each branch runs its sessions in sequence in its own loop, in parallel with the other branches; iterations are grouped into blocks, and all branches wait at a barrier at the end of a block before the meta pass. To open a session, the orchestrator renders the instruction file from a template with the branch’s current guidance last, builds a short briefing from fixed queries (Appendix B), and creates the Session node. The coding-agent CLI then runs non-interactively (claude -p or codex exec ) in the branch’s container. The session ends when the CLI exits or its wall clock expires; a crash or timeout is recorded and the run continues. On close, the orchestrator stores the reasoning text from the transcript on the Session node, writes the exposure edges (§A.2), and commits the worktree. 

State across sessions. A branch keeps its worktree (with solution.py as the last session left it, tools/ , and 

skills/ ), the worktree’s git history, its guidance, the tools the meta agent wrote for it, and the shared graph. Each session is a new CLI process with a re-rendered instruction file. One exception: a session cut off because the model provider’s usage window ran out is resumed with its transcript once the window resets.

A.3 Meta Pass 

The optional meta pass runs at the barrier between blocks; a single meta agent serves all branches, and if the pass fails, the next block keeps the guidance already in place. Its container mounts each branch’s transcripts read-only and gets neither the evaluator, the database password, any solution.py , nor any git history. Besides the skill files of §3.2, it writes through three tools of its own: write_meta_lesson stores its judgment of one session on that Session node; 

add_tool stores a read-only saved query for one branch, which the branch’s later sessions are offered as an MCP tool; and write_strategy stores a branch’s new strategy as a Guidance node that supersedes the previous one and is rendered into the branch’s next instruction file. 

A.4 Execution Safeguards 

• Evaluator isolation. The evaluator is never mounted into an agent’s container, and a worktree’s git history cannot contain it. The server reads solution.py from the agent’s worktree itself and evaluates a copy in a separate container, under limits set per problem and without network access (except on the Enroot and none 

backends, which cannot disable it). Hidden evaluation data is fetched before any candidate exists, into a cache no agent can see. • Agent containers. A search agent’s container holds its own worktree and the problem’s public files, and never the database password. The CLI’s web tools are removed by default, and the prompt forbids looking up results online (Appendix B); the container keeps the network access the CLI needs to reach its model API. • Read-only queries, typed writes. read_graph runs in a Neo4j read transaction, so the database itself rejects any write; all writes go through the fixed tools. • Attribution. The server attributes every call to a session itself, never trusting what an agent says about itself, and offers each caller only its own tools. 15 AgentDiscover: Autonomous Discovery with Minimal Search Scaffolding

C Evaluator Failure Modes and Corrections 

The evaluation sandbox (Appendix A.4) keeps the evaluator and its private files outside the agent’s workspace. The submitted program must nevertheless run somewhere, and the evaluator must determine whether its output is a valid 18 AgentDiscover: Autonomous Discovery with Minimal Search Scaffolding solution. While porting the benchmark evaluators, we repeatedly encountered the following failure modes. We report these recurring patterns rather than attempt an exhaustive audit of every evaluator or upstream version. 

Incomplete output validation. Affected tasks: Signal Processing, LLM-SQL. An evaluator may compute a favorable score for an output that does not satisfy the constraints of the stated task if it checks only that the output can be parsed. On Signal Processing, the required output length was never enforced: a candidate that returned only two samples, with no slope reversals and near-perfect correlation, scored 0.9259 on the evaluator, although it is not a solution to the task at all. Even with the length enforced, the metric rewards smoothness and penalizes the hidden clean signal for its own oscillations, so an oversmoothed output can score above the exact ground truth, which scores 0.727 . We leave the metric itself unchanged, so that our scores stay comparable with the evaluator used in prior work. On LLM-SQL, the returned table was never checked to be a rearrangement of the input rows: a candidate that discarded the input and returned one long constant row n times made every row after the first a full prefix-cache hit and scored 0.994 , against 

0.737 for the best honest reordering we found. We therefore check the output’s shape, contents, completeness, and resource constraints against authoritative task data before scoring it. 

Candidate-controlled scoring. Affected tasks: Signal Processing, 3rd-Autocorr., PRISM, and LLM-SQL result loading. If candidate code runs in the process that computes the score, it can rebind the metric functions, inspect scorer state, or simply print a result in the evaluator’s name. On Signal Processing, a candidate that replaced pearsonr with a function returning 10 9 was scored 2 × 10 8, and one that printed {"score": 1e9} and exited had that value reported at face value. Loading a candidate-controlled serialized object into the scoring process creates the same boundary failure: on LLM-SQL the returned DataFrame was exchanged via pickle , whose deserialization executes code the candidate chooses. We run candidate code separately, exchange only the proposed solution, restrict deserialization to the expected data types, and compute the score in a process the candidate did not enter. 

Information leakage across the boundary. Affected task: EPLB. EPLB scores a placement on the next recorded workload, so the workload data must stay hidden: a candidate that sees the future no longer has to predict it. The agent nevertheless found two ways to obtain it. First, although the agent’s own sandbox blocks the data, the candidate program it submits ran where the file was readable, and candidates that read it raised the balance score from 0.25 to 

0.44 ; a keyword blocklist did not stop this, since a file path can be built indirectly. Second, whatever a candidate prints was returned to the agent as feedback, and the same workloads are replayed in the same order on every evaluation. Candidates printed their inputs, and later candidates hardcoded the answers, lifting the score from a best honest 0.153 

to 0.201 in our strongest run. Candidate processes therefore receive only public task inputs (the private data is replaced by an empty directory), and their stdout and exception messages are withheld from search feedback.
