## 摘要
编程智能体如今能够为开发者修改代码，而开发者则负责描述目标、提供上下文，并对智能体的工作作出回应。然而，提示词、屏幕活动与任务成功各自都只能反映这一图景的一部分。我们提出“说、做、理解”（Say, Do, Understand），一套端到端工作流，用于分析开发者向智能体写下什么、在其工作期间做了什么，以及事后能够解释什么。该工作流包含五个阶段（采集、准备、分析、整合与解释）和三种工具：一份提示词编码手册、一套对屏幕录制活动与事件进行编码的方案，以及分别用于解释过程与解决方案的评分量表。我们将该工作流应用于一项观察性研究，十名经验丰富的开发者在一个不熟悉的代码库上使用 GitHub Copilot。将任务表现与理解程度交叉分析，得到四种人物画像。两项测量在八名开发者身上一致，但在两名开发者身上出现分离：一人通过了多数测试却无法解释解决方案，另一人仅通过少数测试却能很好地解释。在这一样本中，最常要求智能体检查其工作的人物画像，自行测试所花的时间最少。这些模式仅为描述性的，不能推广到样本之外。我们建议计算教育工作者、行业从业者和研究人员采用并调整该工作流，以评估软件工程中的人—AI 沟通。

## Abstract
Coding agents can now change code for developers, who describe goals, supply context, and respond to the agent's work. Yet prompts, screen activity, and task success each tell only part of this story. We present Say, Do, Understand, an end-to-end workflow for analyzing what developers write to an agent, what they do while it works, and what they can explain afterwards. The workflow has five stages (Capture, Prepare, Analyze, Integrate, and Interpret) and three instruments: a prompt codebook, a scheme for coding screen-recorded activities and events, and separate rubrics for explaining the process and the solution. We applied it in an observational study of ten experienced developers who used GitHub Copilot on an unfamiliar codebase. Crossing task performance with understanding produced four personas. The two measures agreed for eight developers but split for two: one passed most tests but could not explain the solution, and another passed few tests but explained it well. In this sample, the personas that most often asked the agent to check its work spent the least time testing on their own. These patterns are descriptive and do not generalize beyond the sample. We recommend the workflow to computing educators, industry practitioners, and researchers to adapt and evaluate human--AI communication in software engineering.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：编码智能体（如 SWE-agent、OpenHands、GitHub Copilot）已能自主检查文件、规划改动、编辑多组件、执行命令与运行测试；开发者的角色转变为"决定问什么、提供什么证据、如何回应结果"。
- **核心问题**：提示词（prompts）、屏幕活动（screen activity）、任务成功（task success）各自只能解释人—AI 协作的一部分，**缺少一种把三者连接起来、同时又保留各自证据边界的实用方法**。
  - 提示分析说明"要求了什么"，但不能证明要求被落实；
  - 行为分析说明"可见地做了什么"，但不能说明目的或是否理解；
  - 任务评估说明"实现达成了什么"，但不能说明开发者能否解释该改动——而这直接影响后续调试、维护、评审与修改。
- **关键概念区分**：把"要求智能体去验证"（Say）、"开发者自己运行测试"（Do）、"事后解释方案"（Understand）视为三种不同证据，不可互相替代；单纯"看代码的时长"只是活动，不能推断理解。
- **研究问题**：
  - RQ1：如何把提示、行为与理解整合为端到端分析工作流？
  - RQ2：应用该工作流能揭示经验开发者与编码智能体沟通的哪些模式？
- **整体含义**：面向计算教育者、行业从业者与研究者，提供可改编、可检验的人机沟通分析框架；本文的应用只支持**描述性、参与者级**模式，而非时间顺序或因果结论。

## 2. 方法论：Say, Do, Understand 工作流

### 2.1 核心思想
- 三条证据流并行分析、在参与者层面整合，但**始终保留每条流的独立含义**：
  - **Say**：开发者写给 AI 的内容，单元为一条提交的提示词；
  - **Do**：交互期间的可见活动，单元为**持续活动状态**与**离散事件**；
  - **Understand**：事后解释，单元为按评分表打分的回答，并区分**过程理解**与**方案理解**。
- 五个阶段：**Capture → Prepare → Analyze → Integrate → Interpret**；每个阶段产出可复用的中间产物（证据语料 → 清洗数据集 → 编码结果 → 参与者画像 → 模式与边界报告）。

### 2.2 关键工具与细节

**（a）Say：提示词编码手册**
- 四步人机协同流程（改编自 Choudhuri 等）：发现候选码 → 调和 → 系统编码 → 精炼。
- 清洗后保留 **380 条提示词**（去除重复、系统通知、3 条离题提示）。
- 三个模型（Claude Opus-5、GPT-6-Astra、Gemini-3.6-Flash）各自独立提出主题，研究者合并为统一编码手册后，各模型再独立编码全部提示词（各自随机顺序），**先给理由再赋码**，数据质量问题单独标记而非强行归类。
- 最终编码手册共 **37 个码 + 2 个子码**：4 个面（facet）——**Referent（指向什么，12）、Context Supplied（提供什么上下文，10）、Constraint（如何限定，7）、Strategy（如何驱动智能体，8）**。
- 另有**验证请求的序数编码**（读提示 + 前一条智能体回复判断）：**V0 无验证请求 / V1 无依据请求 / V2 有依据请求**（有具体问题、症状、怀疑或风险）。
- 赋码规则：**至少两个模型一致**才算该码成立；用理由审查争议边界。信度用 Krippendorff's α，对 α 最低的 7 个码审查了 **179 个争议的"提示—码"对**并精炼定义，重编码后所有码达到 **α ≥ 0.80**，平均 **α = 0.903**（范围 0.81–1.00），V0–V2 的 **α = 0.867**。

**（b）Do：活动状态与事件编码**
- 改编 Shihab 等的编码方案；两名研究者独立编码子集、讨论分歧并加入涌现码；定稿后两人独立编码 **20%** 录像，达 **α = 0.80**，其余均分。
- **14 个互斥活动状态**（占会话时间百分比，覆盖全部时间）：查看任务材料、查看源码、查看网页、查看运行中的应用、查看开发者工具、撰写提示、阅读 Copilot 回复、监控智能体执行、审查智能体产出、手工写代码、命令行测试、与实验者交流、配置智能体、空闲。
- **9 个离散事件**（计数）：批准/拒绝智能体动作、拒绝 diff、撤销智能体步骤、切换 Copilot 模式、开启新会话、停止生成、调用自定义技能、查看 token 用量。
- **禁止混合**：事件计数不与时间百分比相加；监控执行与审查产出分开；代码查看只作时间占用度量（录像无法揭示目的）。

**（c）Understand：过程与方案两套评分表**
- **Q1 过程理解（0–3）**：0 无可恢复过程；1 只列动作；2 有连接但不完整；3 完整连贯（方法、进展、决策理由、终点）。
- **Q2 方案理解（0–4）**：0 无解释；1 核心机制错误；2 有重要错误/漏核心机制/只讲边角；3 核心机制正确但范围或细节有限；4 多机制具体正确且覆盖大部分改动。
- 评分时同时给出任务、参与者**自己提交的代码**；Q2 对照其真实实现而非理想解。
- 三模型独立评分并给理由，序数 α 低于 0.80 则研究者审查争议答案并精炼评分表、重评；最终 **Q1 α = 0.88、Q2 α = 0.81**，每条最终等级取**三取二**多数票。

**（d）Integrate 与 Interpret**
- 参与者画像保留：提示词比例、时间百分比、事件计数、理解得分、测试结果，不做单一总分归并。
- 两次中位数分割：表现 **HP = 通过 > 66/136**；理解 **HU = ≥ 10/14**（中位数 9.5），**平局归低组**，每边各 5 人；交叉得四象限（人物画像）。
- 可选透镜 **Specify / Delegate / Verify** 仅在 Integrate 阶段使用（S = 提示指向与上下文；D = 指令、约束、会话管理事件、请求智能体验证；VF = 命令行测试、查看应用、开发者工具、审查智能体产出）；三流五阶段不依赖该透镜。
- 三条分析原则：① 请求智能体验证 ≠ 开发者自查；② 各类检查活动分别报告、不求和；③ 目的不明的活动只报时间占用。
