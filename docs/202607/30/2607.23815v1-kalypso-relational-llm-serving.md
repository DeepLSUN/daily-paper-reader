## 摘要
大型语言模型越来越多地被用作语义运算符，用于过滤、提取、排序、连接和转换非结构化数据。现有的语义查询处理系统调用的是以请求为中心的LLM服务系统，这些系统不了解查询计划，从而留下了大量未利用的性能机会。本文介绍了关系型LLM服务，这是一种抽象，使LLM服务能够感知语义查询结构，同时保持查询语义和输出准确性。关键机会在于跨语义运算符的流水线执行：当中间元组直接从一个运算符流向下一个时，它们的KV缓存状态可以被重用而不是重新计算。我们提出了Kalypso，一个关系型LLM服务系统，它提供了语义查询计划的API，并使用自适应、内存感知的调度算法来执行它们。Kalypso解决了一个新的在线调度问题，其中流水线操作符执行与GPU内存压力管理相结合，在驱逐之前重用服务引擎中的KV缓存状态。其调度器持续调整内存分配，以平衡上游并行性、下游进度和GPU利用率。我们的评估表明，与使用以请求为中心的LLM服务的基线相比，Kalypso提高了查询完成时间，在各种工作负载下加速比高达4.57倍，表明查询感知的LLM服务可以显著提高语义查询执行的效率。

## Abstract
Large language models are increasingly used as semantic operators for filtering, extracting, ranking, joining, and transforming unstructured data. Existing semantic query processing systems invoke request-centric LLM serving systems that are unaware of the query plan, leaving substantial performance opportunities unused. This paper introduces relational LLM serving, an abstraction that makes LLM serving aware of semantic query structure while preserving query semantics and output accuracy. The key opportunity is pipelined execution across semantic operators: when intermediate tuples flow directly from one operator to the next, their KV-cache state can be reused instead of recomputed.   We present Kalypso, a relational LLM serving system that exposes an API for semantic query plans and executes them using an adaptive, memory-aware scheduling algorithm. Kalypso addresses a new online scheduling problem in which pipelined operator execution is coupled with GPU memory pressure management to reuse KV-cache state in the serving engine before eviction. Its scheduler continuously adjusts memory allocations to balance upstream parallelism, downstream progress, and GPU utilization. Our evaluation shows that Kalypso improves query completion time over baselines using request-centric LLM serving, with speedups up to 4.57x across diverse workloads, demonstrating that query-aware LLM serving can substantially improve the efficiency of semantic query execution.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：大语言模型（LLM）被越来越多地用作语义算子（如过滤、提取、排序、连接、转换），处理表格中的非结构化文本。现有的语义查询处理系统（SQPS）将每个LLM调用视为独立请求，由以请求为中心的LLM服务系统（如vLLM、SGLang）处理，这些系统对上层查询计划一无所知。
- **核心问题**：这种“请求中心”的服务模式忽略了查询计划中运算符之间的依赖关系，导致严重的性能浪费：
  - 当多个运算符顺序作用于同一元组时，其提示词（prompt）通常共享前缀（如系统指令和元组内容），但现有系统在运算符之间会完全物化中间结果，导致KV缓存无法跨算子重用，不得不重新计算前缀，尤其在GPU内存压力下缓存被提前驱逐时。
  - 例如，一个简单的filter→map查询，在大表场景下第二个算子因前缀被驱逐而需要重新prefill，端到端时间急剧增加。
- **整体含义**：论文提出**关系型LLM服务（Relational LLM Serving）** 的新范式，让LLM服务层感知查询计划，利用跨算子的流水线执行和KV缓存重用，在保持查询语义和输出准确性的前提下大幅提升效率。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- **关系型LLM服务**：在SQPS和底层LLM引擎之间增加一个“关系型服务层”。SQPS提交查询计划（而非独立LLM请求），由该层决定元组何时进入哪个算子、如何启动请求、如何分配KV缓存内存。这一调度是执行优化，不改变查询语义和输出准确性。
- **关键机会**：**流水线执行**——当上游算子处理完一个元组后，立即调度下游算子处理该元组，此时上游算子的KV缓存前缀（共享部分）可直接被下游复用，无需重新prefill。

### 关键技术细节

#### a. Kalypso架构（图3）
- 组件：查询解析器、调度器、KV缓存管理器、内存估计器、死锁监视器、算子执行器（Executor）。
- 用户通过API定义查询计划（由语义算子组成），Kalypso负责执行。

#### b. API设计
- 每个语义算子实现为UDF，必须声明执行契约：是否可流水线（pipelining）、是否为谓词算子（predicate）是否修剪输入、是否产生笛卡尔积（CP）。
- 算子通过Executor包装的LLM调用执行，Kalypso跟踪请求上下文和完成状态。
- 支持级联（proxy+oracle）、向量索引等优化，通过UDF封装。

#### c. 调度算法（算法1）
- 查询计划被解析为**阶段（stage）**：流水线内运算符序列（被阻塞算子和笛卡尔积分隔）。一个阶段处理一个元组构成一个**任务（task）**。
- 调度器执行**内存感知的调度**：
  - 每个阶段有动态内存预算，任务启动前需检查预算是否充足。
  - 任务完成后，若未过滤且非最后阶段，则执行笛卡尔积创建子任务加入下一阶段等待队列。
  - 内存管理器跟踪父-子任务依赖，仅在所有子任务完成后释放父任务内存。
- **自适应预算重平衡（Rebalance）**：
  - 检测阶段状态：若等待队列小于低阈值→饥饿（starving），需增加上游预算；若大于高阈值→饱和（saturated），需将预算转移给下游（最后阶段）。
  - 触发条件：完成任何任务后，检查每个阶段队列大小，动态转移内存，避免固定分配导致的资源浪费（如BioDEX和ContractNLI实验所示）。

#### d. 内存管理
- **令牌预算估计**：对每个算子，在线监控输出令牌与输入令牌的比例，取99百分位作为预算；若实际超出则中断并重试（增大预算）。
- **显式钉住 vs. 虚拟钉住**：
  - 显式钉住：要求LLM引擎支持，防止需重用的前缀被驱逐。
  - 虚拟钉住：仅通过调度控制并发，依赖LRU策略的隐含保护。
- **死锁检测与恢复**：周期性检查LLM引擎状态，若存在等待请求但无运行请求，则解除所有钉住，临时切换到虚拟钉住。

1. Kalypso在所有四个工作负载上均优于请求中心的基线，端到端延迟降低1.29×~4.57×（最大加速在ContractNLI）。
