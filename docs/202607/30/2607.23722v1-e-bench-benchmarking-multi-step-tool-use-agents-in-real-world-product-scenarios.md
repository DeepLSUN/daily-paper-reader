## 摘要
大型语言模型（LLM）正越来越多地被部署为与有状态环境进行多步交互的智能体：收集隐藏信息、组合工具调用以及提交状态变更。我们将这种能力称为多步工具使用。现有基准测试推动了工具使用智能体的评估，但往往关注孤立的API调用、短轨迹或难以扩展或控制的设置。我们引入了E-Bench，这是一个完全合成的基准测试，包含三个产品领域（王者荣耀、QQ音乐和腾讯会议）的323个状态变更任务。E-Bench将环境合成与任务合成解耦：图引导的数据库填充构建可重用、无孤立数据的产品环境，而生成器-求解器不对称性创建同时具有信息差距和工具差距的任务，要求智能体在更改状态之前发现隐藏数据并组合多个工具调用。结果通过数据库状态差异进行确定性评分。由于环境和任务都是合成的，E-Bench在环境级别可控，在任务级别可扩展。对11个前沿LLM的基准测试表明，多步工具使用仍然具有挑战性：最强模型的Pass^3低于60%，即使在E-Bench-Code扩展中使用代码执行，可靠性（Pass^3）仍低于70%。

## Abstract
Large Language Models (LLMs) are increasingly deployed as agents that interact with stateful environments over multiple steps: gathering hidden information, composing tool calls, and committing state changes. We refer to this capability as multi-step tool use. Existing benchmarks have advanced tool-use agent evaluation, but often focus on isolated API calls, short trajectories, or settings that are difficult to scale or control. We introduce E-Bench, a fully synthetic benchmark with 323 state-changing tasks across three product domains: Honor of Kings, QQ Music, and Tencent Meeting. E-Bench decouples environment synthesis from task synthesis: graph-guided database filling builds reusable, orphan-free product environments, while generator-solver asymmetry creates tasks with both an information gap and a tool gap, requiring agents to discover hidden data and compose multiple tool calls before changing state. Outcomes are graded deterministically by database-state diffs. Since both environments and tasks are synthetic, E-Bench is controllable at the environment level and scalable at the task level. Benchmarking 11 cutting-edge LLMs shows that multi-step tool use remains challenging: Pass^3 stays below 60% for the strongest models, and even with code execution in the E-Bench-Code extension, reliability (Pass^3) remains below 70%.

## 1. 论文的核心问题与整体含义

- **研究动机**：大型语言模型（LLM）越来越多地作为智能体部署，需要与环境进行多步交互（收集隐藏信息、组合工具调用、提交状态变更），即多步工具使用能力。现有基准测试（如Gorilla、ToolLLM、BFCL）多聚焦于孤立的API调用、短轨迹或静态环境，缺乏对部分可观测性、异构工具、长程依赖和精确状态变更等智能体能力的系统评估。基于真实系统的基准（如WebArena、SWE-bench）难以扩展、成本高、易受数据安全和隐私约束，且易受模型预暴露影响。
- **核心问题**：如何构建一个**可控、可扩展、确定性评分**的基准，来评估LLM智能体在多步工具使用场景下的真实能力？
- **整体含义**：E-Bench通过**全合成**的数据库驱动环境，模拟真实产品（王者荣耀、QQ音乐、腾讯会议）中的状态变更任务，旨在填补现有评估的空缺，揭示当前模型在信息获取、多步协调和可靠执行方面的严重不足。

## 2. 论文提出的方法论

### 核心思想
- **环境合成与任务合成解耦**：先为每个领域构建一个可复用的、完整的模拟产品数据库（而非为每个任务创建快照），然后在此共享环境上合成大量状态变更任务。
- **生成器-求解器不对称**：任务生成器（强LLM，如Claude Opus 4.7）可访问完整数据库和特权工具（`query_sql`、`exec_code`），而求解器（待评估模型）只能通过受限的领域特定MCP工具与环境交互。这人为引入了**信息鸿沟**（隐藏的全局状态）和**工具鸿沟**（无SQL/代码执行），迫使智能体必须主动探索、推理并组合工具调用才能完成任务。

### 关键技术细节
1. **环境构建——图引导数据库填充**：
   - 根据关系模式构建表依赖图（外键约束）。
   - 以拓扑顺序填充表：先根表（如艺术家、部门），再依赖表（如歌曲、会议）。
   - 约束知情合成：LLM在填充表时接收模式、已有记录、域上下文，通过插入工具插入数据，确保主键唯一性和外键有效性。后续进行确定性验证和修复（时间顺序、聚合计数、状态字段等）。
   - 结果：可复用、无孤立记录的数据库（76K+行，41个表，69个外键关系）。

2. **任务合成——产品导向循环**：
   - 生成器执行循环：查看数据 → 决定目标 → 修改状态 → 总结意图。记录数据库状态差异（diff）作为真值。
   - 通过意图重写确保用户查询中不泄露数据库衍生值（如“添加收藏中未下载的歌曲”而非指定歌曲ID）。
   - 六种能力类型自动标注：全数据获取、多条件过滤、聚合与计算、跨步依赖、精确边界判断、跨实体级联。
   - 三重验证器（GPT-5.5, Opus 4.7, GLM-5.1）确认状态变更的正确性，过滤弱基线可解的任务，最终保留323个任务。

3. **评分机制**：确定性数据库状态差异比较，无需LLM评判器，避免了主观性。

4. **E-Bench-Code扩展**：部分关闭工具鸿沟，授予求解器`exec_code`工具（可内调领域MCP函数），其余条件不变，通过对比量化代码执行带来的提升。

## 3. 实验设计

### 使用的数据集/场景
- **领域**：三个真实产品模拟域：
  - **王者荣耀**（MOBA游戏）：玩家社交、组队、对战记录等。
  - **QQ音乐**（音乐平台）：歌曲搜索、播放列表管理、收藏等。
  - **腾讯会议**（企业协作）：组织架构、会议室预订、日程管理、群组创建等。
- **任务数量**：共323个状态变更任务（王110、QQ 104、会议109）。
- **环境规模**：每个域12-16张表，76K+总行数，0.6M+数据单元。

### Benchmark评估设置
- **基线方法**：11个前沿LLM作为求解器（Kimi-K3, GPT-5.5, Opus-4.8, Grok-4.5, GLM-5.2, Qwen-3.7-Max, Hy3, Seed-2.1-Pro, Gemini-3.5-Flash, MiniMax-M3, DeepSeek-V4-Pro）。另含Muse-Spark-1.1（部分结果）。
- **评估指标**：
  - Avg@3：所有任务所有尝试的成功率平均值。
  - Pass@3：至少一次尝试成功的任务比例。
  - Pass^3：三次尝试全部成功的任务比例（可靠性度量）。
- **实验条件**：每个任务独立三次，每次使用新的数据库副本。对比基础E-Bench与E-Bench-Code。

## 6. 论文的主要结论与发现

- **多步工具使用远未解决**：最强模型Kimi-K3在E-Bench上的Avg@3仅为73.8%，Pass^3低于60%（58.8%）。即使加入代码执行（E-Bench-Code），最佳Pass^3仍低于70%（68.66%）。
- **可靠性是关键瓶颈**：几乎所有模型在Pass@3和Pass^3之间都有巨大差距（如Kimi-K3从87.6%降至58.8%），表明模型无法稳定地重复成功，这对于修改真实生产状态而言不可接受。
- **代码执行提升显著但不均衡**：所有模型从代码执行中获益，但提升主要集中在计算密集型能力（多条件过滤、全数据获取、聚合），而对推理密集型能力（精确边界判断、跨步依赖）提升较小。代码执行让模型能将多步骤折叠进程序，显著减少工具调用次数（73.8%下降）和成本。
- **领域难度差异大**：王者荣耀最具挑战性，QQ音乐最容易。不同模型在不同领域的排名有所变化。
- **并行工具调用影响效率**：能够并行发出多个工具调用的模型（如GLM-5.2）消耗更少的令牌和交互轮次，而弱并行模型（如Grok-4.5）成本更高。

## 7. 优点

1. **完全合成、可控可扩展**：环境不依赖真实服务，可重置、可批量复制，任务可无限生成，避免数据污染和隐私问题。
2. **确定性评分**：基于数据库差异，无需LLM评判，结果客观可复现。
3. **环境与任务解耦**：共享环境支持多任务探索，更贴近真实上下文丰富性，而非任务特定快照。
4. **信息鸿沟与工具鸿沟设计巧妙**：真实模拟了智能体在部分可观察环境下的主动信息收集和组合推理需求。
5. **多维度分析**：不仅报告准确率，还深入分析了成本、并行性、代码使用模式、能力类型差异，提供全面洞察。
6. **代码执行扩展对比**：通过E-Bench-Code隔离了工具鸿沟的影响，量化了编程能力带来的性能上限提升。

## 8. 不足与局限

1. **未开源环境和任务**：为避免过拟合，作者未公开数据库和任务，导致其他研究者无法独立复现或贡献新任务，限制了可重现性和社区扩展。
