## 摘要
大型语言模型（LLM）正越来越多地被部署为智能体，在多步骤中与有状态环境交互：收集隐藏信息、组合工具调用并提交状态变更。我们将这种能力称为多步工具使用。现有基准测试推动了工具使用智能体的评估，但通常侧重于孤立的API调用、短轨迹或难以扩展或控制的设置。我们引入了E-Bench，这是一个完全合成的基准测试，包含三个产品领域（《王者荣耀》、QQ音乐和腾讯会议）中的323个状态变更任务。E-Bench将环境合成与任务合成解耦：图引导的数据库填充构建了可重用、无孤例的产品环境，而生成器-求解器不对称性创造了既存在信息差距又存在工具差距的任务，要求智能体在改变状态之前发现隐藏数据并组合多个工具调用。结果通过数据库状态差异进行确定性评分。由于环境和任务都是合成的，E-Bench在环境级别可控，在任务级别可扩展。对11个前沿LLM的基准测试表明，多步工具使用仍然具有挑战性：最强模型的Pass^3仍低于60%，即使在E-Bench-Code扩展中通过代码执行，可靠性（Pass^3）仍低于70%。

## Abstract
Large Language Models (LLMs) are increasingly deployed as agents that interact with stateful environments over multiple steps: gathering hidden information, composing tool calls, and committing state changes. We refer to this capability as multi-step tool use. Existing benchmarks have advanced tool-use agent evaluation, but often focus on isolated API calls, short trajectories, or settings that are difficult to scale or control. We introduce E-Bench, a fully synthetic benchmark with 323 state-changing tasks across three product domains: Honor of Kings, QQ Music, and Tencent Meeting. E-Bench decouples environment synthesis from task synthesis: graph-guided database filling builds reusable, orphan-free product environments, while generator-solver asymmetry creates tasks with both an information gap and a tool gap, requiring agents to discover hidden data and compose multiple tool calls before changing state. Outcomes are graded deterministically by database-state diffs. Since both environments and tasks are synthetic, E-Bench is controllable at the environment level and scalable at the task level. Benchmarking 11 cutting-edge LLMs shows that multi-step tool use remains challenging: Pass^3 stays below 60% for the strongest models, and even with code execution in the E-Bench-Code extension, reliability (Pass^3) remains below 70%.

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- **解耦环境合成与任务合成**：先构建可复用的完整产品数据库，再在此基础上生成多个状态变更任务。
- **生成器-求解器不对称**：任务生成器（Claude Opus 4.7）可访问完整数据库和SQL/代码执行工具；求解器（被测试的LLM agent）仅能通过领域特定的MCP工具与环境交互，引入**信息差距**和**工具差距**。

### 关键技术细节

1. **环境合成——图引导数据库填充（Graph-Guided Database Filling）**
   - 根据关系模式构建表依赖图，按拓扑顺序填充表，确保外键约束完整性。
   - 使用约束上下文感知合成：强LLM作为受约束的合成器，通过插入工具逐步填充数据，数据库自身强制主键唯一性和外键有效性。
   - 事后进行确定性验证与修复，修正语义错误（如时间顺序不一致、计数错误）。

2. **任务合成——产品导向循环**
   - 步骤：**检查数据→决定目标→修改状态→总结意图**。
   - 生成器记录修改前后的数据库差异（diff）作为ground truth。
   - 通过三个强验证者（GPT-5.5、Claude Opus 4.7、GLM-5.1）复现正确状态变更，至少两个一致才接受。
   - 过滤掉弱基线容易解决的任务，并按能力类型分层以保证多样性。

3. **信息差距与工具差距**
   - **信息差距**：不泄漏目标实体的具体名称或数量，仅描述规则（如“添加我收藏中不可用的歌曲”），迫使智能体主动探索。
   - **工具差距**：求解器不能直接查询数据库或执行代码，只能通过MCP工具进行业务级操作。

4. **E-Bench-Code扩展**
   - 给求解器增加`exec_code`工具（Python调用领域MCP函数），部分关闭工具差距，但仍保留信息差距。

5. **确定性评分**
   - 比较最终数据库状态与ground truth diff，每一项字段变化必须完全匹配，**无LLM裁判**，无部分分数。

## 6. 论文的主要结论与发现

1. **多步工具使用远未解决**：最强模型（Kimi-K3）在E-Bench上Avg@3为**73.79%**，但仍有一半以上任务单次尝试失败。
2. **可靠性是核心瓶颈**：Pass^3（所有三次试验成功）最高仅**58.82%**（Kimi-K3），弱模型几乎崩溃（DeepSeek-V4-Pro仅17.34%）。
3. **代码执行提升显著但有限**：E-Bench-Code中Opus-4.8跃升至Avg@3=81.11%，但Pass^3仍低于70%；代码执行尤其帮助**计算密集型能力**（多条件过滤、全量数据获取、聚合计算），而**推理密集型能力**（跨步骤依赖、精确边界判断）提升较小。
4. **并行工具调用影响效率**：强并行模型（如GLM-5.2）token消耗更低；弱并行模型（如Grok-4.5）因多次重复上下文消耗更多token。

6. **域间难度不均**：《王者荣耀》最难（Avg@3~43.64%），QQ音乐最易（Avg@3~61.39%）；代码执行的增益在各域基本一致。

## 7. 优点：方法或实验设计上的亮点

- **完全合成，可控可扩展**：环境与任务均为合成，可任意调整数据规模、域、难度，不受真实数据限制。
- **解耦设计**：环境与任务生成分离，只需构建一次环境即可生成数百任务，避免每个任务独立构建快照的开销。
- **确定性评分**：使用数据库diff进行精确状态匹配，完全客观，无LLM裁判偏差，且评分可复现。
- **生成器-求解器不对称**：通过信息差距和工具差距确保任务必须通过多步交互才能解决，避免了简单猜测或记忆。

- **代码执行变体（E-Bench-Code）** 允许隔离计算执行能力对性能的影响，揭示模型在编排与推理上的分离困难。

- **成本效率分析**：报告了每个模型每任务的API费用，提供了实用部署参考。

## 8. 不足与局限

- **环境完全合成，生态效度有限**：虽然模仿真实产品，但数据分布和交互模式可能与真实世界存在差距，泛化性有待验证。

- **缺少对推理策略的消融**：未对比不同推理范式（如ReAct、Plan-and-Solve、Tree-of-Thought）在同一benchmark上的表现。
- **算力信息缺失**：无法评估评估成本或训练/推理所需的实际计算资源。
