## 摘要
编程智能体需要反复从不断演化的代码仓库中搜索、导航和保留上下文，但是分散的索引、语言服务器和任务局部历史记录导致重复发现并隐藏生命周期成本。CodeNib为每个仓库提交构建可复用的词法、稠密和结构视图，将输出映射到仓库相对源代码范围，在编辑过程中维护选定视图，并通过一个运行时提供排序搜索、符号导航和受限上下文。在100个快照中，我们绘制了仓库上下文生命周期中的质量-成本前沿。当输出与独立重建匹配时，图中值和向量更新的中位数速度分别快8.7倍和25.4倍。在匹配规范化实时服务器位置的静态导航子集（1000个请求中的63%）上，每个请求的实时/静态延迟中位数比为4.7倍。在五个模型上，选定的上下文策略保留了定位能力，同时相比成对的grep/read减少了50-87%的轨迹令牌。总之，这些结果支持具有明确、操作特定的有效性边界的多视图仓库上下文服务。

## Abstract
Coding agents repeatedly search, navigate, and retain context from evolving repositories, but disconnected indexes, language servers, and task-local histories force repeated discovery and obscure lifecycle costs. CodeNib builds reusable lexical, dense, and structural views per repository commit, maps outputs to repository-relative source ranges, maintains selected views across edits, and serves ranked search, symbol navigation, and bounded context through one runtime.   Across 100 snapshots, we map quality-cost frontiers across the repository-context lifecycle. When outputs match an independent rebuild, graph and vector updates are $8.7\times$ and $25.4\times$ faster at the median. On the static-navigation subset matching normalized live-server locations (63% of 1,000 requests), the median per-request live/static latency ratio is $4.7\times$. Across five models, selected context policies preserve localization with 50--87% fewer trajectory tokens than paired grep/read. Together, these results support multi-view repository-context serving with explicit, operation-specific validity boundaries.

# CodeNib 论文详细总结

## 1. 核心问题与整体含义

**研究动机**：编程智能体（coding agents）在执行任务时，需要在不断演化的代码仓库中反复执行搜索、符号导航、代码读取和历史保留等操作。然而，现有系统依赖相互孤立的索引（如文本索引、嵌入存储）、语言服务器（LSP）和任务级局部历史，导致每个任务都必须重新发现上下文，且生命周期成本（构建、更新、查询、交付）不透明。

**核心问题**：如何将仓库上下文从重复的每任务探索转变为可复用、可独立构建与维护的视图，并用统一的运行时提供服务，同时明确每个操作的有效性边界和质量-成本权衡。

**整体含义**：CodeNib 采用数据系统视角——将每次仓库提交视为不可变基数据，将词法、稠密、结构等视为物化视图（materialized views），将智能体请求视为视图查询，将提示上下文视为交付结果。通过解耦视图的构建、维护和服务，使仓库上下文成为一个可测量、可复用的工程问题。

## 2. 方法论

### 核心思想
- **多视图物化**：为每个仓库提交独立构建三种视图：
  - 词法视图（BM25 / Zoekt）
  - 稠密视图（FAISS 向量索引）
  - 结构视图（语义图：文件、符号、引用、包含等关系）
- **视图清单（Manifest）**：记录每个视图的提交、配置文件、状态、能力，是运行时查找边界。
- **独立增量维护**：
  - 图维护：Git diff + LSP 辅助，区分文件级替换与符号级修复（图3）。符号级修复保留未被编辑影响的节点/边，仅修复受影响的符号和引用。
  - 向量维护：内容寻址的嵌入重用，仅对变化的文件重新编码并更新 FAISS 索引。
- **查询与上下文服务**：
  - 排序检索：支持词法、语义、混合、结构（图扩展）路由，可配置预排序截断、重排序、图融合。
  - 符号导航：静态提供者（基于持久化的图/出现记录）与实时 LSP 提供者，共享同一位置接口，但只报告匹配子集的延迟。
  - 上下文策略：三种策略——grep/read（无预注入）、Eager（注入 top-10 候选）、Eager+Compact（一次历史重写，仅保留方向种子、最新读取结果、问题描述）。

### 关键技术细节
- **源单元分层**：L0（文件签名）、L1（命名作用域）、L2（可调用定义），便于排序和投影。
- **查询计划**：四元组 `z = <r, k, ρ, h>`，r 为路由（A-D），k 为宽度（检索扇出、预排序截断），ρ 为重排序器，h 为图扩展步数。
- **图融合公式**：融合稠密与图排序使用加权 RRF（倒数秩融合）：`score(u) = w_d/(κ + r_d(u)) + w_g/(κ + r_g(u))`，缺失项贡献为 0。
- **上下文压缩**：在第 `j` 次调用（第一次成功读取后），历史从 `[S, Q || C_ctx_10, e_1:j]` 重写为 `[S, Q || d_j]`，其中 `d_j` 包含去重路径、最新读取结果、最新非空助手消息的前 600 字符方向提示。

## 3. 实验设计

### 数据集
- **CodeNib Base**：100 个快照，来自 SWE-Bench Verified（Python）和 SWE-Bench Multilingual（C/C++, Go, Rust, TS/JS），共 25 个仓库。使用开发者补丁构建 ground-truth（预补丁中修改/删除的符号和文件）。
- **CodeNib Synthesis**：基于 Base 中每个仓库的最丰富图快照（共 25 个），生成 500 个定位查询（6 类：behavioral, file hint, module hint, reasoning, symbol hint, traversal）。使用 Claude Opus 生成和评判。

### 基准与对比方法
- **Q1（检索）**：5 种嵌入模型（SweRank-Small 137M, Qwen3-Embed-0.6B, Jina-Code-1.5B, Qwen3-Embed-4B, SweRank-Large 7B），重排序使用 Qwen3-Reranker（0.6B/4B/8B），图扩展消融（稠密+图加权融合）。
- **Q2（索引）**：FAISS 索引族对比（Flat, IVF, HNSW），固定 Qwen3-Embed-0.6B 向量和查询。
- **Q3（导航）**：静态索引 vs 实时 JSON-RPC（clangd, gopls, basedpyright, rust-analyzer, typescript-language-server），1000 个请求。
- **Q4（维护）**：完全重建 vs 文件级图替换 vs 符号级图修复；完全重建 vs 内容寻址向量增量更新。8 个仓库各 5 个父级提交过渡。
- **Q5（Agent 上下文）**：grep/read vs Eager vs Eager+Compact，5 个模型（Claude Haiku 4.5, Qwen3.5-9B/27B, Gemma 4-12B, Gemini 2.5 Flash）。

### 评估指标
- Q1: Recall@k（文件和符号）、File Success@k、延迟
- Q2: Neighbor Recall@10（与 Flat 精确集重叠）、构建时间、搜索延迟
- Q3: 规范化路径/起始行集合匹配率、匹配请求条件延迟
- Q4: 输出完全匹配（图事实多集、定义/引用请求）的速度提升；向量需要精确文档身份、向量数值相等、有序 Flat top-10 回放
- Q5: 轨迹 tokens、AnswerRecall@5（前 5 个去重答案源跨度），质量阈值 ΔRecall ≥ -0.05（95% 置信下限）

## 6. 主要结论与发现

1. **检索**：重排序可在数秒内提升 4-6 个百分点召回（文件级别），图扩展效果不确定（跨所有嵌入置信区间包含零）。
2. **索引**：嵌入模型和粒度（L0/L2）主导构建和查询时间；ANN（HNSW）可将 FAISS 搜索加速 34 倍，但在当前规模下构建开销较大（约 2s），需足够查询量摊销。
3. **导航**：静态索引匹配 63.2% 的规范化路径/起始行集（定义 87.4%，引用 39.0%），匹配请求的中位延迟比实时 LSP 低 4.72 倍。但非匹配请求无法自动回退，不能完全替代实时服务。
4. **维护**：向量增量更新匹配率 90.3%（28/31），中位加速 25.44 倍；图符号修复匹配率 45.5%（15/33），中位加速 8.67 倍。Go 和 Python 图修复完全匹配，Rust 和 TS/JS 未通过严格检查。
5. **上下文交付**：候选注入 + 一次性紧凑（Compact）在保留定位质量（ΔRecall≥-0.05）下，将轨迹 tokens 减少至 grep/read 的 13-50% 不等（模型依赖）。紧凑并非总是优于 Eager（Haiku 上紧凑反而多 tokens 23%）。
6. **生命周期复用**：单次构建（~117s）加上运行时加载（7.4s）后，每会话服务仅 0.73s；通过共享驻留运行时，多会话（q=20）每会话投影时间从 13.2s（独立加载）降至 6.2s。

## 7. 优点

- **系统设计清晰**：将仓库上下文服务视为数据系统，解耦视图构建、维护与服务，每阶段可独立评估。
- **严格评估**：维护实验要求完全输出匹配才计入加速，导航只报告匹配子集延迟，防止夸大；使用 bootstrap 置信区间和预设质量阈值。
- **覆盖面广**：从单次构建到增量更新、从检索到导航、从离线索引到在线 Agent 上下文，横跨完整生命周期。
- **开源和可复现**：代码和数据集已发布，实验配置（模型版本、冻结参数）详细记录，便于复现。
- **实用视角**：提供了具体操作边界（如匹配率、条件加速），而非笼统声称“替换实时服务”。
- **公平对比**：上下文策略共享相同候选集，唯一变量是历史处理方式；消融在独立调优集上选择超参数。

## 8. 不足与局限

- **任务范围有限**：仅评估代码定位（localization），未评估补丁生成、测试通过率或

- **任务范围有限**：仅评估代码定位（localization），未评估补丁生成、测试通过率或实际智能体任务成功率。定位质量的微小改进或退化可能无法直接转化为端到端修复能力的变化，论文未验证压缩上下文对最终修复正确性的影响。
- **实验规模有限**：仅使用25个仓库的100个快照，主要来自SWE-Bench，可能无法代表真实世界仓库的多样性（如超大型monorepo、频繁提交、不同语言生态）。生命周期追踪仅针对25快照、20会话，统计能力有限。
- **导航覆盖率不高**：静态索引仅匹配63.2%的请求（定义87.4%，引用39.0%），非匹配请求无法自动降级到实时LSP；论文未提供自动回退机制，限制了其实用性。
- **图维护的泛化性不足**：符号级修复完全匹配仅在Go和Python通过严格检查，Rust和TypeScript/JavaScript因输出多集不匹配而失败，说明依赖语言服务器质量和图模式差异，无法推广到所有语言。
- **依赖外部工具**：图构建依赖LSP和自定义解析器，不同语言支持程度不一；部分语言缺少成熟LSP或无法准确解析符号、引用，可能影响结构视图的完整性和维护迁移率。
- **上下文压缩策略的自适应不足**：紧凑策略在某些模型上反而增加tokens（如Haiku），且方向种子长度固定为600字符，未针对不同模型敏感度或任务动态调整；质量阈值ΔRecall≥-0.05的设置可能不够精细。
- **成本衡量不完整**：仅报告时间加速，未分析内存占用、磁盘I/O、GPU利用率；增量维护的解析开销（如diff、LSP启动）可能在高频提交下显著；未说明并发查询下的锁竞争或资源争用。
- **未讨论并发与分布式支持**：当前实现基于单机运行时加载整个仓库，无法处理超大型仓库或高并发场景；运行时缓存和视图加载策略在规模扩展时可能面临瓶颈。
- **与现有系统对比不足**：未与完全基于实时LSP的方案、或完全基于向量索引、或当前主流Agent框架（如SWE-Agent、OpenHands）进行端到端准确率和延迟对比，缺乏实际部署场景的参照。
- **评估指标单一**：主要关注召回、延迟加速，未关注精度（如导航误报率）、用户满意度、或人工干预成本；维护实验仅检验输出完全匹配，未评估“近似但可行”的上下文是否足够。
