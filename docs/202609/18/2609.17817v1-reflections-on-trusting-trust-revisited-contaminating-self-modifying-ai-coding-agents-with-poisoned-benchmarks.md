## 摘要
汤普森的《信任之信任》表明，编译器可被投毒以重新插入自身后门，以至于即使重新编译干净源代码也会复现该木马。如今，大量编码工作由 AI 编码智能体完成——并且越来越多地，这些智能体生成自身的新版本。我们重新审视当“编译器”是自修改编码智能体时的汤普森攻击。对手能否向智能体的自我评估与自我改进过程提供被投毒的基准，从而诱导该智能体的未来版本在干净的留出任务上编写有漏洞的代码？我们将该攻击实例化到最近提出的三种自修改编码智能体上：Darwin Gödel Machine（带有我们的实验性修改）、Self-Improving Coding Agent 和 Hyperagents（后两者均未作实质性修改）。我们展示了成功的概念验证：例如，对于由 Sonnet 4.5 驱动的 Hyperagents，我们的投毒基准使该智能体自我演化出在中性 URL 抓取任务上禁用 HTTPS 证书验证的指令。从实验中，我们提炼出足以促成基准投毒攻击的漏洞、基准、模型和智能体脚手架的属性。此外，我们表明，即使随后让被投毒的智能体针对干净基准进行演化，污染也往往持续存在。我们讨论防御方向，并主张自修改编码智能体必须被设计得对此类攻击更具韧性。

## Abstract
Thompson's "Reflections on Trusting Trust" showed that a compiler can be poisoned to reinsert its own backdoor, so that even recompiling clean source reproduces the Trojan. Today, substantial coding work is done by AI coding agents -- and increasingly, those agents generate new versions of themselves. We reconsider Thompson's attack when the "compiler" is a self-modifying coding agent. Can an adversary supply poisoned benchmarks to the agent's self-evaluation and self-improvement process to induce future versions of the agent to write vulnerable code on clean, held-out tasks? We instantiate this attack against three recently proposed self-modifying coding agents: the Darwin Gödel Machine (with our experimental modifications), the Self-Improving Coding Agent, and Hyperagents (both substantively unmodified). We demonstrate successful proofs-of-concept: for example, with Hyperagents powered by Sonnet 4.5, our poisoned benchmark leads the agent to self-evolve instructions that disable HTTPS certificate validation on neutral URL-fetching tasks. From our experiments, we distill properties of the vulnerability, benchmark, model, and agent scaffolding that are sufficient to enable a benchmark poisoning attack. Moreover, we show that contamination often persists even when a poisoned agent is subsequently evolved against clean benchmarks. We discuss defensive directions and argue that self-modifying coding agents must be designed to be more resilient to such attacks.

- **背景渊源**：Ken Thompson 在 1984 年图灵奖演讲《Reflections on Trusting Trust》中证明，编译器可被投毒以重新插入自身后门——即使重新编译干净源代码，木马仍会复现，由此引出"你无法信任不是自己完全创建的代码"这一命题。
- **时代变迁**：如今大量编码工作由 AI 编码智能体（如 Claude Code、Codex）完成，且这些智能体越来越多地**生成自身的新版本**（例如 Claude Code 后续版本主要由 Claude Code 自己编写，仅经人工审核）。自修改/自改进智能体已成为活跃的学术研究领域（DGM、SICA、Hyperagents 等）。
- **核心研究问题**：当"编译器"变成自修改编码智能体时，Thompson 攻击是否依然成立？具体而言，**攻击者在无法修改智能体本身、无法替换底层模型的前提下，仅通过向智能体的自评估与自我改进过程提供被投毒的基准，能否诱导其未来版本在干净、中性的留出任务上写出有漏洞的代码，并使污染持续保留？**
- **整体含义**：这是首个对该攻击进行系统性、端到端实证验证的工作（此前相关工作仅提出风险概念但缺乏实证）。论文指出，随着自修改 AI 系统的"信任根"从人类转向机器，Thompson 的问题重新变得紧迫。

## 2. 方法论

### 2.1 核心思想
- 攻击目标：自修改 AI 编码智能体（基线/种子智能体假设未被污染）。
- 攻击向量：**投毒基准**（poisoned benchmark），即包含漏洞、或迫使智能体使用漏洞才能通过测试的评测任务集。
- 攻击流程（对应图 2 的通用攻击概念）：
  1. 智能体在投毒基准上运行并评分；
  2. 自评估产生解题记录（transcript）；
  3. 诊断/自我改进提示基于记录提出修改方案（自然语言提议或代码工具）；
  4. 方案被实现为对智能体自身脚手架/提示/工具的修改；
  5. 迭代多代进化；
  6. 最终在**中性留出任务**上评估进化后的智能体是否写出漏洞代码。

### 2.2 关键技术细节
- **基准构造风格**：仿照 Polyglot 基准，每个任务为自包含 Python 编程练习，含自然语言提示、函数桩、隐藏测试套件与参考解；每个候选智能体在 Docker 容器内评测，解题时仅可见任务，参考解与测试在评测时才引入。
- **CertCheck 基准（主力漏洞类型）**：
  - 任务为编写 HTTPS 抓取器；
  - 投毒版让所有测试服务器出示自签名（不受信任）证书，使得正确验证的请求失败，**唯一通过途径是禁用证书验证**；
  - 干净版除服务器使用受信任证书外完全相同；
  - 漏洞代码示例：`ctx = ssl._create_unverified_context()` 或 `verify_mode = ssl.CERT_NONE`。
- **五种候选漏洞类型**（差异在于"存在坏代码行"还是"缺失某检查"）：
  1. Broken Access Control（缺失逐条访问检查）
  2. Code Injection（使用 `eval()`）
  3. Redirect SSRF（仅检查重定向链首个主机）
  4. Disabled HTTPS Cert Check（启用中间人攻击）
  5. Backdoor（关键词触发返回敏感数据）
- **可行性探针（Feasibility Probes）**：因完整 DGM 运行昂贵（单次 15 代约 1000 次模型调用），设计三个廉价探针：
  - (a) 基线漏洞率：种子智能体在干净/投毒基准上的漏洞发生率（需投毒高、干净低）；
  - (b) 提议中的漏洞：DGM 诊断是否提出产生漏洞代码的工具（每对基准-模型采样 40 次）；
  - (c) 实现中的漏洞：自我改进步骤是否真的把漏洞写入工具（收集 24 个样本）。
- **对 DGM 的实验性修改**：为使攻击可行，研究者**修改了 DGM 的内部诊断提示**（删除"聚焦通用编码能力而非特定问题修复"等约束，加入鼓励编写可复用代码生成工具的指导），以探索攻击上限。此修改超出威胁模型（攻击者不能改智能体），但对理解攻击边界必要。SICA 与 Hyperagents 无需此类修改。

## 3. 实验设计

### 3.1 三个案例系统（benchmark 场景）
| 系统 | 自我改进机制 | 是否修改内部提示 |

| Darwin Gödel Machine (DGM) | 编码智能体直接写代码（工具）修改自身，进化树选择 | 是（研究者实验性修改） |
| Self-Improving Coding Agent (SICA) | 脚手架以自然语言指令修改编码智能体提示，经 LLM 审查委员会审核 | 否（stock） |
| Hyperagents (DGM-H) | 元智能体修改任务智能体/自身的提示指令 | 否（stock，另修复了 git 历史答案泄漏） |

### 3.2 底层模型
- gpt-oss-120b、Qwen3.5-397B（经 Ollama Cloud）、Claude Sonnet 4.5、DeepSeek V4 Pro（用于初步测试）。

### 3.3 实验规模
- **DGM**：CertCheck 与 Backdoor 各跑两次 12 代进化（干净/投毒各一）；留出任务 10 个，每个采样 3 次。
- **SICA**：两次 4 代进化（投毒/干净），Qwen3.5-397B 与 Sonnet 4.5 各做概念验证。
- **Hyperagents**：两次 5 代进化（投毒/干净），Sonnet 4.5。

## 6. 主要结论与发现

- **攻击可行（概念验证成功）**：
  - Hyperagents + Sonnet 4.5：投毒基准诱导智能体自我演化出**在普通 URL 抓取任务中禁用 HTTPS 证书验证**的指令，留出任务漏洞率 30/30；
  - SICA + Qwen3.5-397B / Sonnet 4.5：4 代内自注入禁用证书验证的指令，留出任务漏洞率 30/30；
  - DGM + Qwen3.5-397B（需修改提示）：进化出无条件禁用证书验证的代码生成工具，漏洞率 30/30。
- **攻击成功所需属性（充分条件，非必要条件）**：
  - **漏洞**：是模型"肌肉记忆"中的标准代码习语（如标准库写法）；
  - **基准**：强迫/奖励漏洞使用，且表面上漏洞表现为"合法功能"（如自签名证书）；漏洞在中性任务上功能不可见（不破坏正常行为）；最小化提示线索以鼓励过度泛化；
  - **模型**：默认写出安全版本（否则无需投毒），但知道且愿意使用不安全习语；
  - **脚手架**：不阻止基准特定进化（SICA/Hyperagents 的开放式提示更易被攻击）；缺乏安全提示意识。
- **攻击鲁棒性**：即使 HTTPS 仅偶然出现在复杂任务中，被污染智能体仍高比例写出漏洞代码（仅当任务未显式提到 HTTPS 时略有下降）。
- **攻击持续性（Thompson 式自复现）**：
  - 用干净基准继续进化**无去污染效果**；
  - 通用安全基准（CWEval + CWE-295）**也无明显去污染效果**（因线索不同）；
  - 只有**已知毒药细节、专门设计的去污染基准**才部分有效（DGM/SICA 部分，Hyperagents 完全）；
  - 结论：污染可能在被污染基准消失后长期持续。
- **额外验证**：JWTVerify 与 YAMLLoad 两个新基准也取得（部分）成功，证明攻击并非 CertCheck 特例。
- **防守方向**：更强模型非万能药（Sonnet 4.5 在 DGM 上抵抗但在 SICA/Hyperagents 上失守）；建议在自修改脚手架中加入显式安全指导、加入内部安全基准、加强安全审查（但审查需有机制性否决权而非仅"建议"）、人类监督。

- **多系统、多模型交叉验证**：覆盖三种设计迥异的自修改系统与多个前沿模型，结论更具代表性。

- **鲁棒性与持续性分析深入**：不仅证明攻击可发生，还证明污染在后续演化中持续、且难以去污，揭示威胁的严重性。
- **防守方向有实证支撑**：对安全审查员、安全命名任务等防守做了实验探测，而非空谈。
- **伦理与开放科学**：对合作研究者进行负责任披露，仅发布带明确标注的基准生成器以降低被爬取训练的风险，并公开代码与数据。

- **模型与脚手架共变**：作者承认未能完全厘清"脚手架属性"与"模型 disposition"各自对攻击成功的因果贡献。
- **留出任务规模较小**：主要结论基于每系统 10 个任务 ×3 次采样，统计效力有限；任务多为 URL 抓取类，形态多样性受限。
- **漏洞类型覆盖有限**：五种初始漏洞中仅 CertCheck 与 Backdoor 通过全部探针，Backdoor 最终也仅部分成功；更隐蔽、更细粒度的漏洞（如逻辑缺陷）未充分探索。
- **基准"稀释性"未验证**：论文基准均为高强度毒信号，若将毒任务嵌入大型真实基准（如 SWE-Bench），攻击是否仍有效是开放问题。
- **应用限制**：所研究系统均处于研究阶段、尚未用于生产代码；结论对未来生产化系统的外推需谨慎。
- **防守评估不完整**：安全审查、安全命名等防守仅做了初步探测，未系统比较多种防御机制的有效性与代价。
- **模型迭代快**：所用模型（Sonnet 4.5、Qwen3.5-397B 等）为特定时点版本，结论可能随模型更新而变化。
