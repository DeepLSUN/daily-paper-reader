## 摘要
基于LLM的编码代理将基础模型与塑造代理行为的框架相结合。对于非平凡的任务，实践者如何组织其与编码代理的工作方式决定了是否产生可靠的结果。我们报告了Infobip AI研究团队开发的操作编码代理的分阶段工作流程。该工作流程将代理辅助开发分为四个阶段，其中人力投入集中于前期，随着产物的成熟，委托程度逐渐增加。上下文管理是核心关注点，通过在每个阶段应用的四种策略来应对已知的失败模式。从实践者经验中，我们观察到，研究和规划阶段的上游错误可能在后续阶段累积放大，而修正生成的代码可能引入臃肿和脆弱性。这促使我们将人工审查前置。我们识别出两个开放问题：缺乏衡量工作流程有效性的指标，以及形式化的上下文管理组件与实践者所需的工作流程级模式之间的差距。

## Abstract
LLM-based coding agents combine a foundation model with a harness that shapes agent behavior. For non-trivial tasks, how practitioners structure their work with the coding agents determines whether reliable results follow. We report on a phased workflow for operating coding agents developed by the AI research team at Infobip. The workflow structures agent-assisted development into four phases where human effort is front-loaded and delegation increases as artifacts mature. Context management is the central concern, addressed through four strategies applied at each phase to counter known failure modes. From practitioner experience, we observe that upstream errors in research and planning can compound across later phases, while correcting generated code can introduce bloat and fragility. This motivates front-loading human review. We identify two open problems: the absence of metrics for workflow effectiveness and the gap between formalized context management components and the workflow-level patterns that practitioners need.

## 1. 核心问题与整体含义

- **研究背景**：LLM 编码代理已被广泛用于软件工程任务，但论文指出，在非平凡任务上，其效果更多取决于操作者如何配置 **harness（代理框架）**——尤其是用户可自定义的 user harness（项目级指令、工具选择、会话结构与上下文管理）——而不是底层基础模型的优劣。
- **现有风险证据**：已有研究显示模型性能随输入长度稳定下降、多轮对话平均性能下降约 39%、无关上下文即使正确答案存在也会降低准确率、非结构化使用 AI 工具反而降低开发者生产力。
- **核心问题**：业界缺乏系统性的工作流来引导实践者可靠地操作编码代理——即如何组织人与代理的协作流程、如何管理上下文，以避免错误累积并得到可靠结果。
- **论文定位与含义**：来自 Infobip（约 900 名工程师、月处理 420 亿条消息的云通信平台）AI 研究团队的工业实践报告，面向 CIKM Industry Day，提出了一个 **"人力前置、随工件成熟逐步授权"** 的四阶段操作工作流，为编码代理的可控使用提供了一个实践导向的操作范式。

## 2. 方法论

### 2.1 核心思想
- 将代理辅助开发划分为 **研究（Research）→ 规划（Planning）→ 任务定义（Task Definition）→ 实现（Implementation）** 四个阶段；其中研究和规划每个项目只做一次，任务定义和实现随任务的执行迭代。
- **人力投入前置**于代价最高的上游阶段，随着产物的逐步成熟，人类精力投入递减、对代理的委派递增。
- **上下文管理**是贯穿始终的中心关注点，每阶段通过匹配的风险采用对应策略。

### 2.2 四阶段流程细节

1. **研究阶段（Research）**
   - 人与代理共同探索问题空间，代理仅被授予只读操作、代码库搜索及领域特定工具（如文献检索）。
   - 实践者引导研究方向但**不表达个人意见**，以避免锚定代理的探索。
   - 所有发现必须经过人工验证后才能进入下一阶段。
   - 通过 select（只加载研究相关工具）和 isolate（把会话限定在聚焦范围）降低混淆与分心风险。
   - 输出：一份经过筛选和验证的研究文档。

2. **规划阶段（Planning）**
   - 输入研究文档，实践者与代理通过迭代讨论确定实现方案。
   - 不使用专用规划模式——论文发现专用模式会促使代理过早最终确定方案、在问题尚未充分理解时产出计划产物。
   - 方案定稿后，人工将讨论压缩为经过验证的决策，写入**持久化产物**，替代完整对话进入后续阶段。
   - 该阶段是 **compress 策略**的主要应用场景：丢弃废弃推理路径，减少上游失误造成的 poisoning。
   - 输出：一份精炼的实现方案文档。

3. **任务定义阶段（Task Definition）**
   - 每条机器可读任务记录：稳定 ID、目标、依赖关系、相关代码路径、验收标准、验证方法。
   - 任务粒度被设定为能在**一个全新会话**中完成；当所需上下文超过代理有效工作范围（可远低于名义容量）时拆分任务。
   - 当实现阶段暴露任务定义不佳时，实践者回到本阶段重新定义，而非直接修补实现。

4. **实现阶段（Implementation）**
   - 每个任务在全新会话中运行，加载项目级指令与任务定义。
   - **外部化全部状态**：Git 存代码；任务注册表存任务状态、依赖、验收标准和最新结果；append-only 活动日志记录动作、验证结果、改动文件/提交、失败及下一步操作；对话状态本身可丢弃。
   - 中断恢复时，新会话读取这些持久化产物、查看工作树和最近提交，决定继续或回退不完整工作。
   - 项目级指令为手写，随实践演化：当发现代理跨会话重复犯同一错误时，加入一行简洁的修正指令（需控制指令总数，因为执行准确率随指令数增加而下降）。
   - 实践者负责审查产出而非逐行编写代码，但对整体流程保留所有权。

### 2.3 上下文管理四策略与失败模式
- 四种策略（源自 Martin）：**write**（信息持久化到上下文窗口之外）、**select**（只把相关信息检索进窗口）、**compress**（只保留必要 token）、**isolate**（跨会话/代理切分上下文）。
- 四种已知失败模式（源自 Breunig）：**distraction**（过度依赖累积模式）、**confusion**（无关内容竞争注意力）、**poisoning**（幻觉在轮次间持续留存）、**clash**（新信息与已有上下文冲突）。
- 映射并非一一对应：例如 isolate 可同时防止 poisoning 和 distraction；compress 可同时降低 confusion 和 distraction。

### 2.4 核心论点
- 上游（研究与规划）错误会在后续阶段**复合放大**；
- 事后修正生成代码会引入**冗余与脆弱性**；
- 因此，人工审查应尽可能前置。

## 6. 主要结论与发现

- 分阶段工作流的理念：**把不可靠环节控制在早期**，人工把关最上游、最易引发复合错误的环节，而不是事后修补实现。
- **上下文管理是可操作的核心抓手**：write / select / compress / isolate 四种策略必须按阶段风险搭配使用；将对话状态外包给 Git、任务注册表和活动日志，可实现"跨会话任意中断/恢复"而无需保留对话本身。
- 任务定义 + 上下文隔离 + 持久化工作流状态三者配合，是让代理在单个任务上保持稳定表现的关键。
- 针对指令工程：发现**指令迭代应因"观察到的重复错误"而驱动**，且每条修正必须极其简洁、行数受控。
- 提出两个开放问题：
  1. **缺少工作流有效性度量指标**（可能的方向包括：每会话任务成功率、指令修正率、任务完成时的上下文利用率），已有编码代理基准无法作为代理工作流有效性的可靠代理。
  2. **组件级研究与工作流级模式之间存在鸿沟**：现有文献把修剪、压缩、工具选择等单个上下文管理组件形式化并测评，但并不覆盖实践者实际需要的工作流级组合模式，且缺乏跨团队/跨领域共享术语。

## 7. 优点

- **问题选得准、背景扎实**：将已有文献中上下文长度与无关上下文导致的退化证据集中串联，成功论证"unstructured use is harmful"，为提出结构化流程提供了有力动因。
- **可操作性强**：从企业实际工程团队经验出发，给出了具体到工具权限（只读）、会话隔离策略、产物格式（任务字段、注册表/日志结构）、错误纠正规则（单行指令）的落地细节，并对上游前置给出一致、清晰的实践原则。
- **对专业术语进行了体系化映射**：将写/选/压/隔四策略与分心/混淆/污染/冲突四类失败模式对接，并强调"并非一一对应"，这种分类框架有复用与推广潜力。
- **公开配套材料**：附带了可复用的 workflow materials 在 GitHub 上，便于其他团队借鉴。
- **坦诚面对局限**：通过公开提出两个开放问题（无效果度量、组件级与工作流级鸿沟），指引了该领域的后续研究方向，避免把经验报告包装成被验证的真理。

## 8. 不足与局限

- **缺乏量化评估与对照实验**：没有为"该工作流比非结构化委托更优"或"具体哪个阶段/策略贡献最大"提供任何定量数据支撑；观察结论缺少系统性的效果测量与控制组支持。
- **方法论本身的循环性问题**：论文依赖的实践观察中，"纠正生成代码会引入 bloat 和 fragility"这一判断属于经验断言，没有代码度量（如行数膨胀、耦合度、缺陷率）来客观支撑。
- **单一组织、单一规模的偏差风险**：经验来自 Infobip（一个约 900 名工程师的特定公司团队），其代码库、任务类型、工程文化和模型选择可能与其他团队差异明显，结论推广性受限制。
- **术语来源有限**：上下文管理策略与失败模式分别引用了 Martin [11] 与 Breunig [3] 的既有描述，但这个分类框架在更大学术/工业范围中的外部效度尚未被验证。
- **篇幅所限造成细节不足**：作为 2 页短文，对于四阶段中各阶段如何衔接、任务粒度如何具体度量、项目级指令的迭代策略等关键操作细节仍较为笼统。
- **对基础模型本身的依赖并未交代**：论文说非平凡任务的成败"less depends on model choice than harness"，但并未给出这一论断在何种模型类别/规模下成立，以及弱模型是否可能让该工作流失效。
- **没有任何量化指标**——这也正是作者自己在 Open Problems 中承认的主要局限之一。
