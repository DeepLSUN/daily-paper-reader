## 摘要
多智能体系统可以通过并发执行工作来降低复杂任务的延迟。已有若干开创性的运行框架支持多智能体系统。然而，当前多智能体运行框架的可扩展性往往受限于中心编排器分配任务和协调工作者的能力。为克服这一局限，我们提出 Agensh，一种无需中心编排器的可扩展自组织多智能体运行框架：并发工作者执行一个多智能体合作循环，持续收集上下文、认领并自主分配子任务、采取行动并共享发现、验证结果，并以异步方式合并进展。该循环由智能体化组织基础设施支撑，包含三个组件：共享工作区保存已提议、进行中和已完成的工作；消息接口使工作者能够通信；共享上下文保留可复用的发现与工作意图。为测试 Agensh 的可扩展性，我们在 ProgramBench 的五个最难任务上使用 GPT-5.6-sol (high) 对其进行评估。将智能体数量从 1 扩展到 128，使平均最终测试通过率从 19.31% 提升至 28.78%，相对提升约 49%。规模更大的组织能更早达到相当的测试通过率。在 pandoc 上，将智能体数量从 1 扩展到 1,024，使最终测试通过率从 33.89% 提升至 55.06%。工作者的轨迹进一步表明，随着组织规模扩大，不同形式的自组织合作逐渐涌现并标准化。这些结果揭示了智能体数量可作为多智能体组织的一种新扩展维度，以拓展通用智能的前沿，并为在严格延迟约束或时间预算下的复杂任务提供了一种实用解决方案。

## Abstract
A multi-agent system can reduce latency on complex tasks by executing work concurrently. Several pioneering harness frameworks support multi-agent systems. However, the scalability of current multi-agent harnesses is often constrained by a central orchestrator's capacity to allocate tasks and coordinate workers. To address this limitation, we introduce Agensh, a scalable self-organized multi-agent harness without a central orchestrator: concurrent workers execute a multi-agent cooperation loop, continuously gathering context, claiming and self-assigning sub-tasks, taking action and sharing findings, verifying results, and merging progress in an asynchronous manner. The loop is supported by the agentic organization infrastructure comprising three components: a shared workspace holds proposed, ongoing, and completed work; a message interface lets workers communicate; and shared context retains reusable findings and work intentions. To test the scalability of Agensh, we evaluate it on the five hardest ProgramBench tasks with GPT-5.6-sol (high). Scaling from 1 to 128 agents raises the mean final test-pass rate from 19.31% to 28.78%, an approximately 49% relative improvement. Larger organizations reach comparable test-pass rates earlier. On pandoc, scaling from 1 to 1,024 agents raises the final test-pass rate from 33.89% to 55.06%. Worker trajectories further show that different forms of self-organized cooperation gradually emerges and standardizes as the organization grows. These results reveal the number of agents as a new scaling dimension for multi-agent organizations to expand the frontier of general intelligence, offering a practical solution for complex tasks under hard latency constraints or time budgets.

## 1. 核心问题与研究动机

- **单智能体系统的三重瓶颈**：大模型智能体虽有 ReAct、Reflexion 等范式支撑感知—行动—迭代，但其能力受限于**单一上下文窗口、单一动作流、单一记忆流**，在复杂长程任务上必然表现为串行执行、延迟高。
- **现有多智能体框架的中心化瓶颈**：Codex sub-agent、Claude Code sub-agent/agent teams、Copilot fleet、Kimi Agent Swarm 等主流 harness 普遍采用 **orchestrator–worker（编排器—工作者）** 结构：由主智能体规划、分解任务、分派并发 worker 并整合结果。该结构通常需要训练有素的编排器，且整体可扩展性从根本上受限于**中心编排器管理 worker、协调依赖、整合贡献的容量**。
- **论文的整体含义**：作者主张把"智能体数量"本身作为一种新的扩展维度（scaling dimension）。若把协调职责从中心下放给每个 worker，让它们自组织地认领任务、共享发现、验证并合并成果，则组织智能可随规模增长而增长，从而在严格延迟约束/时间预算下攻克复杂长程任务。

## 2. 方法论

### 2.1 核心思想
- **无中心编排器的自组织多智能体 harness**：所有 worker 对等（all equal），并发、异步运行；谁做什么由 worker 自己认领与协商，而非由中央分配。
- Agensh 是**叠加在单智能体 harness 之上的组织层**，而非替代它：底层 harness（如 Copilot、Claude Code）负责单个 worker 的本地 agentic loop（维护会话状态、调用模型、执行工具）；Agensh 负责组织级行为（worker 身份、协作协议、事件路由、共享工作区、消息、共享上下文、恢复与存活机制）。
- 协作循环**以 prompt 中的工作流指令实现**，而非硬编码进运行时；除 worker ID 外，所有 worker 的 prompt 完全相同，因此可通过轻量适配器接入不同底层 harness（即插即用）。

### 2.2 五步多智能体协作循环（每个 worker 并发异步执行）
1. **Gather context（收集上下文）**：读取共享用户目标、当前状态、同伴进展与消息、已积累发现，并与环境交互规划下一步。
2. **Claim sub-task（认领子任务）**：向共享上下文追加一条 `CLAIM` 声明自己的范围；若与他人的 claim 重叠或冲突，鼓励通过直接消息解决。
3. **Take action（采取行动）**：本地实现子任务，通过工具与环境交互；一旦获得对同伴有用的发现，即写入共享上下文。
4. **Verify results（验证结果）**：将本地进展与子任务验收标准比对，不满足则迭代修正。
5. **Merge progress（合并进展）**：将贡献并入共享工作区，并发布"改了什么 / 思路 / 验证证据"；若合并冲突，则先并入最新同伴进展、解冲突后重试。完成后回到第 1 步。

### 2.3 智能体化组织基础设施（三大组件）
- **共享工作区（Shared workspace）**：保存已提议、进行中、已集成的工作；要求支持并发写、异步读、版本历史与合并冲突暴露。实现上用 **Git 平台（Gitea）**：worker 在私有 checkout/分支上工作，贡献并入 main 分支，用 issue 与 PR 承载工作流。
- **消息接口（Message interface）**：共享任务频道用于团队公告，直接消息（DM）用于紧急一对一沟通。低优先级频道消息在每轮循环开始时投递；高优先级 DM 在每次基础设施工具调用返回时投递（即"轮内插话"，会打断同伴当前动作）。保留会话历史、异步投递，用于解决 claim 重叠、协商依赖、请求协助。
- **共享上下文（Shared context）**：借鉴 DeLM 思路，采用 append-only 数据库 + 近期记忆，条目为**类型化短记录**：
  - `OBSERVED`（观察到的参考行为）、`FACT`（已确认事实）、`FAIL`（被证伪的假设，价值最高，避免同伴重复踩坑）、`CLAIM`（进行中的工作声明）、`PATCH_SUMMARY`（`files= | idea= | evidence=`）。
  - 条目有长度上限（普通 100 字符，`PATCH_SUMMARY` 300 字符），长内容放 `detail` 字段，同伴可用 `board_unfold` 展开。
  - 新增条目作为高优先级更新，在同伴下一次基础设施工具调用返回时被追加；`board_read` 返回最近板面（截断至最新 2000 条），`board_grep` 支持跨全历史的关键词检索（`,` 为 OR，`&` 为 AND）。
- **运行时实现细节**：事件驱动路由（Gitea 用 SSE 拉取新通知，Mattermost 用长连接 + 重连补齐）；事件带唯一 ID 去重、写入持久队列、失败按指数退避重试；worker 空闲 10 分钟触发提醒，若一轮未产出共享上下文条目也会被提醒补写。

### 2.4 算法/流程的文字化描述
> 对每个 worker：`while 目标未达成`：读共享上下文与同伴进展 → 声明 `CLAIM` → 本地实现并与参考程序对拍验证 → 通过则合并入 main 并写 `PATCH_SUMMARY`；冲突则同步 main、重验、重推 → 继续下一轮。

## 6. 主要结论与发现

- **智能体数量是新的扩展维度**：同样模型、同样 harness、同样 6h 预算下，5 个最难 ProgramBench 任务的平均最终通过率从 1 个智能体的 **19.31%** 提升到 8/32/128 个智能体的 **20.68% / 26.52% / 28.78%**；1→128 提升 **+9.47 个百分点，相对提升约 49%**。
- **规模化同时降低延迟**：规模更大的组织能**更早**达到同等通过率。例如 pandoc 上 128 个智能体在 30 分钟检查点即超过 30% 通过率，32 与 8 个智能体分别要到 60、90 分钟，而单智能体在前 2 小时内始终未越过该阈值。
- **可扩展至千级规模**：pandoc 上 1 → 128 → 1,024 个智能体的最终通过率为 **33.89% → 50.94% → 55.06%**；1,024 比 128 高 4.12 个百分点，比单智能体高 21.17 个百分点。
- **自组织协作形态随规模涌现并标准化**（关键定性发现，且所有 worker 使用完全相同的 prompt，仅 ID 不同）：
  - **8 个智能体**：同伴协调——就技术接口达成一致后各自独立实现模块；主动发现并化解 claim 重叠（FFmpeg 中一方改换范围做互补工作）。
  - **32 个智能体**：跨多 worker 的集成管理——多方可共同参与一项贡献，出现"反例否决先前批准 → 作者修复 → 重新评审 → 同伴合并"的流程。
  - **128 个智能体**：自组织专业化与工作流标准化——按既往经验挑选评审者并复用评审关系；可把合并责任转移给同伴；pandoc 上出现被复用的集成协议（作者更新并测试分支 → 发送 commit hash 供同伴验证合并），失败后进一步修订为"授权同伴完成整个更新—测试—检查—合并循环"。
  - **1,024 个智能体**：组织级角色专业化——多个 worker 同时担任集成者，可同时联系多个候选集成者并选第一个有效响应者、取消其余请求；同一技术领域的专家可在同伴失败后接管工作，降低对单个个体的依赖。

- **问题定位清晰且有价值**：准确指出 orchestrator–worker 结构的容量瓶颈，并给出一个不依赖中心编排器的可扩展替代方案。

- **信息经济学设计精巧**：类型化短条目（`FAIL` 被明确标为"最高价值"，用于阻止同伴浪费预算）、字符上限 + `detail` 折叠、`board_grep` 跨全历史检索（突破近期记忆窗口），是对长程协作中"上下文稀缺"的针对性设计。
- **把"智能体数量"当作受控变量**：固定模型、harness、预算与评测流程，做了 1/8/32/128/1024 的规模梯度，并同时报告最终质量与时间曲线两个维度。
- **对公平性的主动补偿**：为单智能体基线加 stop hook、为多智能体加空闲检测器，避免"单智能体提前摆烂"造成的虚假规模收益。
-

- **对"协作协议即 prompt"这一设计选择的验证**：所有 worker 仅 ID 不同、prompt 完全一致，却在不同规模下自发涌现出协调、评审、专业化、角色接管等不同形态——这为"组织行为可由通用指令 + 环境结构诱导，而不必硬编码"提供了难得的经验证据。
- **定性轨迹分析与定量指标互补**：论文没有止步于通过率数字，而是把 8/32/128/1,024 四个规模下的协作形态（claim 重叠化解、反例否决—修复—重审、集成者竞选、专家接管）逐一描述，使"规模如何改变组织形态"这一机制性问题可被观察，而非仅靠指标反推。

## 8. 局限与不足（补充）

- **成本与延迟的"暗面"未评估**：论文强调规模化降低"达到同等通过率所需的时间"，但 128/1,024 个 worker 的总 token 消耗、API 调用量与并发基础设施压力必然量级上升。以延迟换成本是否划算，取决于任务价值与预算约束，论文未给出任何权衡曲线（如"每单位通过率提升的边际 token 成本"）。
- **协调开销的规模上界未知**：共享上下文采用"最近 2000 条截断 + grep 全历史"的策略，在 1,024 worker 下的写入冲突、grep 命中噪声、DM 打断（轮内插话）对同伴动作的干扰，均未量化。规模继续放大到万级时，append-only 板面与低优先级频道投递是否仍是有效瓶颈，缺乏讨论。
- **评测指标单一**：仅用隐藏测试通过率衡量，未涉及生成代码的可维护性、与参考实现的语义偏差类型、以及"通过了测试但实现方式错误"的作弊式解法风险。对于 6 小时重建百万行级项目的任务，测试覆盖率本身可能就是瓶颈。
- **失败模式与失败案例缺失**：论文报告了成功形态，但未系统分析 1,024 worker 下的失败模式——例如重复劳动、claim 争抢导致的震荡、错误 `FACT` 污染共享上下文、集成者竞选失败后的死锁。这些恰是自组织系统最需要证据的地方。
- **泛化边界不清**：5 个任务均属"有明确参考行为 + 有隐藏测试"的软件重建类任务，这类任务天然适合"分而治之 + 对拍验证"。对目标模糊、验收标准主观、或需要单点深度推理（而非广度分工）的任务，去中心化组织是否仍优于中心编排，论文未做讨论。
- **关键超参数敏感性未知**：条目 100/300 字符上限、10 分钟空闲提醒、错峰激活节奏（30 秒→3 秒）、T−45/T−5 收尾提醒等，均是影响结果的工程选择，但未做敏感性分析。

## 9. 可复现性与工程启示

- **可复现性中等偏好**：模型、底层 harness、时间预算、评测流程、节点拓扑（16×64）均有交代，架构组件也选用了开源成熟件（Gitea、Mattermost），原则上可复刻。但 prompt 全文、事件路由与去重/重试的具体实现、共享上下文条目的写入触发规则等关键细节未在总结所及范围内充分展开，且缺少重复运行，复现的"结果一致性"难以保证。
- **对工程实践的三点直接启示**：
  1. **把协调做成"环境"而非"代码"**：用版本控制、频道消息、类型化黑板这些已有原语承载协作，比自研编排 DSL 更容易接入异构 harness。
  2. **上下文是稀缺资源，要按信息价值分级**：`FAIL` 优先、短条目 + 折叠详情、跨全历史 grep，本质上是在做"组织级上下文管理"，这一思路可迁移到任何长程多智能体系统。
  3. **收尾阶段需要显式协议**：`T−45min` 停止新功能、`T−5min` 确认构建可用，是对"多智能体容易无限探索"这一失效模式的务实补丁。

## 10. 总体评价

论文的核心贡献不在于某个新算法，而在于**提出并初步验证了一个可扩展的组织范式**：把协调职责下放给对等 worker，用共享工作区、消息接口与类型化共享上下文这三件"轻基础设施"支撑自组织，从而让智能体数量成为独立于模型能力与上下文长度的第三条扩展轴。其最有力的证据是 1→1,024 的单调（虽非线性）提升与时间曲线的前移，以及"同一 prompt 诱导出不同规模下不同组织形态"的定性观察；最明显的短板则是缺少消融、缺少重复与方差、缺少与中心化编排器在同规模下的受控对比，以及成本信息的完全缺位。

因此更稳妥的读法是：**这是一篇提出方向、给出可行性证据的开创性工作报告，而非对"去中心化优于中心化"的定论性证明**。它把"组织规模"从一个工程直觉提升为可测量的研究变量，后续工作若能在受控消融、成本—质量权衡曲线、失败模式分类以及与 orchestrator 结构的同规模对照上补齐证据，该方向的学术地位将更为稳固。
