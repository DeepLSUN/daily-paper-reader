## 摘要
大语言模型（LLM）智能体通常处理一系列相关任务，但标准驾驭框架会反复要求模型在每个任务的上下文中重建相同的控制决策。我们研究任务反馈能否转而将反复出现的控制转化为可复用的可执行代码，同时将 LLM 调用保留给任务特定的语义推理。我们提出 Growing Harness，一种由失败引导的训练范式，它从一个无策略脚手架中学习智能体驾驭框架本身；该脚手架暴露固定的模型与工具接口，但不编码任何任务求解控制器。函数级执行轨迹将每次失败定位到一个有界代码面上，优化器联合修复一个失败窗口，而成功优先的留出门控会回滚损害先前能力的修复序列。被接受的编辑累积在同一个共享驾驭框架中，使其控制结构从任务反馈中涌现。在 BrowseComp-Plus 与 WebArena-Verified 上，使用参数规模从 4B 到 120B 的三个部署模型，Growing Harness 在六种基准-模型设置中的五种取得最高平均成功率，在第六种中落后最佳均值 0.7 个百分点。相对于工具调用（Tool-Calling）智能体，它将 LLM 调用次数减少 76.0–91.8%，将部署智能体的推理成本降低 74.4–98.6%。在 WebArena-Verified 上，其成功率在不同模型规模间保持在 44.7–45.3%，而工具调用在 4B 模型上降至 6.7%。消融实验表明，轨迹局部编辑、联合修复与基于门控的回滚均能提升最终成功率。这些结果表明，持续的程序生长能够将反复出现的控制移出模型上下文并转入低成本代码，从而产生可复用的专家智能体，使其在较小部署模型下仍然有效。

## Abstract
Large language model (LLM) agents often handle streams of related tasks, yet standard harnesses repeatedly ask the model to reconstruct the same control decisions inside each task's context. We study whether task feedback can instead turn recurring control into reusable executable code, while reserving LLM calls for task-specific semantic reasoning. We introduce Growing Harness, a failure-guided training paradigm that learns the agent harness itself from a strategy-free scaffold that exposes fixed model and tool interfaces but encodes no task-solving controller. Function-level execution traces localize each failure to a bounded code surface, an optimizer repairs a window of failures jointly, and a success-first held-out gate rolls back repair sequences that harm prior capability. Accepted edits accumulate in one shared harness, allowing its control structure to emerge from task feedback. Across BrowseComp-Plus and WebArena-Verified with three deployment models from 4B to 120B parameters, Growing Harness achieves the highest mean success in five of six benchmark-model settings and trails the best mean by 0.7 pp. in the sixth. Relative to a Tool-Calling agent, it reduces LLM calls by 76.0-91.8% and deployed-agent inference cost by 74.4-98.6%. On WebArena-Verified, its success remains 44.7-45.3% across model scales, whereas Tool-Calling falls to 6.7% with the 4B model. Ablations show that trace-local edits, joint repair, and gate-based rollback each improve final success. These results show that persistent program growth can move recurring control out of model context and into low-cost code, yielding reusable specialist agents that remain effective with smaller deployment models.

# 论文总结：Grow the Harness, Not the Context

## 1. 核心问题与研究动机

- **背景**：LLM 智能体通过模型推理与外部工具交替执行来完成任务。但在真实部署中，智能体往往不是面对孤立任务，而是**反复处理同一任务族（task family）的实例**，使用相同的模型与工具接口。
- **痛点**：任务目标与观测虽在变，但**周边控制逻辑高度重复**——细化查询、过滤观测、验证进度、错误恢复、决定何时停止等。常规驾驭框架（harness）要么预先硬编码这些行为，要么把它们全部委托给 LLM，导致：
  - 每个控制决策都要一次额外推理调用；
  - 上下文持续膨胀（提示、观测、输出不断累积），增加输入成本，并可能让关键证据更难被利用（长上下文"迷失中间"问题）。
- **核心机会——"驾驭框架成长"（harness growth）**：利用任务反馈，把反复出现的控制转化为**持久的可执行代码**，后续执行直接复用，而不是每次通过在线推理重建。LLM 则保留给任务特定的语义推理。
- **中心研究问题**：如何让一个**没有预定义控制器**的脚手架，从任务反馈中生长，从而不再要求 LLM 重建本可由代码执行的行为？
- **三条设计需求**：
  - **可复用性（reuse）**：训练任务中学到的行为应帮助同分布的未见任务，而非编码实例特解；
  - **上下文高效执行**：减少重复模型调用，避免把例行控制塞进不断增长的上下文，同时在语义关键处保留 LLM 推理；
  - **低先验承诺（low prior commitment）**：初始化时不需要完整控制器（区别于优化已有 harness 或规定结构内合成代码的做法），即从 **strategy-free scaffold（无策略脚手架）** 出发。
- **三项技术挑战**：
  - 什么该变成代码、什么该留给 LLM 调用（确定性可迁移行为 vs. 语义判断）；
  - 如何在**不每次处理整个程序**的前提下优化不断增长的程序（需要把失败定位到有界局部代码面）；
  - 如何避免脆性与回归——局部修复可能编码实例特解或破坏既有能力，且持续优化中局部增益未必能累积（已有工作指出 agent 优化器存在此问题）。

## 2. 方法论：Growing Harness

### 2.1 问题形式化

- 智能体工作流 = 可执行 harness `h` + 固定 LLM 后端 `M` + 固定工具集 `T`。部署形态为 `h(x; M, T)`，决定如何调用模型与工具、维护中间状态、处理观测、恢复错误、终止判断。
- **`M` 与 `T` 固定，harness `h` 是唯一可学习对象**（不更新模型权重）。
- 任务划分为训练集 `D_tr`、门控验证集 `G`、最终评测集 `D_te`；优化器**从不观测 `D_te` 的结果或轨迹**。
- 训练从最小可执行脚手架 `h0` 开始：只暴露任务入口与固定的 LLM/工具接口，无完整手工策略。因其保留对 `M`、`T` 的通用访问，LLM 介导的智能体仍在假设空间内可表示。

### 2.2 核心思想

失败引导的训练范式：**函数级执行轨迹定位失败 → 联合修复一个失败窗口 → 成功优先的留出门控回滚有害编辑 → 接受的编辑累积到同一个共享 harness**。控制结构从任务反馈中涌现，而非预先规定。

### 2.3 关键技术细节

- **函数级执行轨迹（trace）**：
  - 每个任务记录执行图 `G_i = (V_i, E_i)`；节点表示 harness 函数调用、LLM/工具调用、返回或运行时错误，记录操作、输入、输出/错误、父节点、耗时；边表示动态作用域内的调用关系。
  - 轨迹 `τ_i = (x_i, G_i, y_i, o_i, u_i)`，其中 `y_i` 为输出，`o_i ∈ {0,1}` 为基准判定结果，`u_i` 为 token/成本/运行时测量。
  - `F(τ_i)` = 该轨迹中被调用的 harness 函数集合，用于约束优化器可修改的函数范围。

- **失败窗口课程（Failure-Window Curriculum）**：
  - 维护容量为 `K` 的有界失败窗口 `W_t`，每项为 `(x_i, τ_i, a_i)`（任务、最新轨迹、修复尝试次数）。
  - 当前 harness 用未见任务填满窗口；直接成功的任务离开课程。
  - 优化器**联合修复整个窗口的失败**，以鼓励可复用行为；修复后已解决任务 `P_t` 离开，未解决任务 `U_t = W_t \ P_t` 保留新轨迹并递增尝试计数，达到 `R_max` 的任务被淘汰。
  - 窗口演化：`W_{t+1} = {x_i ∈ U_t : a_i < R_max} ∪ F_t`（`F_t` 为新失败）。
  - 优化整窗之前做全状态检查点；若整窗任务耗尽预算仍无修复，则恢复检查点，防止无效修复序列在无即时门控回归时残留。

- **轨迹引导的函数级优化**：
  - 优化器接收 `Z_t = (h_t, {τ_i : x_i ∈ W_t}, E)`，其中 `E` 为离线诊断产物（评测器反馈、检索文档 ID、证据、动作统计、错误等），**这些产物对部署 harness 不可见**。
  - 优化器模型 `M_opt`（可与 `M` 不同）产出**完整可执行候选** `ĥ_{t+1} = O(Z_t; M_opt)`。
  - 可修改集合 `A_t = {main} ∪ ⋃_{x_i∈W_t} F(τ_i)`；可新增可复用辅助函数，但**未出现在轨迹中的既有函数不得改动**；`d_fun(h_t, ĥ_{t+1}) ≤ L`（编辑预算，计修改+新增函数数）。
  - 约束：保持函数签名与运行时接口、不得删除既有函数、不得编码任务标识/期望答案/固定解；候选须能解析编译、暴露入口、满足轨迹范围与编辑预算，否则拒绝。
  - 分工导向：代码承担确定性、可复用控制（解析、校验、状态更新、条件式查询细化、错误恢复、停止）；LLM 保留语义解释、合成、模糊比较、答案生成。

- **候选评估与窗口更新**：
  - 有效候选在整个活跃窗口上重执行，得到已解决集 `P_t` 与未解决集 `U_t`。
  - 候选成为临时 harness，`P_t` 离开窗口，`U_t` 更新计数与轨迹。每次修复都是完整 harness，因此辅助函数与控制逻辑跨轮次**累积**，而非任务特解补丁。
  - 合成/验证失败可重试而不改变 `h_t`；耗尽优化器内部重试上限则恢复最近接受的检查点并停止训练。harness、窗口、任务游标、计数器、检查点元数据均序列化以支持恢复。

- **留出门控验证与事务性回滚**：
  - 在 `h0` 上评估门控集 `G`，此后每解决 `Q` 个任务重新评估。
  - 相对最近接受的检查点 `h_gate`，接受条件为 `SR_G(h_t) ≥ SR_G(h_gate)`；否则**回滚自上次门控以来的整段修复序列**，且不仅回滚代码，还恢复任务游标、失败窗口、计数器与训练记录，使状态与序列开始时一致。
  - 训练流与窗口耗尽后，最后一次门控评估决定最终 `h*`；仅在门控成功率不低于 `h_gate` 时选用当前 harness。
  - **成功优先（success-first）原则**：更低的在线成本不能补偿更低的门控成功率（成本仍记录用于比较）。

### 2.4 算法流程（Algorithm 1 文字版）

1. 初始化 `t=0`，`W_t = ∅`。
2. 若仍有未见任务或窗口非空：用 `h_t` 跑未见任务，收集失败与轨迹直至窗口满或训练流结束。
3. 若窗口为空则终止。
4. 优化器基于 `h_t` 与窗口轨迹产出满足 `d_fun ≤ L` 的轨迹范围候选 `ĥ_t`。
5. 在窗口全部任务上重执行候选，得解决集 `P_t` 与未解决集 `U_t`。
6. 若 `|P_t| < Q`（修复不足）→ 丢弃候选、保留 `h_t`，递增尝试计数、淘汰达 `R_max` 者，继续。
7. 若 `SR_G(ĥ_t) < SR_G(h_t)`（门控回归）→ 同样回滚，继续。
8. 否则接受：`h_{t+1} ← ĥ_t`，窗口置为未解决任务 `U_t`（带新轨迹与递增计数），淘汰达上限者，`t ← t+1`。
9. 循环结束后返回 `h*`。

## 3. 实验设计

- **数据集 / 场景**（互补的两类任务族）：
  - **BrowseComp-Plus**：固定、人工验证检索语料下的深度搜索智能体基准，考察开放域检索与证据合成。

  - 每个基准划分为 **200 训练 / 50 门控 / 50 最终评测**任务，固定随机种子 42。
- **部署模型**：gpt-oss-120b、gpt-oss-20b、Qwen3.5-4B（覆盖 4B–120B）。
- **对比方法**：
  - 通用：**Tool-Calling**（固定、不学习的 ReAct 式工具调用循环）。

- **指标**：成功率（SR）、LLM 调用次数、输入/输出 token、时间、总在线成本。成本公式按请求累加 `(未缓存输入×π_in + 缓存读×π_cache + 输出×π_out)/10^6`，缓存读按与同任务先前请求的最长公共前缀估计，不假设跨任务缓存复用；成本仅含部署智能体 LLM 调用，**排除评测器与离线优化器调用**。

## 5. 实验数量与充分性

- **主实验规模**：2 个基准 × 3 个部署模型 × 3 次独立运行，共 6 个"基准–模型"设置；每个方法在每个设置下报告完整指标（成功率、调用数、token、时间、成本）。
- **消融实验**：在 BrowseComp-Plus 上以 gpt-oss-20b 为部署模型、GPT-5.6-terra 为优化器，对三个核心机制各做一次移除（无函数级引导、无门控验证、无失败窗口），每个配置优化 10 步、在相同 50 任务最终集上单次评估。论文自己也声明该对比是"对这些运行的描述，而非内在难度比较"。
- **收敛分析**：给出训练步 vs. 门控成功率曲线（图 3），以及消融变体的 10 步轨迹（图 4）。
- **额外分析**：图 5 给出与 Tool-Calling 的任务级效率对比；图 6 对最终学到的 harness 做**事后抽象**，展示 BrowseComp-Plus 的共享检索-验证流水线与 WebArena-Verified 的分层浏览器控制程序。
- **充分性与公平性评价**：
  - 优点：跨两个差异较大的任务族、跨 4B–120B

- 优点：跨两个差异较大的任务族、跨 4B–120B 三个规模部署模型、每配置 3 次独立运行并报告置信区间，任务划分固定随机种子且优化器不接触最终评测集，比较方法与本文方法共享部署模型、任务划分、工具与评测协议，公平性较好。
  - 局限：消融仅在单一基准（BrowseComp-Plus）、单一部署模型（gpt-oss-20b）与单次评估下进行，且论文自陈"是对这些运行的描述，而非内在难度比较"，因此无法区分各机制的贡献是否在其他设置下同样成立；每配置仅 3 次运行、最终集仅 50 任务，任务级 cluster bootstrap 虽缓解了方差估计问题，但绝对样本量仍偏小；成本核算排除离线优化器与评测器开销，使得"是否值得"这一核心经济性判断无法从报告数字直接得出。

## 6. 主要结果

- **成功率**：在两个基准上，Growing Harness 相对 Tool-Calling 基线普遍取得更高成功率，且在多数"基准–部署模型"设置中优于领域专用方法（BrowseComp-Plus 上的 Self-Ask、IRCoT；WebArena-Verified 上的 WebDreamer、AgentOccam）。成功率提升在较小部署模型上通常更明显，说明生长出的控制代码在一定程度上弥补了模型能力不足。
- **在线效率**：方法在提高成功率的同时减少了每任务的 LLM 调用次数与输入 token，主要因为重复出现的查询细化、观测过滤、进度校验与终止判断被固化为代码，不再每步触发额外推理；输出 token 的下降相对温和，因为语义合成仍由 LLM 承担。由于成本核算按任务内最长公共前缀估计缓存读、不假设跨任务缓存复用，报告的成本是相对保守的估计。
- **任务级效率分布**：图 5 显示，相对 Tool-Calling 的效率优势并非均匀分布，而是在需要多轮检索/多步交互的任务上更集中；简单任务上两者差距缩小，因为此时控制开销本就占比不高。
- **收敛行为**：门控成功率随训练步数总体上升，但呈阶梯式而非单调平滑上升，与"失败窗口 → 联合修复 → 门控接受/回滚"的事务性更新方式一致；回滚事件对应曲线上的平台或短暂回落。
- **消融结论**（BrowseComp-Plus / gpt-oss-20b，10 步优化）：
  - **去掉函数级引导**（改为整程序级或无轨迹定位的修改）：优化器需在更大的代码面上搜索，修复效率下降，门控成功率提升更慢且更易引入回归；
  - **去掉门控验证**：短期在线指标可能改善，但最终成功率下降，验证了"成功优先"原则的必要性——低成本不能补偿低成功率；
  - **去掉失败窗口**（改为逐任务修复）：学到的控制更接近实例特解，跨任务复用性变差，成功率提升受限。
- **学到行为的定性形态**（图 6 事后抽象）：BrowseComp-Plus 上生长出共享的"检索—验证"流水线（查询改写、结果去重与过滤、证据充分性校验、条件式再检索、终止判据）；WebArena-Verified 上生长出分层的浏览器控制程序（站点识别、动作空间约束、观测压缩、失败重试与状态恢复）。这些结构在 `h0` 中并不存在，是训练过程中从失败反馈里涌现的。

## 7. 局限与讨论

- **离线优化成本未量化**：论文明确将优化器调用排除在成本之外，只在结论中定性指出方法的价值取决于"复用学到的 harness 能否抵消离线优化开销"。对于任务族规模小或实例多样性高的场景，这一前提可能不成立。
- **可迁移范围**：harness 在同一任务族内复用，跨族迁移能力未被研究；任务族边界如何界定、窗口与门控集如何在新族上重建，均属开放问题。
- **函数级可修改集合的保守性**：未出现在窗口轨迹中的既有函数不可改动，这限制了"重构式"改进（如跨函数合并逻辑），可能使 harness 结构受早期修复路径锁定。
- **依赖轨迹质量与诊断产物**：优化器依赖离线诊断产物（评测器反馈、检索文档 ID、动作统计等），这些产物不可用于部署 harness；若诊断信号稀疏或误导，失败定位会退化。
- **回滚粒度较粗**：门控回归时回滚自上次门控以来的整段修复序列，虽保证了状态一致性，但可能一并丢弃其中有效的局部改进。
- **评估规模**：最终集 50 任务、每配置 3 次运行，对小幅度提升的分辨能力有限；置信区间较宽时应谨慎解读排序。

## 8. 结论与启示

- 论文提出的核心命题是：面对反复出现的同一任务族，**应让脚手架（harness）成长，而非让上下文膨胀**。反复出现的控制决策应被编译为持久、可执行的代码并跨实例复用，LLM 的推理预算则集中投向任务特定的语义判断。
- 方法以"函数级执行轨迹定位失败 → 联合修复失败窗口 → 成功优先的留出门控与事务性回滚 → 接受的编辑累积到同一共享 harness"构成闭环，在无预定义控制器（strategy-free scaffold）的前提下让控制结构从任务反馈中涌现。
- 实验支持两点：其一，生长出的 harness 在两类差异较大的智能体任务族上提升了成功率；其二，同时降低了每任务的 LLM 调用次数与输入 token，表明"可复用代码替代例行推理"在效率上可行。
- 更广义的启示：智能体系统的能力增长可以发生在**模型之外的可执行结构**上，而不必依赖权重更新或上下文堆积；由此带来的问题是——离线优化开销、任务族边界、以及"生长"过程中如何避免锁定与回归——这些都构成后续研究的直接方向。
