## 摘要
即使具备完全可观测性和以对象为中心的状态，任务与运动规划（TAMP）问题仍然很困难，因为离散决策与几何、运动学和动力学约束紧密耦合。广义 TAMP 通过利用问题实例之间的规律性来减少新实例上的规划开销，从而应对这一困难。然而，现有方法需要大量针对 TAMP 的专门工程。我们研究编码智能体能否通过合成可跨实例泛化的程序来自动化这一过程。给定任务描述和模拟器访问权限，每个智能体在固定合成预算内开发程序时自行选择如何与环境交互。随后程序被冻结，并在未见过的实例上评估。我们在来自 KinDER 和 PDDLStream 的 28 个模拟环境中评估 Claude Code（Opus 5）和 Codex（GPT-5.6 Sol 和 GPT-6 Astra），其对象数量超出原始基准中评估的数量。在所有程序合成方法中，我们在各 100 个留出实例上评估了 980 个生成程序，共计 98,000 个评估回合。总体而言，我们发现编码智能体在广义 TAMP 上出乎意料地有效：在可提供规划器的 16 个环境中，三种智能体配置的平均成功率均优于手工设计的规划器、一次性生成以及基于 LLM 的广义规划基线（56% 至 95%，而规划器为 47%）。随着对象数量增长，智能体的程序保持比规划器更高的成功率，且平均每个实例的计算量少一个数量级。日志显示，智能体利用交互来校准物理模型、测试边缘情况并改进策略。我们发布所有代码，包括提供给智能体的完整提示。这些发现表明，编码智能体是广义 TAMP 的一个强基线。

## Abstract
Task and motion planning (TAMP) problems remain difficult even with full observability and object-centric states because discrete decisions are tightly coupled to geometric, kinematic, and dynamic constraints. Generalized TAMP addresses this difficulty by exploiting regularities across problem instances to reduce planning effort on new instances. However, existing methods require substantial TAMP-specific engineering. We investigate whether coding agents can automate this process by synthesizing programs that generalize across instances. Given a task description and simulator access, each agent chooses how to interact with the environment while developing a program within a fixed synthesis budget. The program is then frozen and evaluated on unseen instances. We evaluate Claude Code (Opus 5) and Codex (GPT-5.6 Sol and GPT-6 Astra) on 28 simulated environments from KinDER and PDDLStream, with object counts beyond those evaluated in the original benchmark. Across all program synthesis methods, we evaluate 980 generated programs on 100 held-out instances each, 98,000 evaluation episodes in total. Overall, we find that coding agents are surprisingly effective at generalized TAMP: all three agent configurations outperform hand-engineered planners, one-shot generation, and an LLM-based generalized planning baseline in mean success (56% to 95% versus 47% for the planners, on the 16 environments where a planner is available). As object counts grow, the agents' programs maintain higher success than the planner, using an order of magnitude less computation per instance on average. Logs show agents using interaction to calibrate physical models, test edge cases, and refine strategies. We release all code, including the full prompts given to the agents. These findings suggest that coding agents are a strong baseline for generalized TAMP.

## 2. 方法论：AgenticGenPlan

### 2.1 问题形式化

- 研究**有限视野、目标导向的 MDP**：$M = \langle \mathcal{S}, \mathcal{A}, P, R, \rho, H \rangle$，其中 $\mathcal{S}$、$\mathcal{A}$ 为状态与动作空间，$P$ 为转移模型，$R$ 为稀疏奖励，$\rho$ 为初始状态分布，$H$ 为视野。
- 状态**完全可观测且以对象为中心**：每个带类型对象映射到描述位姿、几何、关节构型、速度等属性的实值特征向量。
- 环境 = MDP + 任务描述 $d$；$\rho$ 生成物体数量、构型、几何各异的实例。
- **仿真器访问**：通过 `reset` 采样 $s_0 \sim \rho$，通过 `step` 从 $s_t$ 执行 $a_t$ 得到 $s_{t+1} \sim P(\cdot \mid s_t, a_t)$ 及奖励和终止信号。
- **合成与评测分离**：学习阶段在固定预算内产出程序；评测阶段程序被冻结，**不再调用任何 LLM 或智能体**，在隐藏的初始状态上评测。程序可维护内部状态，诱导策略记为 $a_t = \pi(h_t)$，$h_t$ 为交互历史。
- **主指标**：成功率（在视野 $H$ 与墙钟时限 $\tau$ 内到达目标的概率）；辅助指标为**每实例的规划/决策计算时间**（不含合成时间与环境推进时间）。

### 2.2 核心思想

- 给定任务描述 $d$ 与仿真器访问权，**编码智能体在固定合成预算内自行决定如何与环境交互**（写代码、跑实验、探测状态、渲染图像），据此开发并测试程序，最终返回**单个程序**。
- 主设置中，智能体**不获得环境源代码，也不获得任何人工设计的 TAMP 谓词、算子、采样器或技能**。

### 2.3 关键技术细节

- **智能体后端**：Claude Code（Opus 5，high）与 Codex（GPT-5.6 Sol，medium；GPT-6 Astra，high）。所有基线也用 Opus 5，以保证同模型比较。
- **沙箱隔离**：智能体运行在 Docker 容器内，独立文件系统、无网络。主设置中沙箱极简，**只有 Python 解释器加 NumPy 和 SciPy**，迫使智能体生成端到端程序而非依赖现有库。通过红队测试验证隔离（尝试读取环境源码、导入禁用库、访问主机或网络）。
- **初始提示**：包含环境名称、任务/观测空间/动作空间/目标的描述，说明物体数量可变且方案需支持任意合法数量，并告知评测时限 $\tau$。**不提供任何手写 TAMP 组件**。
- **仿真器接口**：智能体只能看到一个 client，其 `reset`、`step` 以及状态渲染等辅助函数由容器外的 server 实现，不可访问内部实现。
- **程序接口**：策略实现为一个类，含 `reset`（回合初始化）与 `get_action`（计算 $a_t = \pi(h_t)$）。**不约束其内部抽象或求解策略**（可自选搜索、优化、采样或任务专用流程）。
- **版本管理**：要求智能体在每次测试前把程序提交到 git 仓库，以便回放每个修订版本、追踪程序演化轨迹。
- **+ source 设置（参考对照）**：把环境源码放入容器，智能体可阅读实现、导入辅助函数（如逆运动学求解器），甚至**任意设置状态**，从而获得对转移模型的生成式访问能力。用于衡量"完全知晓环境"时的表现上限。

### 2.4 基线方法

- **TAMP 规划器**：符号搜索 + 采样满足连续约束，使用基准官方实现的手写谓词、算子、采样器与运动规划器（技能），**每个评测实例重新规划**；28 个环境中只有 16 个提供规划器。
- **LLMGenPlan**（复现）：非智能体的 LLM 广义规划方法，使用 Opus 5，链式思维提示、关闭 thinking，**不能使用工具或访问文件系统**，但获得完整环境源码；写出程序后由固定流水线执行并返回**预定义反馈**（异常与 traceback、非法动作、未解实例及其随机种子）。预算与智能体相同，但**不能自主选择运行什么、不能写自定义测试**。
- **One-shot**：LLMGenPlan 生成的第一个程序，用于评估无任何改进循环时的表现。

## 6. 主要结论与发现

### 6.1 定量结论

- **三种智能体配置均优于手工规划器**：在 16 个有规划器的环境上，规划器均值 47%，Claude Code/Opus 平均 82%（约 1.7 倍），Codex/GPT-6 Astra 达 95%，GPT-5.6 Sol 为 56%。
- **分族表现（Astra）**：Kinematic2D 99%、Dynamic2D 97%、Kinematic3D 93%、Dynamic3D 65%、PDDLStream 接近 100%；Opus 对应为 96%、92%、90%、45%、78%。
- **逐环境胜出数**：Astra 在 15/16 个有规划器的环境中超过规划器，Opus 12/16，Sol 9/16。
- **泛化性**：随着物体数量增长，智能体程序保持更高成功率，且**平均每实例计算量比规划器低约一个数量级**（Opus 2.1 s、Astra 0.5 s vs 规划器 29 s）。
- **对基线**：三种智能体在 28 个环境的平均成功率上均优于 One-shot 与 LLMGenPlan。
- **源码访问有帮助**：Opus 从 74% 提升到 84%，Astra 从 86% 提升到 95%。但**源码本身不充分**：同样拿到源码、同样模型、同样预算的 LLMGenPlan 只有 28%，Opus + source 在 28 个环境中的 27 个更高，说明增益主要来自**可运行、可测试、可迭代的 agentic 循环**。
- **智能体间比较**：Astra > Opus（28 个环境中 20 个更高），但其中 11 个环境里 Opus 的最佳程序不逊于 Astra
