## 摘要
调用工具的 LLM 智能体正越来越多地部署于企业应用中。然而，有效的评估与优化需要高质量、多样化的任务数据集，而由于隐私及其他限制，这类数据集往往难以获取。现有的合成任务生成方法通常生成通用任务，忽略了智能体的底层状态或数据库，未能反映真实世界使用场景的多样性。我们提出 EdgeGen，一种合成任务生成框架，它从智能体的规范中提取合规规则，并利用这些规则生成基于数据库、旨在违反这些规则的边缘案例任务。与现有合成数据生成技术结合后，EdgeGen 可通过微调和测试框架优化来提升智能体。由此形成的流程构成一个完全自动化、无需人工标注的闭环系统。在 tau2bench 航空领域上，使用 EdgeGen 生成的数据进行微调可带来 2% 至 42% 的平均进度稳定提升，而其他基线方法在某些模型上则出现性能下降。另一方面，在测试框架优化方面，对于 Gemma-4-e4b 模型，我们的方法相较于人工构建的测试框架和基础测试框架，平均进度分别提升 10% 和 30%。

## Abstract
Tool-calling LLM agents are increasingly deployed in enterprise applications. However, effective evaluation and optimization require high-quality, diverse task datasets that are often difficult to obtain due to privacy and other constraints. Existing synthetic task generation methods often produce generic tasks that ignore an agent's underlying state or database and fail to reflect real-world usage diversity. We propose EdgeGen, a synthetic task generation framework that extracts compliance rules from an agent's specification and uses them to generate database-grounded edge-case tasks designed to violate these rules. When combined with existing synthetic data generation techniques, EdgeGen enables agent improvement through finetuning and harness optimization. The resulting pipeline forms a fully automated closed-loop system that requires no human annotation. Finetuning on data generated by EdgeGen yields a consistent mean progress improvement of 2 percent to 42 percent on tau2bench airline domain, while other baseline methods show degradation for some models. On the other hand, for harness optimization, our method shows a mean progress improvement of 10 percent and 30 percent over the human-curated and base harnesses, respectively, for the Gemma-4-e4b model.

## 1. 核心问题与研究动机

- **背景**：工具调用型 LLM 智能体正被广泛部署到企业系统中，需要自主调用工具、查询数据库、执行多步工作流，同时遵守复杂的业务政策与运营约束。
- **核心痛点**：
  - 真实生产日志因隐私问题通常不可获取；人工构造现实任务成本高、难规模化。
  - 现有合成任务生成方法（Self-Instruct、APIGen、ToolACE、TaskBench、FuncBenchGen 等）多聚焦**通用函数调用任务**，忽略了智能体的底层状态与数据库，也无法反映真实使用场景的多样性。
  - 企业场景下，正确性不仅取决于"是否调用了正确的工具"，还取决于**是否遵守领域业务规则**（如拒绝不符合退款条件的请求、按会员等级适用行李政策等），这类行为本质上是**有状态、依赖政策**的，通用合成任务几乎不覆盖。
- **覆盖度问题**：在窄化或模板化评测上表现良好的智能体，部署后仍会在罕见边缘案例上失败。鲁棒评测需要多样化、**基于真实数据库状态落地**的场景，系统性地探测失败模式，而非只测"顺利路径（happy path）"。
- **关键区分**：不仅是"如何执行工作流"，更是"何时应当拒绝"。同一取消请求在不同数据库状态下可能应批准或应拒绝，因此有信息量的边界案例必须把请求与一个**可验证期望响应的确定状态**配对。
- **整体含义**：作者提出 **EdgeGen**——从智能体规范文档中抽取合规规则，据此生成**刻意违反规则的、数据库落地的边缘案例任务**，并与合成数据库生成结合，构成**完全自动化、无需人工标注的闭环**智能体改进流水线（微调 / harness 优化）。

## 2. 方法论

### 2.1 问题形式化

- 智能体部署由三要素刻画：
  - **工具集** `T = {t1, ..., tn}`，每个工具 `ti` 有输入 `In(ti)` / 输出 `Out(ti)` 签名；
  - **政策文档** `P`（自然语言行为约束）；
  - **关系数据库** `D`（智能体通过读写交互）。
- 将 `P` 形式化为原子合规约束集合 `R = {r1, ..., rn}`，每条规则是一个可验证的行为断言（如"修改预订前必须验证用户身份"）。规则由 LLM 自动抽取；为控制枚举规模，**只保留最重要的 5 条规则**，故最多 `2^5 = 32` 个子集（再经可行性过滤）。
- **测试用例定义**：`x = ⟨q, w, A, S⟩`
  - `q`：基于数据库具体值落地的用户任务描述；
  - `w = {ti, ..., tk}`：有序工具调用序列（工作流）；
  - `A = {a1, ..., an}`：自然语言断言集合，作为评测目标；
  - `S ⊆ R`：该用例意图违反或压力测试的政策规则集合。
- **有效性两条判据**：
  1. **数据落地（Data Grounding）**：`q`、`w` 所用的标识符与数据库事实必须被 `D` 支持（刻意虚假的用户主张、待创建的值不在此列）；
  2. **场景可行性（Scenario Feasibility）**：可用工具与数据库状态必须允许**期望的政策合规响应**，包括对禁止操作的拒绝。
  - 这两条针对的正是既有方法的两大失败模式：**幻觉标识符**与**不可行的工具序列**。

### 2.2 五阶段测试用例生成流水线

- **Stage 1 — 工具图构建与路径采样**
  - 构建有向依赖图 `G = (V, E)`，`V = T`，边定义为数据类型兼容：`(ti, tj) ∈ E ⟺ Out(ti) ∩ In(tj) ≠ ∅`。
  - 关键改进：可行工作流还依赖政策 `P`（政策常规定"某动作前必须先调用某工具"），这类约束过于复杂难以显式编码，因此用 LLM 在 `P` 条件下选择有效工具集，即 `w ∼ p(w | P)`。
  - 采样三类结构：**NODE**（单工具）、**CHAIN**（线性组合）、**DAG**（分支多工具工作流）。

- **Stage 2 — 违规场景生成**
  - 定义合规条件空间为规则集的**幂集** `S ⊆ R, S ∈ P(R)`；每个子集 `S` 表示同时被强制/被违反的约束集合。
  - `|S|` 控制复杂度：`|S| = 0` 即 happy path；`|S| = 1` 隔离单一政策约束；`|S| ≥ 2` 生成需同时处理多条交互规则的更难场景。
  - **可行性过滤**：`P*(R) = {S ∈ P(R) | Feasible(S)}`，`Feasible(S)` 由 LLM 一致性检查器实现，剔除逻辑上互斥的规则组合。

- **Stage 3 — 场景感知的数据库采样**
  - 由**迭代式 SQL 智能体**执行接地过程：`ρ ∼ π_SQL(D | w, S)`，`ρ` 是实例化该场景的数据库行集合。
  - 若找不到有效 `ρ`，则重新采样 `w` 与 `S`。SQL 智能体以**只读**方式（`sqlite3 mode=ro`、仅 SELECT）通过 JOIN 沿外键检索真实实体，并输出 `_feasibility` 字段说明可执行的操作与约束。

- **Stage 4 — 测试用例生成**
  - 给定 `P`、`w ∼ p(w|P)`、`S ∈ P*(R)`、接地状态 `ρ ⊂ D`，用 LLM 生成任务摘要 `q`（含数据库中的具体标识符、时间戳等实体）与自然语言断言 `A`（编码给定约束下期望的智能体响应，如因政策违规而拒绝）。

- **Stage 5 — 验证**
  - 两项独立检查：(1) **数据落地**——用确定性 SQL 查询校验标识符与数据库事实（含用户主张与存储状态的矛盾）；(2) **场景可行性**——期望响应在现有工具与状态下可达成（创建类操作的前置条件须存在；拒绝类场景的状态须确实触发拒绝理由）。
  - **两项均通过才接纳**，否则丢弃并从 Stage 1 以新采样的 `w`、`S` 重来。

- **数据库生成**：合成数据库由 **Generalist Populator**（LLM 智能体）填充，它调用 API 写操作而非直接改行，每次操作前检查前置条件，被拒操作不改变状态，重复运行产生一致的关系数据库。该检查仅涉及 API 强制的前置条件，而非全部行为政策；EdgeGen **对数据库来源不敏感**，可用任何兼容的关系数据库。

### 2.3 复杂度感知生成

- **两条正交可控轴**：
  - **结构复杂度**：通过工作流分布控制（提高 CHAIN / DAG 采样率）；
  - **场景复杂度**：由 `|S|`（违规规则数）决定。
- 两轴共同定义一个**结构化难度覆盖空间**，可诱导出从简单数据库查找到多步多政策决策的可控难度分布。
