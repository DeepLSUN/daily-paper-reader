## 摘要
非技术利益相关者往往无法编写从业务数据库中提取洞见所需的 SQL。我们构建并评估了一个端到端弥合这一差距的 Text-to-SQL 智能体：一个六节点 LangGraph StateGraph 会检查问题相关性、获取实时模式、生成 PostgreSQL、通过试运行进行验证、在失败时重试、执行查询，并以通俗英语叙述结果集。该智能体仅使用提示工程；未对任何模型进行微调。我们在 Chicago Crime 数据集（约 850 万条记录、22 个属性）上，使用包含 100 个自然语言问题及其真实 SQL 的人工基准进行评估，该基准按 30 个简单、40 个中等和 30 个困难项目分层。比较同一智能体的两个提示版本后，修订系统（V2）达到了 93% 的有效 SQL 率（此前为 87%），在混合关系等价度量下执行准确率为 60%（此前为 47%；在严格 JSON 匹配下从 12% 提升至 19%），平均合成质量为 4.34 分（满分 5 分，此前为 3.91）。最大的单一驱动因素是从系统提示中移除了 LIMIT 10 指令，该指令此前会截断多行答案。错误分析将剩余失败归因于相关性检查器的误拒、问题语义模糊以及免费层 API 速率限制，而非语言生成步骤。我们未报告与外部基线系统或公共基准的比较；该研究是一项单模型工程评估。

## Abstract
Non-technical stakeholders frequently cannot write the SQL needed to extract insights from operational databases. We built and evaluated a Text-to-SQL agent that closes this gap end to end: a six-node LangGraph StateGraph checks question relevance, fetches the live schema, generates PostgreSQL, validates it with a dry run, retries on failure, executes the query, and narrates the result set in plain English. The agent uses prompt engineering only; no model was fine-tuned. We evaluated it on the Chicago Crime dataset (approximately 8.5 million records, 22 attributes) against a hand-built benchmark of 100 natural language questions with ground-truth SQL, stratified into 30 Easy, 40 Medium and 30 Hard items. Comparing two prompt revisions of the same agent, the revised system (V2) reached a Valid SQL Rate of 93% (from 87%), an Execution Accuracy of 60% under a hybrid relational equivalence metric (from 47%; 19% from 12% under strict JSON matching), and a mean Synthesis Quality of 4.34 out of 5 (from 3.91). The single largest driver was removing a LIMIT 10 instruction from the system prompt, which had been truncating multi-row answers. Error analysis attributes the residual failures to relevance-checker false rejections, ambiguous question semantics, and free-tier API rate limits rather than to the language generation step. We report no comparison against an external baseline system or a public benchmark; the study is a single-model engineering evaluation.

## 2. 方法论

### 2.1 核心思想
- 采用**六节点 LangGraph StateGraph**，以迭代循环弥补可及模型的推理局限，并增加自然语言合成步骤，完整闭合"提问—取数—解读"的操作链路。
- 仅使用**提示工程**，不微调任何模型。

### 2.2 六节点流程（文字化算法）
共享状态携带：`question`、`sql_query`、`schema`、`results`、`answer`、`error_log`、`retry_count`、`is_relevant`。

1. **Relevance Checker（相关性检查）**：正则 + 关键词快速路径（<5 ms），输出 `is_relevant` 标志；相关则路由至 Schema Fetcher，否则至 END。
2. **Schema Fetcher（模式获取）**：调用 `SQLDatabase.get_table_info()` 获取实时数据库模式，耗时 50–200 ms。
3. **Query Generator（查询生成）**：LLM 生成 SQL；严格系统提示要求双引号标识所有标识符、禁止 DML、无法回答时返回 `INVALID_REQUEST`；嵌入固定（非检索式）少样本示例；`temperature=0`，`max_tokens=500`。
4. **Query Validator（查询校验）**：`EXPLAIN` 试运行 + DML 正则检查；失败时递增重试计数（最多 3 次）。
5. **Query Runner（查询执行）**：`db.run(fetch="all")`；**V1 系统提示将传给合成步骤的结果上限设为 10 行，V2 移除了该上限**。
6. **Answer Synthesizer（答案合成）**：LLM 将 JSON 结果总结为通俗英语；被拒查询返回预设提示信息。

### 2.3 条件边与安全约束
- 相关性检查器 → Schema Fetcher（相关）或 END（不相关）。
- 校验失败 → 回退至 Query Generator（最多 3 次），仍失败则落入 Answer Synthesizer 并给出用户友好的错误信息。
- 强制只读访问，拒绝 `INSERT/UPDATE/DELETE/DROP/ALTER`；范围限定于 Chicago Crime 数据库；支持 `JOIN`、`GROUP BY`、`HAVING`、`ORDER BY`、`LIMIT` 与子查询。

### 2.4 训练/优化策略
- 无微调，仅四阶段迭代提示工程：
  1. 最小基线提示（高语法错误、DML 泄漏）；
  2. 显式 PostgreSQL 约束（双引号标识符、阻断 DML）+ 后生成正则校验；
  3. 嵌入真实 Chicago Crime 列名与示例查询，减少幻觉、改善 JOIN 与 LIMIT 准确性；
  4. 分离相关性检查与查询生成，加入基于 `EXPLAIN` 的重试校验与细化错误信息。

### 2.5 关键超参数
- 温度 0（确定性、可复现）；最大 token 500；重试上限 3；相关性阈值 = 2 个以上动作动词 + 数据上下文；结果行上限 V1=10 / V2=无；模型 `openai/gpt-oss-120b`（32k 上下文）。

### 2.6 数据预处理
- 列名统一为 `UPPERCASE_SNAKE`，消除 LLM 双引号开销；字符串时间戳转 `TIMESTAMP`；坐标转 `FLOAT8`。
- 空值按列组处理：类别型改为 "OTHER OFFENSE"；地理型缺失时用所属 BEAT 均值替代；时间型用同 YEAR 高频日期填补；逻辑型标记为 "Unknown"。

## 3. 实验设计

### 3.1 数据集与场景

- 通过 Airflow 每周 ETL 摄入 Docker 化 PostgreSQL v14+；每周模式校验确认结构一致性。
- 假设模式在周度校验间稳定，实时查询存在 7 天数据刷新滞后。

### 3.2 Benchmark
- **手工构建的 100 题自然语言基准**，配真实 SQL：
  - 30 题 Easy（单表聚合，如 COUNT/SUM）
  - 40 题 Medium（JOIN、GROUP BY + HAVING、时间范围分析）
  - 30 题 Hard（窗口函数、CTE、复杂日期运算）

### 3.3 评价指标
- **Execution Accuracy (EX)**：结果集与真值一致的比例（预设目标 85%）。

- **Valid SQL Rate (VSR)**：语法有效且可执行查询比例（目标 95%）。
- **Synthesis Quality (SQ)**：1–5 分 Likert 均值，人工标注 + LLM-as-a-Judge 混合（目标 ≥4.0）。

### 3.4 对比对象
- 计划中的两个外部基线（规则词法匹配器、无数据库特定规则的零样本 LLM）**未运行**。

- 评估四阶段：查询执行、与 PostgreSQL 副本比对（5 秒超时）、指标打分、按失败类型与难度层归类错误。

## 6. 主要结论与发现

- **V2 全面优于 V1**：
  - VSR：87% → **93%**
  - EX（混合度量）：47% → **60%**；严格 JSON 匹配：12% → **19%**
  - SQ：3.91 → **4.34**（V2 超过 4.0 目标，V1 差 0.09）
- **分层表现**：
  - Easy：V1 93%/80%/4.53 → V2 **100%/97%/5.00**
  - Medium：V1 78%/35%/3.62 → V2 **92%/43%/4.20**
  - Hard：V1 93%/30%/3.67 → V2 87%/47%/3.87（VSR 因限流下降）
- **最大单一驱动因素**：从系统提示中**移除 LIMIT 10 指令**，此前该指令会截断所有多行结果，Hard 层窗口函数输出受影响最重（如"每个社区区域前 3 类犯罪"需 77 区共 231 行）；Hard 层严格 JSON 匹配 EX 由 7% 升至 17%。
- **相关性检查器改进**：加入领域词（"breakdown"、"distribution"、"statistics"）与动作动词（"calculate"、"identify"），主要贡献 Medium 层 VSR 提升（78%→92%）。
- **瓶颈定位**：SQL 生成质量而非语言生成是主要瓶颈——SQL 正确时合成器质量稳定（V2 中 85/100 行 SQ ≥ 4）。
- **SQ 分布迁移**：满分 5 由 58→69，1 分由 15→8，3 分由 10→3；SQ≤2 总数由 21→12。
- **失败根因**：V1 相关性误拒 10→3（降 70%）；LIMIT 截断 4→0；V2 新增 4 例 API 限流失败（基础设施问题，非 SQL 逻辑）；聚合解释错误 4→4；分类逻辑错误 1→1；完全错误 2→1。
- **残余 V2 失败模式**：相关性误拒（3 题）、聚合范围歧义（ID 81：全局平均 vs 按街区平均）、时间歧义（ID 90：年内日期聚合 vs 具体日历日期，1 月 1 日 5,394 vs 2020-05-31 1,901）、派生指标约定不明（ID 87、90："夜间时段"定义分歧）。

## 7. 优点

- **端到端闭环设计**：不仅生成 SQL，还执行并合成通俗英语答案，真正面向非技术用户。

- **工程可复现性**：Docker 容器化、Airflow 周度 ETL、版本明确的软件栈、温度 0 保证确定性。
- **错误分析细致**：按失败模式逐条计数并跨版本对照，定位到具体题目 ID，归因清晰。
- **学术诚实**：明确声明无外部基线

## 8. 局限与不足

- **评估范围狭窄**：仅使用 Chicago Crime 单一数据集、单一模型 `openai/gpt-oss-120b`、单次运行，未在 Spider、BIRD 等公共 Text-to-SQL 基准上验证，也未与 DAIL-SQL、DIN-SQL、MAC-SQL 等已有方法对比。
- **缺乏严格消融**：V1 到 V2 同时改动多处（移除 LIMIT、增强相关性检查、调整提示），无法分离各改动的独立贡献；LIMIT 移除被事后归因为最大驱动因素，但并非受控实验。
- **统计严谨性不足**：未报告多次运行的方差、置信区间或显著性检验；SQ 评分依赖 LLM-as-a-Judge 与人工标注，但未收集标注者间一致性或人机一致性统计，评分误差未被量化。
- **基准覆盖偏差**：100 题手工基准在系统开发前构建，边界词汇题（如 ID 49、66、68）暴露覆盖缺口；难度分层虽明确，但题量较小，Easy/Medium/Hard 分别为 30/40/30，Hard 层仅 30 题，指标波动敏感。
- **泛化性受限**：系统深度绑定 Chicago Crime 数据库的列名、取值与领域词汇，迁移到其他数据库需重新设计少样本示例与相关性检查词表；周度模式校验虽保证结构稳定，但实时查询存在 7 天数据刷新滞后。
- **基础设施依赖明显**：Groq 免费层限流（30 req/min、8,000 TPM）直接导致 V2 Hard 层 VSR 从 93% 降至 87%，新增 4 例 API 限流失败，说明结果受外部服务可用性影响，而非纯算法因素。
- **安全与合规讨论有限**：仅强制只读、拦截 DML，未涉及隐私、PII 脱敏、审计日志、多租户隔离等生产级数据库智能体所需的安全议题。

## 9. 启示与未来方向

- **对可及模型的提示工程仍有效**：在不微调模型的前提下，通过四阶段迭代提示工程，可将 VSR 从 87% 提升至 93%、EX 从 47% 提升至 60%，说明系统化提示修订对中小规模或本地部署模型具有实用价值。
- **端到端闭环是差异化方向**：将 SQL 生成、执行与自然语言合成统一编排，直接服务非技术用户，比仅返回表格的系统更贴近运营智能场景。
- **多行结果截断是隐蔽陷阱**：系统提示中人为设置 `LIMIT 10` 会系统性破坏多行聚合与窗口函数结果，移除后 Hard 层严格 JSON 匹配 EX 从 7% 升至 17%，提示设计需避免全局性输出约束。
- **相关性检查可显著影响 VSR**：加入领域词与动作动词后，Medium 层 VSR 从 78% 升至 92%，表明前置路由质量对整体执行成功率有放大效应。
- **未来工作应优先补齐评估短板**：在 Spider、BIRD 等公共基准上与外部基线对比；多模型、多数据集、多次运行并报告方差；开展严格消融，分离 LIMIT、相关性检查、少样本示例、重试机制各自的贡献；收集人工标注一致性统计。
- **技术增强方向**：引入检索增强生成、模式链接、自一致性投票、查询计划缓存、更鲁棒的重试与回退策略；探索对小模型进行轻量微调以降低对 Groq 等外部推理服务的依赖；扩展至多数据库、多语言、多轮对话场景。
- **工程与安全并重**：生产化需考虑限流退避、成本控制、PII 脱敏、审计追踪、权限隔离与结果可解释性。

## 10. 总体评价

本文是一份诚实、细致但科学严谨性有限的**系统与评估报告**。其核心价值不在于提出新的 Text-to-SQL 架构，而在于展示了一条可复现的工程路径：用 LangGraph 编排六节点智能体，通过迭代提示工程与自纠错循环，让可及模型在特定领域数据库上完成“提问—取数—解读”的端到端任务。错误分析逐题定位、跨版本对照，具有较强实践参考意义。

然而，由于缺少公共基准、外部基线、严格消融与统计检验，论文无法回答“该智能体相对已有方法处于何种水平”这一关键问题。其结论应被理解为：**在 Chicago Crime 数据集、`openai/gpt-oss-120b` 模型与特定提示修订序列下，V2 优于 V1**，而非普遍性的方法优越性。若后续工作能补齐评估设计并验证跨领域泛化，该架构有望成为低资源 Text-to-SQL 部署的有用起点。
