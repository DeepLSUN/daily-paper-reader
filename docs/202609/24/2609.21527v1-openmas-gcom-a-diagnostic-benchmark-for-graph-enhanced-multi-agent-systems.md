## 摘要
图增强多智能体系统（G-MAS）通过通信图和角色分配来协调大语言模型智能体，这些通信图和角色分配决定了智能体如何交换信息并划分职责。然而，跨系统的最终分数比较混合了模型、通信模式、角色和计算成本方面的差异，使得性能差异难以归因于特定的通信结构、角色分配和信息流。为解决这一评估归因问题，我们提出 OpenMAS-GCom，一个通过受控干预来诊断这些组件如何影响 G-MAS 性能的基准。我们通过协作单元、通信链路、共享中间信息和执行规则来表示系统。OpenMAS-GCom 将原始系统与仅改变一个组件、同时保持任务、模型、提示和预算限制不变的修改版本进行比较。我们重连通信边、移除专家或批评者智能体、将中间消息替换为错误内容，并在执行过程中禁用工作者。该基准在六个领域的 29 个数据集上评估了 17 种单智能体、普通多智能体和图增强配置。我们新增了 400 个 G-MAS-Complex 任务，要求智能体整合来自多个文档的信息、解决冲突记录，并返回带有来源标识符的指定值。实验表明，移除专家后平均损失大于移除批评者后，尽管原始分数相似，错误消息和工作节点故障下的性能下降不同，并且在 G-MAS-Complex 上不同配置取得了最高准确率和每 token 准确率。

## Abstract
Graph-enhanced multi-agent systems (G-MAS) coordinate large language model agents through communication graphs and role assignments, which determine how agents exchange information and divide responsibilities. However, final-score comparisons across systems combine differences in models, communication patterns, roles, and computation costs, making performance differences difficult to attribute to specific communication structures, role assignments, and information flows. To address this evaluation attribution problem, we introduce OpenMAS-GCom, a benchmark for diagnosing how these components affect G-MAS performance through controlled interventions. We represent systems through collaboration units, communication links, shared intermediate information, and execution rules. OpenMAS-GCom compares original systems with versions modified by changing one component while keeping tasks, models, prompts, and budget limits fixed. We rewire communication edges, remove specialist or critic agents, replace intermediate messages with incorrect content, and disable workers during execution. The benchmark evaluates 17 single-agent, ordinary multi-agent, and graph-enhanced configurations on 29 datasets across six domains. We add 400 G-MAS-Complex tasks requiring agents to combine information from multiple documents, resolve conflicting records, and return specified values with source identifiers. Experiments show larger mean losses after specialist removal than after critic removal, different performance degradation under incorrect messages and worker failures despite similar original scores, and different configurations achieving the highest accuracy and accuracy per token on G-MAS-Complex.

## 1. 核心问题与整体含义

- **研究背景**：图增强多智能体系统（G-MAS）通过通信图与角色分配协调 LLM 智能体，决定信息如何交换、职责如何划分。这类系统在数学推理、代码生成、问答等任务上被广泛使用。
- **核心问题（评估归因问题）**：现有评估主要比较最终任务分数，但一个更高的分数可能同时来自更强的模型、更多的智能体、不同的通信链路或角色、更高的算力开销。这些因素在方法间往往同时变化，导致**无法把性能差异归因到具体的组织结构选择**（通信结构、角色组成、信息流）上。
- **核心追问**：当其他评估设置固定时，通信结构、角色组成和信息流如何影响性能？
- **整体含义**：论文提出 OpenMAS-GCom，一个通过**受控组织干预**来诊断 G-MAS 各组件的基准，把系统评估从"比总分"推进到"可归因的组织诊断"，为配置选择与组织设计提供依据。

## 2. 方法论

### 2.1 核心思想
- 将每个 G-MAS 统一表示为可执行组织 **O = (V, E, S, π)**：
  - **V**：可运行的协作单元（含智能体单元 VA 及工具/控制单元）；
  - **E**：允许的有向通信关系；
  - **S**：共享信息与中间状态；
  - **π**：激活、路由、状态更新与终止策略。
- 每个单元声明其角色、局部状态及输入/输出模式，从而把"参与、通信、信息访问、执行决策"四类属性解耦。
- 对比原则：**每次只改一个组织组件**，任务、模型、提示、解析器、路由策略与算力预算全部固定。

### 2.2 执行与记录
- 对输入 xi，执行产生轨迹 **τi = ((vt, mt, at))_{t=1}^{T}**，记录执行的单元、可用消息状态、输出/控制动作。
- 任务得分：**s(F, O_T, T) = (1/N) Σ M_T(P(oi), yi)**，其中 P 为解析器，M_T 为任务指标。
- 同时记录 token 用量、模型调用数、延迟、执行单元与关系、重试次数、终止状态等成本字段。
- 区分"**配置的组织**"（可用单元与关系）与"**执行的轨迹**"（实际使用的单元与关系）。

### 2.3 两阶段诊断流程
- **参考阶段**：执行原始组织，记录预测、轨迹与成本。
- **干预阶段**：修改一个组件后在相同任务上重跑。
- 共享控制集：**C = {D_T, Θ, M_T, P}**（数据、后端/提示/解码/路由/预算、指标、解析器）。
- 配对干预响应：**Δ_r(F, T) = s(F, O'_{r,T}, T) − s(F, O_T, T)**，负值表示修改后性能下降。

### 2.4 四类干预协议
- **结构干预**：有向边交换（u→a, v→b 改为 u→b, v→a），保持智能体集合、入/出度序列、边数与通信预算不变；拒绝自环、重复边、非法角色连接。重连比例取 10%/30%/50%/70%。
- **节点干预**：移除角色节点及其关联边。变体包括 **No critic**、**No specialist**、**Expert only**（仅保留专家诱导子图）。
- **信息干预**：以格式合法但内容错误的上游记录/候选替换原有中间信息，腐蚀率 c ∈ {0, 0.2, 0.4, 0.6, 0.8}，经原图与路由传播到下游。
- **执行干预**：运行中禁用 k ∈ {0,1,2,3,4} 个 worker，从最后有效共享状态经重试/回退/重路由恢复。

### 2.5 评估维度
- **Utility（效用）**：单智能体 vs 普通 MAS vs 图增强 MAS 的任务得分对比。
- **Effectiveness（有效性）**：跨六域与 G-MAS-Complex 各层级的得分与排名。
- **Robustness（鲁棒性）**：绝对分数变化与相对保留率。
- **Efficiency（效率）**：token、调用、延迟、执行节点/边、重试；G-MAS-Complex 上用严格精确匹配（Strict EM）与 **Strict EM/K Tokens**。

## 3. 实验设计

- **G-MAS-Complex（新增）**：400 个冻结的多文档任务，分 4 个难度层级（Medium/Hard/Ultra/Extreme，各 100 个），每任务含查询、源文档、依赖元数据、冲突标注与机器可校验的 JSON 输出契约；答案表示为 **zi = (fi, vi, ri, ℓi, hi, χi)**（字段、值、排序、来源、检查点、校验和约束）。仅当全部字段、值、排名、来源、检查点与校验和同时满足才计为正确。

### 3.2 对比方法（17 种配置）
