## 摘要
大语言模型已成为现代编程助手的核心，但 Claude Code 或 Codex 等最先进系统依赖非常大的云端托管模型，带来显著的计算成本和数据隐私问题。本文研究能否通过将计算负担从推理阶段转移出去，围绕小型开源模型构建一个实用的、完全本地的编程智能体。我们开发了一个面向科学代码理解的检索增强生成（RAG）系统，它将昂贵的离线摄取阶段——解析、结构图构建、LLM 生成的实体解释以及嵌入——与轻量级的在线回答阶段严格分离。该系统在一个包含 100 个问题、涵盖十一个类别的基准上进行了评估，基准基于用 C++ 编写的 IPPL 科学代码库，答案由作为评判者的独立前沿模型评分。在七个回答模型上，我们发现模型家族和检索质量比参数规模更重要，即一个 9B 模型取得了最高平均分（0.795），优于我们流水线中更大的模型，也优于将相同模型嵌入 Claude Code 检索架构后的表现。结果表明，将代码理解前置到一个可复用、面向特定代码库的向量存储中，使小型本地模型能够给出有依据且针对特定代码仓库的答案，从而使该智能体非常适合作为面向内部科学代码库的隐私保护开发工具。

## Abstract
Large language models have become central to modern coding assistants, but state-of-the-art systems such as Claude Code or Codex rely on very large, cloud-hosted models with significant computational cost and data-privacy implications. This work investigates whether a useful, fully local coding agent can be built around small open-source models by shifting the computational burden away from inference. We develop a Retrieval-Augmented Generation (RAG) system for scientific code understanding that strictly separates an expensive offline ingestion stage parsing, structural graph construction, LLM-generated entity explanations, and embedding from a lightweight online answering stage. The system is evaluated on a 100-question benchmark spanning eleven categories over the IPPL scientific codebase written in C++, with answers scored by an independent frontier model as the judge. Across seven answering models, we find that model family and retrieval quality matter more than parameter count, i.e. a 9B model achieves the highest average score (0.795), outperforming both larger models within our pipeline and the same models embedded in the Claude Code retrieval architecture. The results indicate that front-loading code understanding into a reusable, codebase-specialised vector store enables small local models to deliver grounded and repository-specific answers, making the agent well suited as a privacy-preserving development tool for in-house scientific codebases.

# 论文总结：面向科学代码理解的检索增强生成（RAG for Scientific Code Understanding）

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 已成为编程助手的核心，但 Claude Code、Codex、Cursor、Gemini Code Assist 等最强系统依赖**大型云端托管模型**，存在三重障碍：
  - 计算成本高、推理开销大；
  - 数据隐私风险（科学代码库通常私有）；
  - 相关知识分散在多年积累的专用 C++ 代码、数值算法与领域（数学/物理）知识中，难以一次性放入上下文。
- **核心问题**：能否通过**把计算负担从在线推理转移到离线预处理**，围绕**小型开源本地模型**构建一个真正有用、完全本地运行的代码智能体？
- **研究定位**：本文不追求"全功能编码智能体"，而是聚焦**代码理解（code understanding）**——即回答关于仓库结构、API 用法、数据流、算法语义的技术问题。
- **整体含义**：若成立，则可得到一个**隐私保护、零边际成本、可复现**的本地"代码教师"，适用于高校教学、企业内部代码库入职培训等场景。

## 2. 方法论

### 2.1 核心思想
- **严格两阶段解耦**：
  - **离线摄取（Retrieval Preparation）**：解析 → 结构图构建 → LLM 生成实体解释 → 嵌入 → 存入向量库（一次性、算力昂贵）；
  - **在线回答（Inference）**：向量检索 + 元数据重排 + 查询意图路由 + 结构扩展 + 提示构建（轻量）。
- **关键假设**：当回答模型很小时，**预先准备的检索上下文质量**比检索时的智能体循环更重要。

### 2.2 离线摄取关键细节
- **文件抽取**：源码 `.cpp/.hpp/.h`；文档 `.md/.rst/.txt`。
- **解析（基于 Tree-sitter 增量具体语法树，非正则）**：
  - `cpp_parser.py`：抽取函数实体，字段包括 `symbol_name`、`parent_symbol`、`class_name`、`return_type`、`parameters`、`leading_comment`、`code` 等；`_split_qualified_name()` 拆分 `ippl::initialize`；`CommentExtractor` 关联前导注释。
  - `header_parser.py`：抽取命名空间、类、结构体、方法/自由函数声明，产出 `chunk_type=class/struct` 等记录。
  - `doc_parser.py` + `DocChunker`：抽取文档逻辑小节，超长按 `max_chunk_size` 切分并加数字后缀（`section_title_1`…）。
- **结构图与高阶实体**：
  - `ProjectStructureBuilder` 构建调用/依赖图，输出 `project_structure.json`，节点分 `symbols`（函数/类/结构体）、`files`、`modules` 三层；
  - 三种实体构建策略（配置于 `runtime_settings.json`）：
    - `unified_whole_file_with_fallback_v1`（文件级）；
    - `module_entities_from_descendant_files_v1`（模块级）；
    - `direct_call_neighborhood_v1`（调用链邻域级）。
- **嵌入与向量库**：
  - 嵌入后端 Ollama + `nomic-embed-text`（768 维），亦支持 sentence-transformer `BAAI/bge-code-v1`；
  - 嵌入提示同时包含**语义解释 + 结构元数据**（File / Symbol / Chunk Type / Parent Symbol / Section Path / Generated Explanation / Code），并对超长提示做截断重试；
  - **查询嵌入也结构化**：用正则检测查询中的文件名，并推断意图、chunk 类型、代码片段，使查询向量与内容向量"同构"；
  - 存储使用 **FAISS 精确 L2 检索**，32 位浮点；持久化 manifest（示例：8013 条向量、`max_chunk_size=400`）避免重复重建。

### 2.3 在线检索流水线
- **候选来源（多路混合检索）**：
  - 语义 Top-k 向量检索（始终）；
  - 精确文件名注入（同名不同后缀如 `BareField.h/.hpp` 距离置 0）；
  - 精确符号注入（仅取前 2 个候选，带上下文匹配优先）；
  - 模块名精确注入；比较类查询的平衡候选；API 字面调用点候选；目标实体层级对齐候选。
  - 之后 `_merge_candidates()` 按注入优先级合并并去重。
- **元数据重排（`reranker.py`）**：
  - `semantic_score = 1.0 / (1.0 + max(distance, 0.0))`
  - `metadata_score = lexical_metadata_weight × lexical_metadata_score + entity_target_weight × entity_target_score`
  - `combined_score = semantic_score + metadata_score`
  - 另含针对性加成：API 调用点、数据流方向词（gather/scatter/interpolation）、比较主体；并对 `i/j/x` 等低信息符号与测试域块做惩罚。
- **主候选选择与约束**（`_select_primary_candidates`）：相对分数下限 0.4、分数断崖阈值 8.0、绝对下限 1.25、同符号上限 1、同文件上限 2、主导文件比例 0.75，防止上下文弱化或重复。
- **测试/构建噪声过滤**：`TEST_MODULE_SCOPES`、`BUILD_FILE_NAMES`、`TEST_QUERY_KEYWORDS`，非测试类查询时剔除测试/构建块。
- **查询意图路由（`query_intent_router.py`）**：9 类意图（api_usage、location_lookup、data_flow、comparison、symbol_explanation、file_purpose、module_overview、workflow_explanation、default），映射到不同**结构扩展模式**：
  - `mode_api_usage` ≤3、`mode_1_minimal` ≤2、`mode_2_balanced` ≤3、`mode_3_broad` ≤4 个扩展块；
  - 同时检测显式实体目标（file/module/call chain/function/documentation section）与符号级提示。
- **结构扩展（`structural_expander.py`）**：不做新语义搜索，仅沿摄取阶段建立的结构关系（文件↔模块↔调用链↔符号）扩展，条件包括存在主块、有扩展模式、有相关块、未超上限等。
- **最终过滤与提示（`LLMAgent.py`）**：对块打最终质量分（正向：有生成解释、前导注释、include/引用、高阶实体、足够代码；负向：`skipped_low_information`、平凡声明），满足"低分 + 有同源更优块 + 差距≥3"则丢弃；`build_context()` 生成结构化上下文字符串。
- **提示模式（`prompt_templates.py`）**：`general`（单实体解释）、`file_level`、`file_level_fallback`、`module_level`、`call_chain`、`retrieval_answer`（旧）、`retrieval_answer_v2`（严格接地回答，评测使用）。提示模板签名纳入运行时 manifest，改提示会触发重建。

### 2.4 运行时配置
- 集中在 `config/runtime_settings.json`：嵌入后端/模型、各角色模型、提示模式、检索参数（`candidate_k=20`、`supplementary_k=3`、`lexical_metadata_weight=0.4`、`entity_target_weight=0.7` 等）。
- 适配新代码库只需改 `raw_data_path` 等，并做干净重建（`FORCE_CLEAN_REBUILD=1 sbatch job.sh`）。

## 7. 方法有效性的解释与讨论

- **为什么离线制备对小模型特别有效**：
  - 小模型的上下文利用率（in-context learning 的鲁棒性）弱于大模型，智能体循环中多轮工具调用产生的噪声、冗余与错误检索会被进一步放大；而离线阶段由更大模型（14B/32B）生成的"实体解释"相当于把推理成本前置，并把结果以**自然语言 + 结构化元数据**的形式直接供给小模型，降低了在线阶段的推理难度。
  - 结构元数据（文件、符号、父符号、模块、调用链）在嵌入提示与查询嵌入中被**同构编码**，使得即使回答模型很小，检索层仍能提供"语义相近 + 结构正确"的上下文，弥补了小模型自身规划能力不足。
- **意图路由与结构扩展的作用**：作者认为不同问题类型（定位、API 用法、数据流、比较、模块概览）需要不同的上下文组织方式；用固定 prompt 处理所有问题会导致上下文或过窄或过散。路由到不同扩展模式（minimal/balanced/broad）是一种**低成本的结构化 RAG 变体**，不需要额外的 LLM 调用。
- **模型家族差异的解释**：Qwen2.5 系列随规模增大反而下降，作者倾向解释为"指令跟随/格式稳定性"与"对长上下文的抗干扰能力"差异，而非知识量差异——即在同一严格接地提示（`retrieval_answer_v2`）下，更大的模型未必更擅长"只依据给定上下文作答"，可能更倾向于补充自身先验，从而与参考答案偏离。

## 8. 局限性与未来工作

- **归因不足**：缺少逐组件消融（向量检索 / 精确注入 / 元数据重排 / 意图路由 / 结构扩展 / 最终过滤），无法量化各模块边际贡献；作者将"组件替换的持续评测"列为未来工作。
- **评测可靠性**：LLM-as-judge 存在偏好与不一致风险，未做人工标注抽样校验，也未报告裁判一致性（如与人工评分的相关性、重复评测方差）。
- **泛化性有限**：仅一个 C++ HPC 代码库（IPPL）、100 题，且题目由强模型基于完整仓库生成，可能偏向"文档可回答问题"；对 Python/多语言、超大规模仓库、缺少注释的遗留代码是否成立未知。
- **超参数与提示统一**：所有模型共用同一套提示与解码参数，作者自承对部分模型可能次优，因此"家族 > 规模"的结论需谨慎，可能部分来自提示适配度差异。
- **规模与成本的权衡未量化**：论文强调"离线贵、在线便宜"，但未给出总拥有成本对比（云端 API 成本 vs 本地 GPU 时数），也未给出冷启动重建时间随仓库规模的增长曲线。
- **类别结论稳健性**：numerical_meaning 仅 3 题、testing_and_workflow 4 题、boundary_and_halo 5 题，类别级结论的标准误较大，不宜作强推断。

## 9. 对实践的启示

- **可迁移的设计模式**：
  1. **把 LLM 推理前置到摄取阶段**，让在线阶段只做检索与拼装，是让小模型可用的关键杠杆；
  2. **查询与文档的嵌入表示同构**（都带文件名/符号/意图/结构信息），比单纯提升嵌入模型更划算；
  3. **用结构关系做扩展而非再做语义搜索**，可显著降低成本并避免语义漂移；
  4. **多路候选注入 + 元数据重排 + 硬性选择约束**是控制上下文质量的有效组合，尤其适合"上下文预算紧张"的小模型场景。
- **适用边界**：适合代码库相对稳定、文档/注释较完善、问题以"理解"为主（定位、职责、数据流、API 用法）的场景；对需要跨仓库推理、实时修改代码、复杂调试的任务，仍需要强模型驱动的智能体循环。
- **工程建议**：把提示模板签名、嵌入模型、chunk 解释模型纳入 manifest 并在变更时强制重建，是保证结果可复现的重要实践；`runtime_settings.json` 集中配置 + 干净重建脚本降低了迁移到新代码库的门槛。

## 10. 一句话总结

论文提出并验证了一个**两阶段解耦、离线重投、在线轻量**的本地 RAG 代码理解系统：在 IPPL 这一 C++ HPC 代码库的 100 题基准上，它让 **9B 级开源模型（Qwen3.5 9B，0.795）** 超过同管线的 32B 模型，并显著优于"Claude Code 式智能体 + 同款小模型"的基线（如 Qwen2.5 7B 的 0.720 vs 0.520），核心论点可概括为：**当回答模型足够小的时候，检索上下文的质量比检索过程的智能更决定成败**；但其组件贡献缺乏消融验证、评测依赖 LLM 裁判且仅覆盖单一代码库，结论应视为方向性证据而非定论。
