## 摘要
近年来，大语言模型（LLMs）的快速发展重塑了软件工程，使自主代码智能体能够迭代地规划、执行并利用外部工具来解决复杂任务。除了实现功能正确性之外，这些智能体还必须在整个开发生命周期中忠实遵循过程指令和约束。然而，现有基准通常关注最终的功能正确性，或将指令遵循评估局限于单轮、通用聊天或简单代码生成场景，导致多轮智能体编程中的指令遵循仍未得到充分探索。为弥合这一差距，我们提出了 MTAC-IFBench，一个针对这一关键能力的综合基准。它包含多轮渐进式软件开发指令，其约束多样，涵盖 6 个一级类别和 18 个二级类别。每个实例平均包含 7.04 轮和 91.33 个约束，对当前 LLMs 构成了严峻挑战。为使评估可靠，我们为每个约束和功能需求构建检查清单，并集成验证脚本和评判智能体来验证每个检查清单项。MTAC-IFBench 揭示了现有代码智能体在多轮指令遵循方面存在显著不足，随着交互会话变长，其性能迅速下降。

## Abstract
Recently, the rapid development of large language models (LLMs) has reshaped software engineering by enabling autonomous code agents that plan, execute, and utilize external tools iteratively to tackle complex tasks. Beyond achieving functional correctness, these agents must faithfully follow process instructions and constraints throughout the development lifecycle. However, existing benchmarks typically focus on final functional correctness or confine instruction-following evaluation to single-turn, general chat or simple code generation scenarios, leaving instruction-following in multi-turn agentic coding underexplored. To bridge this gap, we propose MTAC-IFBench, a comprehensive benchmark for this critical capability. It features multi-turn progressive software development instructions with diverse constraints spanning 6 primary and 18 secondary categories. With an average of 7.04 turns and 91.33 constraints per instance, it poses a rigorous challenge to current LLMs. To make the evaluation reliable, we construct a checklist for each constraint and functional requirement, and integrate verification scripts and judge agents to verify each checklist item. MTAC-IFBench identifies significant deficiencies in existing code agents in multi-turn instruction-following, with their performance degrading rapidly as the interaction session grows longer.

## 1. 核心问题与整体含义

- **研究背景**：LLM 驱动的自主代码智能体（如 Claude Code、Kilo）正从传统人工开发转向自主规划、执行、调用外部工具的智能体式开发范式。除功能正确性外，智能体还必须在整个开发生命周期中严格遵循过程指令与约束。
- **核心问题**：现有评估存在双重缺口——
  - 智能体编程基准（SWE-Bench、Terminal-Bench、SWE-Together、SWE-Interact）以**最终功能正确性**为导向，忽视过程约束遵循；
  - 指令遵循基准（ComplexBench、CodeIF、AgentIF 等）多局限于**单轮、通用聊天或单文件代码生成**，即便如 OctoBench 也缺乏系统性约束分类且基本限于单轮。
- **研究意义**：多轮智能体编程中的指令遵循能力尚未被充分探索，而这一能力是代码智能体在生产环境中可靠部署的前提。论文提出 **MTAC-IFBench**，填补这一空白。

## 2. 方法论

### 2.1 核心思想
构建一个**多轮、渐进式软件开发指令**基准，将功能需求与多样化过程约束融合，通过逐项检查清单 + 混合验证（脚本 + 评判智能体）实现可靠评估。

### 2.2 约束分类体系（6 个一级 / 18 个二级类别）
- **Content（内容）**：Keyword、Persona、Format
- **Language（语言）**：Response Language、Comment Language、File Encoding
- **Quantity（数量）**：Range、Exact Value、Complexity
- **Style（风格）**：Layout、Naming、Paradigm
- **Environment（环境）**：File Path、File Operation、Logging
- **Workflow（工作流）**：Tool Usage、Orchestration、Testing

### 2.3 数据构建流程（半自动化四阶段）
1. **指令收集与多轮扩展**：从人工策划与现有基准（ZfrontendBench、CC-Bench）收集单轮指令，用 Gemini-3.1-Pro 通过增量扩展提示生成 5–10 轮的渐进式序列（每条做两次独立扩展，共 374 条）。
2. **分类体系引导的约束集成**：逐轮迭代集成 + 验证流水线。
   - 先集成到仓库策略文件（如 Claude.md，4–6 类、最多 8 条约束），再逐轮集成到用户指令（每轮 2–4 类，新增/修改约束上限 2 条）。
   - 采样按类别曝光次数反向排名加权（权重为反向排名的平方），优先欠曝类别。
   - 允许新增或修改既有约束，模拟需求动态演化；策略文件约束全程不可变。
   - 用 Seed-2.0-Pro 验证清晰性、一致性、完整性、可行性，失败重试最多 5 次，否则丢弃。
3. **检查清单生成与评估方法设计**：为每轮生成约束检查清单、为最终项目生成功能检查清单，每项标注评估方式：
   - **代码评估**：验证脚本（确定性约束，如 Keyword、Exact Value）
   - **评判智能体评估**：用于主观或复杂约束（如 Paradigm、Orchestration），功能项全部由评判智能体验证
4. **人工质量检查**：17 名高校学生按清晰性、一致性、完整性、可行性四准则筛查指令，并修正检查清单。

### 2.4 评估指标（公式文字说明）
- **CSR_t**（约束成功率）：第 t 轮满足约束数 / 该轮约束总数
- **C-ISR_t**（约束-指令成功率）：第 t 轮所有约束**全部**满足则为 1（严格完成）
- **BSR**（构建成功率）：最终项目是否可执行
- **FSR**（功能成功率）：满足功能数 / 功能总数
- **F-ISR**（功能-指令成功率）：所有功能**全部**满足则为 1
- 数据集级指标为各实例得分的平均。

### 2.5 评估协议
- 代码评估：Claude-Opus-4.6 生成验证脚本，脚本与项目同环境运行，输出二值判断。
- 评判智能体：基于 Claude Code 框架，功能清单用 Claude-Sonnet-4.6（可用 Playwright 模拟浏览器交互、npm 部署前端），约束清单用 DeepSeek-V4-Pro；采用 IF-Critic 单次推理评估所有约束的提示策略。

## 3. 实验设计

- **Benchmark 规模**：100 个实例、9,133 条约束；平均每实例 7.04 轮、16.07 个功能检查项、91.33 个约束检查项（平均每轮 12.97 条约束）。
- **任务分布**：前端开发 24、应用开发 20、UI/UX 优化 19、数据分析 22、构建与部署 10、机器学习 5。
- **对比模型（11 个）**：
  - 专有：Claude-Opus-4.6、Gemini-3.1-Pro、Qwen3.6-Plus、Seed-2.0-Pro、Claude-Haiku-4.5
  - 开源：GLM-5.2、GLM-5.1、DeepSeek-V4-Pro、DeepSeek-V4-Flash、Kimi-K2.6、Qwen3.5-27B
- **智能体框架**：主实验用 Claude Code v2.1.14；另在 OpenCode v1.1.21 下对比 8 个模型。
- **分析维度**：不同框架、不同约束类别、不同约束来源（策略文件 / 新增约束 / 替换约束）、约束放置位置（系统提示 vs 首轮用户提示）。
- **评估可靠性验证**：随机抽 200 个功能项 + 400 个约束项（164 脚本、236 评判智能体）由 2 名标注者独立验证 + 第 3 人交叉校验。

## 6. 主要结论与发现

1. **基准极具挑战**：即使最强的 GLM-5.2 也违反约 20% 的约束；CSR 中等（60.6%–80.4%），但 C-ISR 极低（大多低于 10%）。
2. **性能随交互轮次快速衰减**：所有模型 CSR 与 C-ISR 随轮次持续下降，多数模型 6 轮后 C-ISR 归零；更强模型衰减更小。
3. **过程约束比功能需求更难**：所有模型 C-ISR 显著低于 F-ISR，说明仅看最终结果会掩盖开发过程中的关键失败。
4. **类别差异明显**：静态孤立约束（编码、文件路径）近乎满分；Orchestration、Paradigm、Naming、Quantity（多步协调、全局一致性、精确量化控制）表现最差，暴露智能体在长交互中维持全局状态与纪律化流程的弱点。
5. **约束来源差异**：仓库策略文件中的约束长期鲁棒性优于用户指令；用户指令中**修改既有约束比新增约束更难**（受被替代约束干扰），表明追踪演化用户意图存在困难。
6. **框架影响显著**：Claude Code 下整体表现优于 OpenCode，但 OpenCode 下多轮衰减更缓（上下文管理机制优势）；模型层级大体稳定，中低层排名存在框架差异。

- **问题定位精准**：明确区分“过程约束遵循”与“最终功能正确性”，揭示结果导向评估的盲区。
