## 摘要
基于 LLM 的 AI 智能体通过迭代推理和工具执行来处理用户请求，通常涉及远程 LLM API 的调用以及本地工具容器的使用。这种执行模型会使智能体服务的优化变得困难，因为延迟、本地资源需求和容器瓶颈在不同请求之间相互交织。然而，当前智能体生态系统在运行时很少考虑资源动态，这导致宝贵资源的显著浪费。本文分析了 AI 智能体在三种代表性任务中的资源交织情况：检索增强问答、网络搜索和软件编程。为此，我们刻画了在并发处理多个请求和任务时，延迟与资源动态之间的关系。我们的测量表明，智能体会因任务不同而表现出广泛的行为差异，因此即使是同一工具，其资源动态也可能存在显著差异。我们还发现，并发运行多个请求会暴露出资源动态中依赖于任务的瓶颈，例如 CPU、磁盘 I/O 和内存。此外，我们发现更快的 LLM 响应或更多的 CPU 核心并不总能加速智能体。基于这些观察，我们展示了利用任务资源动态的新优化机会：CPU 感知的工具准入和任务感知的 CPU 分配。我们的结果表明，与原生智能体相比，CPU 敏感型智能体任务的延迟改善了约 5.4 倍，多个任务的平均延迟降低了约 32%。

## Abstract
LLM-based AI agents process user requests through iterative reasoning and tool execution, often involving the invocation of remote LLM APIs with local tool containers. This execution model can make the optimization of agent serving difficult because latency, local resource demand, and container bottlenecks inter-mix across requests. However, the current agent ecosystem runs without much consideration of resource dynamics, which results in significant waste of the precious resources. This paper analyzes the resource inter-mix of AI agents for three representative tasks: retrieval-augmented question answering, web search, and software coding. To this end, we characterize the latency with respect to the resource dynamics of processing multiple requests and tasks concurrently. Our measurements show that agents have a wide range of behaviors depending on tasks, so that even the same tool can differ substantially in resource dynamics. We also find that running multiple requests concurrently exposes task-dependent bottlenecks in resource dynamics such as CPU, disk I/O, and memory. Furthermore, we uncover that faster LLM responses or more CPU cores do not always accelerate agents. Based on these observations, we demonstrate new optimization opportunities that exploit the resource dynamics of tasks: CPU-aware tool admission and task-aware CPU allocation. Our results show that the latency of CPU-sensitive agent tasks improves $\sim$5.4$\times$, and the average latency across multiple tasks is reduced $\sim$32% compared to native agents.

## 2. 方法论

论文定位为**测量与刻画型研究**，而非提出完整系统；核心贡献是系统化测量 + 由观察导出的两个优化机会原型。

### 2.1 分析框架（三维度）

- **任务刻画（顺序执行）**：测量端到端延迟分解（LLM API 时间 / Web API 时间 / 本地工具执行时间）、平均与峰值 CPU、平均与峰值内存，用以识别各任务的本地执行占比与资源特征。
- **并发请求分析**：请求速率从 **0.5 → 6 req/s**（12×）扫描，观察延迟与资源随并发的变化；当 CPU/内存无法解释延迟增长时，补充测量**磁盘写吞吐**与 **CPU I/O wait 比例**。
- **敏感性分析**：联合变化两个因素——LLM 响应时间（按顺序执行实测值缩放 **1×/2×/3×**）与工具容器 CPU 分配（**2/4/6/8 核**），指标为端到端延迟与 **CPU throttling ratio**（容器在调度周期内被限流的时间占比，反映 CPU 争用程度）。

### 2.2 关键技术细节

- **确定性回放（replay）**：LLM 输出具非确定性，会污染运行时测量。作者先顺序跑每个 benchmark，记录 LLM 输出与每步延迟形成轨迹，后续实验**回放 LLM 输出、只真实执行对应工具调用**，以保证配置间可比性。作者亦实测验证 LLM API 延迟在不同请求速率下稳定。
- **容器结构建模**（Fig. 1）：
  - RAQA 与 Web search 使用**共享工具容器**（多请求共用一个容器，共享知识库/库状态）。
  - Coding 使用**每请求独立容器**（独立文件系统与进程环境，避免干扰、保留执行状态）。
  - 编排容器一般不是瓶颈，分析聚焦工具容器与外部 API。
- **资源采集**：CPU/内存来自容器 cgroup，报告平均值与峰值。

### 2.3 观察驱动的优化机会（文字化流程）

- **CPU 感知的工具准入（CPU-aware tool admission）**：将**同时运行的工具执行数限制为分配的 CPU 核数**，多余执行排队等待。逻辑依据是敏感性分析——只有对 CPU 分配高度敏感（CPU 争用受限）的任务才能获益；对远程等待主导的任务只会引入排队延迟。因运行中容器难以动态改核数，故选择"控制并发工具数"这一等价手段。
- **任务感知的 CPU 分配（task-aware CPU allocation）**：在混合负载下，按各任务的 **CPU 敏感性**分配核数——给 CPU 敏感的 RAQA 更多核，给 CPU 不敏感的 Web search 更少核，对敏感性混合的 Coding 保持接近均分；同时对 RAQA 叠加 CPU 感知工具准入。

## 6. 主要结论与发现

- **结论一：端到端延迟不能直接反映工具资源需求，各任务压力点不同。**
  - RAQA：延迟 62% 花在本地检索，平均 CPU 最高（86%），常驻索引内存最大（均值最高达 98 GB，峰值 99 GB）；HotpotQA 因平均 1.94 个并行工具调用而峰值接近 2 核，TriviaQA 仅 1.01 个故接近 1 核。
  - Web search：延迟主要由远程 Web API 等待主导（49%），本地摘要仅 10.5%，CPU 最低（14%），但内存约 13 GB；峰值 CPU 方差大（约 0.98 核），因抓取文本量跨三个数量级。
  - Coding：延迟主要由 LLM API 主导，本地 Bash 执行占 39%，CPU 均值 22%，内存最小（2–73 MB 均值），但峰值可达均值的 2–4 倍，且 benchmark 间方差极大（SWE-bench 1.57 核、BigCodeBench 1.49 核、APPS 0.29 核）。
  - 迭代次数决定延迟量级：RAQA 最少（2.4–3.0），Web search 居中（6.4–13.9），Coding 变化最大（7–36.9 次迭代，21.5–95.4 s）。
- **结论二：并发暴露任务相关瓶颈，且不是单一资源。**
  - 请求速率提升 12× 时延迟增幅差异巨大：HotpotQA 13.1×、TriviaQA 10.2×；BFCLv4 1.5×、QASC 1.04×；BigCodeBench 6.4×、SWE-bench 2.4×、APPS 几乎不变。
  - CPU 饱和点不同：RAQA 最早（1 req/s），SWE-bench 2 req/s，BFCLv4 2 req/s、QASC 4 req/s，APPS 从不饱和。
  - **BigCodeBench 的主瓶颈是磁盘 I/O 而非 CPU**：即使在 0.5 req/s，磁盘写已达约 200 MB/s（接近 207 MB/s 上限），CPU 饱和要到 4 req/s，且 I/O wait 比例随速率上升。
  - 内存随并发增长：RAQA 2.5×、Web search 5.8×、Coding 1.6×；RAQA 因共享索引在各速率下内存占用最高。
- **结论三：更快的 LLM 响应或更多 CPU 核并不总能加速智能体。**
  - HotpotQA 对 CPU 分配高度敏感（2→8 核延迟降 8.9–13.0×），对 LLM 响应时间几乎不敏感（1×→3× 仅增 1.01–1.14×，8 核时 1.48×）。
  - BFCLv4 恰好相反：2→8 核仅降 1.02–1.04×，而 1×→3× LLM 时间使延迟增约 1.7×；throttling 在 4 核以上近乎为零。
  - SWE-bench 为混合型：1× 时 2→8 核降 1.88×，但 3× 时仅降 1.09×；反之 2 核时 LLM 时间 1×→3× 仅增 1.50×，8 核时增 2.59×。原因是**更慢的 LLM 响应会摊薄本地工具执行的重叠**，从而降低额外核数的边际收益（throttling 从 78% 降到 41%）。
- **结论四：观察可转化为优化收益。**
  - CPU 感知工具准入：HotpotQA 平均降延迟 **3.23×**；但同一策略使 SWE-bench 延迟**增加 2.76×**，说明必须按任务自适应使用。
  - 任务感知 CPU 分配：6 核预算下混合负载总平均延迟降 **32%**（HotpotQA 降 5.4×，BFCLv4 因减核升 28% 但权重较小）；12 核预算下降 **23%**（HotpotQA 降 3.2×，BFCLv4 几乎不受影响）。

## 8. 局限与可质疑之处

- **代表 benchmark 的外推风险**：敏感性网格与优化实验每类任务仅取一个 benchmark（HotpotQA / BFCLv4 / SWE-bench），而文中自己已显示 Coding 类内部差异极大（APPS 峰值 CPU 仅 0.29 核、几乎不受并发影响，与 SWE-bench 1.57 核判若两类）。因此"Coding 保持接近均分"这类结论是否适用于 APPS 类轻量任务，论文未给出证据。
- **单点硬件与单一 LLM**：所有测量在同一台 24 vCPU VM、同一个 Gemini 3 Flash API 上完成。CPU 核数、磁盘带宽（207 MB/s）、内存容量都会直接改变饱和点与敏感性结论；换硬件或换模型（尤其是本地部署、响应时间分布不同的模型）后，各任务的"敏感/不敏感"标签可能翻转。
- **未测质量指标**：全文以延迟与资源为核心指标，未报告答案正确率、任务成功率或工具调用成功率。CPU 感知准入把多余工具执行排队，可能改变并发工具间的时序与依赖关系，从而影响最终答案质量——这一风险未被量化。
- **优化原型未经端到端系统化**：两条优化机会属于"从观察导出的机会演示"，未实现为完整调度系统，也未与 AgentCgroup 等既有容器化智能体资源控制方案做对照，只与原生 ReAct 基线比较。因此其收益在真实系统中能保留多少尚不确定。
- **replay 的可信边界**：回放 LLM 输出保证了配置间可比性，但也意味着实验中不存在"因资源变慢而导致 LLM 看到不同中间结果、进而改变后续推理路径"的反馈回路。真实系统里，工具执行变慢可能改变上下文长度与迭代次数，从而使延迟敏感性比本文测得的更强或更弱。
- **未涉及能耗与成本**：资源浪费是论文动机之一，但没有给出能耗、碳排放或 API 调用成本的量化，因而"浪费"的代价只以资源占用间接体现。

## 9. 总体评价与启示

- **定位**：这是一篇典型的"先测量、后启发"的系统测量论文，其最大价值不在于新算法，而在于用一套受控实验**证伪了"延迟高即资源紧"的直觉**，并给出一个统一解释框架：**本地工具执行在端到端延迟中的占比，决定了该任务对 CPU 分配和并发的敏感性**。
- **对实践者的启示**：
  1. 不要把智能体当作同质工作负载做统一资源配额；至少应按 RAQA / Web search / Coding 三类分别设定 CPU 与并发策略。
  2. 磁盘 I/O 可能先于 CPU 成为瓶颈（BigCodeBench 在最低速率下就已接近磁盘上限），仅监控 CPU/内存会漏判。
  3. 给容器更多核或换更快的 LLM 都非普遍有效——更慢的 LLM 会摊薄工具执行重叠，反而降低加核收益，这类交互效应必须在容量规划中考虑。
- **对后续研究的启示**：需要在多硬件、多模型、多 benchmark 上复现敏感性分类；需要把质量指标纳入优化目标；需要把"任务感知分配"落地为可在线识别任务类型与 CPU 敏感性的调度器，并与已有智能体资源控制方案做端到端对比。
