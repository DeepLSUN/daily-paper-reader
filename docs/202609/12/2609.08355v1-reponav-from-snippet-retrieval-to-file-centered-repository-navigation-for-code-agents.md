## 摘要
解决仓库级代码任务需要基于LLM的智能体使用代码搜索工具来导航大型代码库，并识别一小组相关文件和函数。然而，当前的检索工具通常返回孤立代码片段的扁平列表：这类列表能暴露相关文件，但为智能体提供的结构不足，使其难以区分目标函数与同一文件中语义相似的替代项。我们提出RepoNav，一种轻量级的检索后接口，将检索到的片段重新组织为以文件为中心的导航支架。通过呈现紧凑的结构线索和候选目标，该支架引导按需的文件结构浏览，帮助智能体在选择目标函数前比较同级符号。在LocBench上跨多种模型，RepoNav提升了函数级定位，并缩小了从文件到函数的差距。受控消融实验表明，这些收益来自结构化的证据组织，而非仅仅暴露额外的文件结构，且该方法还提升了一个仓库级问答基准上的性能。

## Abstract
Solving repository-level code tasks requires LLM-based agents to use code search tools to navigate large codebases and identify a small set of relevant files and functions. However, current retrieval tools typically return flat lists of isolated code snippets: such lists can surface relevant files, but provide insufficient structure for agents to distinguish the target function from semantically similar alternatives in the same file. We introduce RepoNav, a lightweight post-retrieval interface that reorganizes retrieved snippets into a file-centered navigation scaffold. By presenting compact structural cues and candidate targets, this scaffold guides on-demand file-structure browsing, helping agents compare sibling symbols before selecting a target function. Across diverse models on LocBench, RepoNav improves function-level localization and narrows the file-to-function gap. Controlled ablations demonstrate that these gains come from structured evidence organization rather than simply exposing additional file structure, and the approach also improves performance on a repository-level question-answering benchmark.

## 1. 核心问题与整体含义

- **研究背景**：仓库级代码任务（如 issue 修复、缺陷定位）要求 LLM 智能体在两级粒度上工作——先找到相关**文件**，再定位文件内的具体**函数**。现有代码检索/搜索工具（bash 探索、snippet 检索、RepoCoder、CodeRAG-Bench 等）大多返回**扁平的、孤立的代码片段列表**。
- **核心痛点**：扁平片段列表足以暴露"相关文件"，但缺乏结构信息，无法帮助智能体在同一文件中区分目标函数与语义相近的兄弟符号。
- **关键经验诊断（论文的出发点）**：作者用 mini-SWE-agent 框架做失败分类，发现函数级失败中 **"正确文件、错误函数" 占 44%–58%**（跨 GPT-OSS-120B、Qwen3-Next-80B、Gemini-3-Flash 等不同骨干）。这说明"到达正确文件"并不能可靠转化为"找到正确函数"，即存在 **file-to-function gap（文件到函数鸿沟）**。
- **失败机制命名**：**premature anchoring（过早锚定）**——智能体在检查同级定义或文件结构视图之前，就锁定在显眼的邻近符号（如公共包装函数、请求处理器、入口方法）上。这被类比为长上下文中的"lost in the middle"现象。
- **整体含义**：论文主张检索后（post-retrieval）界面不应把检索证据当作"终局答案"，而应组织成**可行动的导航选择**，使"继续探索"比"过早承诺"更容易。RepoNav 正是这样一种轻量级、以文件为中心的导航界面。

## 2. 方法论

### 核心思想
- RepoNav **不是新检索器**，而是一个**检索后接口层**：不修改底层稠密检索结果与相似度分数，而是改变检索证据的**呈现组织方式**，将片段级命中转化为**以文件为中心的导航脚手架（file-centered navigation scaffold）**。
- 三条设计原则：① 把 chunk 级证据聚合为**候选文件**；② 暴露**紧凑的文件内部结构**（不倾倒完整函数体）；③ 加入**显式继续探索线索**。
- 与 RepoGraph / CodexGraph / LocAgent / LingmaAgent 等"重量级图系统"的区别：不构建仓库级图或持久结构索引，只在**排名最高的少数文件**上动态抽取局部结构。

### 关键技术细节

**阶段一：证据聚合（Stage 1: Evidence aggregation）**
- 稠密检索后端返回 top 排名 chunk 及其相似度分数，RepoNav 用**混合打分规则**把 chunk 级分数聚合为文件级排名。
- 对候选文件 \(f\)，其检索到的 chunk 分数降序为 \(s_{f,(1)} \ge s_{f,(2)} \ge \dots\)，取 \(m_f = \min(m, |C_f|)\)，聚合公式为：

  \[
  \text{Score}(f) = \alpha s_{f,(1)} + (1-\alpha)\frac{1}{m_f}\sum_{i=1}^{m_f} s_{f,(i)}
  \]

  - 第一项捕捉**峰值证据强度**，第二项奖励**被多个高分区域共同支持**的文件（而非单一虚假匹配）。
  - 全部实验设 \(m=3\)；不足 3 个 chunk 的文件对可用 chunk 取平均。
  - 敏感度分析显示性能在 \(\alpha \in [0,1]\) 上稳定：排序类指标（Acc@1、MRR）在 \(\alpha=0.5\) 附近峰值，召回类指标在 \(\alpha \ge 0.7\) 后进入平台期。最终固定 \(\alpha=0.5\)（仅影响交互前的文件排序，在留出开发集上用离线检索指标选定）。

**阶段二：在线结构抽取（Stage 2: On-the-fly structural extraction）**
- 仅动态解析 Stage 1 的 **top-\(k\) 文件，\(k=5\)**；前 3 个候选文件自动展开完整三块条目，其余解析文件留待按需浏览。
- Python 文件使用内置 `ast` 模块抽取函数/类定义、import 语句，以及**轻量级同文件调用邻域**（仅当调用表达式能匹配到同文件内定义的函数时才建立连接；不做可靠的静态分析、不恢复跨文件依赖、不构建过程间调用图）。调用信息不可用时回退到纯文件结构骨架。
- 过程是**确定性的、局部的**，避免仓库级图构建。

**三块式脚手架序列化（明文、基于缩进的树）**
- **[ANCHORS]：入口点**。通过符号名与智能体检索 query 的轻量词法匹配识别锚点符号；每个锚点标注**行号区间**与紧凑的**同文件调用上下文**；每文件锚点上限为 **2 个**。无匹配时回退到结构草图。
- **[GLIMPSE]：结构草图**。暴露最多 **3 个非锚点符号**（若排名第一的文件无锚点匹配则放宽到 **5 个**），提供"文件里还有什么"的概览，防止只盯锚点；只给示意图式条目，不给完整函数体或长签名。
- **[CANDIDATE_TARGETS]：可行动的候选目标短名单**。汇总锚点、精选 glimpse 符号与轻量同文件调用上下文（不引入新检索证据或完整函数体），上限 **4 条**，并附带**固定继续提示语**，鼓励在承诺前检查兄弟符号。排序规则：锚点优先 → 锚点的同文件调用邻域符号 → 选中的 glimpse 符号。调用上下文仅为导航线索，非可靠的静态分析。
- **`list_symbols` 工具：按需文件结构浏览**。给定文件路径返回轻量文件骨架（imports、类、函数、方法、行范围、可选签名），**不含完整函数体**；不做语义搜索、不对目标函数排序。让智能体能检查候选文件内的可编辑对象、比较兄弟符号。

### 算法流程（文字描述）
1. 智能体发出自然语言检索 query；
2. 稠密后端返回 top 排名 chunk（主实验每 query 取 80 个原始 chunk）；
3. RepoNav 按混合打分公式把 chunk 聚合为文件级候选；
4. 解析 top-5 文件，抽取符号、行范围、import 与同文件调用邻域；
5. 前 3 个文件自动展开 [ANCHORS] / [GLIMPSE] / [CANDIDATE_TARGETS] 三块脚手架，附继续提示；
6. 智能体可调用 `list_symbols` 进一步查看任意候选文件的骨架，比较兄弟符号后再选定目标函数。

## 3. 实验设计

### 数据集 / 基准
- **LocBench**（Chen et al., 2025）：仓库级代码定位基准，**560 个 Python 实例**，每个实例将自然语言 issue 与对应 patch 的金标文件、函数配对。
- **SWE-QA-Bench**（Peng et al., 2026）：仓库级问答基准，要求智能体定位、检查并综合代码仓库中的证据，用于检验收益能否**迁移到定位之外**。

### 对比方法与设置
- 统一使用 **mini-SWE-agent** 脚手架，固定 agent loop、环境与交互预算，对比四种接口：
  - **Bash**：仅 shell 探索；
  - **Snippet Search**：增加返回扁平 chunk 列表的稠密搜索工具；
  - **Snippet+ListSym（S+L）**：在扁平片段接口上加入与 RepoNav **相同的 `list_symbols` 工具**，用于**控制文件结构浏览的可及性**（工具匹配基线）；
  - **RepoNav（R）**：把同一稠密检索基底重组为文件中心脚手架 + `list_symbols`。
- **检索设置**：三种检索型设置共享同一 chunk 索引、嵌入模型、检索后端与原始 chunk 分数。函数级切块（每个顶层函数/方法为一个 chunk），主检索器为 **CodeRankEmbed**，主实验每 query 检索 **80 个原始 chunk**；另有 **UniXcoder** 的 100 实例固定试点。
- **模型**：7 个（Gemini-3-Flash、MiniMax-M2.5、GPT-OSS-120B、Qwen2.5-72B-Instruct、Qwen3-Coder-30B-A3B、Qwen3-Next-80B-A3B、GLM-4.7）。SWE-QA-Bench 上用其中 4 个模型。
- **指标**：文件/模块/函数级的 Accuracy@k 与 Recall@k（模块级匹配把预测映射到其所属模块）。
- **RQ2 受控消融**：File-Only（仅聚合候选文件，无文件内结构）→ Inline Scaffold（在检索输出中直接暴露更丰富的文件内结构）→ Tree Scaffold（即 RepoNav，紧凑可导航脚手架 + 选择性线索 + 显式下一步提示），检索后端、工具、工作流、验证约束全部一致，**只改证据呈现**。
