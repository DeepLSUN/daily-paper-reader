## 摘要
背景：由于软件系统日益复杂以及AI编码智能体加速生成代码，开展有效的代码审查正变得愈发具有挑战性。基于大语言模型的代码审查方法在识别缺陷和改进代码质量方面已展现出良好前景。然而，现有方法很少考虑项目特定的情境化知识，也鲜有在工业环境中得到评估。目标：在本研究中，我们提出了一种基于多智能体的解决方案，可对代码变更提供多方面的评估。方法：遵循设计科学研究流程，我们在工业环境中开发并评估了该解决方案。我们的解决方案将专门的智能体技能与特定上下文知识相结合，以从可读性、可维护性、可靠性和性能四个维度识别代码变更中的反模式。使用该解决方案，我们为若干代码提交生成了审查意见，并识别出200多个问题。随后，案例公司的开发人员对这些问题的正确性和重要性进行了人工验证。结果：评估结果表明，我们的解决方案在正确识别所调查代码提交中的问题方面达到了96%的准确率。此外，在正确识别的问题中，约69%被评为重要，其中约33%被评为必须修复的严重问题，36%被评为应当修复的重要问题。开发人员的定性反馈印证了这些发现，并凸显了所生成审查意见的有用性。结论：我们的发现提供了来自工业评估的经验证据，表明将专门的智能体技能与特定上下文知识相结合，能够产生准确且实际有用的代码审查。

## Abstract
Context: Conducting effective code reviews is increasingly challenging due to the growing complexity of software systems and the accelerated code generation by AI coding agents. LLM-based approaches for code reviews have shown promising results in identifying defects and improving code quality. However, existing approaches rarely consider project-specific contextualized knowledge, and few have been evaluated in industrial settings.   Objective: In this study, we propose a multi-agent-based solution that provides multifaceted assessments of code changes.   Method: Following the Design Science Research Process, we developed and evaluated our solution in an industrial setting. Our solution combines specialized agent skills with context-specific knowledge to identify antipatterns in code changes across four dimensions: readability, maintainability, reliability, and performance. Using our solution, we generated reviews for several code commits and identified more than 200 issues. These issues were then manually validated by the developers of the case company for their correctness and importance.   Results: The evaluation results show that our solution achieves 96% accuracy in correctly identifying issues in the investigated code commits. Furthermore, around 69% of the correctly identified issues were rated as important, with approximately 33% rated as severe issues that must be fixed and 36% as important issues that should be fixed. Qualitative feedback from developers corroborates these findings and highlights the usefulness of the generated reviews.   Conclusion: Our findings provide empirical evidence from an industrial evaluation that combining specialized agent skills with context-specific knowledge yields accurate, practically useful code reviews.

## 1. 核心问题与整体含义（研究动机与背景）

- **现实痛点**：代码审查是保障软件质量与知识共享的核心实践，但软件系统规模与复杂度持续增长，审查者需在快速迭代节奏下理解变更意图、推断系统级影响并发现问题，认知负荷极高。
- **AI 编码智能体带来的新压力**：随着组织将越来越多实现工作交给 AI 编码智能体，代码产出速度与体量已超出人工审查能力，审查者成为瓶颈；在迈向"AI 原生"开发（编排式智能体并行工作）的公司中，质量保障必须跟上代码生成速度而非滞后。
- **现有研究的两个关键缺口**：
  - **缺乏项目特定情境知识**：多数 LLM 方法仅依赖孤立的 diff 或局部代码片段，而真实审查依赖架构、组织规范、依赖关系、领域约束等本地与全局上下文。
  - **审查视角狭窄**：人类审查者通常同时权衡可读性、可维护性、可靠性、性能等多维质量属性，而现有工作多聚焦单一维度。
  - **工业评估不足**：大量研究停留在离线实验或开源数据集，缺少真实工业场景的验证。
- **研究目标**：提出并工业验证一种情境化、多方面的多智能体代码审查方案，围绕三个研究问题展开——RQ1（关键设计选择）、RQ2（问题识别准确率）、RQ3（重要问题识别有效性）。

## 2. 方法论：核心思想与关键技术细节

- **总体框架**：遵循 Offermann 等人的设计科学研究流程（DSRP），分三阶段——问题识别（文献综述 + 与 Ericsson 三位实践者讨论，含 1 名经理、2 名资深开发者）、方案设计与开发、评估。方案核心是"专门化智能体技能 + 上下文特定知识"。

- **两大核心设计决策**：
  1. **按质量维度分解为专门化智能体**，每个智能体拥有独立的提示词、反模式目录与审查指令，解决"审查视角狭窄"问题。
  2. **智能体不推理孤立 diff**：由上下文构建器（Context Builder）从代码仓库与代码知识图谱构造上下文视图，解决"上下文有限"问题。

- **四个审查维度与对应反模式目录**：
  - **Readability Expert（可读性）**：命名清晰度、结构组织、嵌套复杂度、格式、视觉可读性等，采用文献中的可读性反模式表（如代码结构、嵌套、代码长度、魔术数字、命名、代码模式、视觉组织等）。
  - **Maintainability Expert（可维护性）**：采用 Fowler 等经典重构反模式，如神秘命名、重复代码、长函数、长参数列表、发散式变化、霰弹式修改、特性依恋、数据泥团、基本类型偏执、重复 switch、消息链、中间人、大类等。
  - **Reliability Expert（可靠性）**：聚焦异常处理/故障管理反模式，如过度捕获、空处理器、捕获后不做任何事、返回 null、捕获泛型异常、破坏性包装、日志后抛出、嵌套 try、finally 中抛出等。
  - **Performance Expert（性能）**：如 The Stifle、昂贵数据库调用、空半挂车、The Blob、绕路寻宝、错误缓存、单车道桥、不当数据结构、未优化循环、重复计算、过度 I/O 等。

- **系统架构与实现**：
  - **LLM 编排器（Orchestrator）**：以 JSON 智能体配置 + persona 文档声明式定义，负责解析用户提示、决定参与审查的智能体、调用上下文构建器、汇总生成统一审查报告。
  - **MCP 服务器（两个）**：
    - **GitLab MCP 服务器**（Docker 容器化）：暴露 GitLab API，提供提交元数据、代码 diff、变更文件等**局部上下文**。
    - **代码知识图谱 MCP 服务器**（Docker 容器化）：索引仓库结构、文件级导入关系、符号定义（DEFINES 边）、外部库使用，支持依赖影响分析（文件级扇入/扇出）、目录结构探索、AI 生成的文件/目录摘要、语义/混合代码搜索、直接执行 Cypher 查询。
  - **上下文构建器**：收集并组织上下文，为不同智能体生成**差异化上下文提示**（如可读性智能体聚焦局部结构与格式，可维护性智能体额外获得依赖与结构关系），以降低提示复杂度并保留各维度最相关信息。
  - **四个专门化审查智能体**：基于 Kiro CLI（终端式 AI 编码助手）实现，采用 Agent Skills 协议；每个智能体由 JSON 配置定义（名称、系统提示、附带技能文档、工具权限），作为子智能体由编排器并行调用，仅接收共享上下文文档路径与磁盘源文件；输出严格四字段格式：反模式名称、位置、问题描述、修复建议。

- **编排工作流**（文字化算法流程）：
  1. 输入 Commit ID；
  2. 编排器构建上下文；
  3. 将上下文保存到磁盘；
  4. 委派给 4 个专门化智能体并行分析；
  5. 汇总各智能体报告；
  6. 保存最终审查报告。

## 6. 主要结论与发现

- **RQ1（关键设计选择）**：
  - **编排与输出格式**：编排是单点故障，任一环节出错都会传导到最终报告，即使单个智能体推理正确；验证上下文构建器与报告格式是必要的，提供正/负例是约束输出的有效手段。
  - **专门化审查智能体**：每个智能体都贡献了其他智能体未发现的问题，单一维度审查最多只能覆盖约三分之一的报告内容，维度分解是多方面评估的关键。
  - **上下文接地**：仅 4% 的问题被判为不正确，低误报率归因于通过上下文构建器与代码知识图谱提供的上下文信息；为每个智能体提供定制化上下文视图还降低了提示复杂度。
- **RQ2（准确率）**：206 个问题中 **197 个被确认为正确，准确率约 96%**；仅 9 个（约 4%）被判为不正确。作者认为该准确率水平已具备实际可用性，但需在更多项目与编程语言上进一步验证泛化性。
- **RQ3（有效性）**：在 197 个正确问题中，**33%（65 个）为 High（严重、必须修复）**，**36%（70 个）为 Medium（重要、应当修复）**，两者合计约 **69%**；其余 31%（62 个）为 Minor（低影响建议）。说明多数发现被开发者认为值得处理。
- **定性反馈**：开发者反馈积极，例如"审查评论非常好，尤其是可维护性和性能部分"、"部分评论与我们自己发现的一致，但你们的审查发现了更多"。
- **总体结论**：工业评估提供经验证据，表明将专门化智能体技能与上下文特定知识相结合，可产生准确且实际有用的代码审查。
- **额外工程经验**：编排准确性与智能体设计同等重要；输出格式是设计的一部分而非呈现细节；关注点分离应延伸到智能体之外（每个智能体拥有独立提示、反模式目录与上下文视图，扩展新维度只需新增智能体）。

## 7. 优点（方法与实验设计亮点）

- **真实工业落地**：在 Ericsson 真实开发环境中开发与评估，弥补了 LLM 代码审查研究普遍缺乏工业验证的缺口。
- **情境化上下文设计**：通过 GitLab MCP + 代码知识图谱 MCP + 上下文构建器，使智能体基于仓库结构、依赖关系与符号定义推理，而非孤立 diff，这是降低幻觉与误报的关键机制。
- **多方面维度分解**：四个专门化智能体各配独立提示、反模式目录与上下文视图，既能覆盖多质量属性，又具备良好可扩展性（新增维度只需新增智能体，不必修改既有智能体）。
- **可复现性设计**：智能体以 JSON 配置与 markdown 技能文档声明式定义，反模式目录与反馈模板在论文中完整披露，便于重建实验设置。
- **评估的可信度设计**：由代码原作者（资深开发者）验证正确性与重要性，兼顾语义理解与系统特定知识；同时用三级重要性区分"正确但无价值"与"正确且重要"的发现。
- **务实的工程洞察**：明确指出编排层是单点故障、输出格式约束是设计要素、正负例对约束输出有效，这些经验对后续构建者具有直接参考价值。

  - 仅使用**单一 LLM**（Kiro CLI 默认模型），准确率与重要性评分可能随模型/框架变化。

- **实验设计局限**：
  - **无消融实验**，无法量化上下文构建器、代码知识图谱、维度分解等各组件的独立贡献。
  - **无基线对比**，未与现有 LLM 代码审查方法或人工审查进行受控比较，增益幅度不明。
  - 作者自述结果为"可行性证据"而非"受控对比证明"。
- **可复现性限制**：代码提交与生成的审查结果均为专有资产，无法公开，限制独立复现与第三方验证。
- **LLM 非确定性**：同一提交重复运行可能产生不同发现；虽通过声明式配置与公开反模式目录支持重建，但结果稳定性未被系统量化。
- **应用限制**：方案依赖代码知识图谱与 MCP 基础设施，对缺少此类基础设施的组织存在迁移成本；编排层单点故障也提示生产部署需要额外健壮性设计。
