## 摘要
现有的计算机使用智能体基准测试并未充分评估作为助手行动的智能体。一个有用的助手会在复杂的多步骤工作流中检索信息，将其综合为产物（文档、演示文稿、电子表格），并导航程序界面以生成连贯的最终产品。此类工作流要求推理与综合、复杂任务的分解，以及视觉和空间理解。为了研究智能体在这类工作流上的表现，我们提出了 KNOWS，一个开放式、复杂、基于浏览器的任务基准，联合评估这些能力，每项任务最终都会产出一个产物。为了编写任务，我们制定了任务设计准则以及一套确保任务满足要求的协议。每项任务都配有一个评估器，该程序将确定性检查与 LLM 判断相结合，以平衡智能体评估中固有的丰富性、可靠性和自动化之间的权衡。我们评估并分析了前沿的计算机使用智能体和基于浏览器的执行框架。它们在部分成功指标上取得中等分数，但最佳表现者在不到 3% 的复杂、长时程任务中完全成功。视觉步骤上的失败会导致生成的产物不可用，即使智能体完成了超过 50% 的其他评估步骤。我们的结果揭示了当前智能体作为端到端助手的局限性，并呼吁在工具使用、视觉理解和长时程推理方面取得进展。

## Abstract
Existing computer-use agent benchmarks do not fully evaluate agents acting as assistants. A useful assistant retrieves information across complex, multi-step workflows, synthesizes it into artifacts (documents, presentations, spreadsheets), and navigates program interfaces to produce a coherent final product. Such workflows demand reasoning and synthesis, decomposition of complex tasks, as well as visual and spatial understanding. To study agents on workflows like these, we introduce KNOWS, a benchmark of open-ended, complex, browser-based tasks that jointly evaluate these capabilities, with each task culminating in a produced artifact. To write tasks, we develop a task design rubric and a protocol for ensuring that tasks meet the requirements. Each task is paired with an evaluator, a program that combines deterministic checks with LLM judgments to balance the richness, reliability, and automation tradeoff inherent to agent evaluation. We evaluate and analyze frontier computer-use agents and browser-based harnesses. They achieve moderate scores on partial-success metrics, but the best performer fully succeeds in fewer than 3% of our complex, long-horizon tasks. Failures on visual steps render the resulting artifacts unusable, even when agents complete more than 50% of other evaluation steps. Our results expose limitations of current agents acting as end-to-end assistants, and call for progress on tool use, visual understanding, and long-horizon reasoning.

## 一、核心问题与整体含义

- **研究动机**：智能体正快速进入真实工作流充当"助理"，但现有基准与真实助理任务存在错位。大量计算机使用（computer-use）基准采用"单一、简短、可验证答案"的成功判定方式（如购物车中是否有某商品），这与真实任务的开放式本质严重不符。
- **现有基准的缺口**：
  - 传统 Web 智能体基准（WebShop、WebArena、Mind2Web 等）任务短、动作少、不产出复杂产物；
  - "深度研究"类基准（DeepResearchBench、Mind2Web 2、DEER）虽要求跨站检索与整合，但最终交付物仍是长文本报告，缺少对产物结构、视觉与空间的组织要求；
  - 办公套件类基准（OSWorld、OfficeBench、OdysseyBench）侧重工具操作，检索与综合成分不足；
  - 最接近的 PresentBench 仅聚焦幻灯片生成，检索范围受限于精选学术源，且更偏开放式评分而非结构约束评估。
- **核心主张**：真实工作空间中，纯文本报告极少是最终交付物；发现的信息需要被编排为幻灯片、电子表格、文档等产物，其有效性依赖内容布局、配色、配图选择、表格组织等视觉/空间/结构决策。这使任务时程更长，擅长文本输出的智能体在"最后一公里"可能彻底失败。
- **整体含义**：论文提出 **KNOWS（Knowledge Navigation and Organized Web Synthesis）**，这是首个同时覆盖**实时网页搜索 + 生产力工具使用 + 视觉/空间理解**的基准，用以暴露当前智能体作为端到端助理的能力缺口。

## 二、方法论

### 2.1 核心思想

- 构建开放式、复杂、基于浏览器的任务集合，每个任务最终**产出一个结构化的 Google Workspace 产物**（Docs / Sheets / Slides）。
- 每项任务配备**评估器（evaluator）**，通过"确定性检查 + LLM/VLM 判断"的混合方案，平衡评估中固有的**丰富性、可靠性、自动化**三角权衡。

### 2.2 任务设计准则（Rubric）

- **真实性（Realism）**：任务须是真实用户可能想做、且自动化后能节省时间的事。
- **显著信息检索**：须浏览实时网页，从 ≥2 个网站获取 ≥5 条不同信息。
- **产物综合**：须用 Google Workspace 工具生成连贯、组织良好的产物，且须有意义地综合而非直接复制粘贴。
- **视觉/空间理解**：须包含识别/编辑特定元素、空间关系（左/右/上）、颜色修改等成分。
- **复杂性**：≥4 步信息检索、≥1 步创建产物、≥10 步信息整合与综合。
- **离散检查点**：将任务拆解为可度量的里程碑。

### 2.3 任务创建流程

1. 依据准则编写 Google Colab 引导笔记本（头脑风暴 → 自我检查 → 编写检查点）；
2. 由另一名标注者独立复核，对照准则验证并反馈修订；
3. 从种子任务扩展（如"视频游戏史→CRISPR 基因编辑"保持步骤结构但更换网站与信息），共收集 **110 个任务**；
4. 每个任务从构思到完成平均耗时 **9–18 小时**专家工作。

### 2.4 评估器设计

- **分解层次**：任务 → 检查点（Checkpoint）→ 评估步骤（Evaluation Step），逐步独立验证。
- **七类共享评估工具**：
  1. **结构性检查**：元素存在性、顺序、层级（Workspace API 的顺序化数据）；
  2. **信息检索检查**：与金标准比对，精确匹配、模糊匹配、带容差数值比较；
  3. **格式化检查**：字体粗细/大小/颜色、对齐、合并单元格等；
  4. **空间检查**：元素物理位置、尺寸、重叠；Slides/Sheets 用 EMU 边界框几何运算，Docs 用 300 DPI PDF 渲染 + 尺度不变模板匹配；
  5. **内容检查**：来源忠实度与语义准确性，主要依赖 LLM-as-a-Judge（二元 yes/no 问题）；
  6. **网页访问检查**：拉取访问 URL 的 HTML，验证信息是否可从中提取（防预训练记忆绕过浏览）；
  7. **视觉检查**：像素级匹配、感知哈希或 VLM 判断图像内容与来源。
- **生成方式**：先由人工制作金标准产物，再用 Claude Code 结合共享工具库生成初版评估脚本，随后人工反复调试、同行复核，并用 Comet 产物做最终验证。
- **评估器验证**：与专家判断对比，100 次判断中 Cohen's κ = 0.64、成对准确率 82%；在纯 LLM/VLM 步骤的独立 100 次判断中，κ = 0.69、准确率 89%。

### 2.5 评估指标（公式文字说明）

设任务 $i$ 含 $C_i$ 个检查点，检查点 $j$ 含 $S_{ij}$ 个评估步骤，其中 $k_{ij}$ 个正确：

- **成功率 SR**：仅当所有检查点所有步骤全部正确时记 1，否则为 0（严格完整成功）；
- **平均成功检查点 ASC**：某检查点全部步骤正确才记 1，再对所有检查点取平均（里程碑级严格）；
- **平均检查点分数 ACF**：先算每个检查点内步骤正确比例，再对检查点取平均（较宽松）；
- **步骤分数 SF**：直接以正确步骤数除以总步骤数（复杂检查点因步骤多而权重更高）。

### 2.6 实时网页与维护策略

- 坚持使用实时网页以保留真实的检索难度与干扰源，不缓存、不使用 Internet Archive；
- 通过"信息在多个网站可得、与时间无关"的设计降低脆弱性；
- 制定维护与弃用政策：人工定期核查 23 个 URL 与 20 个任务，脚本变更时发布新版本并归档旧版本。

## 六、主要结论与发现

- **长时程任务依然极难**：SR 在多数方法与分片上近乎为 0；最佳 Comet 仅在 Docs 上达 12.0%、Slides 上 2.7%，**总体完整成功率不足 3%**。部分成功指标上，最佳基线 ACF 约 70.0%、SF 约 64.7%。
- **视觉模态至关重要**：为 Opus 4.7 增加截图输入带来显著提升（ASC +10.3、ACF +25.5、SF +25.5），说明大量视觉/空间步骤无法仅靠可访问性树解决。
- **执行框架（harness）与模型同等重要**：同一 Opus 4.7 骨干，Comet 框架相较 BrowserGym 整体提升 SR +2.7、ASC +18.7、ACF +27.5、SF +25.6；专有框架在复杂网页与弹窗广告处理上有明显优势。
- **步骤级强弱**：Comet 在确定性精确匹配上最强（83.2%），

- **步骤级强弱**：Comet 在确定性精确匹配上最强（83.2%），但在需要语义判断、空间几何与视觉比对的步骤上明显下滑；纯文本（AXT）配置在所有方法中系统性弱于多模态配置，说明"可访问性树能读结构、但读不到布局"。
- **失败模式的层级差异**：
  - **检索层**：漏掉某个必须访问的网站、未从 ≥2 个来源交叉验证、把预训练记忆当作检索结果（被网页访问检查捕获）；
  - **综合层**：直接复制粘贴原始段落、未按要求重组织为表格/要点/层级结构、跨来源数据未做一致性校验；
  - **产物层**：元素顺序与层级错误、合并单元格/表头样式不符、颜色与字体未按规格修改；
  - **空间层**：图文重叠、超出画布边界、左右/上下相对位置颠倒——这类错误在 Slides 任务中最集中，也最难被纯文本观察发现；
  - **依赖链断裂**：前序检查点失败导致后续步骤无法执行，被记为"未满足依赖"而非独立错误，因此真实能力缺口可能比步骤分数显示的更大。
- **检查点层面的"高开低走"**：多数基线能完成前 1–2 个检查点（如"打开正确网页并记录 5 条信息"），但在需要把信息落到产物并满足格式/空间约束的后半段急剧下降，形成典型的"最后一公里坍塌"。
- **产物类型差异**：Docs 相对最容易（Comet SR 12.0%），Sheets 居中，Slides 最难（Comet SR 2.7%），与视觉/空间步骤占比的排序一致。
- **模型与框架的交互**：开源模型（DeepSeek V4 Pro）以约 1/20 的成本取得远低于专有模型但非零的分数，说明任务难度来自"端到端编排"而非单点推理能力；换框架带来的增益（ASC +18.7）甚至超过换模型带来的增益，提示当前瓶颈在智能体循环、错误恢复与页面鲁棒性，而非底层语言能力。
- **跨平台检验**：Comet 在 Microsoft 365 网页版上完成同一批 5 个任务时，成功率与 Google Workspace 上无系统性差异，初步否证了"基准只在为 Google 自家工具优化"的假说；但样本小，作者将其定位为探索性证据。
- **评估器可靠性**：整体 κ = 0.64 / 成对准确率 82%，纯 LLM/VLM 步骤 κ = 0.69 / 准确率 89%，说明混合评估方案在"丰富性—可靠性—自动化"三角中取得了可用平衡，但尚未达到人类专家级别的一致性。

## 七、局限性

- **无受控人类基线**：受成本限制（单任务约 5,000 美元），仅以作者自测证明任务可解，缺少人类在同等时间/工具约束下的定量参照，因而"智能体差距"缺少分母。
- **评估成本的规模瓶颈**：2,716 个评估步骤、110 个任务、9–18 人时/任务的构建成本，使基准难以快速扩展；也使得"每新增一个模型就全量重跑"在金钱（$80–$2,200）与时间（≥10 小时）上都偏重。
- **实时网页的固有脆弱性**：虽然通过"多源可得、时间无关"设计降低脆弱性，但页面改版、反爬策略、地区差异仍可能造成假阴性；未使用缓存或 Internet Archive 是刻意取舍，代价是可复现性下降。
- **闭源 AI 浏览器的可观测性缺口**：Comet/Atlas 不暴露 token 消耗与动作轨迹，189 个网页访问步骤对 Comet 不可评（占其失败步骤 12.1%），使跨系统比较存在结构性不可比。
- **LLM-as-a-Judge 的偏差风险**：内容与视觉检查依赖模型判断，可能受提示措辞、图像分辨率、模型自身知识影响；虽然做了 κ 验证，但未做多 judge 交叉或对抗性扰动测试。
- **单次运行、无方差报告**：论文未报告多次采样的均值与置信区间，温度、随机种子、网页瞬时状态带来的波动无法量化。
- **任务覆盖的边界**：仅限 Google Workspace 三类产物与浏览器场景，未覆盖桌面应用、代码仓库、企业内网、需要登录/付费墙的页面；20 个领域中部分领域的任务数偏少，难以支撑领域级结论。
- **未评估安全与对抗维度**：提示注入、恶意网页、钓鱼弹窗等真实浏览风险未被纳入检查点，尽管实验中已观察到弹窗广告对智能体的干扰。

## 八、启示与未来方向

- **对智能体设计的启示**：
  1. 视觉观察不是可选增强，而是长时程办公任务的前提条件；
  2. 智能体循环（harness）的错误恢复、弹窗处理、状态回滚能力应与模型能力同等投入；
  3. 需要"计划—检索—综合—排版—自检"的分层架构，而非单轮"想—做"循环；
  4. 检索可信度必须可验证（网页访问检查的思路可反向用作智能体的自我校验机制）。
- **对评测范式的启示**：以"结构化产物 + 离散检查点"替代"单一可验证答案"，能在保持自动化的同时捕捉真实工作流的丰富性；指标应从严格到宽松分层报告（SR / ASC / ACF / SF），避免单一数字掩盖能力分布。
- **潜在扩展**：跨平台（Microsoft 365、Notion、Figma）、多人协作与共享状态、需要登录的真实工作流、带安全对抗的浏览环境、以及"人机协作"模式下智能体作为半自动助理的评估。

## 九、总体评价

- **贡献定位**：KNOWS 是首个把**实时网页检索、生产力工具编排、视觉/空间理解**三者合并进单一任务的基准，其价值不在于刷分，而在于指出"搜索只是开始，产物化才是困难所在"这一被现有基准系统性忽略的能力维度。
- **方法上的亮点**：任务设计准则明确可操作；检查点—评估步骤的分解使错误可归因；七类共享评估工具在丰富性与自动化之间给出了可复用的工程范式；评估器经过专家一致性验证，并配有维护/弃用政策，具备长期基准的基本要素。
- **实证上的说服力**：6 个模型–框架组合、双模态对照、步骤级归因、跨平台检验相互印证，得到"视觉必要、框架与模型同等重要、完整成功率 <3%"三个稳健结论。
- **主要保留意见**：缺少人类基线与方差报告、闭源系统的不可观测性、实时网页的可复现性折损，使其更适合作为"诊断性基准"而非"排行榜基准"；未来版本若能在受控缓存副本与真实网页之间做双轨评估，将同时改善可比性与生态真实性。
- **一句话结论**：KNOWS 揭示的核心事实是——当前智能体已经能在检索层面"找到答案"，却几乎无法在真实工作流中"交付作品"；从信息到产物的最后一公里，是下一阶段智能体研究必须正面攻克的主战场。
