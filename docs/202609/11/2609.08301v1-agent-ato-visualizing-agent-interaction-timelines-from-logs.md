## 摘要
AI 编程智能体正逐渐成为开发者工作流的一部分，但仅从最终代码变更很难理解其行为。在任务执行过程中，智能体会通过一系列动作与软件仓库交互，例如搜索文件、阅读代码、编辑程序以及运行测试或构建命令。这些交互连同 token 使用情况通常记录在控制台日志中，但原始日志难以供开发者检查。本文提出 Agent ATO（Agentic Trajectory Observer），一种用于从控制台日志可视化 AI 编程智能体交互时间线的工具。Agent ATO 提取智能体交互，按命令或工具类型对其分类，并将其可视化为时间线。除了全交互时间线外，Agent ATO 还提供过滤后的时间线，分别强调文件发现、文件读取、文件编辑和执行，同时保留上下文。我们使用来自两个修复任务的选定运行实例，说明 Agent ATO 如何帮助开发者检查和比较智能体动作。未来工作将把 Agent ATO 应用于更多智能体、任务和开发环境，并评估其是否减少比较轨迹所需的工作量。

## Abstract
AI coding agents are becoming part of developers' workflows, but their behavior is difficult to understand from final code changes alone. During a task, agents interact with software repositories through sequences of actions such as searching for files, reading code, editing programs, and running tests or build commands. These interactions, together with token usage, are often recorded in console logs, but raw logs are difficult for developers to inspect. In this paper, we propose Agent ATO (Agentic Trajectory Observer), a tool for visualizing AI coding agent interaction timelines from console logs. Agent ATO extracts agent interactions, classifies them by command or tool type, and visualizes them as timelines. In addition to an all-interaction timeline, Agent ATO provides filtered timelines that emphasize file discovery, file reading, file editing, and execution while preserving surrounding context. We illustrate how Agent ATO may help developers inspect and compare agent actions using selected runs from two repair tasks. Future work will apply Agent ATO to more agents, tasks, and development environments, and will evaluate whether it reduces the effort needed to compare trajectories.

# Agent ATO 论文总结

## 1. 核心问题与整体含义

- **研究动机**：AI 编程智能体（如 Pi 等）正逐步融入开发者工作流，但其任务执行过程无法仅从最终代码变更中理解。智能体在任务期间会通过一系列动作与软件仓库交互，包括搜索文件、阅读代码、编辑程序、运行测试或构建命令等。
- **核心痛点**：
  - 这些交互连同 token 使用情况通常记录在控制台日志中，但原始日志以时间顺序堆叠事件，**不清晰呈现交互类型及其顺序**，开发者需阅读冗长日志才能定位搜索、读取、编辑、执行等操作。
  - 这导致难以察觉过程级线索，例如编辑后缺少验证、失败后未进一步探索等。
- **整体含义**：论文提出 **Agent ATO（Agentic Trajectory Observer）**，一个从控制台日志可视化 AI 编程智能体交互时间线的工具，旨在帮助开发者检查过去运行并改进未来运行，而非自动诊断失败或推断隐藏意图。

## 2. 方法论

- **核心思想**：
  - 将 AI 编程智能体行为定义为由可观察的软件开发操作组成的**交互轨迹（interaction trajectory）**。
  - 一次「交互（interaction）」是由一次 LLM 响应发起、通过工具使用实现的连贯活动单元，如仓库导航、文件阅读、文件编辑或命令执行。
  - 将原始事件日志转化为按命令/工具类型分类的交互序列，并以时间线形式可视化。

- **关键技术细节**：
  - **输入**：Pi 编程智能体执行期间收集的事件日志，包括 LLM 消息、工具调用事件、bash 命令、工具结果、token 使用量、时间戳。
  - **交互重建**：在 Pi 中，一个 turn 由一次 LLM 响应及由此触发的工具调用组成；实现中将每个 `turn_start` 到 `turn_end` 的区间视为一次交互。
  - **标签分配**：基于 bash 命令、管道或工具名分配代表性标签（如 `find | grep | head`、`git diff`、`npm test`）。
  - **规则匹配打标**：为每个交互分配一个或多个标签——Discovery、Reading、Writing、Execution。

- **可视化三大组成部分**：
  1. **全交互时间线**：完整轨迹，每个矩形代表一次交互，从左到右按执行顺序排列（注意：不代表真实耗时或持续时间）。
  2. **过滤时间线**：复用同一交互序列，突出四个分析视角，未匹配的交互以灰色保留上下文：
     - **Discovery（蓝色）**：查找文件或信息的操作，如 `ls`、`find`、`rg`、`grep -l`。
     - **Reading（绿色）**：检查文件内容或 diff 的操作，如 `read`、`cat`、`grep`、`git diff`。
     - **Writing（红色）**：修改文件或仓库状态的操作，如 `edit`、`write`、`rm`。
     - **Execution（黄色）**：验证或执行操作，如运行测试、构建、linter、类型检查器或脚本。
     - 若一个交互属于多个视角，则使用混合色表示。
  3. **Token 使用量视图**：与时间线对齐，将每次交互的 token 分为 **LLM 输出 token** 与 **工具结果 token**，帮助区分高 token 消耗的来源。

- **实现与交互**：
  - 原型由两部分组成：用于收集 Pi 事件的 TypeScript 扩展（保存为 JSONL 文件）和用于生成可视化的 Python 脚本。
  - 生成**静态 HTML 文件**，无需运行独立可视化服务器即可在浏览器中打开。
  - 支持悬停显示标签并高亮相同标签交互、点击打开详情面板（标签、时间、token 使用、工具结果、命令输出）、选择连续交互序列并在轨迹中搜索相同操作模式。

## 6. 主要结论与发现

- **Case 1 发现**：在修复方向相似的尝试中，Agent ATO 暴露出验证行为的差异——Attempt 1 形成了重复的**编辑-验证循环**（Writing 后反复跟随 Execution，尤其是测试命令），而 Attempt 2 有多次 Writing 但**没有相应的 Execution 验证**。此外，Attempt 1 的首次验证需要更多中间交互（可能需先识别如何运行相关测试），后续验证则立即执行，提示可通过 prompt 要求早期测试识别与编辑后验证。
- **Case 2 发现**：高 token 使用量可能有不同来源——Attempt 1 的最大尖峰为橙色（LLM 输出 token），源于智能体反复重新考虑竞争性修复策略的长思考片段，属于**推理控制问题**；Attempt 2 的最大尖峰为蓝色（工具结果 token），源于文件阅读产生的大结果，属于**上下文管理或部分阅读问题**。二者对应的干预措施不同。
- **总体结论**：轨迹可视化可指导详细的日志检查，支持 prompt 调试与智能体设计讨论；Agent ATO 的目标不是自动诊断，而是帮助用户观察智能体做了什么、以什么顺序做、以及在哪里出现操作级或 token 级差异。

## 7. 优点

- **问题定位清晰**：准确捕捉到「最终补丁无法反映过程行为、原始日志难以人工检查」这一真实痛点，并提出直观的可视化解决方案。
- **设计简洁实用**：
  - 全交互时间线 + 四类过滤时间线 + 对齐的 token 使用图，三者组合覆盖了「做了什么、顺序如何、消耗在哪」三个关键维度。
  - 过滤视图中保留灰色上下文，避免用户在聚焦单一视角时丢失时间脉络。
  - 多标签交互使用混合色，处理了交互可能同时属于多个视角的现实情况。
- **区分 token 来源**：将 token 使用量拆分为 LLM 输出 token 与工具结果 token，这一设计能够区分「推理冗长」与「工具结果过大」两类本质不同的问题，具有实际诊断价值。
- **交互设计友好**：悬停高亮、点击下钻详情面板、连续序列模式搜索，实现了从概览到细节的渐进式探索，且不替代原始日志。
- **部署轻量**：生成静态 HTML 文件，无需运行独立可视化服务器，降低了使用门槛。
- **诚实的自我定位**：明确声明不推断隐藏意图、不自动诊断失败，并公开承认证据局限，学术态度严谨。
