## 摘要
当智能体编写代码时，开发框架便成为针对一个非确定性执行者的控制系统。自 2025 年以来，规格优先、智能体驱动的框架迅速获得关注；其中可安装的那些——GitHub Spec Kit、obra/superpowers、BMAD、GSD 以及我们自己的框架——都通过规格说明或持久化的规划产物来捕获意图。既然它们在事前捕获意图这一点上是一致的，那么真正将它们区分开来的，是各自如何强制执行那种使智能体所写代码保持整洁、正确且可维护的工程规范。每个框架都以某种方式强制执行这一规范，区别在于方式。我们刻画了三种模式：以说服来强制执行（提示层面的规范，模型可能忽略）、以预先加载的结构来强制执行（强有力的规格，随后是可信的构建），以及通过智能体无法编辑的控制手段来强制执行（确定性编排器、经人工批准的关卡、不可更改的测试，以及必须在实时分支数据库上通过的“绿灯”结果）。我们提出 Consort，一个建立在第三种模式之上的规格优先、测试驱动的智能体框架；它通过智能体身处其中运行却无法绕过的控制手段来强制执行这一规范：一个确定性编排器驱动各个独立的角色智能体，在实时数据库分支上依次经过规格优先的设计通道与测试驱动的构建通道。我们认为，在代码中强制执行测试与关卡，能使智能体编写的代码保持诚实且可验证；而它的那些专业化角色，一如先于它们的人类角色，正是其可维护性的来源。我们将这些主张表述为一个预先注册的、可检验的假设。

## Abstract
When an agent writes code, the development framework becomes the control system for a non-deterministic worker. Spec-first, agent-driven frameworks have gained rapid traction since 2025; the installable ones, GitHub Spec Kit, obra/superpowers, BMAD, and GSD, and our own, all capture intent through a specification or durable planning artifacts. Since they agree on capturing intent up front, what separates them is how each enforces the engineering discipline that keeps agent-written code clean, correct, and maintainable. Every framework enforces that discipline somehow; they differ in how. We characterize three modes: enforcement by persuasion (prompt discipline the model may ignore), by front-loaded structure (strong specs, then a trusted build), and through controls the agent cannot edit (a deterministic orchestrator, human-approved gates, immutable tests, and a green result that must pass against a live, branched database). We introduce Consort, a spec-first, test-driven agent framework built on the third, enforcing that discipline through controls the agent runs inside but cannot bypass, in which a deterministic orchestrator drives separate role agents through a spec-first design lane and a test-driven build lane on a live database branch. We argue that enforcing the tests and gates in code keeps agent-written code honest and verifiable, while its specialized roles, like the human roles before them, are what make it maintainable, claims we frame as a pre-registered, testable hypothesis.

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想：强制执行的三级强度分类学

论文的第一性原理是：**"当执行者是非确定性的，一个它可以选择忽略的控制就不是控制。"** 据此把家族框架分为三类，区分标准是**智能体在物理上能否忽略该控制**：

- **说服式强制执行（by persuasion）**：控制是提示词中的规则、红线与禁令（范例：obra/superpowers）。编排、关卡、测试最终都由模型遵守且可被模型编辑——能抬高行为下限，但无法使违规成为不可能。
- **前置结构式强制执行（by front-loaded structure）**：把规格与计划做扎实，然后交付任务清单并大体信任实现（范例：GitHub Spec Kit）。意图强、构建期强制弱，纪律在智能体接手构建的瞬间"蒸发"。
- **通过智能体不可编辑的控制强制执行（through controls the agent cannot edit）**：控制是智能体在其中运行但无法修改的代码。步骤路由是程序而非模型决策；每个决策由人审批把关；测试在工作单元内不可变；"绿灯"被操作化定义为测试运行器在实时数据库上真实通过。

### 2.2 Consort 架构：双通道 + 确定性编排器 + 角色智能体

**总体结构（Fig. 1 生命周期）**：项目受理（前置条件）→ 规划（PO，含计划关卡与待办选择关卡）→ **设计通道（规格优先）**→ **构建通道（实时分支上的 TDD）**→ 部署 → 晋升（PR/CI/合并）→ 已交付，并按增量循环。六个关卡（intake、plan、spec+test-list、per-story acceptance、deploy、promote）均为**人类决策的菱形节点**。

**（a）确定性编排器（orchestrator）**
- 是**状态机而非智能体**，不写规格、代码或测试；等价于敏捷团队中的 Scrum Master 角色，但以确定性代码实现。
- 职责：为每个工作单元切出数据库的 copy-on-write 分支、驱动 red/green/refactor 步骤、强制人类关卡顺序、工作单元完成后丢弃分支。
- 关键收益：路由是代码 ⇒ 控制回路**不会在上下文压缩（context compaction）中丢失**，也无法被"说服"跳过步骤；分支即夹具（fixture），分支销毁即重置；为每个实验打上设计指纹，设计变更时重新切分支而非静默复用。

**（b）角色分离智能体（role-separated agents）**
- 角色：产品负责人（PO）、规格作者（SA）、架构评审（AR）、DBA、测试策略师（TS）、UX 设计师（仅面向用户的工作），以及构建循环中的**领航员（NAV）与驾驶员（DRV）**。
- **角色是编排器强制的有界职能**：角色不能做别的角色的工作，角色之间**不共享记忆**，全部通过磁盘产物传递（与 BMAD 的"角色扮演人格"形成对比——后者由模型遵守，非强制边界）。
- **UX 设计师**：用浏览器打开 brief 中指定的参考站点，读取真实的字体、颜色、间距；无指定则检索代表性站点，使每个设计 token 都引用可观察的参考而非默认值。
- **测试策略师**：作为监督者而非唯一作者，向按测试类型（行为、fitness、客户端）分派的分析师智能体扇出，再归并与排序为单一测试清单。
- **部署与晋升不是角色智能体**，而是编排器直接运行的确定性步骤，日志记于 release-engineer 标签下。
- 角色分离的两重作用：① **完整性守卫**——同时写代码和评判代码的智能体会倾向宽松评分；② **可维护性来源**——复现人类团队的分工（需求拥有者、实现者、评审者），让每个关注点都有专职负责人。

**（c）构建通道：在实时数据库分支上跑完整 TDD**
- 完整 red/green/refactor 循环（含快速内循环）针对**真实生产形态数据库的 copy-on-write 分支**运行，而非 mock 或合成种子夹具。
- copy-on-write 分支让每个工作单元获得隔离、一次性分支，**近乎常数时间**（与数据规模无关，因分支与父库共享存储直到分叉）。
- 该数据库实践本身来自一篇**匿名审稿中的论文 [11]**，本文将其作为既定前提，贡献在于"如何对非确定性作者强制执行该实践"。
- 因分支廉价且隔离，构建通道可为同一故事**并行运行多个实验**（各自独立数据库分支 + git worktree），保留最满足测试者。

**（d）强制原语（enforcement primitives）**
- **测试在工作单元内不可变**：已批准的测试清单被锁定，循环内删除或弱化测试会被捕获并标记。唯一受控例外：后续故事合法取代先前测试时，由指定步骤在明确规则下**仅重构被取代的测试**并重新验证；普通的失败测试永不触碰。
- **绿灯按定义诚实（honest green）**：只有当测试运行器**真的**在真实分支上通过时才记录成功，而非智能体声称通过（Fig. 2：verify 失败 → 要么是有界代码修复（绝不改测试），要么是规则约束的 permissive-green（仅重构被标记的取代测试），未决情况升级到人类）。
- **跨故事字段契约在写码前检查**：若一个故事要求必填字段，而拥有用户提交路径的故事没有提供该字段的验收标准，设计通道会标记该缺口，而非让功能进入构建并交付一个数据库会拒绝的表单。
- **人类杠杆**：PO 可标记某故事需要端到端测试，设计通道**不能降级**该要求。

**（e）实时数据验证即绿灯条件**
- 每次 verify 都在为该检查新切的分支上运行，完成后丢弃，因此结果反映已提交的 schema 而非累积状态。
- 同时封堵智能体两条最廉价的逃脱路径：不能删测试（不可变），不能用合规 mock 替代真实行为（协作者是真实数据库而非可塑的双替身）——这是对"过度 mock"失效模式的结构性反制。
- 绿灯要求代码在**生产形态数据**上真正可用，且数据库的约束与治理（从分支继承的访问与脱敏策略）生效。

**（f）设计通道**
- 意图被捕获为**规格 + 将证明它的测试清单**，二者在批准关卡处**冻结并哈希**，之后做漂移检查，使智能体构建的目标不能悄悄移动。这是 spec-first，与比较对象相同；差别在于冻结的规格与测试清单喂入的是一个**结构性强制**的构建通道。

**（g）上下文管理**
- 因角色不共享记忆、全部经由磁盘产物传递，**任何一轮都可冷重载**，全新开始总是安全的。
- 编排器跟踪每个会话的 token 使用量：当热恢复会使剩余窗口低于可配置比例（**默认 40%**）时，下一轮改为全新开始；在廉价处保留热恢复（跨故事循环复用 prompt 缓存）。
- 每轮只交给智能体一个**上下文包**（必须通过的精确测试、相关需求、测试所在位置），而非整个代码库，降低开销并消除无范围游荡。

## 3. 实验设计

**本论文没有进行任何实证实验。** 其"评估"是**分析性对比**，加上一个**预注册的未来实验计划**。

- **对比对象（5 个可安装、智能体写代码的框架）**：
  - **GitHub Spec Kit**（spec-first；命令流水线从 constitution 到实现与收敛；TDD 可选且无门禁；constitution 仅为散文；无确定性编排器；无数据库在环）。
  - **obra/superpowers**（spec-first；以自动触发的 agent skills 交付；强 test-first 规则但**未强制**；控制回路本身是 LLM；关卡是软散文；无数据库概念）。
  - **BMAD**（spec-anchored；人格化角色协写 PRD 与架构文档；修订窗口内新增 bmad-loop 确定性编排器与代码强制的 test-architect 关卡，但**在史诗之后**强制覆盖率/质量阈值，循环内不强制 TDD，无数据库在环）。
  - **GSD**（spec-anchored；五阶段循环 discuss/plan/execute/verify/ship；强于上下文卫生与可移植性；强制保持薄——约定与 hook 级；无 TDD、无数据库）。
  - **Consort**（本文）。
- **对比维度（Table I，8 个维度）**：SDD 层级、规格是否冻结/漂移检查、TDD、测试不可变性、数据库在环、编排方式、关卡性质、角色分离、上下文管理。
- **被点名但未评估的相邻系统**：Tessl、Kiro（托管型、spec-as-source 或规格驱动 IDE）、自治的 issue-to-PR 智能体。
- **预注册实验设计（第六节，未来工作）**：
  - 固定同一智能体与同一任务，**仅改变强制执行机制**；任务取自**有状态的、产业相关的特性**而非无状态 kata；每个框架用同一底层模型实现同一批特性。
  - **五类度量**：① 静默回归（通过框架自身关卡但被独立留出测试套件捕获的缺陷）；② 测试作弊（被删除/弱化/调整以强制变绿的测试，直接计数）；③ 可维护性（独立评审 + 重复率、规格到代码漂移等客观代理指标）；④ 真实行为覆盖率（使用真实数据库而非替身的测试占比）；⑤ 成本（固定模型下每交付特性的 token 数，与质量指标一起报告，即"每 token 花费换得的质量"）。
  - **评分工具**：LLM-as-judge，固定模型、固定参照；Consort 自带该评估包（固定模型判别器，将输出分类为 equivalent / superseded shift / regression / insufficient）。因其属于被测系统，计划**开源并中立化**，并绑定五重保障：中立参照（预注册、独立于任何框架编写）、判别器与生成器解耦（不同模型或集成，报告评委间一致性）、人类校准（对照专家评分并报告一致性）、盲化（评委不知输出由哪个框架产生）、独立执行（由非框架作者方运行与评分）。

  - 作为**分类学与设计论文**，分析对比在"可读性与框架定位"上是充分的，且对比较对象的描述相当具体（版本、能力边界、甚至承认 BMAD 在修订窗口内新增了确定性编排器，从而不再让 Consort 独占该特性）。
  - 作为**效果主张的证据**，则**完全不充分**：论文明确承认"分析性对比确立了 Consort 强制了别人只是请求的东西，但它本身并未确立强制会产生更好的代码"，并把输出质量主张**明确表述为假设**而非结论。
- **公平性与客观性风险（论文自陈）**：
  - **作者即被测框架之一（Consort）的构建者**——双重角色，必须声明并以框架中立任务、独立评审者、邀请复现来缓解。
  - **框架间 harness 可移植性不同**，必须固定智能体才能让比较针对"强制机制"而非工具链。
  - **可维护性是一个操作性定义本身就有争议的构念**，必须事先固定。
  - 评分用 LLM-as-judge，作者承认自己的评估包属于被测系统，直接使用不独立，故提出五重保障。
  - 论文的证伪姿态值得肯定：**预先注册假设与各效应的方向，但不断言目标量级**。

## 6. 主要结论与发现

- **分类学结论**：规格优先家族在意图捕获上趋同，差异在于强制执行；三种模式的区别不在于质量刻度，而在于"当智能体可以忽略某个控制时，是什么让它仍然遵守"。
- **Consort 的定位**：是第三种模式（智能体不可编辑的控制）的参考实现——编排器是代码、每个决策由人类把关、测试不可变、绿灯是真实数据库上的真实运行。它**在代码作者身份发生的那一刻、针对真实数据**实施强制，而其他框架只是"请求合规"或"事后强制"。
- **唯一无争议的维度**：**实时分支数据库在环**。没有任何比较对象把数据库放进循环（Spec Kit 止于设计期数据模型；superpowers/BMAD/GSD 无数据概念）。论文精确界定新颖性："针对数据库做测试"是旧事，集成与验收测试一直如此；**新的是以低到可常规化的单周期成本，把整个循环（含快速内循环）跑在真实数据的分支上**。这一轴是输出质量主张的最终落脚点，因为它是唯一改变"智能体被验证的对象"而非"其流程如何被控制"的维度。
- **诚实的让步**：BMAD 的 bmad-loop 使确定性编排与代码强制门禁**不再为 Consort 独有**；但在"被把关的内容"上（不可变测试 + 实时分支数据库上的真实测试通过），Consort 仍然独行。
- **承认比较对象领先之处**：可移植性更强（跨多编码智能体、harness、

harness、IDE 集成），而 Consort 绑定在特定实现上；工具链的成熟度与生态接入度不及成熟框架；Consort 需要真实数据库与分支基础设施作为前提，部署与学习成本更高。论文对此的态度是"用强制力换便携性"，并把它列为需要在预注册实验中量化的代价维度之一。

- **对"可维护性"的因果链条假设**：论文提出角色分离是可维护性的结构性来源——把需求拥有者、实现者、评审者三种关注点分派给互不共享记忆的智能体，使"同时写代码又评判代码"的宽松倾向被制度性地阻断。这一因果主张目前是**机制论证而非实证结论**，被明确放入待检验集合。

- **总体结论的措辞克制**：全文最核心的可证伪命题可概括为——**在代码作者非确定的前提下，"智能体无法编辑的控制"应比"智能体可以选择遵守的控制"产出更整洁、更正确、更可维护的代码，而实时数据库分支在环是其中唯一改变"被验证对象"的维度。** 论文把前半句设为假设、把后半句设为新颖性主张，二者都留待实验裁决。

## 7. 局限性与批判性视角

- **证据层级**：作为立场/架构论文，其全部说服力来自设计论证与分类学清晰度，而非数据。论文对此高度自觉，反复使用"确立了强制了什么，未确立强制带来更好代码"这类限定语，这是学术诚实的表现，但也意味着**任何关于效果的引用都不应超出作者自身的声明**。
- **利益冲突**：作者是 Consort 的作者，同时提出对比框架并设计评估协议。论文以"框架中立任务 + 独立评审 + 邀请复现 + 五重保障"缓解，但结构性风险仍在——包括比较维度的选择本身（8 个维度中多个维度恰是 Consort 的强项）。
- **可移植性与公平比较**：不同框架的 harness 抽象层级不同，若固定智能体则部分框架的固有优势被抹平，若不固定则比较对象从"强制机制"漂移到"工具链质量"。这一两难在论文中被识别但未解决。
- **基础设施依赖**：Consort 的核心主张（分支上跑完整 TDD、每轮新切分支、并行实验）预设了支持 copy-on-write 分支的数据库。论文引用的数据库分支工作本身尚在匿名审稿中，**前提的可用性与普适性未被独立确认**；对无此基础设施的团队，该方法难以直接迁移。
- **成本未被量化**：多角色智能体、每轮一个上下文包、按故事并行多实验、40% 窗口触发冷重启——这些设计都指向更高的 token 与延迟开销。论文把成本列为待测度量，但没有给出量级预估或复杂度分析。
- **适用边界未界定**：论文的预注册任务刻意选择"有状态的、产业相关的特性"，这暗示方法在有状态、数据密集的后端场景收益最大；对无状态算法题、纯前端、探索性原型或研究性代码，强制结构可能成为负担而非助力。论文未正面讨论不适用情形。
- **人类关卡的隐含成本**：六个关卡全部是人类决策节点。这在"信任但验证"的意义上是优点，但也把吞吐量上限绑定在人类审批速度上，论文未讨论关卡密度对实际交付节奏的影响。
- **"诚实绿灯"的边界**：绿灯被操作化为"测试运行器在真实分支上真实通过"，这排除了智能体的自我声称，但**测试本身的质量**仍由测试清单决定；若清单本身覆盖不足（例如缺少边界与并发用例），绿灯依然可能是"正确地通过了错误的测试"。测试策略师的角色分离缓解而非消除这一问题。

## 8. 对领域与实践的启示

- **设计原则可迁移**：即便不采用 Consort，"当执行者非确定时，可被忽略的控制不算控制"是一条可独立采纳的第一性原理。任何智能体工作流都可自问：我这条规则，智能体在物理上能否绕过？若能，它是提示词，不是约束。
- **把流程状态从上下文移到代码**：编排器是状态机而非智能体，使控制回路在上下文压缩、会话重启、模型替换后仍然存在。这对长周期、多轮次的智能体工程具有普遍价值。
- **夹具即分支、重置即销毁**：以一次性分支替代共享测试环境，把"测试隔离"从约定升级为物理事实，同时让并行实验成本近乎常数。这一模式可能超出数据库范畴，启发更一般的"按工作单元物化环境"实践。
- **角色边界的强制化**：把角色从"人设提示"升级为"编排器强制且不共享记忆的职能"，是对"智能体自我评判偏宽"的直接结构性回应，也可缓解长上下文中的角色漂移。
- **评估方法论贡献**：五类度量（静默回归、测试作弊、可维护性、真实行为覆盖率、每交付特性 token 成本）与五重评分保障（中立参照、判别器解耦、人类校准、盲化、独立执行），构成了一套可复用的智能体框架评测协议，其价值可能独立于 Consort 本身。
- **对"氛围编程"的回应姿态**：论文不否认观察式开发的效率叙事，而是主张在可维护性、正确性这类不可事后轻易修复的属性上，必须把验证前移并以代码固定。

## 9. 总结性判断

本文的贡献层次清晰：**分类学（三种强制执行强度）> 参考实现（Consort 的双通道架构与强制原语）> 可检验假设（预注册实验设计）**。它不提供效果证据，也不声称提供；它的价值在于把"规格优先框架之间的差异"这一常被模糊讨论的问题，重新定位为一个可操作、可比较、可证伪的维度——**智能体能否忽略该控制**。其最锋利的洞察是：规格本身已不是区分点，真正区分框架的是规格冻结之后、在真实数据上、于代码作者身份发生的那一刻所施加的强制力。其最大的软肋同样明确：全部质量主张仍是假设，作者身处被测系统之内，且方法依赖尚待确认的数据库分支基础设施。因此，本文应被读作一份**设计宣言与实验协议**，而非一份效果报告。
