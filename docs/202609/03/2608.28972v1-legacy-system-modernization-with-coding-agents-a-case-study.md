## 摘要
基于已停用平台构建的遗留系统，是依赖这些应用程序维持关键业务流程的组织中反复出现的技术负担。尽管现代化在战略上是必要的，但完全通过人工方式执行时，成本高昂且容易出错。在本文中，我们报告了一项在真实工业环境中进行的案例研究，评估了AI编码代理在支持遗留系统向现代平台迁移方面的有效性和效率。通过使用Claude Code代理的一个版本，我们在单代策略下，将企业资源规划（ERP）系统中用Visual Basic 6编写的12个复杂度不同的功能迁移到了C# .NET 10。迁移会话完成后，我们测量了迁移后功能与原始功能的等价性，并收集了代理在过程中花费的时间和消耗的令牌数量数据。在我们的实验中，代理的平均等价性达到70%，且不同复杂度水平之间存在显著不对称：低复杂度功能达到92%，而高复杂度功能得分为47%。在基于成本的指标中也观察到类似的不对称性；低复杂度功能消耗了147万令牌（1.66美元），而高复杂度功能使用了909万令牌（10.28美元）。我们揭示了这种迁移策略在哪些实际场景和情况下更为有效，并讨论了使用AI代理进行遗留系统现代化的局限性和挑战。

## Abstract
Legacy systems built on discontinued platforms are a recurring technological liability in organizations that depend on these applications to sustain critical business processes. Although modernization is strategically necessary, it is costly and error-prone when performed exclusively through manual effort. In this paper, we report on a case study conducted in a real industrial setting, where we evaluate both the effectiveness and efficiency of AI coding agents in supporting the migration of legacy systems to modern platforms. By using one version of Claude Code agent, we migrated 12 features of distinct complexity levels from a corporate ERP system written in Visual Basic 6 to C# .NET 10 under a single-generation strategy. Once the migration sessions were completed, we measured the equivalence of the migrated features against the original ones, and collected data about the time spent and the number of tokens consumed by the agent during the process. In our experiment, the agent achieved an average equivalence of 70%, with a strong asymmetry across complexity levels; low-level features achieved 92%, and high-complexity ones scored 47%. Similar asymmetry was observed in the cost-based metrics; low-level features consumed 1.47M tokens ($1.66), whereas high-level ones used 9.09M ($10.28). We reveal the practical scenarios and circumstances where this migration strategy is more effective, as well as discuss the limitations and challenges of using AI agents for legacy system modernization.

- **总体思路**：采用**单代生成（single-generation / single-pass）策略**——即让智能体在一次性会话中完成整个功能模块的迁移，期间完全自主运作，不引入人工反馈或迭代优化。
- **研究对象与环境**：

- **实验单元划分**：
  - 从两个模块中共选出 **12 个功能**（每模块 6 个），覆盖低（6个）、中（4个）、高（2个）三种复杂度级别。
  - 复杂度分级标准依据三类源码指标联合判定：**代码行数、方法数量、类依赖数量**（至少满足两个阈值条件）。

- **效率度量方法**：

## 6. 论文的主要结论与发现

- **RQ1（等价性）主要发现（Finding #1）** ：
  - 综合等价性均值为 **70%**：持久化维度 71%、功能维度 69%；
  - 随复杂度呈明显漏斗式衰减——低复杂度 **92%**、中复杂度 **81%**、高复杂度仅 **47%**；
  - 高复杂度存在质变：不只是写错，而是**整体模块缺失**（如消费计算中的审批工作流模块被整个漏掉）。
- **RQ2（效率/成本）主要发现（Finding #3）** ：
  - 单功能平均耗时 **4min 54s**、费用 **$4.19**、消耗 3.81M tokens；
  - 输入 token 占绝对主导（99.6%），输出仅占极小比例——成本瓶颈是“模型反复阅读与推理”，对输出量不敏感；
  - 低复杂度功能平均成本 $1.66，高复杂度 $10.23，相差 6 倍以上。
- **失败机理（Finding #2）** ：
  - 100 条迁移失败中：**缺失相邻模块 42 例**（如批量导入、报表、邮件通知等）、缺失特定 DB 操作 22 例、缺失具体规则 20 例、缺失跨模块集成 10 例、错误实现仅 6 例；
  - **规律：绝大多数失败是“该做的没做”（遗漏），而不是“做错了”。** 智能体习惯聚焦“主流程+显式规则”，容易忽略散落在表单事件、条件分支或相邻方法中的隐式行为。
- **结构模式洞察（Section 5）** ：
  - 将业务规则集中封装在领域类（.cls）中的功能迁移成功率远高于同类规则散落在 UI 事件里的功能——**代码结构碎片化是智能体的最大天敌之一**；
  - 显式规则（独立验证方法、明确的 SQL）比隐式约束（查询过滤器、动态配置、可选参数）更容易被正确迁移；
  - 中复杂度功能的规则集中度较高，因此功能等价性反而超过了一些规则分散的低复杂度功能（如 F9 仅67%，低于 F10 的92%）。
- **整体结论**：对低复杂度、边界清晰、代码结构集中的功能，AI 智能体已具备实用价值的半自动迁移能力；但对高复杂度或包含大量跨模块业务流程的功能，需人工兜底或先做功能拆分。

## 7. 优点与亮点

- **真实工业场景**：不同于基于公开代码库的合成任务，使用了运行超过20年、服务200+真实客户的 VB6 ERP，生态效度高、实战参考价值突出。
- **评估体系可复制**：提出一套可普及的量化迁移质量方法——先对遗留系统做“规则/DB操作”编目，再映射到新代码做逐条比对，兼具持久层和行为层双重验证，比单纯“能编译或能通过单测”更为严格。
- **长上下文窗口的巧妙利用**：让智能体在 1M token 窗口内同时读取全套遗留源码、目标工程模板与架构说明，接近现实中的小规模仓库级迁移任务；
- **成本数据透明**：公开了模型定价、token 构成和每功能实际支出，能为后续同行估算投入产出提供明确锚点；
- **审慎的第二评审机制**：对主观性最强的功能规则判定环节引入 Cohen's Kappa 检验，大幅增强结论可信度。
- **故障分类细致**：对100个失败案例做了细粒度归因（缺失相邻模块/缺失规则/缺失DB操作/缺失集成/错误实现），没有止步于“得到了多少分”，而是回答了“为何失分”，对改进方案富有启发性。

## 8. 不足与局限

- **泛化覆盖窄**：仅使用单一智能体（Claude Code 2.1.96）+ 单一模型（Opus 4.6 1M）+ 单一迁移方向（VB6→C# .NET），未扩展到其他语言组合（如COBOL→Java、Delphi→TypeScript），作者指出趋势可能比绝对值更有普适性，但仍需多方复制研究证实；
- **未设置对照组**：没有纯粹人工迁移的耗时与质量基线，也没有对比其他代码翻译工具或其他Agent，难以精确回答“比人工好省多少”的效益问题；
- **高分复杂度样本太少**：高复杂度功能的只有2个样本且分属不同模块，任何单点失败都会对结论有较大扰动，结论更偏指示性而非确证性；
- **单代策略局限**：作者刻意采用了“一次生成、不加入工迭代”的策略来测试Agent自主性；但这意味着没有测试“人在回路”迭代式迁移能提高到何种程度（参考相关研究显示迭代法可显著提升等价性），因而实验结果不能外推至交互式迁移场景；
- **人工编目成本高**：迁移前对每条规则/DB操作的编目依赖维护该系统的资深工程师手工完成，对于缺乏此类资深人员的组织而言，这套方法论的前期门槛可能限制其广泛采用；
- **未测量运行时性能与可维护性**：论文聚焦功能等价与迁移成本，未评估迁移后系统的运行性能、代码可读性、长期可维护性等技术债务变化；
- **输出“可运行但未被接线”的隐性缺陷**：部分规则被正确重写，但未接入实际调用链（如F5的IMEI唯一性校验），作者在评审者分歧中才暴露这一点，说明现行评估指标仍可能高估真实完成度。
