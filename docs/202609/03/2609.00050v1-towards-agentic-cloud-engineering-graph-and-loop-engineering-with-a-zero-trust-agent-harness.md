## 摘要
智能体AI正在推动基于云的工作流，其中自主智能体对运行状态进行推理、调用经授权的工具、修改软件和基础设施、部署服务、验证执行结果，并在长时间跨度、多步骤任务中进行自适应。工程化此类工作流需要显式机制来支持流程推进、受限执行、故障恢复和可验证的完成。我们提出了智体云工作流工程（Agentic Cloud Workflow Engineering），这是一个将自然语言智能体云工程任务转化为经过验证的代码仓库和经过验证的运维云部署的智能体AI框架，用于自动化基于云的智能体工作流。该框架分离了三个互补的关注点：图工程（graph engineering）规定长时间工作流的推进和依赖验证的转换；循环工程（loop engineering）提供有界诊断、修复或重新规划、重试和重新验证；智能体框架工程（agent harness engineering）通过身份、授权、策略限定的能力、隔离和运行时保障来强制执行零信任执行。工作流的推进和完成需要机器可检查的仓库、部署和运行时证据，恢复则受显式操作边界和终止标准约束。我们在Google Cloud上实例化了该框架，并评估了仓库完整性、受控执行、证据门控推进、运维部署和有界恢复。实验结果表明，执行要么以经过验证的运维云部署结束，要么在有界恢复下以可审计的终端失败告终。该框架为基于云的工作流提供了统一的工程架构，涵盖Agentic DevOps、Agentic CloudOps、Agentic SRE/AIOps、Agentic SecOps、Agentic DataOps、Agentic MLOps/LLMOps、AgentOps、Agentic RAG/GraphRAG及相关云工程领域。

## Abstract
Agentic AI is enabling cloud-based workflows in which autonomous agents reason over operational state, invoke authorized tools, modify software and infrastructure, deploy services, verify execution outcomes, and adapt across long-horizon, multistep tasks. Engineering such workflows requires explicit mechanisms for workflow progression, constrained execution, failure recovery, and verifiable completion. We present Agentic Cloud Workflow Engineering, an agentic AI framework that transforms natural-language agentic cloud-engineering tasks into validated code repositories and verified operational cloud deployments for automating cloud-based agentic workflows. The framework separates three complementary concerns: graph engineering specifies long-horizon workflow progression and verification-dependent transitions; loop engineering provides bounded diagnosis, repair or re-planning, retry, and re-verification; and agent harness engineering enforces zero-trust execution through identity, authorization, policy-scoped capabilities, isolation, and runtime safeguards. Workflow progression and completion require machine-checkable repository, deployment, and runtime evidence, with recovery constrained by explicit operational bounds and termination criteria. We instantiate the framework on Google Cloud and evaluate repository completeness, controlled execution, evidence-gated progression, operational deployment, and bounded recovery. Experimental results show that executions terminate with either a verified operational cloud deployment or an auditable terminal failure under bounded recovery. The framework provides a unified engineering architecture for cloud-based workflows spanning Agentic DevOps, Agentic CloudOps, Agentic SRE/AIOps, Agentic SecOps, Agentic DataOps, Agentic MLOps/LLMOps, AgentOps, Agentic RAG/GraphRAG, and related cloud-engineering domains.

## 论文结构化总结

### 1. 核心问题与研究动机

- **背景**：智能体AI（Agentic AI）正被广泛应用于云工程领域，组织需要自主智能体在云平台上完成规划、编码、部署、运维、监控、验证与适配等长跨度多步骤任务。
- **核心问题**：尽管智能体已具备较强的推理与工具调用能力，但云工程工作流需要显式的机制来回答三个关键问题：
  - **流程向何处推进**（workflow progression）？
  - **失败如何被诊断与修复**（failure recovery）？
  - **智能体的权限、工具与运行边界如何约束**（constrained execution）？
- **深层挑战**：已有方法通常依赖智能体自我报告的"任务完成"，缺乏可验证的完成标准；多步骤云工程中的失败恢复若无明确边界，可能导致无限循环、权限失控或不可审计的状态。
- **论文目标**：提出统一的框架，将自然语言云工程任务转化为**经过验证的代码仓库**与**经过验证的云部署**，并保证执行要么以**可验证的完成**终止，要么以**可审计的失败**终止。

### 2. 方法论：三大工程抽象

该框架采纳核心思路：将云工程工作流分解为三个互补的工程关注点，以便实现**解耦的、模型无关的执行控制机制**与**以证据而非智能体自述为门控条件的完成判定**。

#### 2.1 图工程（Graph Engineering）

主要目标是回答“工作流应如何推进”：
- 将工作流显式组织为节点（智能体、动作、状态）、边（转换、条件分支、依赖）和终止状态。
- 转换条件受**验证证据**门控：例如，未通过仓库验证就不能进入部署阶段，未通过部署验证就不能进入运行时监控阶段。
- 图编排器（Graph Orchestrator）使用 LangGraph/Google ADK 实现，协调仓库生成、仓库审查、执行与部署、验证、运行时监控五个核心智能体。

#### 2.2 循环工程（Loop Engineering）

主要目标是回答“失败后如何恢复”：
- 失败触发循环：诊断（Reflection/Diagnosis）→ 修复或重新规划（Repair/Re-plan）→ 重试 → 重新验证。
- 循环必须**有界**，受以下硬性预算约束：
  - 重试次数上限（默认 20 次）
  - 时间预算（默认 120 分钟）
  - 模型 Token 预算（默认 10,000,000）
  - 工具调用预算（默认 500 次）
  - 成本、权限（最小权限）、爆炸半径限制
- 若预算耗尽而关键验证条件仍未满足，执行进入**可审计失败状态**，不允许无限循环。

#### 2.3 智能体框架工程（零信任 Agent Harness Engineering）

主要目标是回答“什么动作可以被执行”：
- **身份与认证**：IAM、Workload Identity Federation（无长期凭据）
- **授权**：基于角色（RBAC）与基于属性（ABAC）的访问控制
- **策略执行**：OPA Gatekeeper 策略即代码 + 审批门（approval gates）
- **隔离**：VS Code 沙箱（代码操作）、Chrome 沙箱（浏览器操作）、GKE Sandbox + gVisor（部署与验证操作隔离）
- **网络安全**：Cilium NetworkPolicy、Cloud Service Mesh、Secure Web Proxy
- **软件供应链**：构建、测试、Semgrep（静态分析）、Gitleaks（密钥检测）、Checkov（IaC 策略检查）、Trivy（漏洞扫描）、SLSA 来源证明；GitOps via Argo CD、策略门控 Terraform
- **可观测性/审计**：OpenTelemetry、Prometheus、Cloud Logging/Trace
- **状态管理**：Redis（会话）、Spanner（持久工作流状态）、AlloyDB + RLS（租户隔离数据）

#### 2.4 完成判定公式

成功完成 ⟺ RepoValid(R*, Z*) ∧ DeployVerified(D*, Z*) ∧ RuntimeVerified(D*, Z*)

即三重验证条件（仓库、部署、运行时）**必须全部成立**，且需要机器可检查的证据（保留在 Cloud Storage）加以证明，而非仅凭智能体自述。

### 3. 实验设计

#### 3.1 基准（Benchmark）
- 作者指出：**此前不存在**评估端到端智能体云工程的基准，因此构建了 14 个领域的基准（共 140 个自然语言任务，每个领域 10 个）：
  - Agentic DevOps、CloudOps、SRE/AIOps、SecOps、DataOps、MLOps/LLMOps、AgentOps、RAG/GraphRAG、数据库运维、网络运维（NetOps）、IAM、治理/合规、推理运维（Inference Operations）、FinOps
- 每个任务要求端到端完成仓库生成、云部署、运行时验证。

#### 3.2 受控条件（6 种）
每个任务在 6 种条件下评估：
1. 名义执行（no perturbation）
2. 仓库验证扰动（注入仓库级失败）
3. 部署验证扰动
4. 运行时验证扰动
5. 授权策略违规（引入越权或越范围调用）
6. 恢复预算耗尽（保证验证条件持续失败直至预算用尽）

共 **140 × 6 = 840 条件-任务执行/模型**；4 个新近模型共 3,360 次执行。

#### 3.3 对比模型
- Gemini 2.5 Flash-Lite、Gemini 2.5 Flash、Gemini 2.5 Pro、GPT-5.6 Sol（均使用默认配置，无任务特定调优）
- 对比按 6 个研究问题（RQ1-RQ6）对应的 6 个指标展开：VTCR、EGER、RSR、UCDR/ACPR、BTR、跨领域汇总。

#### 3.4 消融实验
- **消融 1（恢复循环）**：禁用 Reflection/Diagnosis 与 Repair/Re-plan 路径 → VTCR 从 95.0% 降至 12.9%（GPT-5.6 Sol），证明有界恢复对完成任务至关重要。
- **消融 2（验证门控）**：将机器可检查的验证门控替换为模型自行判断 → EGER 从 100.0% 降至 99.0%（4/420 次出现未经验证的推进，集中在运行时验证环节），证明显式验证门控能消除残差错误。

### 6. 主要结论与发现

1. 端到端智能体云工程自动化可行：最强的 GPT-5.6 Sol 在名义执行下达到 95.0% 的完整任务成功率（133/140 完成验证）。
2. 模型能力差异显著：Gemini 2.5 Flash-Lite 与 GPT-5.6 Sol 差距巨大（VTCR 56.4% vs 95.0%；RSR 51.0% vs 93.1%），印证了模型推理能力在完成长跨度任务中的关键作用。
3. 证据门控有效：验证条件不满足时，所有模型中无一例越过门控或提前宣告完成（EGER 100.0%）。
4. 有界终止可靠：恢复预算耗尽后，所有执行均进入可审计失败状态（BTR 100.0%）。

7. 修复难度梯度：仓库验证失败最易修复，部署验证次之，运行时验证最难修复（跨模型一致的结论）。

### 7. 优点

- **概念清晰、抽象完整**：用"图（去哪儿）+ 循环（怎么恢复）+ 框架（什么能做）"三分法精确切割了智体工作流工程中的核心问题，具备较高的概括力。
- **用证据而非语言来判定完成**：以存储的机器可核查证据（仓库/部署/运行时）作为流程推进与完成的唯一依据，避免了大模型常见的“幻觉完成”问题，是本工作最重要的设计亮点。
- **零信任设计系统化**：从身份、授权、隔离、供应链、观测审计到租户隔离，形成了纵深防御体系。
- **评估维度全**：六类 RQ 从“能否完成”延伸到“能否受控失败”“能否拒绝越权”，比通常只报成功率的评测更全面。
- **消融刻画精确**：通过去除恢复循环和替换验证门控，定量分析了各组件的核心贡献，支撑设计选择的有效性。
- **跨任务、跨模型实验规模大**：3,360 次执行足够支撑核心结论的可信度。

### 8. 不足与局限

- **平台单一性**：所有实验均基于 Google Cloud，关键机制（IAM、GKE、gVisor、Argo CD 等）与谷歌生态深度耦合。AWS/Azure 的可迁移性和全套架构效果尚待验证。
