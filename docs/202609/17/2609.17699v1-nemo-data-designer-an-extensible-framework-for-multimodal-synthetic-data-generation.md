## 摘要
我们提出 NeMo Data Designer（NDD），一个开源、通用的多模态合成数据生成（SDG）框架。NDD 设计得直观易用，提供声明式配置格式，人类和/或智能体用户可在其中定义每个数据集列，列类型涵盖文本、代码、结构化输出、图像、嵌入以及统计采样器，这些采样器可被显式配置以引导数据集多样性。借助该框架灵活的插件系统，可以引入额外的列类型和功能。NDD 的配置是一种可检查的产物，支持工作流共享和可复现性。SDG 本质上是一个迭代过程。因此，NDD 将预览与修订循环构建到其核心工作流中，使用户能够生成并检查少量记录、完善规范，然后大规模重新运行生成。在运行时，NDD 解析依赖关系，调度对用户提供的模型端点的调用，并重试失败的请求。我们描述 NDD 的架构和编程模型，并展示跨结构化、智能体、多模态和领域专用任务的案例研究，包括用于 Nemotron 模型开发和生产型企业部署的数据集。

## Abstract
We present NeMo Data Designer (NDD), an open-source, general-purpose framework for multi-modal synthetic data generation (SDG). Designed to be intuitive to use, NDD provides a declarative configuration format in which human and/or agent users define each dataset column, with column types spanning text, code, structured outputs, images, embeddings, and statistical samplers that are explicitly configured to steer dataset diversity. Additional column types and functionality can be introduced using the framework's flexible plugin system. NDD's configuration is an inspectable artifact, supporting workflow sharing and reproducibility. SDG is an inherently iterative process. NDD therefore builds a preview-and-revision loop into its core workflow, allowing users to generate and inspect a small number of records, refine the specification, and rerun generation at full scale. At runtime, NDD resolves dependencies, schedules calls to user-provided model endpoints, and retries failed requests. We describe NDD's architecture and programming model and present case studies spanning structured, agentic, multimodal, and domain-specialized tasks, including datasets used in Nemotron model development and in production enterprise deployments.

## 1. 核心问题与整体含义

- **背景**：合成数据生成（SDG）已贯穿 LLM 与智能体系统的全生命周期——预训练阶段的改写/增强语料（数十亿至数万亿 token）、后训练阶段的合成指令、偏好与推理轨迹，以及智能体、多模态能力的训练数据。Nemotron 3 系列的技术报告也大量依赖 SDG 管线（代码、STEM 推理、结构化输出、SQL、搜索、工具调用、文档抽取、引用行为等）。
- **核心痛点**：
  - 合成数据的有用性取决于**对数据组成与多样性的刻意控制**、**正确性与质量验证**、以及与真实数据的混合与接地；但实践中这些目标通常靠**一次性脚本和胶水代码**实现，导致管线难以解释、共享和复现。
  - 多模态 SDG 缺少统一、可复现、易迭代的框架；配置往往与执行细节、端点信息耦合。
  - SDG 本质是**迭代过程**（很少一次生成就满足需求），但现有工具缺乏内建的预览—修订闭环。
- **论文含义**：提出开源通用框架 NDD，把"数据设计"从孤立 prompt 集合提升为**显式、可检查、可复用的数据设计过程**，并主张"构建数据管线就是构建模型的一部分"。

## 2. 方法论

### 2.1 核心思想：声明式列级配置 + 依赖图编译

- 数据集由**列（column）**声明式定义，支持 YAML 或 Python 的 `DataDesignerConfigBuilder`，两者等价（附录 B.1 给出对照）。每个列产出一个具名值，可作为最终数据集字段或下游列的输入。
- 列类型覆盖：seed/seed reader、统计采样器、LLM 文本、代码、结构化输出（Pydantic / JSON Schema）、图像生成、embedding、验证列、LLM judge、processor 导出视图。
- 配置本身是**可检查、可共享的产物**（`builder_config.json` 可序列化、重载、修订、重跑），支持 `results.push_to_hub()` 直接发布到 Hugging Face Hub。
- **依赖推断**：DAG 编译器从显式配置与 prompt/表达式中的 Jinja2 引用（如 `{{ schema }}`、`{{ persona.age }}`）自动推断列间依赖；循环依赖在生成前编译期即被拒绝。

### 2.2 关键技术细节

- **模型别名与 Provider 分离**：
  - `ModelProvider` 描述服务边界（如何、向何处发请求，凭据与端点拓扑属 provider 关注点）。
  - `ModelConfig` 把工作流可见的别名绑定到 provider、底层模型标识、操作族（chat / embedding / image）与推理策略。
  - 同一底层模型可配置多个别名（如高温度 `generator` 与低温度 `critic`），也可在不改 prompt 与依赖图的前提下把别名从托管 API 重绑到企业网关或自托管端点。
  - 运行前只解析被编译图引用的别名并做健康检查（可关闭），提前暴露不可用依赖。
- **异步运行时**：
  - 编译后的 DAG 作为**活执行计划**：某行所需输入一就绪，该单元即可运行；独立分支自然重叠，无需命令式编排。
  - 按 **row group** 处理记录，限定内存并作为 checkpoint 单元；行组内就绪粒度按列类型区分（模型列通常每行一个任务，采样器/seed/向量化自定义列按组执行）。
  - 公平队列 + 全局/组/资源限额，按 provider、模型、请求域分组，避免单个宽分支或限流分支独占资源。
  - 支持按行条件跳过列，仅影响依赖该值的下游；永久失败的单元会移除该行及其下游工作；若触发不可重试错误阈值则保留已完成行、丢弃部分行。
  - 长任务可把完成的行组以 Parquet 持久化并释放内存，支持乱序完成与中断后 `ResumeMode.IF_POSSIBLE/ALWAYS` 续跑，续跑前重建进度并校验配置兼容性。
  - 可选任务 trace 记录派发、准入、完成、状态与错误，用于区分排队延迟与执行耗时。
- **自适应请求准入（AIMD）**：
  - `ModelRequestExecutor` 拦截每次实际出站尝试，将调用映射为规范化请求资源（provider + 底层模型 + 请求域：chat / embedding / image / health check），向共享 `AdaptiveRequestAdmissionController` 申请 **lease**，调用后以分类结果（成功、限流、超时、provider 失败、本地取消、未知失败）释放，保证异常/取消时许可不泄漏。
  - `max_parallel_requests` 为 provider–模型对的硬并发上限；上限之下用**加性增、乘性减（AIMD）**反馈适配端点真实容量：收到 HTTP 429 时按 `Retry-After` 或回退冷却期并乘性下调并发上限，成功窗口后再加性恢复；可选启动爬坡从 1 并发开始。
  - 限流与普通重试分离：429 用于驱动 AIMD，可重试的瞬时连接失败/特定服务端错误走独立的指数退避重试策略，且每次重试也经过准入层，避免端点已过载时重试加剧负载。
  - 同一 provider+底层模型的多个别名共享全局请求上限；自适应状态按请求域独立。
- **质量门与溯源**：验证直接作为图阶段——确定性验证器、远程服务、LLM judge 消费生成字段并产出 pass/fail 或分数，可与原始生成 prompt 分离；MCP 工具调用的消息历史可作为**副作用 trace 列**保留而不混入生成字段。
- **Processor 与物化**：processor 在生成/验证之后重塑批次或最终数据集（如丢弃中间列、schema transform 生成 chat 格式视图）；物化阶段汇总主记录、processor 视图、trace、checkpoint 与诊断信息。
- **插件系统**：三类插件——seed reader（引入新源系统）、column generator（与内置列同等的依赖语义）、processor（项目特定的检查/训练/评估视图）。插件包由配置类、实现类、插件描述符、Python entry point 组成，可作为独立包分发，但依赖解析、调度、模型客户端、验证、trace 与物化仍由 NDD 负责。
- **部署边界**：单 job 模式与分片模式；分片时由外部调度器（如 Slurm job array）为每分片启动独立 NDD 进程，各自持有调度器、准入状态、checkpoint、trace 与产物命名空间，输出由外部合并；NDD 只负责编译、调度、批处理、重试、验证、准入适配与物化。
- **设计方法学（Section 3）**：记录契约 → 显式化变异（seed/sampler，即"统计接地" statistical grounding）→ 分解为多阶段（确定性变换 vs 语义生成）→ 提前指定质量门 → `preview()` 小样本检查（分布是否匹配、prompt 上下文是否正确、记录是否重复、验证器是否拦到预期失败、schema 是否匹配下游）→ 全量 `create()` → 用评估结果与被拒诊断驱动下一轮迭代。
- **采样与约束**：类别/子类别采样器支持加权与层级选择，数值与 SciPy 采样器覆盖常见分布，条件采样依据先前列改变参数，person sampler 可生成 Faker 风格或 Nemotron-Personas 画像；约束可把控制从边缘分布扩展到联合条件（例如某采样列受另一列的不等式约束），使顺序与阈值**按构造成立**，避免 generate-and-discard 过滤导致的分布偏斜。
- **可复现性定位**：不追求逐字节确定性，而追求**可审计配方**（seed 标识、采样参数、prompt 模板、模型别名与版本、推理设置、验证阈值、judge rubric、工具配置、trace 设置、processor 输出、导出 schema），并保留被拒样本与中间字段。

## 3. 实验设计

论文以**案例研究（case studies）**而非统一 benchmark 对照的形式呈现，Table 1 汇总了各应用、NDD 强项、数据规模与报告结果。

- **结构化输出与模型可用性**
  - 场景：程序化可验证的 JSON/YAML/XML/TOML/CSV 输出、schema 依从、内联引用。
  - 数据：Nemotron 3 Nano 用约 9K JSON-schema 依从任务做 RL（奖励为精确 schema 一致），发布数据集含 9,949 条已验证 JSON 样本。
  - 结果：JSONSchemaBench 80.2% → 86.9%；StructEval-Text 64.5% → 72.1%（TOML、XML 仍最弱）。
  - 企业案例（Perplexity AI）：为 Nemotron 3 Ultra 构建 JSON/YAML/XML/TOML/CSV 课程、复杂嵌套字段文档抽取、多种内联引用格式与自由格式指令遵循；确定性验证器检查 schema、格式、引用正确性与引用覆盖；纳入 RLVR 与 model-usability teacher training 后 StructEval-T 78.6% → 82.1%。
- **Text-to-SQL 与 CrowdStrike CQL**
  - 场景：自然语言到可执行、方言适配的 SQL；记录需同时保留请求、schema 与样本数据、方言、目标查询、推理轨迹与验证元数据。
  - 方法：采样行业、领域、SQL 概念、难度、脏数据模式、任务类型、语言风格，再分阶段生成请求、schema 上下文（故意引入干扰表/列与生产式不规则：文本存日期、货币符号、内嵌 JSON）、方言特定查询；方言验证器 + 5 个 LLM critic 评分后过滤。
  - 规模：生成 300K 候选（PostgreSQL/MySQL/SQLite），质量瀑布拒绝约 68%，保留 96.5K。
  - 结果：BIRD 26.77% → 41.80%（对比 GPT-OSS-120B 的 38.25%）。
  - 企业案例：CrowdStrike 对分析师编写的 CQL 查询先去重并脱敏（保留结构），再反向生成自然语言描述，按分析师画像与复杂度过滤，用于微调 Llama-3.3-Nemotron-Super-49B-v1.5；得到 96% 有效查询准确率与 2.50/5 语义分，对比 Claude Sonnet 4.5 的 94% 与 2.35/5。
- **搜索智能体轨迹**
  - 场景：多跳、依赖实时信息、需要完整交互轨迹（推理轮次、搜索查询、工具调用、检索观察、支持 URL、终止状态、综合回答）。
  - 方法：从 Wikidata 知识图抽取 4–8 跳路径 → 转为自然语言问题并混淆中间实体 → rollout agent 通过 Tavily MCP 工具用实时网页搜索求解，NDD 强制工具白名单、轮次上限与超时，捕获完整 Thought–Action–Observation 历史。
  - 规模与产出：50K 知识图种子 → 24K rollout 问题 → 约 7K 有效轨迹，端到端产率约 14%；被接受轨迹平均约 12 次工具调用；纳入 Nemotron 3 Super 的监督微调。
- **长文档 VLM 理解**
  - 场景：跨多页 PDF 的文本、版面、表格、图表、示意图与证据理解；记录需全程保留文档/页面标识、渲染页面图像、OCR 文本、问题、答案、推理轨迹、问题类型标签与 judge 决策。
  - 方法：四条互补生成流——OCR 接地的文本 QA、分类过滤的视觉 QA、通用单页 QA、分组页 QA（再分多页与整文档路径）；由评估失败决定下一步补充哪类文档与推理模式；独立 VLM judge 过滤正确性、问题质量、视觉接地、格式合规与训练信号强度。
  - 规模：约 11.4M 视觉问答对，约 45B token（含问题、答案、推理轨迹与视觉 token）。
  - 结果：MMLongBench-Doc 上 26.32% → 59.00%；发布的 Nemotron 3 Nano Omni 报告 57.5%。
- **Prompt 鲁棒性**
  - 场景：不改变任务本身，只改变指令措辞、语气、位置与答案格式；所需产物是可互换的前言与格式指令池。
  - 方法：从 50 组手写前言锚点与正则配对的答案格式出发，沿句子类型

变体（陈述句、疑问句、命令式等）、措辞强度、系统提示位置（前/中/后）、分隔符与格式指令组合进行受控扰动，生成大规模"同义任务、异构表面"的指令池；同一底层语义任务在不同表述下共享答案与验证标准，从而把"鲁棒性"从模型属性转化为可由数据设计控制的变量。该案例的产物被用于对齐阶段，使模型对 prompt 措辞与格式约定的敏感性下降，而任务正确性不受损。

- **图像与多模态生成**
  - 场景：需要文本与图像成对且语义一致、可验证的训练样本（如带标注的对象、场景、图表与示意图）。
  - 方法：以 seed 与采样器确定图像类别、属性、布局与风格，用图像生成列产出资产，再用文本/OCR/embedding 列反向生成描述、问答与结构化标签，形成"图像—描述—问答—验证"的多列记录；judge 与确定性检查共同过滤语义不一致或视觉接地失败的样本。
  - 特点：图像生成列与文本、embedding、验证列共享同一 DAG 与准入机制，因而多模态数据与纯文本数据可在同一管线中协同扩展。

- **文档抽取与企业数据**
  - 场景：从多页 PDF、扫描件、表格与嵌套字段中抽取结构化信息。
  - 方法：以 seed reader 引入文档源，渲染页面、OCR、抽取候选字段，再用 schema 依从的结构化输出列与验证列确保字段级正确性与引用覆盖；被拒样本与中间字段保留，用于下一轮迭代与错误分析。

## 4. 工程实现与可复现性保障

- **配置即产物**：`builder_config.json` 完整记录列定义、别名绑定、采样参数、验证阈值与 processor 视图，可序列化、重载、diff 与重跑；配合 `push_to_hub()` 使数据配方随数据集一同发布，降低"数据管线不可复现"的风险。
- **预览—修订闭环**：`preview()` 在小样本上暴露分布不匹配、prompt 上下文错误、记录重复、验证器失效与 schema 不兼容等问题，把大部分迭代成本前移到全量生成之前。
- **可审计而非逐字节确定**：论文明确不承诺逐字节可复现，而是追求可审计配方——seed 标识、采样参数、prompt 模板、模型别名与版本、推理设置、验证阈值、judge rubric、工具配置、trace 设置与导出 schema 均可回溯；被拒样本与中间字段被保留，以支持诊断与再设计。
- **插件与扩展**：seed reader、column generator、processor 三类插件通过 entry point 分发，扩展新源系统与新检查视图时无需改动核心调度、准入、验证与物化逻辑。
- **部署弹性**：单 job 与分片两种模式，分片由外部调度器（如 Slurm job array）驱动，各分片独立持有调度、准入、checkpoint、trace 与产物命名空间，输出由外部合并，适应大规模离线生成。

## 5. 主要贡献与创新点

1. **声明式列级数据设计抽象**：把数据管线从一次性脚本提升为显式、可检查、可共享、可复用的配置产物，列类型覆盖 seed、采样、LLM 文本/代码/结构化输出、图像、embedding、验证、judge 与 processor。
2. **依赖图自动编译**：从配置与 Jinja2 引用推断列间 DAG，编译期拒绝循环依赖，并在运行前仅解析被引用的模型别名做健康检查。
3. **模型别名与 Provider 解耦**：同一底层模型可配多个别名（如 `generator`/`critic`），可在不改 prompt 与依赖图的前提下重绑到托管 API、企业网关或自托管端点。
4. **异步运行时与自适应准入**：以活执行计划实现就绪即运行、按 row group 批处理与 checkpoint、公平队列与资源限额；AIMD 根据 429 反馈动态适配端点真实容量，限流与瞬时重试分离。
5. **验证即图阶段 + 副作用 trace**：质量门（确定性验证器、远程服务、LLM judge）与生成解耦，MCP 工具调用历史作为 trace 列保留而不污染生成字段。
6. **统计接地与约束采样**：seed/sampler、层级与条件采样、persona 采样与跨列约束，使控制从边缘分布扩展到联合条件，避免 generate-and-discard 造成的分布偏斜。
7. **多领域案例验证**：结构化输出、Text-to-SQL/CQL、搜索智能体轨迹、长文档 VLM、prompt 鲁棒性等案例显示 NDD 在质量、规模与可复现性上的实用性。

## 6. 局限性与开放问题

- **不承诺逐字节确定性**：受模型服务非确定性、并发调度与外部工具影响，复现依赖配方与运行环境记录，而非严格位级一致。
- **对底层服务质量的依赖**：AIMD 与重试只能适配端点容量，无法弥补端点本身错误率过高或语义质量不足。
- **验证器与 judge 的覆盖边界**：质量门的效果受限于验证器与 rubric 的设计质量；未被覆盖的错误类型仍可能进入数据集。
- **多模态与工具生态的成熟度**：图像生成、MCP 工具与多模态 judge 的稳定性和成本仍是实际瓶颈。
- **分片模式下的状态隔离**：分片各自持有调度与准入状态，跨分片的全局最优调度与统一准入并非内建能力，需外部协调。
- **成本与工程门槛**：显式数据设计提高了可审计性，但也要求使用者理解采样、约束与验证的语义，存在学习曲线。

## 7. 结论与启示

NDD 的核心主张是：**数据管线是模型的一部分**，应当像模型代码一样被显式设计、版本化、检查与复用。它通过声明式列配置、依赖图编译、模型别名解耦、异步运行时、自适应准入、验证即图阶段与统计接地，把合成数据生成从"孤立 prompt 集合 + 胶水脚本"转变为可迭代、可审计、可扩展的数据设计过程。案例研究表明，该方法在结构化输出、Text-to-SQL、搜索智能体、长文档 VLM 与 prompt 鲁棒性等方向均能带来可测量的能力提升，同时保留被拒样本与中间字段以驱动下一轮设计。其更广泛的启示在于：随着合成数据在 LLM 与智能体训练中的比重上升，**数据设计的可解释性、可控性与可复现性**将与模型架构和训练算法同等重要。
