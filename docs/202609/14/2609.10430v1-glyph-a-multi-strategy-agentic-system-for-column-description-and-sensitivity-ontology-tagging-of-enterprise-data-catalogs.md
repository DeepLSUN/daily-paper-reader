## 摘要
企业数据湖中表的积累速度快于人工数据管理员记录或分类的速度，导致许多列缺少描述且未分配治理标签。这种文档债务会削弱数据发现、访问控制和监管合规。我们提出 Glyph，一个生产系统，将两个耦合问题——列描述生成与用于数据分类的列类型标注——构建为以有状态图编排的协作式 LLM 智能体。Descriptor 将生成过程建立在产生每一列的流水线源代码之上，这些代码通过一个推理—行动工具循环（主动检索增强生成）按需从企业 GitHub 中检索。Tagger 通过并行运行三种互补策略（描述标注器、业务线正则表达式标注器，以及由在向量数据库上微调的对比编码器支持的元数据标注器），从受治理的 275 个叶节点的数据分类本体中分配标签，然后使用倒数排名融合（RRF）融合其排序输出。我们使用批内对比目标微调了一个 6 层 MiniLM 元数据编码器，相对于原始基础编码器，将同标签检索在分布内留出集上的 NDCG@10 从 0.55 提升至 0.92（MAP@100 0.19 → 0.90）。我们报告了在三个评估组上以召回加权的 F2 目标衡量的端到端多标签标注质量、一项隔离每种策略与 RRF 融合的消融实验，以及使 Glyph 区别于先前列类型标注工作和商业化的基于取值/正则的敏感性扫描器的工程决策：不依赖取值且以代码为依据的设计、逐标签溯源以及优雅降级。这些共同使多智能体 LLM 编目作为生产服务可审计且可运营。

## Abstract
Enterprise data lakes accumulate tables faster than human stewards can document or classify them, leaving columns with missing descriptions and unassigned governance labels. This documentation debt undermines data discovery, access control, and regulatory compliance. We present Glyph, a production system that frames two coupled problems, column description generation and column type annotation for data classification, as cooperating LLM agents orchestrated as stateful graphs. The Descriptor grounds generation in the pipeline source code that produces each column, retrieved on demand from an enterprise GitHub via a reasoning--acting tool loop (active Retrieval-Augmented Generation). The Tagger assigns labels from a governed 275-leaf Data Classification Ontology by running three complementary strategies in parallel (a description tagger, a line-of-business regex tagger, and a metadata tagger backed by a fine-tuned contrastive encoder over a vector database), then fuses their ranked outputs with Reciprocal Rank Fusion (RRF). We fine-tune a 6-layer MiniLM metadata encoder with an in-batch contrastive objective, lifting same-tag retrieval on an in-distribution held-out split from NDCG@10 0.55 to 0.92 (MAP@100 $0.19 \rightarrow 0.90$) relative to the stock base encoder. We report end-to-end multi-label tagging quality under a recall-weighted F2 objective across three evaluation groups, an ablation isolating each strategy and the RRF fusion, and the engineering decisions that distinguish Glyph from prior column-type-annotation work and from commercial value/regex sensitivity scanners: value-free and code-grounded design, per-tag provenance, and graceful degradation. Together these make multi-agent LLM cataloging auditable and operable as a production service.

- **背景：企业数据目录的"文档债务"**。现代分析组织的数据目录包含数万张表、数百万列，每一列在使用前都必须回答两个问题：**这一列是什么意思（文档）**，以及**它承载哪一类数据（分类与治理）**。实践中二者几乎全靠人工，导致描述缺失或过时、敏感数据标签严重滞后于数据发现。
- **代价具体而高昂**：未登记的 PII 往往在事故发生后被动发现，而非主动预防；新工程师无法理解非自己构建的数据集。
- **规模与异构性双重挑战**：
  - 单一组织的生产目录约 **340 万列、约 9.8 万张表**，横跨 **4 条业务线（LOB）** 与 **3 种存储后端**（Apache Iceberg、关系型数据库 RDBMS、Cassandra 列族存储）。
  - 即使按每分钟标注一列的乐观速度，也需约 **30 人年**的专家投入，且目录漂移速度远超任何团队的人工追赶速度。
- **第二项任务属于列类型标注（CTA）**：该问题已被研究十五年（从 web 表格的联合图模型到监督深度分类器、预训练表格编码器，再到近期的大语言模型）。
- **Glyph 与既有脉络的三点结构性差异**：
  1. **目标不是开放域类型词表**（DBpedia / Schema.org），而是**受治理的企业敏感性本体**——275 个叶节点标注，按敏感级别组织，其中占主导的"内部非敏感"类（`NON_SENSITIVE`）覆盖约 **72%** 的列。
  2. **设计上隐私保护**：**从不读取单元格取值**。编码器只看到结构化键 `catalog.database.table.column`，Descriptor 以产出列的源代码为依据。
  3. **异构策略排序融合 + LLM-as-Judge 自精炼 + 逐标签溯源**，每个标签都携带来源、分数与理由，比商业扫描器的规则日志或学术 CTA 系统的裸标签更细粒度。
- **四条设计要求**：(1) 以证据而非猜测为依据；(2) 纵深防御（多信号互补）；(3) 可度量、可自我改进的质量；(4) 生产纪律（无状态水平扩展、确定性解码、按请求鉴权、结构化追踪、可复现训练）。

## 2. 方法论

### 2.1 总体架构

- Glyph 是**图结构的智能体应用**：每个智能体是由节点（对类型化状态的纯函数）通过普通边与条件边连接的有向图，基于 **LangGraph** 构建。
- 状态用 **Pydantic** 建模并在每一跳校验；配置分三层：环境默认 → 每次部署的 `AgentConfig` → 每请求的 `HyperParams`。
- 两个智能体是**可独立部署的 REST 服务**，但天然组合：Descriptor 生成的描述正是描述标注器的理想输入。
- 二者均以 **temperature 0.0** 解码以保证确定性，限制 token 用量，并按请求创建 LLM 句柄（模型与凭证可逐次调用变化）。
- 设计哲学：在受治理的敏感性本体场景下，**可审计、失败模式已知的组件比新颖机制更重要**；贡献在于组合方式——融合哪些信号、如何对照本体校验、如何服务化。

### 2.2 Descriptor 智能体（回答"这一列是什么意思"）

四阶段流水线：

- **Schema 发现**：`fetch_schema` 查询企业数据注册表，收集列名、类型、既有描述等表级细节。
- **源码依据的生成（主动 RAG）**：
  - 为避免逐列调用的延迟与不一致，`analyze_batch` **在单次 LLM 调用中批量分析整表列**，每批最多 **50 列**。
  - 模型被赋予一个工具——**GitHub Enterprise 代码搜索**，可自主调用；证据是**代码而非数据**，Descriptor 从不读取列取值。
  - 这实现了**主动检索增强生成**（active RAG / ReAct 式推理-行动循环），与固定稠密检索器形成对比：由 LLM 决定检索什么查询，**默认预算为每列 3 次工具调用**，每批有上限并强制收尾，读取匹配点周边上下文。
  - **限流感知**：60 秒窗口内 25 次调用后主动暂停 2 秒，并采用指数退避（初始 30 秒、翻倍、最多 5 次尝试）。
  - 每段描述由可观测信号（长度、是否含技术与业务术语、是否定位到产出作业、是否具备 PII 意识）赋一个启发式置信度，上限 1.0。
- **PII 标记**：`user_id` 之类列被加上显式 PII 警告前缀，自动评分器直接对 PII 意识打分。与 Presidio、Cloud DLP 等**基于取值格式**的扫描器不同，Glyph 从**代码与元数据**推理敏感性，能捕捉取值是不可解读哈希、格式检测器会漏掉的标识符。
- **数据集级描述**：`generate_dataset_description` 从列级结果合成表级业务目的摘要，使目录条目自文档化。
- **评分与精炼**：`grade_results` 用评审模型分批打分，四项标准——**合理性、具体性、完整性、PII 意识**，以固定权重 **(0.35, 0.25, 0.25, 0.15)** 聚合；默认要求**评审模型与生成模型属于不同模型家族**，以规避 LLM 评委的自增强偏置。低于阈值的列连同逐项反馈回到 `analyze_batch` 重试，重试时对得分最差的列重新检索 GitHub；循环上限默认 **2 轮**。

### 2.3 Tagger 智能体（回答"这是哪一类数据"）

核心特征：**多策略并行 + 有原则的融合**。三种策略并发运行（各自扇出为工作批次），其排序标签列表由专门的融合节点合并。三者的选取标准是**失败模式互不相关**，使融合能够调和彼此。

#### (a) 描述标注器（description tagger）
- 基于列的**语义**，且是**检索受限**的：对每列构造查询 `"{name}: {description}"`（描述存在时用注册表中的人工描述，否则只用列名），经语义检索召回余弦相似度高于阈值 **C** 的本体标注，再让 LLM **从这些候选中选择并排序**最佳标签，并给出理由。
- 由于候选被约束为真实本体条目且事后校验，**幻觉标签会被拒绝**。这是对单提示 LLM CTA 的"检索受限 + 候选校验"变体，也是 ArcheType 式标签落地，但把约束放在**生成阶段**而非事后重映射。
- 本体标注是丰富的自然语言记录（如 `EMAIL_ADDR: an electronic mail address, typically written as user@domain`），因此该检索直接使用通用的 **all-MiniLM-L6-v2（384 维）**句编码器，不做微调。
- **评分与精炼**：`evaluate_metrics` 以零成本确定性指标 + 批式 LLM-as-Judge 打分，低于阈值的列回到 `llm_desc_tagger` 重试，构成**有界的 Self-Refine 循环**。**只有描述标注器经过该评委**。

#### (b) 正则标注器（regex tagger）
- 把**机构知识**编码为领域专家定义的、按业务线定制的列名模式规则（如 `email` 列硬编码规则指派 `EMAIL_ADDR`）。
- 属于 T2K 匹配血脉，提供**高精度锚点**，与学习型信号互补。

#### (c) 元数据标注器（metadata tagger）
- 仅依赖**结构化元数据**——完整限定键 `catalog.database.table.column`，不需要人工描述；是值特征分类器与"相似于已标注样例"排序器的元数据版本。
- 本身是一个 RAG 系统：用**微调后的句编码器**编码元数据键，在由人工标注语料构建的**精确内积（flat）向量索引**上检索。向量做 L2 归一化，使内积等于精确余弦相似度；相似度高于阈值 **S1** 的候选继承其最近历史邻居的标签。
- 长而深层嵌套的类型在干净分隔符边界处**截断到 200 字符**，以匹配训练期格式并降低嵌入噪声。
- 工作节点将候选连同**内联相似度归因**呈现给 LLM，由其从候选中选择并排序最终标签；每个标签带一条理由记录，标明**哪个来源以何种置信度贡献**（如 `[sources: ann=0.92]`）。作者称这种逐标签多源溯源在既有 CTA 系统中尚未出现，也比商业扫描器的规则命中日志更细。

#### (d) 跨策略融合：倒数排名融合（RRF）
- 三种策略产出**分数尺度不可比**的独立排序列表（ANN 余弦、LLM 置信度、二元规则命中）。`merge_all_tags` 使用 **RRF（k = 60）**，无需分数校准，且与自一致性集成不同——它融合的是排序列表而非对样本投票。
- 对在来源列表中排名为 $r_i$（1 起）的标签：
  $$\mathrm{rrf}(t)=\sum_{i \in \text{lists containing } t} \frac{1}{k+r_i},\quad k=60$$
- 以理论最大值 $n_{\text{active}}/(k+1)$（即被所有活跃来源都排在第 1 位的分数）归一化，得到 [0,1] 置信度，**只有全体一致排第一时才等于 1.0**。
- 多策略同时提名同一标签时，按固定优先序 **`llm_desc_tagger` > `llm_metadata_tagger` > `regex_tagger`** 继承其溯源字段（理由、本体、评分），而置信度取跨策略 RRF 分数；按标注名去重，同序决定保留谁的溯源，并以标注名的确定性规则打破平局。
- **`tag_normalizer` 按受治理的敏感级别重新打分**：将 RRF 置信度 $c$ 与该标注的本体层级权重 $w$ 混合为 $\alpha c + (1-\alpha)w$。未分级与更高敏感性标注权重 $w=1.0$，较低敏感层级（2、3、4 级）权重分别为 **0.75、0.5、0.25**。低于最小归一化分数的标签被丢弃并重排，使最终排序同时反映跨策略一致性与受治理的敏感级别。
- 论文以 Table 1 演示该打分：某 country 列（"2 位 ISO 3166-1 alpha-2 国家代码"）中，正则与描述标注器投 `INTERNAL`，元数据标注器投 `COUNTRY` 与 `NON_SENSITIVE`（且把 `COUNTRY` 排在 `NON_SENSITIVE` 之前），最终 RRF 分数为 0.333 / 0.667 / 0.328。

### 2.4 领域特定嵌入微调

- **动因**：元数据标注器的 ANN 检索是通用编码器唯一无法胜任的组件。查询是**简短、缩写密集、非语言化**的元数据键，通用模型不知道 `uat.core_db.users.uid` 与 `prod.analytics.events.user_id` 指同一概念；缩写、目录前缀、类型变体对其不透明，导致大量同标签召回未被释放（微调前 MAP@100 ≈ 0.19）。
- **模型**：微调紧凑的 **all-MiniLM-L6-v2**（6 层蒸馏 BERT，384 隐单元，约 **90 MB**）。该编码器专用于元数据索引；描述标注器的本体检索仍用原始编码器不变。
- **训练数据**：从生产系统抽取已标注且经校验的 `metadata_key → tags` 语料。**在标签组内构造配对**：任意两列只要共享标签就构成 (anchor, positive) 对。由于少数标签（尤其 `NON_SENSITIVE
