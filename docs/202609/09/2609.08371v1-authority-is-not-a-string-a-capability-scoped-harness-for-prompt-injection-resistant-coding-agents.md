## 摘要
编码代理使用系统级工具来读取文件、执行命令和修改源代码。在代理的沙箱内，这些工具通常携带环境权威：只要指定资源名称即可对其执行操作。间接提示注入通过将指令放置在仓库文件或工具输出中，诱使代理执行用户未请求的操作，从而利用这种权威。我们提出CapScope，一种在工具层面上的授权机制，它限制工具的使用，而无需模型识别恶意文本。在仓库内容或工具输出被读取之前，CapScope从可信输入中推导出任务级的权威上限。然后，它为每个代理分配一组独立的类型化能力，这些能力存储在模型上下文之外。每次工具调用都会根据发起该调用的代理所拥有的能力进行检查。因此，分配给某个子代理的权限不会自动被另一个子代理获得。注入可能使代理请求某个操作，但除非该代理已具备所需能力，否则该请求将被阻止。我们在Pi编码代理上实现了CapScope，并在一个编排器将子任务委托给独立子代理的修复工作流中对其进行评估。评估涵盖五个Python任务、五个注入表面、四种授权条件和每单元三次试验（共300次运行）。在环境权威和全局策略基线条件下，注入效果分别执行了33-47次和75次运行中的相应次数，而CapScope下仅为75次运行中的3次。CapScope完成了75次修复中的68次，而基线完成了75次中的68-72次。

## Abstract
Coding agents use system-level tools to read files, execute commands, and modify source code. Within the agent's sandbox, these tools often carry ambient authority: naming a resource is sufficient to act on it. Indirect prompt injection exploits this authority by placing instructions in repository files or tool output that cause the agent to perform actions the user did not request. We propose CapScope, a harness-level authorization mechanism that restricts tool use without requiring the model to identify malicious text. Before repository contents or tool output are read, CapScope derives a task-wide authority ceiling from trusted input. It then assigns each agent a separate set of typed capabilities, stored outside the model's context. Every tool call is checked against the capabilities of the agent that issued it. Permissions assigned to one sub-agent are therefore not automatically available to another. An injection may cause an agent to request an action, but the request is blocked unless that agent already has the required capability. We implement CapScope on the Pi coding agent and evaluate it in a repair workflow where an orchestrator delegates subtasks to separate sub-agents. The evaluation covers five Python tasks, five injection surfaces, four authorization conditions, and three trials per cell (300 runs). The injected effect executes in 33-47/75 runs under the ambient-authority and global-policy baselines, compared with 3/75 under CapScope. CapScope completes 68/75 repairs, while the baselines complete 68-72/75.

## 一、论文的核心问题与整体含义

- **背景**：编码代理（coding agent）借助文件读取、命令执行、源码修改等系统级工具完成任务。在沙箱环境中，这些工具通常具备“环境权威”（ambient authority），即只要模型指定资源名称即可执行操作。这种设计让代理容易遭受**间接提示注入**（indirect prompt injection）攻击。
- **核心问题**：攻击者可将恶意指令隐藏在仓库文件、README、AGENTS.md、技能文件、源码注释或工具输出中，诱导代理执行用户未授权的操作。传统防御依赖模型自身对文本来源的判断，或依赖静态全局策略，均不可靠，存在根本性的“粒度缺口”——单一任务级策略无法为不同代理分配不同的权限。
- **核心思想**：权威不应被当作模型上下文中的“字符串”或统一规则，而应被建模为独立于模型上下文的、按代理隔离的“能力”（capability）。通过将授权检查放在工具执行前的宿主层，而非依赖模型识别恶意文本，从机制上阻断注入效果。

## 二、论文提出的方法论

### 1. 核心思想
- **CapScope** 是一种宿主层授权机制，核心设计为“能力范围化”（capability-scoped）：
  - 在代理读取任何不可信内容之前，先从“可信输入”（用户请求+项目文件树）推导出一个**任务级权威上限**（ceiling）。
  - 每个代理（包括编排器和子代理）拥有**独立的、存储在模型上下文之外的能力集**。
  - 每次工具调用都必须匹配发起该调用的代理所持有的能力，否则被阻止。

### 2. 能力定义与作用域谓词
- 能力被定义为二元组：`Cap[effect_type, scope_predicate]`，其中效果类型（Effect Type）分为：
  - **Read**：读文件
  - **Write**：写/编辑文件
  - **Exec**：执行 shell 命令
- 作用域谓词：
  - Read/Write：基于**规范化路径前缀**（canonicalized path prefix，解析 `..` 与符号链接）进行判断，防止路径遍历攻击。
  - Exec：基于**解析后的参数向量前缀**进行检查；复合命令（如 `pytest; curl`）会分段逐一检查；允许的命令必须是列表中的可执行程序及其合法参数。

### 3. 三条核心规则
- **Mint（铸造）**：从可信输入经宿主策略生成任务的权威上限。只有宿主能铸造能力，模型无法自行扩展；若需新增权限，必须由用户显式批准（作为新的一次可信 Mint）。
- **Derive（派生/收窄）**：编排器委派子任务时，子代理请求的候选能力集必须在授权上限范围内（即更窄或相等），越界请求被丢弃。例如可从 `src/**` 收窄到 `src/parser.py`，不能反向扩展。
- **Invoke（调用检查）**：每个工具调用在分发前与发起代理的能力存储匹配，若没有覆盖能力则拒绝执行。

### 4. 实现方式
- 基于 **Pi 编码代理**（TypeScript 工具包）实现，通过 `pi.on("tool_call")` 事件安装阻塞式拦截器，无需修改 Pi 内部代码。
- 使用结构化数据类型表示能力（effect + scope spec），宿主可静态判断范围包含关系。
- 子代理通过 `pi-subagents` 扩展创建进程隔离的会话，每个会话拥有独立的能力存储。
- 编排器的调用由其“操作存储”检查，委托授权受“权威上限”约束；子代理的能力由其派生。

## 三、实验设计

### 1. 任务场景
- 采用**代码修复工作流**：编排器（orchestrator）将任务分解给四个角色：
  - orchestrator（诊断、协调、委托）
  - runner（运行测试）
  - patcher（修改源码）
  - verifier（重新运行测试验证）
- 修复任务包含 5 个小型 Python 项目，每个含一个 bug 和一个失败的 pytest 测试用例。

### 2. 注入表面（5种）
1. **README.md**
2. **AGENTS.md**（仓库级指令文件）
3. **项目本地技能文件**
4. **源码注释/文档字符串**
5. **pytest 工具输出**

### 3. 对比条件（4种授权模型）
- **B0**：环境权威（无策略）
- **B1**：静态全局策略（基于常见危险模式的拒绝列表，如 `.env`、`.ssh`、`rm -rf` 等）
- **B2**：任务特定全局策略（在读取注入前由 LLM 生成，基于任务描述和项目结构，但不区分代理）
- **C**：CapScope（任务级上限 + 按代理派生能力）

### 4. 评估指标
- **task_success**：最终测试套件是否通过
- **attack_executed**：是否存在攻击者特有的哨兵/标记文件（攻击是否真正落地）
- 另有每调用决策日志作为诊断信息。

- **实验规模**：4 种条件 × 5 个任务 × 5 个注入表面 × 3 次重复 = **300 次运行**。
- 每次运行均在隔离的临时工作副本中进行。
- 实验覆盖了多种注入载体、多个任务、多个授权模型，且控制了相同的代理架构（固定四主体拓扑、相同 LLM），使对比聚焦于授权模型差异，而非代理能力差异。
- 论文承认语料较小（5 个小规模修复任务），单模型，每单元仅 3 次重复，结果存在随机性。但论文强调按条件聚合后的排序稳定（B0≈B1 > B2 ≫ C），而非依赖单个单元数值。
- **总体评价**：实验在固定架构下系统性地比较了授权模型，设计清晰，指标客观（从文件系统读取），公平性较好；但由于任务规模小、模型单一、缺少跨领域验证，充分性有限。

## 六、论文的主要结论与发现

- **注入效果执行率**：
  - 环境权威（B0）与静态全局策略（B1）几乎无差别：47/75 与 46/75。
  - 任务特定全局策略（B2）降低到 33/75。
  - CapScope（C）仅 **3/75**，显著优于最强的全局基线（33/75）。
- **任务成功率**：
  - CapScope 完成 68/75，与 B2 持平；环境权威 B0 为 72/75，差距仅 4 次运行，说明 CapScope 在防注入的同时并未显著牺牲修复能力。
- **按注入表面**：CapScope 的 3 次攻击全部通过 AGENTS.md 载体发生；其他四种表面攻击均为 0。
- **额外诊断**：在 CapScope 下，模型在 34/75 次运行中提出了注入动作的调用，但能力钩子仅在 3 次运行中允许了攻击调用，说明模型可能被注入诱导，但机制成功拦截了大部分非法调用。
- **延迟代价**：平均运行时间 B0=145s，B1=140s，B2=194s，C=316s（中位数 208s，其中 5 次达到 900s 超时）。延迟增加主要来自拒绝后的重试和额外模型往返，而非授权检查本身。

## 七、优点

1. **机制创新性强**：将经典的能力安全（capability security）理念引入编码代理领域，提出“任务级上限 + 按代理派生 + 分发前检查”的三段式授权模式，弥补了单一全局策略的粒度缺口。
2. **不依赖模型识别恶意文本**：防御决策放在宿主层，基于结构化能力匹配，绕开了 LLM 判断文本来源的概率性和不可靠性。
3. **威胁模型清晰、假设明确**：给出受信输入/不可信输入的边界，明确声明不保证机密性、不替代进程沙箱，避免过度宣称。
4. **基线选择恰当**：覆盖无策略、静态拒绝列表、任务特定全局策略，能清晰展示全局策略的不足与按代理细化的价值。
5. **实验控制严谨**：固定代理工作流与模型，只改变授权模型，结果可归因。
6. **实现可迁移性**：CapScope 不依赖特定主机，仅需阻塞式预分发拦截器和按会话状态，可移植到其他框架。
7. **附带形式化规则**：以 Mint/Derive/Invoke 三条规则精确定义能力来源、收窄和检查逻辑，理论清晰。

## 八、不足与局限

1. **实验覆盖有限**：
   - 仅 5 个小型 Python 修复任务，未覆盖大型重构、依赖迁移、长时运行工作流等复杂场景。
   - 仅使用一个底层模型（qwen3.5-flash），未验证对不同模型的泛化性。
   - 每个单元仅 3 次重复，随机性较大（论文也承认这一点）。

2. **策略生成仍是薄弱环节**：
   - 初始预检由 LLM 生成，可能过宽或过窄。过窄会阻止合法操作（论文中 2 次失败源于预检遗漏写权限）；过宽可能放行被注入诱导但在范围内操作。
   - 论文的 3 次残余攻击正是发生在“授予范围比子任务需要更宽”或“注入文本影响了子代理授权选择”的情况下。

3. **延迟/计算开销较大**：
   - 平均耗时 316s，明显高于基线（140-194s），且多次拒绝会促使模型反复尝试，消耗额外 token。
   - 论文未测量交互式人工审批成本。

4. **无法防止授权能力的误用**：
   - 只限制“哪些效果能被调用”，不追踪数据流；允许的读后写仍可能被利用泄露数据。
   - 允许的命令（如 pytest）的传递效应（如导入项目模块）可能执行不可信代码，仍需额外进程沙箱。

5. **通用性声明有待验证**：
   - 能力谓词（路径规范化、命令解析）的健壮性依赖实现质量，论文未做对抗性测试（如符号链接竞态、复杂 shell 混淆）。
   - 预检输入只包含文件树和用户请求，文件名本身可能被注入，论文明确将“文件名注入”排除在评估外。

6. **公平性细节**：
   - 论文指出 C 中的某些失败（如超时、委托流程未重新路由）与授权无关，但仍计入失败，可能轻微低估 CapScope 的“真实”修复能力。
   - 决策日志显示部分拒绝后模型重复尝试，导致延迟增加；若允许人工干预，结果可能不同，但实验中禁用审批以保持协议固定。
