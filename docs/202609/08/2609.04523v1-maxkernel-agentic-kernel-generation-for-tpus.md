## 摘要
为加速器设计并编写高性能定制内核是一项复杂任务，需要深入的硬件级专业知识。大型语言模型（LLM）可结合实时编译器反馈，构建用于内核生成的智能体系统。在本工作中，我们提出MaxKernel，一个实现三种不同TPU内核开发范式的多智能体系统：(1) 人机协同（HITL）智能体，用于协作式逐步设计；(2) 自主（Auto）智能体，执行全自动的、基于指标/追踪的优化循环；(3) 基于图的自主动态搜索，扩展Auto智能体以全局探索设计空间。所有三种范式均利用共享的专业子智能体池来处理规划、实现、自我调试、测试和硬件性能分析。我们在JaxBench上评估MaxKernel，这是一个包含50项多样化TPU内核任务的全套基准，同时涵盖来自最新开源模型的复杂真实工作负载。我们证明MaxKernel能持续生成高度优化的实现，匹配专家手工调优的基线，并在基准测试中带来显著的性能提升。我们的智能体已开源，可在 https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel 获取。

## Abstract
Designing and authoring high-performance custom kernels for accelerators is a complex task that requires deep hardware-level expertise. Large Language Models (LLM) can be leveraged together with real-time compiler feedback to build agentic systems for kernel generation. In this work, we present MaxKernel, a multi-agent system that implements three distinct paradigms for TPU kernel development: (1) a Human-in-the-Loop (HITL) agent for collaborative, step-by-step design; (2) an Autonomous (Auto) agent that executes a fully automated, metric/trace-driven optimization loop; and (3) a Graph-Based Autonomous Search that scales the Auto agent for global exploration of the design space. All three paradigms leverage a shared pool of specialized sub-agents to handle planning, implementation, self-debugging, testing, and hardware profiling. We evaluate MaxKernel on JaxBench, a comprehensive suite of 50 diverse kernel tasks for TPUs, alongside complex, real-world workloads from state-of-the-art open-source models. We demonstrate that MaxKernel consistently generates highly optimized implementations, matching expert hand-tuned baselines and delivering significant performance across the benchmark. Our agent is open-sourced and available https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel.

- **整体含义（答案）** ：MaxKernel 通过一个**模块化多智能体架构**回答了上述问题。它由多个专业子智能体（规划、实现、测试、自动调参、性能剖析）构成，提供三种协作范式 —— **人机协同（HITL）**、**自主闭环（Auto）** 和基于**搜索图的大规模并行搜索（Graph-Based Search）**。实验证明，这一框架能生成与专家手工调优相当甚至更优的 TPU 内核，代表了"智能体编译（Agentic Compilation）"方向的重要进展。

## 2. 论文提出的方法论

### 2.1 核心思想
- 利用 LLM 作为代码生成与推理引擎，但**不依赖零样本直接生成最终代码**——而是将内核生成拆解为规划、写码、编译、测试、剖析、调优等多个串联环节，并在每个环节中**引入真实硬件反馈（编译错误、数值验证、XProf 硬件 traces）** 作为 LLM 迭代优化依据。
- 系统整体以 Pallas/JAX 框架下的 TPU 内核为研究对象，但该方法论可迁移到其他硬件（GPU/Tranium/MTIA 等）。

### 2.2 关键技术细节

**（1）共享的专业子智能体池**：
- **规划智能体（Planning Agent）**：基于硬件规格和参考实现，产出高层算法优化方案。
- **实现智能体（Implementation Agent）**：将规划方案转换为可编译的 Pallas 内核代码；配合编译修复循环，不断理解编译器反馈并修正语法/结构错误。
- **测试与验证智能体**：测试综合代理生成完备的测试案例；执行代理在目标硬件上运行测试，验证优化内核与参考实现的数值等价性，并严格执行各问题设定的数值容差（atol/rtol）。
- **自动调参智能体（Autotuning Agent）**：系统搜索 block size、tile 维度等超参数配置，在当前内核结构下寻找最优参数。
- **剖析智能体（Profiling Agent）**：通过 XProf 捕获底层硬件执行数据，提取延迟、内存带宽利用率、计算密度等关键指标，反馈给规划智能体驱动下一步优化。

**（2）知识库与检索增强（RAG）**：
- 将 Pallas/Mosaic/XLA 框架文档、内存布局指南、性能手册等静态外部知识存入外部知识库，通过 RAG 按需动态检索到上下文窗口，减轻 LLM 上下文过长的负担。
- **关键设计**：知识库中不包含任何人工调优的 kernel 代码，避免生成结果依赖人类基线，确保评估智能体的自主发现与泛化能力。

**（3）三种编排范式**：

- **Human-in-the-Loop（HITL）智能体**：采用"One Agent, Then Wait"模式。每个子智能体完成一步后立即交还控制权给开发者，用户可以审查优化计划、代码草稿、修正方向。适合复杂内核，需要专家直觉引导 LLM。
- **自主闭环（Auto）智能体**：自动串行执行迭代循环，流程为：Plan Generation → Implementation → Compilation Validation → Test Execution → Autotuning → Profiling。关键机制包括：
  - **冻结测试套件**：进入循环前基于参考代码构建测试套件并严格冻结，不允许下游修改（防止 reward hacking）。
  - **失败短路处理**：达到编译修复上限或未通过数值正确性检查时，保留错误上下文并回退至规划阶段重试。
  - **Best-of-N 状态回滚**：记录每个成功迭代的代码、编译状态、测试结果、延迟与剖析摘要；结束时自动恢复到延迟最低的方案。
  - **文件路径严格管理**：由编排者统一指定绝对路径，保证多轮执行不污染状态。
- **基于图的自主搜索（Graph-Based Autonomous Search）**：将 Auto 智能体作为节点扩展算子，整个优化过程建模为**搜索图**。每个节点保存内核源码、优化方案、经验指标；搜索编排器通过不同启发式策略完成"节点选择→并行展开→状态更新→收敛"。当前实现了两种搜索算法：
  - **并行搜索（Parallel Search）**：给每个独立轨迹分配 5 次迭代的充裕预算，不竞争、不剪枝，适合需要长时间逐步解决复杂编译错误的方案。
  - **Beam Search**：维持 top-k 候选前沿（beam width=3, depth=3, 每节点 2 个分支），各候选迭代预算较浅，中途及时剪枝低潜力的路径，保留多样性和竞争力。搜索图结构有助于防止 LLM context 溢出（每次节点展开都是独立会话），支持崩溃后恢复。

### 3.2 评估环境与对比方法
- **硬件**：TPU v6e；**性能采集**：基于 XProf 过滤 host 端 JAX dispatch 开销，只记录纯设备端执行时间。
- **LLM**：Gemini 3.1 Pro。
- **数值容差**：默认 atol=rtol=1e-2，部分任务放宽至 1e-1（附录列出 50 个任务的完整容差表）。
- **对比方法**：
  - **Best-of-N（零样本）**：100 次独立零样本补全，取其中最快且正确的样本；
  - **MaxKernel Auto（单轨迹，5 次迭代，重复 5 次报告中位数与上下界）**；
  - **MaxKernel Parallel（5 条 Auto 轨迹并行，取所有运行中最快的正确内核）**；
  - **MaxKernel Beam（beam width=3，max depth=3，每节点 2 扩展，内循环最多 2 次迭代）**。

### 3.3 评估指标
- **编译率**：能成功在硬件目标上编译的内核比例；
- **正确率**：与未优化 JAX 参考实现数值等价的比例；
- **几何平均加速比**：相对标准 XLA 编译器基线的加速（速度退化按 1.0× 下限计）；
- **fast_p**：既严格正确又超过某加速阈值 p 的任务占比。

## 6. 论文的主要结论与发现

- **零样本最佳-of-N 效果差**：编译率与正确率仅为 10/50，几何均值加速比仅 1.08×——证明没有实时编译器反馈和迭代剖析的静态 LLM 生成无法处理 TPU 内核的低层级复杂约束。
- **迭代是关键但方差大**：引入 Auto 闭环后，编译/正确率大幅提升（49/50 与 48/50），几何平均加速比上升到 1.39×；但单次 Auto 轨迹的中位数上下界跨度大，说明易陷入局部最优，需要更强的探索机制。
- **并行探索效果最好**：MaxKernel Parallel 达到 50/50 编译且 50/50 正确，几何平均加速 1.58×，single fast1 34/50。
- **Beam 搜索有竞争力且更节省**：Beam 达到 50/50 编译/正确、1.49× 几何平均加速，fast1 31/50，证明结构化剪枝能有效避开局部最小值（其 fast_p 曲线也优于单个 Auto 轨迹）。
- **匹配/超越人类专家**：在 8 个有手工调优基线的工作负载上，Parallel 几何平均加速达到 2.32×，超过人类手工内核的 2.02×；在 7/8 个任务上 Agent 优于/等同于人类；尤其值得一提的是人类在 MLA Attention 出现了性能退化（0.69×），而 Agent 仍找到了 1.21~1.23× 的有效方案。
- **真实模型加速显著**：DeepSeek-V4 Sparse Attention 的 decode 加速 2.36×、prefill 加速 7.85×；Qwen3-Next Gated DeltaNet 训练步骤（正反向前向+反向）总体加速 4.70×；同时证明可用于"修复濒死 / 死锁"等鲁棒性问题。

## 7. 优点

- **模块化设计**：将内核开发分解为可复用的子智能体（规划-编写-测试-调参-剖析），模块可单独替换、组合；一套共享代理池支撑了三种不同的编排范式，是"Agent 系统"在编译器/HPC 领域的一个典型好案例。
- **范式灵活性与实用导向**：同时提供 HITL 与全自动两种用户路径，兼顾安全可控与批量化大规模优化需求，符合真实工程场景中对"人在回路"的实际诉求。
- **利用硬件遥测作为第一反馈信号**：通过 XProf traces 提取设备端真实性能特征（而非只靠墙钟时间），将瓶颈信息输入 LLM 驱动下一轮规划，这是本系统成功的关键。
- **对 benchmark 严谨性有考量**：冻结测试套件防止智能体投机性修改验证标准；设置数值容差明细表（附录）；性能退化下限按 1.0× 计（不虚报）。
- **设计避免上下文溢出**：图搜索中每次节点扩展独立会话，避免单次 prompt 中累计过多内核代码。
- **开源**：代码公开（GitHub link），利于复现与社区后续扩展。

## 8. 不足与局限

- **硬件/LLM 泛化范围有限**：只验证了 TPU v6e + Pallas/JAX + Gemini 3.1 Pro 的组合，未展示跨硬件架构迁移能力，也未测试其他 LLM 后端，无法证明该框架对 LLM 的容忍度和鲁棒性；不同编译器错误风格、API 严格程度可能显著影响结论。
- **RAG 知识库静态且排除人工基线代码**：当前知识库仅限官方文档等静态资料，知识库的局限性可能限制了对不明文档的低层优化应用；此外排除手工调优代码虽提升了评测纯粹性，但也可能人为限制了性能天花板——如果允许参考高质量人工内核，优化结果可能更优。
- **Auto 模式稳定性欠佳**：单轨迹方差较大，同一 workload 的多次运行速度结果波动明显，对没有探索预算的普通用户不够友好。
- **计算成本/效率分析缺失**：论文没有报告 token 代价、智能体运行时长、并行 vs Beam 的实际资源消耗差异，读者无从判断两种搜索方法的成本效率比。
- **搜索参数未做敏感性分析**：Beam width、depth、branch factor、iteration budget 是启发式设定，没有消融实验验证其敏感性。
- **性能剖析相对表层**：论文主要报告端到端延迟，缺少对每个 kernel 内部分项（如 HBM→VMEM 搬运时间、compute pipeline 忙碌比例）的详细分解，以解释是否真正接近 roofline。
- **真实模型评测的类型有限**：SOTA 模型评测中以 memory-bound / attention 类算子为主，大型 GEMM 或需要精细控制流的算子覆盖较有限；同时缺少与更底层手工 Pallas 之外的第三方编译器（如 XLA 特化、Triton）的对照，降低了对"超越人类内核"这一结论的一般性。
