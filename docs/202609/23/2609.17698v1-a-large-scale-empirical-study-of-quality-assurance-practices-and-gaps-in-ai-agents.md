## 摘要
基于大语言模型（LLM）的智能体正越来越多地应用于软件工程、Web自动化、研究和生产力应用等领域。它们对规划、记忆、工具使用、代码执行和外部交互的集成带来了更强的自主性，但也引入了新的可靠性、安全与安保风险。我们对157个至少拥有100个GitHub星标的开源LLM智能体项目中的质量保证（QA）实践进行了大规模实证研究。我们分析文档、源代码、配置和测试，以刻画执行面、防护措施、测试制品、风险场景和反复出现的缺口等方面的QA实践。我们发现，当前QA主要关注基本功能和高风险操作，而覆盖范围仍然碎片化。防护措施在等效执行路径上的应用并不一致，测试很少考察边界、对抗性或多步工具使用故障，而已识别的风险也很少被转化为端到端QA检查。这些发现凸显出，需要超越功能级测试，转向系统化的端到端验证，以确保智能体工作流在与不可信输入、工具、持久状态和外部API交互时仍处于预期边界之内。

## Abstract
Large language model (LLM)-based agents are increasingly used across software engineering, web automation, research, and productivity applications. Their integration of planning, memory, tool use, code execution, and external interactions enables greater autonomy but also introduces new reliability, safety, and security risks. We present a large-scale empirical study of quality assurance (QA) practices in 157 open-source LLM-based agent projects with at least 100 GitHub stars. We analyze documentation, source code, configurations, and tests to characterize QA practices across execution surfaces, safeguards, testing artifacts, risk scenarios, and recurring gaps. We find that current QA primarily focuses on basic functionality and high-risk actions, while coverage remains fragmented. Safeguards are inconsistently applied across equivalent execution routes, tests rarely examine boundary, adversarial, or multi-step tool-use failures, and identified risks are seldom translated into end-to-end QA checks. These findings highlight the need to move beyond feature-level testing toward systematic end-to-end validation that ensures agent workflows remain within intended boundaries when interacting with untrusted inputs, tools, persistent state, and external APIs.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景转变**：基于 LLM 的智能体已从"仅返回回答"的 LLM 应用，演进为融合规划、记忆、检索、工具调用、代码执行、浏览器交互、文件操作与外部服务的自主系统，广泛用于软件工程、Web 自动化、研究辅助与个人生产力场景。
- **新风险维度**：传统 LLM 应用出错最多是"回答错误、幻觉或误导性建议"；而智能体可能执行 shell 命令、修改文件、浏览网站、调用 API、安装依赖或委派子智能体，模型输出可直接影响外部动作，导致文件损坏、隐私泄露、不安全命令、不安全依赖安装、财务损失、凭据被窃或有害的第三方交互。
- **核心问题**：尽管智能体架构、基准与安全研究快速发展，但**"QA 在真实开源项目中究竟是如何被工程化的"仍缺乏系统认识**：开发者采用了哪些 QA 实践？防护与测试如何跨不同执行路径整合？现有仓库是否能提供模型中介动作的端到端保障证据？
- **研究切入点**：开源仓库暴露了测试基础设施、防护实现、配置文件、文档、评估脚本与部署制品，为观察真实开发中的 QA 活动提供了独特窗口。
- **整体含义**：智能体 QA 必须从"模型输出是否正确"扩展到"模型影响的动作是否在所有执行面上被授权、限定范围、监控与测试"，即从功能级检查走向端到端工作流验证。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想

- 智能体行为是推理、规划、执行接口、外部工具与运行时防护交互的**涌现结果**，因此 QA 不能仅靠检查模型输出，而需考察动作如何被引入架构、经执行面暴露、被防护约束、被测试验证，以及如何串成风险链。
- 提出**四层编码框架（Four-Layer Coding Rubric）** 作为分析骨架：

| 层级 | 关注内容 |
|---|---|
| 执行面（Execution Surfaces） | UI、CLI、API、浏览器、文件系统、shell、插件、子智能体等可被调用或可施加影响的路径 |
| 防护（Safeguards） | 审批、策略、沙箱、脱敏、域限定等约束/验证/监控机制 |
| 测试制品（Testing Artifacts） | 测试、评估、基准、复现脚本、安全测试、面向失败的检查 |
| 风险场景（Risk Scenarios） | 不可信上下文或智能体行为可能触达敏感动作/资产/持久状态的端到端路径（候选情形，非确认漏洞） |

## 6. 主要结论与发现

- **总体结论**：智能体 QA 实践普遍存在，但覆盖范围在四层之间**碎片化、不均衡**；主要缺口不在"是否有 QA 制品"，而在"这些制品是否覆盖完整智能体工作流"。
- **RQ1.1 执行面层**：QA 的核心是**权威边界**。模型决策可经多条路径触达凭据、文件、命令、插件、浏览器状态与外部 API，但路径级控制往往应用不均（如 96.8% 项目存在跨重叠路径的控制不一致问题）。
- **RQ1.2 防护层**：防护广泛存在，关键挑战是**上下文敏感覆盖**——同一能力在不同场景下风险不同，防护需考虑动作是"如何、在哪、以何种权限"被触达的。
- **RQ1.3 测试层**：测试仍以**常规回归测试为主导**（87.3%）；面向边界违规、不可信上下文攻击与多步工具行为的智能体专属测试**明显不系统**（提示注入/对抗测试仅 5.1%）。
- **RQ1.4 风险场景层**：常见做法包括**设计期风险削减**与**关键点链路中断**（授权、隔离、脱敏），以及系统化风险规避（策略限定、扩展权限可审查化、浏览器会话域限定）。
- **RQ2 欠覆盖问题**：
  - 执行面：凭据配置、网络/API、文件访问、命令执行与动态代码路径常"暴露但未绑定对应边界"；
  - 防护层：存在通用控制，但**未把正确防护绑定到具体敏感动作**；
  - 测试层：缺乏对不可信上下文的对抗测试、对多步行为的回归/重放测试、对高权威动作的边界测试；
  - 风险场景：风险链需**转化为 QA 需求**（明确触发点、受保护资产、所需控制与回归检查）。
- **建议**：
  1. 按"受保护动作或资产"而非"接口"定义控制，使同一密钥/文件/shell/插件/浏览器/网络边界跨 CLI、API、MCP、浏览器、无头与批处理路径一致适用；
  2. 每条高权威路径或风险链应有面向失败的测试或重放用例——当所需审批、沙箱、策略、脱敏、域限定或扩展检查被移除时，测试应当失败。

## 7. 优点

- **问题新颖且切中要害**：首次大规模系统刻画开源 LLM 智能体"QA 工程实践"而非仅评估能力/攻击，填补了"实践现场"的认知空白。
- **四层框架清晰可操作**：执行面—防护—测试—风险场景的划分，将"能力"与"QA 机制"分离，便于编码、比较与跨项目综合。
- **语料规模与多样性好**：157 个高星项目、6 大类别，覆盖 SWE、编码、浏览器、研究、个人助手与领域特定智能体。
- **证据可追溯**：每个标签指向仓库可见制品，并提供具体项目示例（如 gemini-cli、OpenHands、codex、browser-use、goose、MaxKB 等）说明挑战与实践。
- **区分"可见性"与"有效性"**：明确声明编码只代表"存在可审查机制"，不主张运行时防护有效，避免了过度声称。
- **风险场景以"链"为单位**：从单点表面/控制上升到端到端路径分析（如 secret-to-tool、untrusted-context-to-action），更贴合智能体真实失效模式。
- **提供可复现数据链接**与固定编码模式，增强了可重复性。
- **威胁效度讨论诚实**：对内部、构念、外部效度均有交代，并说明未计算标注者间一致性的原因。

## 8. 不足与局限

- **无传统实验与对照**：没有基线方法对比、没有消融实验、没有干预实验，统计为描述性；无法证明某防护机制在实际运行时有效。
- **标注效度风险**：采用归纳式开放编码，**未计算 inter-rater agreement**，虽以共识裁决缓解，但主观性与不一致性风险仍存。
- **仓库可见性偏差**：只能观察仓库内可检查的制品，**无法覆盖托管服务、供应商侧控制、部署特定设置或快照外依赖行为**；自动化检索与 LLM 辅助摘要可能引入假阳性/假阴性。
- **外部效度受限**：
  - 语料为 2026 年 5 月固定快照，且**过度代表编码类与浏览器/计算机使用类智能体**；
  - 非全量普查，闭源、企业级与小原型项目可能不同；
  - GitHub stars 只是描述性元数据，**不是安全成熟度指标**；仓库在采集后可能已变化。
- **框架非通用分类法**：部分制品可合理归入多层（如插件既暴露工具、又约束使用、又记录风险），四层划分是操作性规则而非普适本体。
- **风险场景为候选而非确认漏洞**：所报风险链需边界审查，不能解读为已确认的安全缺陷。
- **应用限制**：结论面向开源仓库的 QA 工程实践画像，不宜直接外推为智能体运行时安全性的评价；建议中的"按受保护资产定义控制"与"失败导向测试"落地成本与可行性未做实证评估。
