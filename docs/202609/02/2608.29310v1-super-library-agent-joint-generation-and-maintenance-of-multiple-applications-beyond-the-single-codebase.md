## 摘要
组织通常开发并维护一组相关的应用程序：这些应用程序是独立部署的代码库，但共享大量领域逻辑、接口模式或操作约定。随着LLM编码智能体越来越多地用于生成和维护此类软件，逐应用开发的朴素工作流会在不同代码库间重复共享逻辑，并使得长期的智能体维护积累冗余、死代码和结构侵蚀。我们提出了“超级库代理”问题，即智能体在维护一个包含可复用跨应用组件的共享超级库的同时，按顺序生成N个相关应用的组合。原则上，一个简单的顺序脚手架可以提取共享代码并将应用程序迁移到不断演进的库中，但在实践中，它存在提取召回率低和依赖迁移脆弱的问题。我们通过以下方法解决这些问题：基于代码块摘要的候选引导提取、提取前的代码库整合，以及利用提取痕迹和调用图信息的上下文感知迁移。在WebGen-Bench和PaperBench上，我们的方法在保持应用功能的同时，显著降低了冗余和词元足迹（冗长度、词元长度），相较于零样本方法，并避免了朴素库构建引入的结构侵蚀，同时进一步减少了代码行数（LOC）和最小描述长度（MDL）。我们的代码可在 https://github.com/sbigstar0310/super-library-agent 获取。

## Abstract
Organizations often develop and maintain portfolios of related applications: independently deployable codebases that share substantial domain logic, interface patterns, or operational conventions. As LLM coding agents are increasingly used to generate and maintain such software, a naive application-by-application workflow duplicates shared logic across codebases and allows prolonged agentic maintenance to accumulate verbosity, dead code, and structural erosion. We introduce the Super Library Agent problem, where an agent sequentially generates a portfolio of N related applications while maintaining a shared Super Library of reusable cross-application components. A minimal sequential scaffold can in principle extract shared code and migrate applications to the evolving library, but in practice suffers from low extraction recall and fragile dependency migration. We address these failures with candidate-guided extraction over code chunk summaries, pre-extraction codebase consolidation, and context-aware migration using extraction traces and call-graph information. Across WebGen-Bench and PaperBench, our method preserves application functionality while significantly reducing redundancy and token footprint (verbosity, token length) over zero-shot, and avoiding the structural erosion introduced by naive library construction, with additional reductions in LOC and MDL. Our code is available at https://github.com/sbigstar0310/super-library-agent.

### 1. 核心问题与研究动机

- **问题背景**
  - 组织往往开发并维护一组**相关应用程序组合（portfolio）**：各应用虽然独立部署，却共享大量领域逻辑、界面模式、数据处理流程或运行约定。
  - 随着 LLM 编码智能体被大规模用于生成和维护此类软件，若采用逐一生成（application-by-application）的朴素工作流，会出现：
    - 共享逻辑在不同代码库中被重复实现（违反 DRY 原则），形成不一致表面——每次 bug 修复或变更都要人工同步到各近似副本；
    - LLM 长期维护会产生 measurable code smells，研究（如 SlopCodeBench）表明智能体在长时间迭代中会积累可读性差、过度冗长、结构腐化的 "slop" 代码；
    - 多个隔离的智能体各自生成相似代码时，演进漂移加剧。

- **核心问题定义——Super Library Agent (SLA) 问题**
  - 给定一串相关应用需求 `X = (x1, ..., xN)`，智能体须按顺序生成每个应用，同时维护一个共享的 **Super Library** `Lt`（存储跨应用可复用组件）。
  - 在每一步 t，智能体产生新代码库 `ct`、更新既有代码库（使其迁移到新库版本，记作 `C'<t`）以及更新库 `Lt`。
  - 理想状态下超级库包含所有被至少两个应用使用的组件；应用特有代码保持本地。
  - 目标是在**功能正确性**与**可维护性**之间取得最大 Pareto 最优——既保证应用满足需求，又使代码得到合理抽取、去重、复用和更新。

- **诊断出的两大挑战**
  1. **抽取召回率（Extraction Recall）问题**：功能等价的代码实现可能在语法与结构上差异很大，靠表面相似性（文本或嵌入）分组极易漏掉有效复用候选，导致库覆盖率受限。
  2. **迁移正确性（Migration Correctness）问题**：抽取并非局部编辑。把本地实现挪到共享库后，还需同步修改 import、调用点、依赖辅助函数乃至外部 API。若迁移不完整则会产生破引用、重复实现或死代码。

### 2. 方法论

论文提出一个三阶段协作方案（SLA-FULL），在最小顺序脚手架基础上进行两处关键增强。

- **对比基准——最小智能体脚手架（SLA-NAIVE）**
  - 每个新应用先由 **coding agent** 生成，然后由一个**库维护智能体**对所有既有代码库同时执行"抽取+迁移"——即将共享组件抽取进 Super Library，同时改写受影响的代码库使用新库。
  - 这种"单智能体包办、无结构化交接"的做法在实践中表现不佳，是后续改进的基准。

- **核心技术 1：基于索引的候选抽取（Index-based Candidate Extraction）**
  - **代码块索引**：用 AST 将每个代码库划分成语义边界清晰的代码块（函数、类、模块等），并生成每块的一行自然语言摘要；增量维护（hash 未变则复用旧摘要）。
  - **LLM 候选选择器**：在跨应用的**代码摘要索引**上筛选两类候选——
    - 抽取候选（多个代码库中实现相似功能的块），送入库抽取智能体；
    - 迁移候选（库符号 + 其可替代的应用本地块），送入依赖迁移智能体。
  - 以"块做什么"而非"怎么写"来匹配功能等价实现，解决低抽取召回率问题。
  - **提取前代码整合**：在跨应用抽取前，先在单个新代码库内做本地整合——识别并重构库内重复/重叠实现为应用内共享模块，避免把过于本地化的代码纳入跨应用抽取考量。

- **核心技术 2：上下文感知的依赖迁移（Context-Aware Dependency Migration）**
  - **基于提取痕迹的桥接（Extraction-Trace Bridging）**：库抽取智能体每次抽取/更新库符号时，输出结构化 **extraction trace**（涵盖来源代码位置、该模式为何可归纳、如何用库 API 替换原代码）。迁移智能体直接利用该 trace，无需从头重新发现对应关系。
  - **调用图条件约束（Call-Graph Conditioning）**：针对每个迁移候选，向迁移提示注入相关 import 声明和本地 caller/callee 关系（即 also-refactor 列表），明确需同步更新的文件，避免漏改调用点或留下死代码。

### 3. 实验设计

- **Benchmark 设定**
  - **WebGen-Bench**：评估根据自然语言指令生成网站，用可执行 UI 测试与视觉质量评分。构造 3 个不相交的 8 任务套件（suite）作为顺序应用流。套件聚类自 101 个任务（嵌入式聚类），分为内容展示、数据管理 CRUD 和用户互动平台三类主题。为公平比较，所有方法获得相同的渲染页面布局描述作为附加输入。
  - **PaperBench (Code-Dev 变体)**：评估智能体复现 ICML 2024 Spotlight/Oral 论文的 AI 研究贡献（LLM 评判其对照 rubric 的实现）。构造 5 个不相交的 4 任务套件（其中 S1–S3 主题一致、S4 扩散/分数推断类、S5 为异质低复用压力测试套件）。

### 6. 主要结论与发现

- **功能不与可维护性冲突**：SLA-FULL 在 WebGen-Bench 上的 Accuracy 为 77.21（较 Zero-Shot 76.04 提高 1.5%），PaperBench 的 Code-Dev Score 为 0.4809（较 0.4687 提高 2.6%），统计上无显著差异，说明共享库抽取不损害功能。
- **显著改善可维护性**：WebGen 上 LOC -9.0%、Token -6.7%、Verbosity -38.0%（统计显著）、Erosion -4.4%；PaperBench 上全部五项可维护性均最低（LOC -5.0%、Token -7.4%、Erosion -10.4%、Verbosity -2.0%、MDL -2.8%）。零样本基线 0% 复用；SLA-FULL 库导出 13.3 个符号，其中 4.8 个被 6–8 个应用复用，远高于所有基线；
- **消融证实设计有效性**：NL 摘要候选比隐式和 Ward 聚类抽取更多共享组件；局部整合减少 Verbosity/Erosion/LOC；调用图条件能修复因迁移不完整导致的精度下降（Acc. 74.48→77.21）。
- **动态轨迹显示复用随时间累积**：SLA-FULL 随着轮次推出后新应用时，旧应用本地代码显著减少，而 NAIVE 曲线平坦——印证正确抽取/迁移机制比单纯建库更重要。
- **提取质量更高**：除基础 UI 类库外，SLA-FULL 额外捕获行为 hooks、页面/领域模式（如 useSearchFilter、useLocalStorage、FeatureCardGrid、MessageBanner），而朴素方法多停留在 Header/Card 等浅层组件。
- **维护更省**：对共享策略更新打补丁时，SLA-FULL 的 Patch Size 最小（256 vs Zero-Shot 936），且将大多数修改集中到库本身（应用层 232 行）。
- **成熟库可进一步充当生成先验**：8 个新任务中使用最终 SLA 库可将平均 UI 精度提升 3.4%（84.35 vs 80.95），同时减少约 11% 总 LOC。

### 7. 优点

1. **问题定义新颖且贴合实际**：将"库学习"从单代码库扩展到顺序相关的多代码库组合，填补 Librarian 等以事后重构为主、无力应对在线顺序多代码库设置的空白；与软件工程界的"家族/产品线开发"问题直接对应。
2. **模块解耦与信息传递设计**：把"抽象发现"（候选引导）和"依赖迁移"（trace + 调用图）拆成两阶段并用结构化桥接而非让大模型凭感觉迁移；这是工程上较优雅、可扩展的方案。
3. **NL 摘要作为中间表征**：天然缓解功能等价但表面代码差异大的匹配难题，理念朴素而有效（消融证明胜过隐式或嵌入聚类）。
4. **实验全面与分析深入**：兼顾领域类型（网页 vs 研究代码）、顺序流变化、低复用压力测试、不同骨干、统计检验、库利用率和抽象质量等多个剖面；逐轮 LOC 动态分析揭示"复用随时间积累"的机制。
5. **对工程实践的启发**：Patch 大幅减小，直接支撑"共享库有助于减少跨应用重复修改"的行业直觉；论文还提供算法伪代码、完整 Prompt 和库导出清单，便于复现与后续研究。

### 8. 不足与局限

1. **缺少 SLA 原生 benchmark**：现有数据集均由单任务 benchmark（WebGen-Bench 与 PaperBench）人为组套，缺乏面向"长期库增长、跨应用复用、顺序维护"的原生评估任务；应用的维护对象本身是生成的产物，没有真实用户/提交历史/生产约束。
2. **维护实验仅单轮**：无法观察共享库对多次需求漂移的承受力，以及累积错误和回归防控。
3. **可维护性指标依赖静态代理**：LOC/Token/MDL/Verbosity/Erosion 这些代理指标并不完全反映代码理解、修改、扩展的真实难度。MDL 指标的消融表现也说明代理模型存在对训练数据的选择性偏好；部分差异（如 MDL、Erosion，在若干套件中）在统计上不显著。
4. **公平性隐患**：同一 backbone（deepseek-v4-flash/reasoning effort 等）的上下文并不完全等同生成成本；维护实验中的 LIBRARIAN 因没有"逐轮补丁前状态"而无法产生可比结构指标差（表注自认）。更值得注意的是，Zero-Shot 在 Post-construction 维护实验中采用"每应用一个独立智能体、禁止建立库"的设定未必是最贴近生产实际的 Zero-Shot 形态。
5. **方法在低复用套件中表现下降**：压力测试中 SLA-FULL 功能（Accuracy与Appearance）低于 Zero-Shot——共享库在这类场景中并非纯收益，存在过度抽取/迁移引入 bug 的风险。
6. **对长链条 Agent 行为高度依赖**：多层智能体、多轮 LLM 调用在任务复杂场景中容错性还未深度验证，且论文未披露训练的算力与模型规模，成本可控性缺乏端点数据支撑。
7. **道德和部署警示已在文中自查**：自动化批改代码、缺少人类审阅，如果库中某个符号出错，会瞬时传播到所有下游应用——这是共享库方法固有的集中风险。
