## 摘要
长程大语言模型（LLM）智能体需要上下文组装：运行时必须在硬性上下文窗口预算和字节敏感的提示缓存限制下，决定每个提示中包含什么内容、以何种顺序排列，以及何时压缩历史。在生产级智能体系统中，该逻辑分散在提示构建器、临时压缩例程、缓存破坏性变通方案及各家提供商适配层中。我们认为，上下文组装在结构上与关系数据库中的查询执行同构：两者均在硬性预算下运行，利用分层缓存，并借助统计信息。我们在ContextPipe中采用了这一原则：这是一个五阶段流水线（计划-绑定-优化-执行-反馈），由结构化数据源目录、确定性缓存感知优化器和EXPLAIN ANALYZE追踪提供支持。我们证明ContextPipe中的上下文是可审计、可重放且具有故障隔离性的。使用SWE-bench Pro Qutebrowser子集的初步评估表明，与仅追加式上下文构建策略相比，ContextPipe将总令牌量减少31%，LLM调用减少23%，响应时间减少9%，代价是KV缓存命中率较低。

## Abstract
Long-horizon large language model (LLM) agents require context assembly: the runtime must decide what to include in each prompt, in what order, and when to compact history under a hard context-window budget and a byte-sensitive prompt cache. In production agentic systems, this logic is scattered across prompt builders, ad hoc compaction routines, cache-break workarounds, and per-provider shims. We argue that context assembly is structurally isomorphic to query execution in a relational database: both execute under a hard budget, exploit a tiered cache, and leverage statistics. We adopt this discipline in ContextPipe: a five-phase pipeline (Plan Bind Optimize Execute Feedback) backed by a structured data-source catalog, a deterministic cache-aware optimizer, and an EXPLAIN ANALYZE trace. We show that context in ContextPipe is auditable, replayable, and failure-isolated. A preliminary evaluation using the SWE-bench Pro Qutebrowser subset shows that, compared with the append-only context construction policy, ContextPipe reduces total token volume by 31%, LLM calls by 23%, and response time by 9%, at the cost of a lower KV cache-hit ratio.

## 1. 核心问题与整体含义

论文面向长程大语言模型（LLM）智能体在生产环境中的**上下文组装（Context Assembly）**问题。所谓上下文组装，是指运行时系统在每个回合中需要决定：向模型提示词中放入哪些内容（系统提示、工具 schema、历史对话、检索记忆、技能指令、运行时身份等）、按什么顺序排列、以及何时对历史进行压缩——所有这些都受限于模型的硬上下文窗口预算和字节敏感的提示缓存机制。

论文指出，现有生产级智能体系统中这类决策逻辑高度分散：分布在各自的提示构建器中、临时压缩例程里、针对缓存失效的变通方案、以及不同模型提供商的适配代码中。这导致系统行为不透明、难以调试、缓存利用率不稳定、且无法解释关键决策的成因。作者观察到，这一结构性问题与关系数据库中的查询执行问题高度同构：数据库在硬性资源预算下运行、利用分层缓存（buffer pool）、依赖统计信息（catalog statistics），并有成熟的优化器和 EXPLAIN 机制。因此，作者提出将上下文组装视为一种“数据库式查询执行”问题，并用一套规范化流水线加以解决，使得组装过程可审计、可重放、故障可隔离。

## 2. 提出的方法论

### 2.1 核心思想
ContextPipe 将一次 LLM 回合视为一次五阶段流水线调用：**Plan → Bind → Optimize → Execute → Feedback**。该流水线是产生 LLM 调用的唯一路径，所有子调用（工具执行、技能运行、压缩代理等）都必须经过它，从而消除了分散的并行构建器。

- **Plan（计划）**：纯函数计算，基于数据源目录和统计信息，决定本回合应包含哪些分区（section）、各分区 token 预算、选择哪种压缩层级的策略，以及缓存策略。其核心输入是**上下文压力**（context pressure）。

- **Bind（绑定）**：唯一进行外部 I/O 的阶段，并发地取回记忆、历史、工具 schema、技能、以及上一回合遗留的 emergent context。输出为类型化的工件列表。

- **Optimize（优化）**：执行确定性的缓存感知优化，对绑定后的内容进行排序、压缩、剪枝、溢出和缓存标记放置，输出可直接序列化的请求及完整追踪（trace）。

- **Execute（执行）**：通过 provider 适配器完成序列化并调用模型，支持 EXPLAIN-only 模式免调用检查。

- **Feedback（反馈）**：记录实际产生的输入输出 token 数、缓存命中/未命中情况、截断等，更新统计表（PipelineStats），供下一轮 Plan 使用。

### 2.2 关键技术细节

#### （1）预测性上下文压力（Predictive Context Pressure）
定义压力为两个量：

- 原始压力：\(P_{raw} = T_{used} / L_{eff}\)
- 预测压力：\(P_{pred} = (T_{used} + R_o + R_t + R_s) / L_{eff}\)

其中 \(L_{eff}\) 为有效输入上限；\(R_o\)、\(R_t\)、\(R_s\) 分别为期望模型响应、扩展思考、工具 schema 增长的预留 token。\(R_o\) 采用按（模型、查询来源）分桶的**百分位估计**（稳态用 p75，恢复期用 p95），而非平均值，以应对长尾编码任务。

#### （2）层级门控压缩（Tier-Gated Compaction）
根据压力值选择压缩层级：
- \(P < 0.60\)：Normal
- \(0.60 \le P < 0.75\)：TrimSchemas（剪枝工具 schema）
- \(0.75 \le P < 0.90\)：CompactHistory（清除最旧工具结果并放置占位符）
- \(P \ge 0.90\)：AggressivePrune（额外丢弃最旧整轮对话）

同时采用“只升级不降级”的门控规则：取原始与预测压力中更激进者；若存在恢复状态（如 prompt too long 错误）则进一步升级。每个转换还受 OptimizeLimits 中的布尔门控制，若门关闭则记录“SkippedOptimization”到 trace 中。

#### （3）缓存感知有序放置（Cache-Aware Ordered Placement）
将可重排分区按键（缓存范围波及度：Global < Session < None）做**升序稳定排序**，固定锚点（Identity、Constraints）不参与排序并保留前置位置。顺序变更只有在重排移动次数不超过 `max_reorder_moves` 时才采用，否则跳过并记录日志。缓存标记放置在缓存范围边界，排序保证稳定前缀尽可能长，最大化提供商自动前缀缓存的命中。

#### （4）溢出（Spill）
单个分区超过 10,000 tokens 且配置了溢出后端时，将其持久化，并在原位置替换为轻量的 SpillReference，释放 token 预算。Identity、Constraints、Working Memory 永不溢出。重补水时采取 fail-open 策略。

#### （5）数据源目录：ContextSources
将智能体循环中会出现的所有上下文数据源划分为**八个生命周期层级**（如表所示），每种数据源在目录中注册固定 schema（tier, kind, scope, priority, est tokens, bind latency, recoverable, provider markerable, dependencies）。

| 层级 | 示例 |
|---|---|
| 不可变核心 | 规则、输出格式 |
| 每智能体静态配置 | 工具 schema、技能目录 |
| Latched（SessionLatches） | beta 头、缓存范围、功能开关 |
| 每会话静态 | 边界画像、项目规则、自我模型 |
| 每回合变动 | 消息、事实、活跃技能 |
| 外部 / I/O | 外部记忆、溢出、云快照 |
| Emergent（EmergentContext） | 预取记忆、技能发现、工具使用摘要、附件 |
| 反馈统计 | 缓存统计、token 直方图 |

其中 **SessionLatches**（会话闩锁）和 **EmergentContext**（涌现上下文）是两个新型层级——前者将首次触发后冻结的配置值显式建模，避免缓存破坏；后者承载回合中动态发现的新上下文，并具有 TTL、内容哈希去重、列表上限三重安全机制。

#### （6）EXPLAIN ANALYZE 追踪
每个回合会产出结构化 trace：执行前部分说明压力分解、所选压缩层、各分区预算与实际 token、缓存标记位置；执行后部分记录实际输入/输出 token、缓存读出/创建量、缓存命中率等。它还充当审计日志，记录每个应用或跳过的优化决策。配套 8 条告警规则，如显式缓存破坏（含归因）、冷启动、缓存命中率回退、压缩级联、恢复循环等。

#### （7）核心不变量与保证
算法保证四个重要性质：
- **锚点与顺序**：Identity、Constraints 保持领先位置，排序不跨缓存范围类边界；
- **保护**：优先级为 Never 的分区永不被清除；
- **配对与可恢复**：工具结果与工具调用保持配对，被清除的过大结果保留可恢复引用；
- **审计完整性与重放确定性**：每个应用或跳过的变换都被记录；相同输入快照保证字节完全一致的输出；
- **故障隔离**：失败调用不会污染百分位桶，重试无需特殊清理。

## 6. 主要结论与发现

- 在 Qutebrowser 3 个实例上，相比 Flat 的 append-only 策略，ContextPipe（Structured）可减少 **30.1% 总 prompt token**、**23.1% LLM 调用数**、**7.8% 响应时间**（原摘要宣称 31%/23%/9%，正文表 4 给出 30.1%/23.1%/7.8%，存在轻微数字差异）。
- 代价是 **缓存命中率从 95.3% 降至 86.2%**（降幅 9.1%），新鲜（未缓存）token 量翻倍（增加 114.6%）。
- 在按提供商量价模型计算时，若缓存 token 与新鲜 token 价格比 \(r\) 低于 0.145，Flat 的计费成本更低；高于 0.145 时 Structured 更优。
- trace 案例显示：每次压缩层级升级（如 TrimSchemas、CompactHistory）会引发一次短暂缓存未命中（8%–11%），但下一调用即恢复至 99%–100% 命中；而 Flat 轨迹中压力单调上升直至达到最大回合限制，暴露出无预算控制的风险。
- 整体说明：ContextPipe 的主要收益在于上下文总量、调用数、响应时间与上下文窗口余量的控制，而非在低缓存价格场景下无条件节省费用。

## 7. 优点

1. **问题抽象具有洞察力**：把上下文组装类比为数据库查询执行，并据此做了可执行的结构化映射，概念上清晰有据。
2. **确定性、可审计设计**：固定排序策略而非搜索，每个决策（含被门禁止的决策）都写入 trace，支持事后完全重建决策过程。这比许多 ad hoc 提示构建器更容易调试与验证。
3. **显式目录与统计学设计**：八层级 ContextSources 目录、PercentileDigest 存量、per-section churn 监控等设计，让原本隐式的会话状态成为可规划对象。
4. **预测性压力与门控压缩**：利用历史百分位而不是平均值做预算预留，且只用升级不能降级，避免抖动与恢复循环，值得借鉴。
5. **强不变量保障**：锚点位置、保护级分区不丢失、工具配对、溢出可恢复等特性通过 Lemma 与 Property 明确声明，并经阶段边界校验加以约束。
6. **落地细节充实**：provider 缓存策略抽象、ForkPrefix（父子 agent 共享缓存前缀）、阴影（shadow）流水线部署、追踪告警体系等，体现出生产级考量。
7. **写作规范**：对局限性和开放消融的态度诚实，未夸大实验结果。

## 8. 不足与局限

1. **实验规模极小**：只跑了 3/79 个实例，每个实例重复 3 次——不足以做任何有统计功效的结论，研究本身也承认“preliminary”。
2. **主实验对成本结论不利**：在常见的便宜缓存价格下（如 DeepSeek 约 1/10），Flat 的计费成本反而更低，说明该方案在“省成本”维度并非普适——只削减总 token 与调用数，不一定省账单。
3. **缓存命中率损失较大**：压缩会主动打破前缀，导致新鲜 token 翻倍，在缓存价格远低于新token 的第三方场景中，经济性尤差。

5. **质量指标缺失**：没有报告 resolve rate 或任何实际任务成功率的对比，无法判断优化后输出质量是否受损或受益。
6. **未做消融**：A1–A4 几乎全部缺失，无法把收益归因到某个具体机制（如排序 vs. 压缩 vs. EmergentContext）；替代解释（如单纯丢弃历史）未被排除。
7. **外部效度受限**：仅一种任务型基准、一种模型（DeepSeek-V4-Pro）、单一 codebase 类型；不覆盖 chat、retrieval-heavy、multi-agent 等。作者也没有披露实际算力/部署条件，复现成本未知。
8. **范围假设较强**：只比较“结构化压缩”与“完全 flat、不压缩”的极端二分情况；现实系统的通常做法是介于两者之间的 ad hoc 策略，横向对比不够完整。
9. **一些设计现阶段仍是半成品**，例如 ForkPrefix 在默认 executor 中尚未真正接线（仍以子代理 fresh 方式运行），只能做审计而不产生实际的跨代理缓存共享——宣传的功能与实现之间有一定落差。

总体而言，ContextPipe 提出了一套系统化、工程化程度高的进程间上下文管理方案，以数据库范式统一了 LLM 智能体上下文组装中的预算、排序、缓存与压缩问题，在可维护性上具备明显架构优势；其方法论完整且有理论规范性，但当前论文仅提供了小样本的可行性验证，完整效能（尤其质量与成本综合收益）尚待更大规模实验和消融证实。
